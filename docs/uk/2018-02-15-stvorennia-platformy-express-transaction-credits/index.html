The making of the Express Transaction Credits Platform

Архітектура токенів, виплати з мультипідписом і передачі з часовим блокуванням на Ethereum у 2018 році.

Резюме / Ключові висновки

  • Первісна проблема. ERC-20, домінуючий стандарт токена Ethereum у 2018 році, мав структурний недолік: токени, безпосередньо передані на адресу смарт-контракту, беззвучно знищувалися, якщо контракт не мав обробника. Будь-яка платіжна платформа на базі ERC-20 успадковувала цей ризик (Ethereum EIPs).
  • ERC-223 як виправлення. ERC-223 вимагав від контрактів-одержувачів реалізації функції tokenFallback(address, uint, bytes). За її відсутності переказ атомарно відкочувався. Жоден токен не міг бути беззвучно втрачений (Ethereum EIPs GitHub).
  • П'ять примітивів контракту EXTC. Ідентифікація токена (name, symbol, 18-знакова точність), фіксована пропозиція, сумісний із ERC-223 переказ, мультипідписна корпоративна виплата та постійні доручення, заблоковані за висотою блоку.
  • Механізм заставної позики. Позичальники блокували токени EXTC в ескроу контракту; контракт атомарно вивільняв кошти позики після отримання застави — без затримки перевірки або затвердження кредитним комітетом.
  • Що експеримент виявив про обмеження Ethereum. При пропускній здатності mainnet ~15 TPS і вартості газу $0,10–$1,00 за транзакцію на піку січня 2018 року платіжна мережа, що обробляє навіть обсяги переказів, була економічно та технічно нездійсненною на публічному Ethereum без інфраструктури Layer-2.

Проблема дизайну: чому ERC-20 був недостатнім #

Стандарт ERC-20, запропонований у 2015 році та формалізований у Ethereum Improvement Proposal 20, визначив канонічний інтерфейс взаємозамінного токена, що живив ICO-бум 2017–2018 років. Його шість основних функцій — totalSupply, balanceOf, transfer, transferFrom, approve та allowance — були достатніми для простого випуску та обміну токенів.

Однак для платіжної платформи ERC-20 мав критичний для виробництва недолік. Функція transfer(address _to, uint256 _value) переміщала токени на будь-яку адресу, включно з адресами контрактів, не запускаючи жодного коду в контракті-одержувачі. Контракт, який не був спеціально запрограмований для відстеження вхідних переказів ERC-20, не мав способу їх виявити. Токени, надіслані таким чином, застрягали назавжди без механізму відновлення.

Спільнота Ethereum підрахувала, що десятки мільйонів доларів у токенах ERC-20 були безповоротно втрачені до середини 2018 року через цей механізм. Будувати платіжну платформу, де перекази могли беззвучно зазнавати збою та знищувати кошти користувачів, було неприйнятно.

Рішення ERC-223: атомарний переказ із сповіщенням #

ERC-223, запропонований у трекері задач GitHub Ethereum EIPs, вирішив проблему беззвучної втрати, змінивши вимоги до переказу токенів. За ERC-223 transfer(address _to, uint256 _value, bytes _data) перевіряв, чи містила адреса одержувача код контракту. Якщо так, переказ викликав _to.tokenFallback(address _from, uint256 _value, bytes _data).

Критична властивість: якщо контракт-одержувач не реалізовував tokenFallback, уся транзакція переказу відкочувалася. Жоден токен не покидав баланс відправника. Жоден токен не застрявав. Переказ був атомарним — він або завершувався з виконанням коду одержувача, або повністю зазнавав збою з незміненим станом.

Для EXTC це означало:

  • Платіж до смарт-контрактів був безпечним за конструкцією. Ескроу-контракти, мультипідпис-гаманці та кредитні контракти могли отримувати токени EXTC без ризику безповоротної втрати коштів.
  • Поле _data дозволяло багаті метадані платежу. Байтове корисне навантаження могло містити посилання на рахунки-фактури, коди маршрутизації або підтвердження відповідності — інформацію, яку простий переказ ERC-20 не міг передати.
  • Витрати газу були незначно вищими. Виклик tokenFallback додавав приблизно 2 000–5 000 газу на переказ — незначні накладні витрати за цінами газу 2018 року.

Архітектура контракту EXTC #

Токен-контракт EXTC був реалізацією Solidity, структурованою навколо п'яти модулів:

1. Ідентифікація токена #

string public name = "Express Transaction Credits";
string public symbol = "EXTC";
uint8 public decimals = 18;

Вісімнадцять десяткових знаків надавали EXTC точність нижче цента, відповідаючи деталізації, необхідній для мікроплатежів і мікропозик. Символ EXTC був ідентифікатором у ланцюжку, зареєстрованим у токен-контракті.

2. Фіксована загальна пропозиція #

Загальна пропозиція встановлювалася під час розгортання контракту і не могла бути збільшена подальшими емісіями. Цей проєктний вибір зробив EXTC дефляційним: будь-які токени, безповоротно вилучені з обігу через незворотні операції спалення, скорочували пропозицію без заміни. Модель фіксованої пропозиції була стандартом у дизайні платіжних токенів 2018 року, відображаючи вплив Bitcoin: припущення, що дефляційний тиск є перевагою для засобу обміну.

3. Баланс і переказ, сумісні з ERC-223 #

Основна функція переказу реалізовувала повний інтерфейс ERC-223. Внутрішні маппінги балансів відстежували активи кожної адреси. Допоміжна функція isContract(address) відрізняла адреси EOA (зовнішньо керовані акаунти) від адрес контрактів для визначення необхідності виклику tokenFallback.

4. Корпоративні виплати з мультипідписом #

Корпоративні платіжні процеси вимагали спільної авторизації: жоден окремий підписант не міг одноосібно ініціювати виплату вище визначеного порогу. Контракт EXTC реалізував схему мультипідпису два з N:

  1. Призначений ініціатор пропонував переказ, вказуючи одержувача, суму та нонс.
  2. Співпідписант підтверджував нонс.
  3. Переказ виконувався лише після запису обох підписів у ланцюжок.

Це усувало ризик єдиної точки відмови для корпоративних рахунків, водночас зберігаючи весь потік авторизації в ланцюжку та доступним для аудиту без посередника клірингової палати.

5. Постійні доручення, заблоковані за висотою блоку #

Повторювані платежі — зарплати, підписки, заплановані погашення позик — вимагали примітиву постійного доручення. EXTC реалізував це як блокування за часом: запис про переказ зберігався в контракті з параметром releaseBlock. Переказ не міг виконатися, поки висота блоку Ethereum не досягала releaseBlock.

Висота блоку як часовий проксі була прагматичним вибором у 2018 році. Ethereum цілився на 15-секундний інтервал між блоками, що робило висоту блоку достатньо надійним проксі для реального часу в межах кількох хвилин. Абсолютні мітки часу (block.timestamp) були доступні, але піддавалися маніпуляціям майнера в межах ±900 секунд, що робило висоту блоку безпечнішим орієнтиром для фінансових контрактів.

Механізм миттєвих позик із заставним забезпеченням #

Кредитний примітив EXTC був найскладнішим компонентом. Дизайн:

  1. Позичальник блокує заставу. Позичальник викликав lockCollateral(uint256 _collateralAmount), передаючи токени EXTC в ескроу кредитного контракту через ERC-223 tokenFallback.
  2. Перевірка коефіцієнта позика-до-вартості. Контракт зчитував попередньо налаштований коефіцієнт LTV (наприклад, 50%) і розраховував максимальну суму позики відносно заблокованої застави.
  3. Атомарна видача позики. Якщо застава відповідала мінімальному порогу, контракт негайно переказував суму позики на адресу позичальника. Без черги перевірки, без кредитного комітету, без затримки розрахунку.
  4. Погашення та вивільнення. Після погашення — основна сума плюс фіксована процентна ставка — контракт повертав заставу позичальнику. Невиконання погашення до releaseBlock запускало автоматичну ліквідацію: контракт передавав заставу на визначену адресу кредитора.

Весь потік забезпечувався кодом контракту. Жодній зі сторін не потрібно було довіряти іншій або покладатися на посередника для дотримання умов.

Що виявив експеримент #

Архітектура контракту EXTC була технічно логічною. ERC-223 усунув найсерйозніший недолік безпеки ERC-20. Примітиви мультипідпису та блокування за часом безпосередньо відповідали реальним корпоративним платіжним процесам. Механізм заставної позики продемонстрував, що забезпечене кредитування може бути повністю автоматизованим і самозастосовним у ланцюжку.

На практиці виявилися два обмеження:

Витрати газу. На піку січня 2018 року ціни газу Ethereum досягали 50–100 gwei, що робило вартість одного переказу токена ERC-223 $0,50–$2,00. Для мікроплатежів або переказів на $10–$50 ці комісії були непосильними.

Пропускна здатність. Ліміт газу блоку mainnet Ethereum на початку 2018 року становив приблизно 8 мільйонів газу. Переказ ERC-223 споживав приблизно 50 000–80 000 газу. Таким чином, мережа могла обробляти приблизно 100–160 переказів токенів EXTC на блок, або приблизно 7–11 на секунду при 15-секундному інтервалі блоку. Масштаб платіжної мережі — сотні або тисячі транзакцій на секунду — не був досяжний на публічному Ethereum без інфраструктури Layer-2, яка ще не існувала у виробничому вигляді.

Це були обмеження інфраструктури, а не недоліки дизайну EXTC. Логіка контракту була правильною. Базовий блокчейн ще не міг підтримувати обсяг платежів у масштабі фінансової галузі.

Ідеї, що досягли виробництва #

Декілька шаблонів дизайну з EXTC були підтверджені подальшим розвитком:

Атомарний переказ токена з сповіщенням одержувача — основна властивість ERC-223 — стала основою для ERC-777 (2019), який розширив модель сповіщень і пізніше був включений до протоколів кредитування DeFi. Шаблон tokenFallback присутній у всій сучасній архітектурі DeFi.

Мультипідписна авторизація для корпоративних виплат — шаблон вимоги кількох підписів у ланцюжку перед виконанням — став стандартною моделлю для управління скарбницею DAO та інституційних рішень зберігання. Gnosis Safe, запущений у 2018 році, популяризував цей шаблон у масштабі.

Миттєві позики з заставним забезпеченням без посередників — механізм блокування застави в ескроу та атомарного вивільнення коштів позики — є фундаментальним дизайном протоколів кредитування DeFi, таких як Compound (2018) і Aave (2020).

Блокування за висотою блоку для запланованих платежів — шаблон кодування майбутнього часу виконання в контракті — з'являється в контрактах вестингу токенів, відкладених пропозиціях управління та дизайнах оракула часово-зваженої середньої ціни (TWAP) у всій екосистемі DeFi.

Експеримент EXTC не досяг виробничого масштабу. Для дозрівання необхідної для цього дизайну інфраструктури знадобилося ще три-п'ять років. Проєктні питання, які він порушував, були правильними для 2018 року.

Часті запитання #

Чому ERC-223 так і не став домінуючим стандартом токена, незважаючи на виправлення недоліку ERC-20?

ERC-223 вимагав від контрактів-одержувачів реалізації tokenFallback, що порушувало зворотну сумісність із тисячами контрактів, вже розгорнутих для токенів ERC-20. Існуюча екосистема ERC-20 була надто великою для міграції. Подальші пропозиції — зокрема ERC-777 і ERC-1363 — вирішували ту ж проблему з різними компромісами щодо сумісності, але ERC-20 залишався домінуючим завдяки поєднанню мережевих ефектів та запровадження шаблонів обгорнутих токенів, які уникали сценарію беззвучної втрати.

Що сталося з токеном і платформою EXTC?

EXTC був концептуальним підтвердженням і раннім дослідницьким проєктом 2018 року. Ширший ринок ICO та платіжних токенів різко скоротився протягом 2018–2019 років, коли стали очевидними обмеження масштабованості Ethereum і регуляторна невизначеність. Ідеї, закладені в дизайні EXTC, відродилися в пізніших протоколах, що мали доступ до інфраструктури Layer-2, кращих інструментів і чітких регуляторних рамок.

Як модель заставної позики EXTC порівнюється з сучасними протоколами DeFi, такими як Aave?

Основний механізм однаковий: блокувати заставу, отримати позику відповідно до коефіцієнта LTV, погасити або зазнати ліквідації. Відмінності: (1) сучасні протоколи DeFi використовують цінові оракули для динамічного LTV замість фіксованих коефіцієнтів; (2) вони використовують алгоритмічні процентні ставки, що реагують на завантаженість пулу; (3) вони працюють у мережах Layer-2 із витратами газу в 10–100 разів нижчими, ніж mainnet 2018 року; (4) Aave і Compound пройшли формальні аудити безпеки та утримували мільярди доларів ліквідності, забезпечуючи емпіричне підтвердження того, що базова модель є надійною.

Які були обмеження версії Solidity на початку 2018 року?

Контракт EXTC був написаний для Solidity 0.4.x — домінуючої версії на початку 2018 року. У Solidity 0.4 бракувало багатьох функцій безпеки, введених у пізніших версіях: перевірки переповнення цілих чисел (автоматично додана у 0.8.0), require/revert з повідомленнями про помилки (обмежено у 0.4) та явна видимість функцій (за замовчуванням public у 0.4). Контракт покладався на бібліотеку SafeMath від OpenZeppelin для захисту від переповнення — поширений шаблон до того, як компілятор примусово застосовував це.
