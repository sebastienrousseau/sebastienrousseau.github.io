The making of the Express Transaction Credits Platform

Tokenarkitektur, multisignaturutbetalningar och tidslåsta överföringar på Ethereum år 2018.

Sammanfattning för beslutsfattare / Viktiga slutsatser

  • Grundproblemet. ERC-20, den dominerande Ethereum-tokenstandarden 2018, hade ett strukturellt fel: tokens som överfördes direkt till en smart kontraktsadress förstördes tyst om kontraktet saknade en hanterare. Varje betalningsplattform byggd på ERC-20 ärvde den risken (Ethereum EIPs).
  • ERC-223 som lösningen. ERC-223 krävde att mottagarkontrakten implementerade en tokenFallback(address, uint, bytes)-funktion. Om den saknades återgick överföringen atomiskt. Inga tokens kunde tyst gå förlorade (Ethereum EIPs GitHub).
  • EXTC:s fem kontraktsprimitiver. Tokenidentitet (namn, symbol, 18 decimalers precision), fast utbud, ERC-223-kompatibel överföring, multi-signatur företagsutbetalning och block-höjds tidslåsta stående order.
  • Säkerhetslånemekanismen. Låntagare låste EXTC-tokens i ett kontrakts escrow; kontraktet frigav låneintäkter atomiskt vid mottagning av säkerhet, utan garantiförseningar eller kreditkommittégodkännande.
  • Vad experimentet avslöjade om Ethereums begränsningar. Vid mainnet-genomströmning på ~15 TPS och gaskostnader på $0,10–$1,00 per transaktion vid toppen i januari 2018 var ett betalningsnätverk som behandlade ens remittansvolym ekonomiskt och tekniskt ogenomförbart på offentligt Ethereum utan Layer-2-infrastruktur.

Designproblemet: Varför ERC-20 Var Otillräcklig #

ERC-20-standarden, som föreslogs 2015 och formaliserades i Ethereum Improvement Proposal 20, definierade det kanoniska utbytbara tokengränssnittet som drev ICO-boomen 2017–2018. Dess sex kärnfunktioner — totalSupply, balanceOf, transfer, transferFrom, approve och allowance — räckte för enkel tokenutgivning och utbyte.

För en betalningsplattform hade ERC-20 dock ett produktionskritiskt fel. Funktionen transfer(address _to, uint256 _value) flyttade tokens till vilken adress som helst, inklusive kontraktsadresser, utan att utlösa någon kod i det mottagande kontraktet. Ett kontrakt som inte var specifikt programmerat för att spåra inkommande ERC-20-överföringar hade inget sätt att upptäcka dem. Tokens som skickades på detta sätt fastnade permanent, utan mekanism för återhämtning.

Ethereum-gemenskapen uppskattade att tiotals miljoner dollar i ERC-20-tokens hade gått permanent förlorade i mitten av 2018 genom denna mekanism. Att bygga en betalningsplattform där överföringar tyst kunde misslyckas och förstöra användarnas pengar var inte acceptabelt.

ERC-223-lösningen: Atomisk Överföring med Avisering #

ERC-223, som föreslogs i Ethereum EIPs GitHub issue tracker, löste problemet med tyst förlust genom att ändra vad en tokenöverföring krävdes att göra. Under ERC-223 kontrollerade transfer(address _to, uint256 _value, bytes _data) om mottagaradressen innehöll kontraktskod. Om den gjorde det kallade överföringen _to.tokenFallback(address _from, uint256 _value, bytes _data).

Den kritiska egenskapen: om mottagarkontraktet inte implementerade tokenFallback återgick hela överföringstransaktionen. Inga tokens lämnade avsändarens saldo. Inga tokens fastnade. Överföringen var atomisk — den antingen slutfördes med mottagarens kod som kördes, eller misslyckades helt med tillståndet oförändrat.

För EXTC innebar detta:

  • Betalning till smarta kontrakt var säker av konstruktion. Escrow-kontrakt, multi-sig-plånböcker och utlåningskontrakt kunde ta emot EXTC-tokens utan någon risk för att medel oåterkalleligt gick förlorade.
  • Fältet _data möjliggjorde rik betalningsmetadata. Bytes-nyttolasten kunde bära fakturareferenser, routningkoder eller compliance-intyg — information som en enkel ERC-20-överföring inte kunde förmedla.
  • Gaskostnaderna var marginellt högre. Att anropa tokenFallback lade till ungefär 2 000–5 000 gas per överföring, en liten overhead vid 2018 års gaspriser.

EXTC-kontraktarkitekturen #

EXTC-tokenkontraktet var en Solidity-implementering strukturerad kring fem moduler:

1. Tokenidentitet #

string public name = "Express Transaction Credits";
string public symbol = "EXTC";
uint8 public decimals = 18;

Arton decimaler gav EXTC sub-cent precision, vilket matchade den granularitet som krävs för mikro­betalnings- och mikroutlåningsanvändningsfall. Symbolen EXTC var den on-chain-identifierare som registrerades i tokenkontraktet.

2. Fast Totalt Utbud #

Det totala utbudet fastställdes vid kontraktsdistribution och kunde inte inflationeras av efterföljande prägningar. Detta designval gjorde EXTC deflationärt: tokens som permanent togs bort från cirkulation — genom irreversibla bränningsoperationer — minskade utbudet utan ersättning. Modellen med fast utbud var standard i 2018 års betalningstoken-designer, vilket återspeglade det Bitcoin-influerade antagandet att deflationstryck var en funktion för ett bytesmedium.

3. ERC-223-kompatibelt Saldo och Överföring #

Kärnöverföringsfunktionen implementerade det fullständiga ERC-223-gränssnittet. Interna saldomappningar spårade varje adresss innehav. Hjälparen isContract(address) skilde EOA-adresser (externt ägda konton) från kontraktsadresser för att avgöra om tokenFallback behövde anropas.

4. Multi-signatur Företagsutbetalningar #

Företagsbetalningsarbetsflöden krävde sam-auktorisering: ingen enskild undertecknare kunde ensidigt initiera en utbetalning över en definierad tröskel. EXTC-kontraktet implementerade ett tvåav-N multi-signatur-schema:

  1. En utsedd initiativtagare föreslog en överföring och angav mottagare, belopp och ett nonce.
  2. En medsignerare bekräftade nonce.
  3. Först efter att båda signaturerna registrerats on-chain utfördes överföringen.

Detta eliminerade risken för single-point-of-failure för företagskonton samtidigt som hela auktorisations­flödet hölls on-chain och granskningsbart utan ett clearinghouse-mellanhänder.

5. Block-höjds Tidslåsta Stående Order #

Återkommande betalningar — löner, prenumerationer, schemalagda låneåterbetalningar — krävde en stående-order-primitiv. EXTC implementerade detta som ett tidslås: en överföringspost lagrades i kontraktet med en releaseBlock-parameter. Överföringen kunde inte utföras förrän Ethereum-blockhöjden nådde releaseBlock.

Blockhöjd som en tidsproxy var ett pragmatiskt val 2018. Ethereum syftade till ett 15-sekunders blockintervall, vilket gjorde blockhöjden till en rimligt tillförlitlig proxy för väggklockstid inom ett antal minuter. Absoluta tidsstämplar (block.timestamp) var tillgängliga men känsliga för minarmanipulation inom ett ±900-sekunders fönster, vilket gjorde blockhöjden till den säkrare referensen för finansiella kontrakt.

Mekanismen för Omedelbart Lån med Säkerhet #

EXTC:s utlåningsprimitiv var den mest komplexa komponenten. Designen:

  1. Låntagaren låser säkerhet. Låntagaren anropade lockCollateral(uint256 _collateralAmount) och överförde EXTC-tokens till utlåningskontraktets escrow via en ERC-223 tokenFallback.
  2. Kontroll av belåningsgrad. Kontraktet läste ett förkonfigurerat LTV-förhållande (t.ex. 50%) och beräknade det maximala lånebeloppet mot den låsta säkerheten.
  3. Atomisk låneutbetalning. Om säkerheten uppfyllde minimigränsen överförde kontraktet omedelbart lånebeloppet till låntagarens adress. Ingen garantikö, ingen kreditkommitté, ingen avvecklingsförsening.
  4. Återbetalning och frigörande. Vid återbetalning — kapital plus en fast ränta — frigav kontraktet säkerheten tillbaka till låntagaren. Underlåtenhet att återbetala vid releaseBlock utlöste automatisk likvidation: kontraktet överförde säkerheten till långivarens angivna adress.

Hela flödet verkställdes av kontraktskod. Ingen part behövde lita på den andra eller förlita sig på en mellanhand för att verkställa villkoren.

Vad Experimentet Avslöjade #

EXTC-kontraktarkitekturen var tekniskt sammanhängande. ERC-223 löste ERC-20:s allvarligaste säkerhetsfel. Multi-signatur- och tidslåsprimitierna mappade direkt till verkliga företagsbetalningsarbetsflöden. Säkerhetslånemekanismen visade att säkrad utlåning helt kunde automatiseras och självverkställas on-chain.

Två begränsningar visade sig i praktiken:

Gaskostnader. Vid toppen i januari 2018 nådde Ethereums gaspriser 50–100 gwei, vilket gjorde en enskild ERC-223-tokenöverföring till att kosta $0,50–$2,00. För mikrobetalningar eller remittanser på $10–$50 var dessa avgifter prohibitiva.

Genomströmning. Ethereum mainnets blockgasgräns i början av 2018 var ungefär 8 miljoner gas. En ERC-223-överföring förbrukade ungefär 50 000–80 000 gas. Nätverket kunde därför behandla ungefär 100–160 EXTC-tokenöverföringar per block, eller ungefär 7–11 per sekund vid 15-sekunders blockintervallet. Betalningsnätverksskala — hundratals eller tusentals transaktioner per sekund — var inte uppnåelig på offentligt Ethereum utan Layer-2-infrastruktur som ännu inte existerade i produktionsform.

Dessa var infrastrukturbegränsningar, inte designfel i EXTC. Kontraktslogiken var korrekt. Den underliggande blockkedjan kunde ännu inte stödja betalningsvolym i finansindustrin skala.

Idéerna som Nådde Produktion #

Flera designmönster från EXTC validerades av efterföljande utveckling:

Atomisk tokenöverföring med mottagaravisering — kärnegenskapen hos ERC-223 — blev grunden för ERC-777 (2019), som utvidgade aviseringsmodellen och senare inkorporerades i DeFi-utlåningsprotokoll. Mönstret tokenFallback förekommer genomgående i modern DeFi-arkitektur.

Multi-signatur-auktorisation för företagsutbetalningar — mönstret att kräva flera on-chain-signaturer före utförande — blev standardmodellen för DAO-kassaförvaltning och institutionella förvaringslösningar. Gnosis Safe, lanserat 2018, populariserade detta mönster i stor skala.

Säkerhetsstödda omedelbara lån utan mellanhänder — mekanismen att låsa säkerhet i escrow och frigöra låneintäkter atomiskt — är den grundläggande designen hos DeFi-utlåningsprotokoll som Compound (2018) och Aave (2020).

Block-höjdstidslås för schemalagda betalningar — mönstret att koda framtida utförandetiming i kontraktet — förekommer i tokenvesting-kontrakt, fördröjda styrningsförslag och tidsvägt genomsnittspris (TWAP) oracle-designer i hela DeFi-ekosystemet.

EXTC-experimentet nådde inte produktionsskala. Den infrastruktur som krävdes för att göra designen livskraftig tog ytterligare tre till fem år att mogna. Designfrågorna det ställde var de rätta för 2018.

Vanliga Frågor #

Varför antogs ERC-223 aldrig som den dominerande tokenstandarden trots att den fixade ERC-20:s fel?

ERC-223 krävde att mottagarkontrakt implementerade tokenFallback, vilket bröt bakåtkompatibiliteten med de tusentals kontrakt som redan distribuerats för ERC-20-tokens. Det befintliga ERC-20-ekosystemet var för stort för att migrera. Efterföljande förslag — framför allt ERC-777 och ERC-1363 — adresserade samma problem med olika kompatibilitetsavvägningar, men ERC-20 förblev dominerande genom en kombination av nätverkseffekter och introduktionen av inslagna tokenmönster som undvek det tysta förlust-scenariot.

Vad hände med EXTC-tokenet och plattformen?

EXTC var ett proof-of-concept och ett tidigt forskningsprojekt från 2018. Den bredare ICO- och betalningstoken-marknaden krympte kraftigt under 2018–2019 när Ethereums skalbegränsningar och regulatorisk osäkerhet blev tydliga. Idéerna inbyggda i EXTC-designen dök upp igen i senare protokoll som hade tillgång till Layer-2-infrastruktur, bättre verktyg och tydligare regulatoriska ramar.

Hur jämförs EXTC:s säkerhetslånemodell med moderna DeFi-protokoll som Aave?

Kärnmekanismen är densamma: lås säkerhet, ta emot ett lån dimensionerat mot ett LTV-förhållande, återbetala eller möt likvidation. Skillnaderna är: (1) moderna DeFi-protokoll använder oracle-prisflöden för dynamisk LTV snarare än fasta förhållanden; (2) de använder algoritmiska räntor som svarar på poolanvändning; (3) de opererar på Layer-2-nätverk med gaskostnader 10–100 gånger lägre än 2018 mainnet; (4) Aave och Compound har genomgått formella säkerhetsrevisioner och hållit miljarder dollar i likviditet, vilket ger empirisk validering att grundmodellen är sund.

Vilka var Solidity-versionsbegränsningarna i början av 2018?

EXTC-kontraktet skrevs för Solidity 0.4.x, den dominerande versionen i början av 2018. Solidity 0.4 saknade många säkerhetsfunktioner som introducerades i senare versioner: kontroll av heltalsspill (lades till automatiskt i 0.8.0), require/revert med felmeddelanden (begränsat i 0.4) och explicit funktionssynlighet (standard var public i 0.4). Kontraktet förlitade sig på OpenZeppelins SafeMath-bibliotek för att skydda mot spill, ett vanligt mönster innan kompilatorn verkställde detta inbyggt.
