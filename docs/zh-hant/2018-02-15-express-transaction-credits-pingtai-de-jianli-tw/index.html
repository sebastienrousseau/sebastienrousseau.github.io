The making of the Express Transaction Credits Platform

2018年以太坊上的代幣架構、多重簽名分發及時間鎖定轉帳。

執行摘要 / 核心要點

  • 根本問題。 ERC-20是2018年主流Ethereum代幣標準，存在結構性缺陷：代幣直接轉入智慧合約位址時，若合約缺少處理程式，將被靜默銷毀。基於ERC-20建構的任何支付平台都繼承了這一風險（Ethereum EIPs）。
  • ERC-223作為解決方案。 ERC-223要求接收合約實現tokenFallback(address, uint, bytes)函數。若不存在，轉帳將原子性回滾。代幣不會被靜默遺失（Ethereum EIPs GitHub）。
  • EXTC的五個合約原語。 代幣身份標識（名稱、符號、18位小數精度）、固定供應量、符合ERC-223的轉帳、企業撥款多簽名授權，以及基於區塊高度的時間鎖常委託。
  • 抵押貸款機制。 借款人將EXTC代幣鎖入合約託管；合約在收到抵押品後原子性釋放貸款，無需承銷延遲或信貸委員會審批。
  • 實驗揭示的Ethereum限制。 2018年1月高峰時主網吞吐量約15 TPS，每筆交易Gas費用$0.10–$1.00，處理匯款規模流量的支付網路在沒有Layer-2基礎設施的情況下，在經濟和技術上均不可行。

設計問題：ERC-20為何不足 #

ERC-20標準於2015年提出，並在Ethereum改進提案20中正式確立，定義了推動2017–2018年ICO熱潮的標準同質化代幣介面。其六個核心函數——totalSupply、balanceOf、transfer、transferFrom、approve和allowance——足以支援簡單的代幣發行和交換。

然而，對於支付平台而言，ERC-20存在生產級關鍵缺陷。transfer(address _to, uint256 _value)函數可將代幣移動至任何位址，包括合約位址，而不會觸發接收合約中的任何程式碼。未專門程式設計追蹤傳入ERC-20轉帳的合約無法偵測到這些轉帳。以這種方式傳送的代幣將永久被困，沒有任何恢復機制。

Ethereum社群估計，截至2018年中，透過這一機制永久損失的ERC-20代幣價值達數千萬美元。建構一個轉帳可能靜默失敗並銷毀使用者資金的支付平台是不可接受的。

ERC-223解決方案：帶通知的原子轉帳 #

ERC-223在Ethereum EIPs GitHub問題追蹤器上提出，透過改變代幣轉帳的必要操作來解決靜默遺失問題。在ERC-223下，transfer(address _to, uint256 _value, bytes _data)會檢查接收位址是否包含合約程式碼。若包含，轉帳將呼叫_to.tokenFallback(address _from, uint256 _value, bytes _data)。

關鍵屬性：若接收合約未實現tokenFallback，整個轉帳交易將回滾。傳送方餘額中不會減少代幣，也不會有代幣被困。轉帳具有原子性——要麼在接收方程式碼執行後完成，要麼完全失敗且狀態不變。

對於EXTC而言，這意味著：

  • 向智慧合約付款在構造上是安全的。 託管合約、多簽名錢包和借貸合約均可接收EXTC代幣，無需擔憂資金被不可逆轉地損失。
  • _data欄位支援豐富的支付元資料。 位元組載荷可攜帶發票引用、路由代碼或合規證明——這些資訊是簡單的ERC-20轉帳無法傳遞的。
  • Gas費用略有增加。 呼叫tokenFallback每次轉帳約增加2,000–5,000 Gas，在2018年的Gas價格下屬於小額開銷。

EXTC合約架構 #

EXTC代幣合約是圍繞五個模組建構的Solidity實現：

1. 代幣身份標識 #

string public name = "Express Transaction Credits";
string public symbol = "EXTC";
uint8 public decimals = 18;

十八位小數給予EXTC亞分精度，滿足小額支付和小額貸款用例所需的精細度。符號EXTC是在代幣合約中登錄的鏈上識別碼。

2. 固定總供應量 #

總供應量在合約部署時設定，後續鑄造無法增發。這一設計選擇使EXTC具有通縮特性：透過不可逆銷毀操作永久從流通中移除的代幣將減少供應而無法補充。固定供應模型是2018年支付代幣設計的標準，反映了受Bitcoin影響的假設——通縮壓力對於交換媒介而言是一種特性。

3. 符合ERC-223的餘額與轉帳 #

核心轉帳函數實現了完整的ERC-223介面。內部餘額映射追蹤每個位址的持有量。isContract(address)輔助函數區分EOA（外部擁有帳戶）位址和合約位址，以確定是否需要呼叫tokenFallback。

4. 多簽名企業撥款 #

企業支付工作流需要聯合授權：沒有單一簽名者可以單方面發起超過規定閾值的撥款。EXTC合約實現了N中取2的多簽名方案：

  1. 指定發起人提出轉帳，指定接收方、金額和隨機數。
  2. 聯署人確認隨機數。
  3. 僅在兩個簽名均記錄在鏈上後，轉帳才會執行。

這消除了企業帳戶的單點故障風險，同時將整個授權流程保持在鏈上且可稽核，無需清算所中介。

5. 基於區塊高度的時間鎖常委託 #

定期支付——工資、訂閱、預定貸款還款——需要常委託原語。EXTC將其實現為時間鎖：轉帳記錄儲存在合約中，帶有releaseBlock參數。在Ethereum區塊高度達到releaseBlock之前，轉帳無法執行。

以區塊高度作為時間代理在2018年是務實的選擇。Ethereum目標區塊間隔為15秒，使區塊高度成為分鐘範圍內相當可靠的掛鐘時間代理。絕對時間戳（block.timestamp）雖然可用，但在±900秒視窗內易受礦工操縱，使區塊高度成為金融合約更安全的參考。

抵押擔保即時貸款機制 #

EXTC借貸原語是最複雜的組件。設計如下：

  1. 借款人鎖定抵押品。 借款人呼叫lockCollateral(uint256 _collateralAmount)，透過ERC-223的tokenFallback將EXTC代幣轉移至借貸合約託管。
  2. 貸款價值比檢查。 合約讀取預配置的LTV比率（例如50%），並根據鎖定抵押品計算最大貸款金額。
  3. 原子性貸款撥付。 若抵押品滿足最低閾值，合約立即將貸款金額轉移至借款人位址。無需承銷佇列，無需信貸委員會，無需結算延遲。
  4. 還款與釋放。 在還款——本金加固定利率——後，合約將抵押品釋放回借款人。未能在releaseBlock之前還款將觸發自動清算：合約將抵押品轉移至貸款方指定位址。

整個流程由合約程式碼強制執行。雙方無需互相信任，也無需依賴中介來執行條款。

實驗揭示的內容 #

EXTC合約架構在技術上是連貫的。ERC-223解決了ERC-20最嚴重的安全缺陷。多簽名和時間鎖原語直接映射到真實的企業支付工作流。抵押貸款機制證明了有擔保貸款可以完全自動化並在鏈上自我執行。

實踐中暴露了兩個限制：

Gas費用。 在2018年1月高峰時，Ethereum Gas價格達到50–100 gwei，使單次ERC-223代幣轉帳成本為$0.50–$2.00。對於$10–$50的小額支付或匯款，這些費用是不可接受的。

吞吐量。 2018年初Ethereum主網區塊Gas上限約為800萬Gas。ERC-223轉帳消耗約50,000–80,000 Gas。因此網路每個區塊約可處理100–160筆EXTC代幣轉帳，在15秒區塊間隔下約為每秒7–11筆。支付網路規模——每秒數百或數千筆交易——在沒有生產形式的Layer-2基礎設施的情況下，在公鏈Ethereum上無法實現。

這些是基礎設施限制，而非EXTC的設計缺陷。合約邏輯是正確的。底層區塊鏈尚無法支援金融行業規模的支付量。

進入生產的想法 #

來自EXTC的幾種設計模式在後續開發中得到驗證：

帶接收方通知的原子代幣轉帳——ERC-223的核心屬性——成為ERC-777（2019年）的基礎，ERC-777擴展了通知模型，後來被納入DeFi借貸協議。tokenFallback模式貫穿現代DeFi架構。

企業撥款的多簽名授權——執行前需要多個鏈上簽名的模式——成為DAO國庫管理和機構託管解決方案的標準模型。Gnosis Safe於2018年推出，將這一模式大規模推廣。

無中介的抵押即時貸款——將抵押品鎖入託管並原子性釋放貸款的機制——是DeFi借貸協議如Compound（2018年）和Aave（2020年）的基本設計。

定期支付的區塊高度時間鎖——在合約中編碼未來執行時間的模式——出現在代幣歸屬合約、延遲治理提案和DeFi生態系統中的時間加權平均價格（TWAP）預言機設計中。

EXTC實驗未能達到生產規模。使設計可行所需的基礎設施還需三到五年才能成熟。它所提出的設計問題對於2018年來說是正確的。

常見問題解答 #

為何ERC-223儘管修復了ERC-20的缺陷，卻從未成為主流代幣標準？

ERC-223要求接收合約實現tokenFallback，這破壞了與已為ERC-20代幣部署的數千份合約的向後相容性。現有ERC-20生態系統太大，難以遷移。後續提案——特別是ERC-777和ERC-1363——以不同的相容性權衡解決了同一問題，但ERC-20透過網路效應和引入避免靜默遺失場景的包裝代幣模式保持了主導地位。

EXTC代幣和平台發生了什麼？

EXTC是2018年的概念驗證和早期研究專案。隨著Ethereum可擴展性限制和監管不確定性變得明朗，更廣泛的ICO和支付代幣市場在2018–2019年急劇收縮。EXTC設計中蘊含的想法在後來能夠存取Layer-2基礎設施、更好工具和更清晰監管框架的協議中重新出現。

EXTC的抵押貸款模型與Aave等現代DeFi協議相比如何？

核心機制相同：鎖定抵押品，獲得按LTV比率計算的貸款，還款或面臨清算。區別在於：（1）現代DeFi協議使用預言機價格源進行動態LTV，而非固定比率；（2）它們使用響應池利用率的演算法利率；（3）它們在Layer-2網路上運行，Gas成本比2018年主網低10–100倍；（4）Aave和Compound已通過正式安全審計並持有數十億美元流動性，提供了基本模型合理性的經驗驗證。

2018年初Solidity版本有哪些限制？

EXTC合約為Solidity 0.4.x編寫，這是2018年初的主流版本。Solidity 0.4缺乏後續版本引入的許多安全特性：整數溢位檢查（0.8.0中自動新增）、帶錯誤訊息的require/revert（0.4中受限）以及顯式函數可見性（0.4中預設為public）。合約依賴OpenZeppelin的SafeMath函式庫防止溢位，這是編譯器原生強制執行前的常見模式。
