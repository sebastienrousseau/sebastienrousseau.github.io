Express Transaction Credits プラットフォームの開発

2018年のEthereumにおけるトークンアーキテクチャ、マルチシグネチャ送金、タイムロック転送。

TL;DR. 2018年にEthereum ERC-223上に構築されたEXTCプラットフォームの技術的考察：トークンアーキテクチャ、マルチシグ送金、タイムロック転送、担保付き即時ローンを詳解。

エグゼクティブサマリー / 主なポイント

  • 根本的な問題。 2018年のEthereumドミナントトークン標準ERC-20には構造的な欠陥がありました：スマートコントラクトアドレスに直接転送されたトークンは、コントラクトにハンドラーがなければサイレントに消滅していました。ERC-20上に構築されたあらゆる決済プラットフォームはそのリスクを引き継いでいました (Ethereum EIPs)。
  • ERC-223による解決策。 ERC-223は受信コントラクトにtokenFallback(address, uint, bytes)関数の実装を要求しました。存在しない場合、転送は原子的にリバートされました。トークンがサイレントに失われることはありませんでした (Ethereum EIPs GitHub)。
  • EXTCの5つのコントラクトプリミティブ。 トークンアイデンティティ（名前、シンボル、18桁精度）、固定供給量、ERC-223準拠転送、マルチシグネチャ企業送金、ブロック高タイムロック定期注文。
  • 担保ローンメカニズム。 借り手はEXTCトークンをコントラクトのエスクローに預け、コントラクトは担保受領時に即座に融資額を原子的にリリースしました。引受審査の遅延も信用委員会の承認も不要でした。
  • 実験がEthereumの限界について明らかにしたこと。 2018年1月のピーク時、メインネットのスループット約15 TPS、ガスコスト$0.10–$1.00/取引という状況では、送金規模のボリュームを処理する決済ネットワークでさえ、Layer-2インフラなしにパブリックEthereumで経済的・技術的に実現不可能でした。

設計上の問題：なぜERC-20は不十分だったのか #

2015年に提案され、Ethereum改善提案20として正式化されたERC-20標準は、2017–2018年のICOブームを支えた標準的なファンジブルトークンインターフェースを定義しました。その6つのコア関数 — totalSupply、balanceOf、transfer、transferFrom、approve、allowance — は、単純なトークン発行と交換には十分でした。

しかし決済プラットフォームにとって、ERC-20には本番環境で致命的な欠陥がありました。transfer(address _to, uint256 _value)関数は、受信コントラクト内のコードを起動することなく、コントラクトアドレスを含む任意のアドレスにトークンを移動させました。受信ERC-20転送を追跡するよう特別にプログラムされていないコントラクトは、それを検出する方法がありませんでした。この方法で送られたトークンは回収メカニズムなしに永久に閉じ込められました。

Ethereumコミュニティは、このメカニズムにより2018年半ばまでに数千万ドル相当のERC-20トークンが永久に失われたと推定していました。転送がサイレントに失敗してユーザーの資金を消滅させる可能性がある決済プラットフォームを構築することは受け入れられませんでした。

ERC-223の解決策：通知付き原子的転送 #

Ethereum EIPsのGitHub issueトラッカーで提案されたERC-223は、トークン転送が行うべきことを変更することでサイレントロスの問題に対処しました。ERC-223では、transfer(address _to, uint256 _value, bytes _data)が受信アドレスにコントラクトコードが含まれているかどうかを確認しました。含まれている場合、転送は_to.tokenFallback(address _from, uint256 _value, bytes _data)を呼び出しました。

重要な特性：受信コントラクトがtokenFallbackを実装していない場合、転送トランザクション全体がリバートされました。送信者の残高からトークンは出て行きませんでした。トークンは閉じ込められませんでした。転送は原子的でした — 受信者のコードが実行されて完了するか、状態が変化しないまま完全に失敗するかのどちらかでした。

EXTCにとって、これは次のことを意味しました：

  • スマートコントラクトへの支払いは設計上安全でした。 エスクローコントラクト、マルチシグウォレット、融資コントラクトは、資金が不可逆的に失われるリスクなしにEXTCトークンを受け取れました。
  • _dataフィールドが豊富な支払いメタデータを可能にしました。 バイトペイロードは、請求書参照、ルーティングコード、またはコンプライアンス証明を運べました — 単純なERC-20転送では伝えられない情報です。
  • ガスコストはわずかに高くなりました。 tokenFallbackの呼び出しは転送ごとに約2,000–5,000ガスを追加しましたが、2018年のガス価格では小さなオーバーヘッドでした。

EXTCコントラクトのアーキテクチャ #

EXTCトークンコントラクトは、5つのモジュールを中心に構成されたSolidity実装でした：

1. トークンアイデンティティ #

string public name = "Express Transaction Credits";
string public symbol = "EXTC";
uint8 public decimals = 18;

18桁の小数点以下精度により、EXTCはサブセント精度を持ち、マイクロペイメントとマイクロローンのユースケースに必要な粒度と一致していました。シンボルEXTCは、トークンコントラクトに登録されたオンチェーン識別子でした。

2. 固定総供給量 #

総供給量はコントラクトのデプロイ時に設定され、その後のミントによって増加させることはできませんでした。この設計上の選択により、EXTCはデフレ通貨となりました：不可逆的なバーン操作によって流通から永久に除去されたトークンは、補充なしに供給量を減少させました。固定供給モデルは2018年の決済トークン設計では標準的であり、デフレ圧力は交換媒体の特徴であるというビットコイン影響を受けた仮定を反映していました。

3. ERC-223準拠の残高と転送 #

コア転送関数は完全なERC-223インターフェースを実装しました。内部残高マッピングが各アドレスの保有量を追跡しました。isContract(address)ヘルパーは、EOA（外部所有アカウント）アドレスとコントラクトアドレスを区別し、tokenFallbackを呼び出す必要があるかどうかを判断しました。

4. マルチシグネチャ企業送金 #

企業の決済ワークフローには共同承認が必要でした：定義された閾値を超える送金を一方的に開始できる署名者は存在しませんでした。EXTCコントラクトはN個中2個のマルチシグネチャスキームを実装しました：

  1. 指定された開始者が受取人、金額、ノンスを指定して転送を提案しました。
  2. 共同署名者がノンスを確認しました。
  3. 両方の署名がオンチェーンに記録された後にのみ、転送が実行されました。

これにより、清算所の仲介なしに承認フロー全体をオンチェーンで監査可能に維持しながら、企業アカウントの単一障害点リスクを排除しました。

5. ブロック高タイムロック定期注文 #

定期的な支払い — 給与、サブスクリプション、ローンの定期返済 — には定期注文プリミティブが必要でした。EXTCはこれをタイムロックとして実装しました：転送レコードがreleaseBlockパラメーターとともにコントラクトに保存されました。EthereumのブロックハイトがreleaseBlockに達するまで転送を実行できませんでした。

ブロック高を時間プロキシとして使用することは2018年における実用的な選択でした。Ethereumは15秒のブロックインターバルを目標としており、ブロック高は数分の範囲内で実時間の合理的に信頼できるプロキシとなりました。絶対タイムスタンプ（block.timestamp）は利用可能でしたが、±900秒のウィンドウ内でマイナーによる操作が可能であり、金融コントラクトではブロック高の方が安全な参照でした。

担保付き即時ローンメカニズム #

EXTCレンディングプリミティブは最も複雑なコンポーネントでした。設計：

  1. 借り手が担保を預ける。 借り手はlockCollateral(uint256 _collateralAmount)を呼び出し、ERC-223のtokenFallbackを介してEXTCトークンをレンディングコントラクトのエスクローに転送しました。
  2. LTV比率チェック。 コントラクトは事前設定されたLTV比率（例：50%）を読み取り、預けられた担保に対する最大融資額を計算しました。
  3. 原子的融資実行。 担保が最低閾値を満たした場合、コントラクトは即座に融資額を借り手のアドレスに転送しました。引受審査キューなし、信用委員会なし、決済遅延なし。
  4. 返済と解放。 返済時 — 元本プラス固定金利 — コントラクトは担保を借り手に戻しました。releaseBlockまでに返済に失敗すると自動清算が発動：コントラクトは担保を貸し手の指定アドレスに転送しました。

フロー全体がコントラクトコードによって強制されました。どちらの当事者も相手を信頼したり、条件を執行するための仲介者に依存したりする必要がありませんでした。

実験が明らかにしたもの #

EXTCコントラクトのアーキテクチャは技術的に一貫していました。ERC-223はERC-20の最も深刻な安全上の欠陥を解決しました。マルチシグネチャとタイムロックのプリミティブは、実際の企業決済ワークフローに直接対応していました。担保ローンメカニズムは、担保付き融資がオンチェーンで完全に自動化され自己執行できることを実証しました。

実践では2つの制約が明らかになりました：

ガスコスト。 2018年1月のピーク時、EthereumのガスプライスはKWei 50–100に達し、ERC-223トークン転送1回のコストは$0.50–$2.00になりました。$10–$50のマイクロペイメントや送金には、これらの手数料は法外でした。

スループット。 2018年初頭のEthereumメインネットのブロックガスリミットは約800万ガスでした。ERC-223転送は約50,000–80,000ガスを消費しました。したがってネットワークはブロックごとに約100–160のEXTCトークン転送を処理でき、15秒ブロックインターバルでは1秒あたり約7–11回でした。決済ネットワークの規模 — 1秒あたり数百から数千のトランザクション — は、まだ本番形態で存在しなかったLayer-2インフラなしにパブリックEthereumで達成不可能でした。

これらはインフラの制約であり、EXTCの設計上の欠陥ではありませんでした。コントラクトのロジックは正しいものでした。基礎となるブロックチェーンは、金融業界規模での決済量をまだサポートできませんでした。

本番環境に到達したアイデア #

EXTCのいくつかの設計パターンは、その後の開発によって検証されました：

受信者通知付き原子的トークン転送 — ERC-223のコア特性 — は、通知モデルを拡張し後にDeFiレンディングプロトコルに組み込まれたERC-777（2019年）の基礎となりました。tokenFallbackパターンは現代のDeFiアーキテクチャ全体に見られます。

企業送金向けマルチシグネチャ認証 — 実行前に複数のオンチェーン署名を要求するパターン — はDAOのトレジャリー管理と機関投資家向けカストディソリューションの標準モデルになりました。2018年に立ち上がったGnosis Safeは、このパターンを大規模に普及させました。

仲介者なしの担保付き即時ローン — 担保をエスクローに預け、融資収益を原子的にリリースするメカニズム — は、Compound（2018年）やAave（2020年）などのDeFiレンディングプロトコルの基本設計です。

定期支払い向けブロック高タイムロック — コントラクトに将来の実行タイミングをエンコードするパターン — は、DeFiエコシステム全体でトークンのベスティングコントラクト、遅延ガバナンス提案、時間加重平均価格（TWAP）オラクル設計に現れています。

EXTCの実験は本番規模に到達しませんでした。設計を実現可能にするために必要なインフラは、さらに3〜5年の熟成を必要としました。それが提起した設計上の問いは、2018年にとって正しいものでした。

よくある質問 #

ERC-223はERC-20の欠陥を修正したにもかかわらず、なぜドミナントなトークン標準として採用されなかったのですか？

ERC-223は受信コントラクトにtokenFallbackの実装を要求し、ERC-20トークン向けにすでにデプロイされた何千ものコントラクトとの後方互換性を破りました。既存のERC-20エコシステムは移行するには大きすぎました。その後の提案 — 特にERC-777とERC-1363 — は異なる互換性のトレードオフで同じ問題に対処しましたが、ERC-20はネットワーク効果とサイレントロスシナリオを回避するラップドトークンパターンの導入により、引き続き支配的でした。

EXTCトークンとプラットフォームはどうなりましたか？

EXTCは2018年のプルーフオブコンセプトおよび初期研究プロジェクトでした。EthereumのスケーラビリティとRegulatorの不確実性が明らかになるにつれて、より広いICOと決済トークン市場は2018–2019年にかけて急激に縮小しました。EXTC設計に組み込まれたアイデアは、Layer-2インフラ、より良いツール、より明確な規制フレームワークへのアクセスを持つ後のプロトコルに再浮上しました。

EXTCの担保ローンモデルはAaveなどの現代のDeFiプロトコルと比較してどうですか？

コアメカニズムは同じです：担保を預け、LTV比率に対してサイズ設定されたローンを受け取り、返済するか清算に直面します。違いは：（1）現代のDeFiプロトコルは固定比率ではなく動的LTV向けにオラクル価格フィードを使用します；（2）プール利用に応じたアルゴリズム的金利を使用します；（3）2018年のメインネットより10〜100倍低いガスコストでLayer-2ネットワーク上で動作します；（4）AaveとCompoundは正式なセキュリティ監査を経て数十億ドルの流動性を保有し、基本モデルが健全であることの実証的検証を提供しています。

2018年初頭のSolidityバージョンの制約は何でしたか？

EXTCコントラクトは、2018年初頭のドミナントバージョンであるSolidity 0.4.x向けに書かれました。Solidity 0.4は、後のバージョンで導入された多くのセキュリティ機能を欠いていました：整数オーバーフローチェック（0.8.0で自動追加）、エラーメッセージ付きのrequire/revert（0.4では限定的）、および明示的な関数可視性（0.4ではデフォルトでパブリック）。コントラクトはオーバーフロー対策にOpenZeppelinのSafeMathライブラリに依存していましたが、これはコンパイラがネイティブにこれを強制する前の一般的なパターンでした。
