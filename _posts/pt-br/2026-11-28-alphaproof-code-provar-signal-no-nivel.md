## Por que este resultado importa para quem entrega software criptográfico

O Signal é descrito como o padrão global de fato para mensagens com criptografia de ponta a ponta, com variantes do protocolo implantadas no WhatsApp, no aplicativo Messenger da Meta e no Google Messages. Quando um protocolo sustenta tantas conversas, a distância entre um projeto provado seguro no papel e o código compilado que de fato é executado deixa de ser acadêmica. Uma prova no papel pode ser impecável enquanto a implementação faz algo completamente diferente.

É essa distância que o trabalho ataca. Os autores apresentam as primeiras provas de propriedades de segurança no nível do protocolo para uma implementação amplamente implantada e sem modificações de um protocolo criptográfico. Leia essa frase duas vezes, porque cada qualificador pesa. No nível do protocolo significa que as provas tratam de propriedades como o sigilo futuro, e não apenas da ausência de erros de memória. Amplamente implantada significa libsignal, não um protótipo de pesquisa. Sem modificações significa que ninguém reescreveu o código numa forma mais conveniente para o provador.

Para fundadores, a leitura prática é sobre custo. Os autores apresentam a verificação formal como alternativa à caça reativa de bugs: especificam-se as propriedades de correção e segurança que um sistema de software precisa garantir e depois se prova matematicamente que o sistema as satisfaz. Eles a descrevem como historicamente cara demais para a maior parte do software. Os resultados dos autores sugerem que a IA pode torná-la viável para sistemas reais. É uma afirmação cautelosa, e eu a trato assim: uma sugestão apoiada por um único grande estudo de caso, não um resultado econômico consolidado. Mesmo assim, um estudo de caso nessa escala é uma evidência mais séria do que a maioria das afirmações nessa área.

## O problema da verificação é mais difícil do que parece

O material de origem do framework aponta para uma referência conhecida de quão exigente a verificação pode ser: o compilador C verificado CompCert, cuja verificação levou seis pessoas-ano, segundo o número relatado aqui. Trate esse número com algum cuidado, já que o parêntese sobre pessoas-ano é uma construção da fonte, e não uma citação direta. O ponto se mantém de qualquer forma: verificar software sério tem sido um compromisso de vários anos.

Verificar código industrial preexistente é apontado como ainda mais difícil, porque o provador não pode modificar o código para simplificar a prova. Uma biblioteca de produção compilada por um compilador otimizador é exatamente esse caso. Se você tem liberdade para reestruturar o programa, pode moldá-lo para que a prova surja naturalmente. Se precisa aceitar o código como ele é, herda cada idioma desajeitado e cada decisão do compilador.

O AlphaProof Code escolhe de propósito o caminho mais difícil. O código Rust sem modificações é compilado com o compilador padrão, e o executável é carregado no Lean junto com uma semântica de AArch64. Na prática, os autores ligam a libsignal a um pequeno programa de teste de linha de comando e o compilam com o compilador rustc padrão para código de máquina AArch64 Linux. O objeto da prova é o código de máquina. É um alvo mais forte do que o raciocínio no nível do código-fonte, pois o compilador deixa de ser algo em que se precisa confiar para preservar as propriedades demonstradas.

## Como o framework divide o trabalho

O AlphaProof Code é um framework de colaboração entre humanos e IA para especificação e verificação formais de software real. Ele se apoia num princípio que considero convincente: a maior parte do esforço humano na verificação de software está agora na engenharia da especificação. A escrita de provas, a parte que antes consumia anos de especialistas, é cada vez mais algo que as máquinas conseguem fazer.

Os autores argumentam, com base em seus próprios resultados, que mesmo provas grandes sobre software podem ser escritas por equipes de agentes de IA depois que a especificação é fixada, e que os agentes de prova podem trabalhar de forma autônoma porque o kernel do Lean verifica cada prova no final. O framework divide o trabalho em duas partes. Um usuário humano e agentes de IA escrevem juntos especificações Lean de código real e, depois que o usuário valida uma especificação, uma equipe de agentes autônomos prova que o código a satisfaz. Os autores são explícitos: em sistemas grandes e complexos, a assistência da IA pode reduzir o custo de escrever especificações e da garantia (assurance), mas não substituir completamente o julgamento e a revisão humanos.

A fase de especificação não é um carimbo automático. Um grupo de agentes revisores verifica se um rascunho é fiel às suas fontes e à implementação. No processo dos autores, o usuário revisa, ajusta e aprova a especificação antes que qualquer prova seja escrita, e o commit git dela se torna a referência contra a qual o guardião depois verifica as provas. Eles relatam que podem ser necessárias muitas rodadas de iteração entre o usuário e os agentes para chegar a uma boa especificação, mesmo quando existe um modelo na literatura; no caso do Signal, compor os modelos anteriores do handshake e do ratchet e cobrir o novo ratchet pós-quântico exigiu várias rodadas de rascunhos e revisão. Quem espera que um único prompt produza uma especificação confiável deve ajustar as expectativas.

Os autores propõem uma divisão de responsabilidades: os autores humanos escolhem o que provar, resolvem ambiguidades, avaliam trade-offs de segurança e tomam todas as decisões finais, enquanto os agentes de IA redigem e testam especificações sob direção humana. Considero essa a postura certa. Ela atribui o julgamento à parte que pode responder por ele.

Todos os agentes do AlphaProof Code, incluindo o redator de especificações, são agentes de programação de uso geral cujo comportamento é definido por skills, que são documentos em linguagem natural. Nenhuma arquitetura de provador sob medida é descrita aqui. O comportamento é conduzido por documentos em prosa, o que torna o sistema comparativamente fácil de inspecionar e ajustar.

## Onde a confiança realmente está

A decisão de projeto mais importante do framework é aquilo em que ele se recusa a confiar. As provas de milhões de linhas produzidas pelos agentes de IA não são confiáveis, porque qualquer erro lógico numa prova é rejeitado pelo kernel do Lean. Em outras palavras, como a prova é verificada em última instância pelo kernel do Lean, a confiabilidade dos resultados não depende da confiabilidade dos agentes que escrevem as provas.

Isso importa porque, nas palavras dos autores, a confiabilidade dos resultados não depende da confiabilidade dos agentes de prova: a prova é verificada em última instância pelo kernel do Lean. Segundo o artigo, o agente guardião só aceita uma prova se o kernel do Lean a verificar e o comparador do Lean confirmar que ela prova exatamente uma cópia reservada da especificação. São duas condições, portanto. A prova precisa ser válida e precisa provar o enunciado certo. A segunda condição foi pensada para barrar uma falha sutil: um agente que altera o enunciado e prova algo mais fácil do que foi pedido. O comparador verifica se o enunciado e cada definição de que ele depende são idênticos à cópia reservada, e se a prova usa apenas os axiomas padrão do Lean.

A base confiável é, por consequência, pequena em relação à própria prova. Cerca de 27.000 linhas de especificações confiáveis e semântica de AArch64 sustentam cerca de 6,3 milhões de linhas de prova. A atenção de um revisor é finita, e essa proporção mostra onde investi-la.

Mas a especificação é o ponto fraco, e os autores dizem isso com clareza. No AlphaProof Code, uma especificação consiste num conjunto de enunciados de teoremas Lean junto com cada definição de que eles dependem. Ela precisa ser confiável e não pode ser verificada automaticamente, e uma falha pode enfraquecer a garantia que o teorema oferece. Um teorema que faz suposições restritivas demais sobre as entradas, afirma apenas propriedades fracas da saída ou impõe poucas restrições a testemunhas quantificadas existencialmente pode valer até para código com bugs. Se um erro na especificação enfraquece a capacidade do atacante, a garantia de segurança também se enfraquece.

As definições também podem incluir contratos externos (extern contracts) que estabelecem suposições sobre partes do sistema fora do escopo da campanha de verificação. São fronteiras honestas, mas são fronteiras: o que está por trás de um contrato externo é suposto, não provado.

Assim, o número de destaque, 6,3 milhões de linhas, é o menos importante para avaliar se você deve confiar no resultado. As 27.000 linhas são as que precisam ser lidas.

## O que foi provado sobre o Signal

As provas cobrem o handshake pós-quântico PQXDH e o Triple Ratchet do Signal, estabelecendo sigilo futuro, autenticação, segurança pós-comprometimento e sigilo do handshake. O handshake PQXDH e o Triple Ratchet foram projetados para garantir a segurança das mensagens mesmo quando algumas chaves são comprometidas, e até contra futuros adversários com acesso a um computador quântico.

Duas tradições clássicas de modelagem definem o que "segurança" significa aqui. O modelo simbólico, também conhecido como modelo de Dolev–Yao, trata as primitivas criptográficas como "caixas-pretas" abstratas que atingem propriedades de segurança padrão. O modelo computacional limita a probabilidade de sucesso de um atacante eficiente pela dificuldade das primitivas subjacentes. A prova de segurança computacional afirma que existe uma redução de um ataque ao protocolo para a violação de uma suposição subjacente.

Os dois modelos oferecem garantias diferentes, e os resultados se dividem de acordo. As provas escritas pelos agentes estabelecem sigilo futuro, segurança pós-comprometimento e confidencialidade e autenticidade das mensagens diretamente para o binário compilado contra atacantes clássicos. No modelo simbólico, elas estabelecem o sigilo do handshake contra um futuro atacante quântico. Um leitor atento deve guardar essa distinção. O resultado contra o adversário quântico é enunciado no modelo simbólico, e os resultados contra atacantes clássicos são os que valem diretamente para o binário compilado.

Há uma segunda complicação que explica por que o trabalho de especificação foi difícil. As especificações existentes analisam o handshake e o ratchet separadamente e são anteriores ao ratchet pós-quântico do Signal; os modelos formais anteriores do Signal analisavam separadamente o handshake inicial e o ratchet. Uma prova sobre o protocolo implantado precisa dos dois juntos, além do ratchet pós-quântico. Com orientação humana, os agentes estendem as especificações existentes ao protocolo tal como está implantado. É uma boa ilustração do modelo de colaboração na prática: a literatura fornece um ponto de partida, os humanos conduzem e os agentes fazem a extensão.

Os autores também afirmam que o trabalho mostra que a IA pode verificar código de máquina contra especificações ricas da literatura de pesquisa, incluindo propriedades da interação entre um programa com estado e um adversário adaptativo. É uma classe de propriedade notável. Um programa com estado diante de um adversário adaptativo é exatamente a situação de um cliente de mensagens.

Os autores reivindicam o pioneirismo: nas palavras deles, estas são as primeiras provas que conectam garantias de segurança no nível do protocolo ao código sem modificações de uma implementação de protocolo criptográfico amplamente usada. É uma afirmação deles, não uma constatação independente, e eu a relato como tal. Eles descrevem os resultados como um marco significativo rumo a um grande desafio lançado em abril de 2026.

## As especificações detectam erros reais?

Uma especificação que não distingue código correto de código defeituoso não vale nada, e uma prova contra ela vale ainda menos. Os autores testaram isso diretamente. Reintroduziram dois bugs já corrigidos da libsignal e montaram um conjunto de 17 mutantes sintéticos para verificar se as especificações detectam erros reais.

O resultado, conforme relatado pelos autores: para ambos os bugs históricos e, até agora, para 16 dos 17 mutantes sintéticos, o Lean prova que um rastro registrado (um rastro testemunha para cada um) não pode ser explicado pela especificação simbólica sob uma interpretação concreta das primitivas compatível com a execução registrada. As refutações binárias completas dos dois bugs históricos só foram verificadas pelo kernel contra uma variante anterior (de 36 hooks), posicionada e não confiável, do enunciado; redirecioná-las para o enunciado confiável do teorema principal continua em aberto.

Quero ser preciso sobre o que isso diz e o que não diz. Dezesseis de dezessete não é dezessete de dezessete, e o estudo de caso não explica o mutante restante, então não vou especular sobre ele. Observe também a ressalva sobre os bugs históricos: as refutações binárias completas foram verificadas contra uma variante anterior do enunciado, de 36 hooks, posicionada e não confiável, não necessariamente a final. É um detalhe que vale conhecer antes de alguém citar o resultado como um acerto completo.

Ainda assim, esse é o tipo certo de teste. Ele ataca a especificação, que é onde o framework diz estar o risco residual, em vez de exibir o volume de provas. O teste de mutação de uma especificação é barato em comparação com a campanha de verificação, e responde a uma pergunta que nenhuma quantidade de provas verificadas pelo kernel responde: esse enunciado teria percebido um bug real?

## O que isso significa na prática

Os limites merecem tanta atenção quanto o marco. Em sistemas grandes e complexos, a assistência da IA pode reduzir o custo de escrever especificações e da garantia, mas não substituir completamente o julgamento e a revisão humanos. Os autores não afirmam o contrário. A economia muda, mas não cai a zero, e a parte que continua humana é a que determina se a garantia significa alguma coisa.

Acho essa divisão correta, e ela sugere um jeito sensato de uma equipe ler este trabalho. Não pergunte se agentes conseguem escrever provas; o resultado da libsignal, com cerca de 6,3 milhões de linhas, já responde. Pergunte quem na sua equipe consegue escrever e validar uma especificação do tipo descrito aqui: enunciados de teoremas Lean mais cada definição de que eles dependem, com contratos externos marcando o que é suposto. Essa pessoa, e o processo de revisão em torno do trabalho dela, é o recurso escasso.

Há também uma lição de projeto na forma como o sistema trata componentes pouco confiáveis. Ele não tenta tornar os agentes confiáveis. Torna a confiabilidade deles irrelevante para o resultado, fazendo tudo passar por um verificador pequeno e fixo. Equipes que constroem sistemas agênticos em outras áreas podem fazer a mesma pergunta aos próprios pipelines: qual é o equivalente do kernel do Lean, e o guardião está verificando o enunciado certo?

Para leitores fora da criptografia, o ponto generalizável é a forma do fluxo de trabalho, não o protocolo específico. No projeto dos autores, humanos e agentes redigem juntos a especificação, agentes revisores verificam sua fidelidade, um humano a aprova, um commit a congela como referência, agentes autônomos a provam e um guardião verifica tanto se cada prova é válida quanto se ela prova exatamente o enunciado aprovado. Cada etapa mira um modo de falha diferente.

Nada disso deve ser superestimado. A sugestão de que a IA torna a verificação viável para sistemas reais vem com ressalvas na fonte, e um caso emblemático, por mais impressionante que seja, é um único caso. A especificação continua sendo um artefato confiável que nenhuma ferramenta verifica por você. E a garantia contra o adversário quântico é um resultado do modelo simbólico para o sigilo do handshake, não um resultado computacional.

A questão em aberto que o estudo de caso levanta é aquela para a qual os autores apontam ao chamá-lo de marco rumo a um grande desafio lançado em abril de 2026: se escrever provas agora é barato depois que existe uma especificação, a engenharia de especificação passa a ser o próximo gargalo a atacar? Os resultados de mutação sugerem que a especificação pode ser testada, e a constatação das "muitas rodadas de iteração" sugere que ela continua lenta. Quanto dessa lentidão os agentes conseguem absorver, enquanto os humanos mantêm as decisões finais? Esse é o número a acompanhar no próximo estudo de caso.

## Perguntas frequentes

**O que é o AlphaProof Code?**
Um framework do Google DeepMind e do Google para colaboração entre humanos e IA na especificação e verificação formais de software real. Um usuário humano e agentes de IA escrevem juntos especificações Lean; depois que o usuário valida uma especificação, uma equipe de agentes autônomos prova que o código a satisfaz.

**O que exatamente foi verificado na libsignal?**
O código Rust sem modificações da libsignal, compilado com o compilador rustc padrão para código de máquina AArch64 Linux. As provas cobrem sigilo futuro, autenticação, segurança pós-comprometimento e sigilo do handshake para o handshake pós-quântico PQXDH e o Triple Ratchet do Signal.

**Por que não é preciso confiar nos agentes de IA?**
Cada prova é verificada pelo kernel do Lean, e o guardião só aceita uma prova se o comparador do Lean confirmar que ela prova exatamente uma cópia reservada da especificação aprovada. Um erro lógico é rejeitado, e a prova de um enunciado mais fácil também.

**O que ainda precisa ser confiável?**
Cerca de 27.000 linhas de especificações e semântica de AArch64, além de eventuais contratos externos que descrevam partes do sistema fora da campanha. A especificação não pode ser verificada automaticamente, e uma falha nela enfraquece a garantia que o teorema oferece.

**O trabalho prova segurança contra atacantes quânticos?**
Em parte. O sigilo do handshake contra um futuro atacante quântico é estabelecido no modelo simbólico. Sigilo futuro, segurança pós-comprometimento e confidencialidade e autenticidade das mensagens são estabelecidos diretamente para o binário compilado contra atacantes clássicos.
