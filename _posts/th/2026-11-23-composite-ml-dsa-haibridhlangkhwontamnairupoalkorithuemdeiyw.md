# Composite ML-DSA: ไฮบริดหลังควอนตัมในรูปอัลกอริทึมเดียว

**แนวคิดที่แข็งแรงที่สุดใน RFC มาตรฐานฉบับนี้คือ ไฮบริดหลังควอนตัมไม่จำเป็นต้องเปลี่ยนโปรโตคอลของคุณ: ด้วยการนำเสนอกุญแจสาธารณะเดียวและค่าลายมือชื่อเดียว Composite ML-DSA ปล่อยให้กลไกความคล่องตัวด้านการเข้ารหัสที่มีอยู่ทำงานแทน ขณะที่รายการชุดผสมที่ตั้งใจให้ยาวนั้นมีไว้รับใช้ผู้กำกับดูแลมากกว่าผู้พัฒนา**

> **บทสรุปสำหรับผู้บริหาร**
>
> - RFC นี้เป็นเอกสาร Standards Track ในสาย IETF ลงวันที่พฤศจิกายน 2026 (ISSN 2070-1721) เขียนโดย M. Ounsworth และ J. Gray จาก Entrust, M. Pala จาก OpenCA Labs, J. Klaußner จาก Bundesdruckerei GmbH และ S. Fluhrer จาก Cisco Systems
> - หลักตั้งต้นคือ RSA, DSA และรูปแบบ elliptic curve ของทั้งสองจะตกเป็นเป้าการโจมตีด้วยควอนตัม ความไม่แน่นอนมีเพียงเรื่องเวลา
> - เอกสารสร้างไฮบริด PQ/T โดยใช้ ML-DSA (FIPS 204) เป็นองค์ประกอบหลังควอนตัม จับคู่กับ RSASSA-PSS, RSASSA-PKCS1-v1_5, ECDSA, Ed25519 หรือ Ed448
> - composite ถูกเปิดเผยเป็นอัลกอริทึมอะตอมเดียว โปรโตคอลจึงอาศัยความคล่องตัวด้านการเข้ารหัสที่มีอยู่ได้ แทนการถูกแก้ไข
> - ชุดผสมจำนวนมากมาจากความต้องการรับรองซ้ำตามกฎระเบียบ และเอกสารระบุหลายสิ่งที่ไม่ได้ให้ไว้

## ทำไมต้องใช้ลายมือชื่อแบบไฮบริดตั้งแต่แรก

เอกสารนี้คือ RFC 10073, *Composite Module-Lattice-Based Digital Signature Algorithm (ML-DSA) for Use in X.509 Public Key Infrastructure* เผยแพร่โดย IETF ในเดือนพฤศจิกายน 2026 เขียนโดย M. Ounsworth, J. Gray, M. Pala, J. Klaußner และ S. Fluhrer

RFC เปิดด้วยหลักตั้งต้นที่ระบุโดยไม่มีเงื่อนไข: อัลกอริทึมลายมือชื่อแบบดั้งเดิม เช่น RSA, DSA และรูปแบบ elliptic curve จะตกเป็นเป้าการโจมตีด้วยควอนตัม เอกสารวางสถานการณ์ไว้เป็นเรื่องของเวลาล้วนๆ อัลกอริทึมแบบดั้งเดิมจะถูกเจาะในอนาคต แต่จะยังแข็งแรงในระหว่างนี้ และความไม่แน่นอนเดียวคือเมื่อไร

กรอบนี้สำคัญเพราะตัดการอ่านปัญหาแบบมักง่ายออก ถ้าการถูกเจาะแน่นอนและไม่รู้แค่วันที่ การรอก็ไม่ใช่ทางเลือกที่เป็นกลาง แต่เอกสารก็พูดตรงพอกันเรื่องต้นทุนของการขยับเร็ว กำหนดเวลาการย้ายระบบที่เร่งรัดอาจต้องนำอัลกอริทึมวิทยาการเข้ารหัสลับหลังควอนตัม (PQC) ไปใช้ก่อนที่การพัฒนาจะผ่านการเสริมความแข็งแรงหรือรับรองครบถ้วน RFC ใช้ถ้อยคำระมัดระวังตรงนี้ และเราก็ควรทำเช่นกัน: เอกสารใช้คำว่า "อาจ" ไม่ใช่ "จะ"

วางแรงกดดันทั้งสองไว้เคียงกัน แล้วเหตุผลของไฮบริดก็ปรากฏ คุณต้องการการป้องกันจากอนาคตควอนตัม แต่อัลกอริทึมใหม่และการพัฒนาของมันยังอ่อนวัย RFC ระบุว่าการคุ้มครองข้อมูลด้วยสองอัลกอริทึมอาจเป็นที่ต้องการในระยะเวลายาวขึ้น เพื่อป้องกันความเสี่ยงจากช่องโหว่ด้านความปลอดภัยและข้อบกพร่องอื่นในการพัฒนาใหม่ ถ้อยคำยังคงมีเงื่อนไข เอกสารเสนอเหตุผล ไม่ได้อ้างว่าพิสูจน์แล้วว่าไฮบริดคือคำตอบที่ถูกเสมอ

ควรชัดเจนว่า composite ให้อะไรคุณ อัลกอริทึมแบบ composite ยังคงความปลอดภัยบางส่วนไว้ได้ แม้อัลกอริทึมองค์ประกอบหนึ่งถูกเจาะ วลีคือ "ความปลอดภัยบางส่วน" ไม่ใช่ความปลอดภัยเต็มที่ และ RFC ไม่ได้ขายเกินจริง การอ่านในทางปฏิบัติคือ ความล้มเหลวขององค์ประกอบหนึ่งไม่ได้ทำให้คุณเหลือศูนย์โดยอัตโนมัติ

## เอกสารและผู้เขียน

ก่อนเข้าสู่กลไก ที่มาของเอกสารควรได้หนึ่งย่อหน้า เพราะผู้ก่อตั้งและวิศวกรที่ชั่งน้ำหนักมาตรฐานควรรู้ว่าเป็นมาตรฐานประเภทใด RFC นี้อยู่ในสาย Internet Engineering Task Force (IETF) และอยู่ในประเภท Standards Track เผยแพร่ในเดือนพฤศจิกายน 2026 และมี ISSN 2070-1721 ข้อความมาตรฐานของเอกสารอธิบายว่าเป็นเอกสาร Internet Standards Track: ผลงานของ IETF ที่สะท้อนฉันทามติของชุมชน IETF และได้รับอนุมัติให้เผยแพร่โดย IESG

รายชื่อผู้เขียนครอบคลุมสี่องค์กร M. Ounsworth และ J. Gray มาจาก Entrust, M. Pala จาก OpenCA Labs, J. Klaußner จาก Bundesdruckerei GmbH และ S. Fluhrer จาก Cisco Systems ผมจะไม่ตีความองค์ประกอบนี้เกินกว่าที่เอกสารรองรับ สิ่งที่รายชื่อแสดงคือ นี่ไม่ใช่ผลงานของผู้ขายรายเดียว

เอกสารยังบอกผู้อ่านว่าจะอ่านภาษาเชิงบรรทัดฐานอย่างไร คำสำคัญอย่าง "MUST" และ "SHOULD" ให้ตีความตามที่อธิบายใน BCP 14 (RFC 2119 และ RFC 8174) ก็ต่อเมื่อปรากฏเป็นตัวพิมพ์ใหญ่ทั้งหมดเท่านั้น นี่เป็นแนวปฏิบัติมาตรฐาน แต่คือเหตุผลที่คำว่า "should" ตัวพิมพ์เล็กในข้อกำหนดนี้ไม่มีน้ำหนักพิเศษ ข้อกำหนดยังสอดคล้องกับศัพท์ที่นิยามใน RFC 9794

## กุญแจสาธารณะเดียว ค่าลายมือชื่อเดียว

การตัดสินใจออกแบบหลักนั้นพูดได้ง่าย อัลกอริทึม composite นำเสนอกุญแจสาธารณะและค่าลายมือชื่อเดียว จึงถูกปฏิบัติเป็นอัลกอริทึมอะตอมเดียวได้ในระดับโปรโตคอล

นี่เป็นทางเลือกที่กล้ากว่าที่เห็นในตอนแรก และผมคิดว่าถูกต้อง RFC อธิบายความต่างโดยตรง: ไฮบริด PQ/T จำนวนมากต้องแก้ไขโปรโตคอลให้ "รู้จักไฮบริด" ขณะที่ข้อกำหนดนี้นำเสนอไฮบริดเป็นอัลกอริทึมเดี่ยว จึงใช้ประโยชน์จากกลไกความคล่องตัวด้านการเข้ารหัสที่มีอยู่ได้

ลองคิดว่านั่นหมายถึงอะไรสำหรับใครก็ตามที่ต้องส่งมอบระบบ ไฮบริดที่โปรโตคอลต้องเข้าใจ คือไฮบริดที่แตะทุกโปรโตคอลที่ต้องการใช้มัน ไฮบริดที่ดูเหมือนอัลกอริทึมอื่นทั่วไป คือไฮบริดที่เสียบเข้ากับกลไกการเจรจาหรือการระบุอัลกอริทึมที่มีอยู่แล้วได้ทันที RFC นิยาม "อัลกอริทึม" ในบริบทนี้ว่าโดยทั่วไปหมายถึงฟังก์ชันใดก็ตามที่มี Object Identifier (OID) ลงทะเบียนไว้สำหรับใช้ใน ASN.1 AlgorithmIdentifier composite ได้รับตัวตนของตัวเองในระบบนั้น และระบบรอบข้างปฏิบัติต่อมันเหมือนอัลกอริทึมอื่น

มีประเด็นด้านศัพท์ที่เกี่ยวข้องซึ่งทำให้ชัดว่า RFC อ้างและไม่อ้างอะไร เอกสารนิยาม Protocol Backwards Compatibility ว่าเป็นคุณสมบัติที่เพิ่มฟีเจอร์ใหม่เข้าไปในโปรโตคอลได้โดยไม่ต้องเปลี่ยนข้อกำหนดของโปรโตคอล และเปลี่ยนการพัฒนาเพียงเล็กน้อย แนวทางอัลกอริทึมอะตอมมุ่งเป้าที่การเพิ่มแบบแรงเสียดทานต่ำเช่นนั้นโดยตรง RFC วางเรื่องนี้เป็นเจตนาการออกแบบ: โปรโตคอลอย่าง PKCS #10, CMP, X.509, CMS และ Trust Anchor Format ควรปฏิบัติต่ออัลกอริทึม composite ได้เหมือนอัลกอริทึมอื่น โดยไม่ต้องให้ชั้นโปรโตคอล "รู้จักไฮบริด"

## อะไรอยู่ใน composite

ครึ่งหลังควอนตัมคือ ML-DSA หรือ Module-Lattice-Based Digital Signature Algorithm ที่นิยามใน FIPS 204 ข้อกำหนดใช้เป็นองค์ประกอบหลังควอนตัมของไฮบริด PQ/T ครึ่งแบบดั้งเดิมเลือกจากชุดที่กำหนดไว้ อินสแตนซ์ของรูปแบบ Composite ML-DSA สร้างจาก ML-DSA, RSASSA-PSS, RSASSA-PKCS1-v1_5, ECDSA, Ed25519 และ Ed448

ส่วนศัพท์ระบุองค์ประกอบแบบดั้งเดิมแต่ละตัวชัดเจน RSA ปรากฏในรูป Probabilistic Signature Scheme หรือ RSASSA-PSS ที่นิยามใน RFC 8017 ECDSA คือ Elliptic Curve Digital Signature Algorithm ที่นิยามใน FIPS 186-5 EdDSA คือ Edwards-curve Digital Signature Algorithm ที่นิยามใน RFC 8410 มีชุดพารามิเตอร์สองชุด: Ed25519 และ Ed448 Public Key Infrastructure (PKI) ใช้ตามที่นิยามใน RFC 5280 และ DER หมายถึง Distinguished Encoding Rules ตามที่นิยามใน X.690

เอกสารให้ตัวอย่างเล็กๆ ว่าอะไรนับเป็นองค์ประกอบการเข้ารหัสแบบ composite ตัวอย่างคืออัลกอริทึมอสมมาตร เช่น "ML-DSA-65" หรือ "RSASSA-PSS" และคำว่า "ลายมือชื่อ" ใช้ในความหมายกว้าง: ลายมือชื่อดิจิทัลเชิงการเข้ารหัส โดยไม่สมมติว่าเป็นอัลกอริทึมใด

บทความนี้ไม่ลงรายละเอียดโครงสร้างภายในของลายมือชื่อ composite ซึ่ง RFC กำหนดไว้ในหัวข้อของตัวเองเรื่องการสร้างกุญแจ การลงนาม การตรวจสอบ และการ serialise สิ่งที่สำคัญตรงนี้คือรูปทรงที่มองเห็นจากภายนอก กุญแจเดียวและลายมือชื่อเดียว คือคุณสมบัติที่การออกแบบส่วนที่เหลือพึ่งพา

## ทำไมจึงมีชุดผสมมากมาย

ถ้าคุณกวาดตาดูรายการอัลกอริทึมองค์ประกอบแล้วสงสัยว่าทำไมข้อกำหนดหนึ่งจึงนิยามการจับคู่มากมายขนาดนี้ RFC ตอบตรงๆ การรองรับกรณีการรับรองซ้ำตามกฎระเบียบ มากกว่าข้อกำหนดการออกแบบอื่นใด คือแรงจูงใจของจำนวนชุดผสมอัลกอริทึมที่มากในข้อกำหนดนี้ เอกสารเสริมว่าชุดผสมถูกปรับให้สอดคล้องกับแนวทางของหน่วยงานกำกับดูแลในบางภูมิภาค

เหตุผลเบื้องหลังกรณีนี้ระมัดระวังแต่เป็นรูปธรรม ในบางสถานการณ์ การรับรองผลิตภัณฑ์ที่มีอยู่ซ้ำโดยเพิ่มองค์ประกอบหลังควอนตัมผ่านไฮบริด PQ/T เข้ากับโซลูชันที่สอดคล้องกฎอยู่แล้ว โดยไม่เปลี่ยนองค์ประกอบแบบดั้งเดิม อาจง่ายกว่าการแทนที่องค์ประกอบแบบดั้งเดิม พูดอีกอย่างคือ ผู้ขายที่มีอัลกอริทึมแบบดั้งเดิมที่ผ่านการรับรองแล้วอาจอยากปล่อยไว้ตามเดิม แล้วติดครึ่งหลังควอนตัมไว้ข้างๆ ความต้องการนี้ใช้ได้ก็ต่อเมื่อข้อกำหนดมีการจับคู่ให้กับอัลกอริทึมแบบดั้งเดิมที่ผลิตภัณฑ์ใช้อยู่ นั่นคือที่มาของความกว้าง

นี่คือจุดยืนด้านการออกแบบที่ผมเห็นว่าน่าเชื่อ และเป็นการแก้สัญชาตญาณที่ว่ามาตรฐานควรเล็กที่สุด รายการสั้นจะเรียบร้อยกว่า แต่จะบังคับให้บางผลิตภัณฑ์เปลี่ยนองค์ประกอบที่ผ่านการรับรองแล้ว ซึ่งคือต้นทุนที่ชุดผสมตั้งใจหลีกเลี่ยงพอดี รายการยาวคือราคาของการรองรับผลิตภัณฑ์ภายใต้การกำกับ ณ จุดที่มันอยู่

RFC ยังระวังไม่ให้ความกว้างนั้นกลายเป็นภาระของผู้อ่าน คาดว่าองค์กรจะเลือกใช้อัลกอริทึม composite เพียงตัวเดียวหรือไม่กี่ตัว และผู้พัฒนาจำนวนน้อยมากที่ต้องสนใจรายการทั้งหมด สังเกตถ้อยคำระมัดระวัง: "คาดว่า" นี่คือการคาดการณ์พฤติกรรมการใช้งาน ไม่ใช่ข้อกำหนด แต่บอกคุณว่าควรอ่านเอกสารอย่างไร คุณไม่ได้ถูกคาดหวังให้พัฒนาทุกอย่าง คุณถูกคาดหวังให้หาคู่ของคุณ

## สิ่งที่ข้อกำหนดไม่ได้ครอบคลุม

มาตรฐานที่ดีชัดเจนเรื่องขอบเขตของตัวเอง และฉบับนี้ก็เช่นนั้น ข้อจำกัดสี่ข้อโดดเด่น

ข้อแรก ข้อกำหนดไม่ได้กำหนดอัลกอริทึมที่บังคับต้องรองรับ เมื่อรวมกับความคาดหวังว่าองค์กรจะเลือก composite หนึ่งหรือไม่กี่ตัว หมายความว่าการทำงานร่วมกันระหว่างสองฝ่ายขึ้นอยู่กับว่าทั้งคู่เลือกชุดผสมที่เข้ากันได้หรือไม่ RFC ไม่ได้กำหนดค่าเริ่มต้นที่ทุกฝ่ายต้องรองรับ และเตือนว่าจำนวนชุดผสมอาจแยกระบบนิเวศออกเป็นกลุ่มย่อยที่ทำงานร่วมกันไม่ได้ เมื่อชุมชนต่างๆ เลือกชุดย่อยที่ไม่ทับซ้อนกัน เอกสารสนับสนุนให้องค์กรในโดเมนการใช้งานเฉพาะกำหนดโปรไฟล์ที่เลือก composite จำนวนน้อย ผมขอชี้ว่านี่คือผลในทางปฏิบัติที่สำคัญที่สุดสำหรับทีมที่วางแผนการนำไปใช้: คุณต้องตกลงคู่ของคุณกับคู่สัญญา แทนการสมมติเอาเอง

ข้อสอง ความเข้ากันได้ย้อนหลังในความหมายที่ระบบที่อัปเกรดแล้วยังทำงานร่วมกับระบบเดิมได้ ไม่ได้ให้ไว้ ประเด็นนี้ควรแยกจากประเด็นระดับโปรโตคอลข้างต้น RFC นิยาม Application Backwards Compatibility ว่าเป็นคุณสมบัติที่บ่งชี้ว่าแอปพลิเคชันที่อัปเกรดแล้วและยังไม่อัปเกรดสื่อสารกันได้สำเร็จหรือไม่ Section 10.3 ระบุชัด: กลไกในเอกสารไม่ได้ให้ความเข้ากันได้ย้อนหลังระดับแอปพลิเคชัน เฉพาะระบบที่อัปเกรดแล้วเท่านั้นที่จะเข้าใจ OID ที่เอกสารนิยาม และจะต้องมีกลไกเพิ่มเติมเมื่อต้องการคุณสมบัตินั้น การออกแบบอัลกอริทึมอะตอมช่วยเรื่องการเปลี่ยนโปรโตคอล แต่ไม่ได้อ้างว่าแก้ปัญหาว่าแอปพลิเคชันที่อัปเกรดแล้วจะคุยกับแอปพลิเคชันที่ยังไม่อัปเกรดได้หรือไม่

ข้อสาม มีข้อจำกัดด้านคุณสมบัติความปลอดภัย Composite ML-DSA ใช้ได้ในกรณีที่ยอมรับ primitive ลายมือชื่อที่มีคุณสมบัติ EUF-CMA ที่อ่อนกว่า แทนคุณสมบัติ Strong Unforgeability under Chosen Message Attack (SUF-CMA) ที่เข้มกว่า ซึ่ง Composite ML-DSA ไม่ได้ให้ หากแอปพลิเคชันของคุณพึ่งพา SUF-CMA รูปแบบนี้ตามที่กำหนดไว้ไม่เหมาะ นี่คือขอบเขตที่ชัดและตรวจสอบได้ และผู้ก่อตั้งที่ประเมินรูปแบบนี้ควรทดสอบความต้องการของตัวเองกับขอบเขตนี้ก่อนไปต่อ

ข้อสี่ ซึ่งเล็กกว่า เอกสารยอมรับว่าแรงกดดันด้านเวลาเองก็มีความเสี่ยง ดังที่กล่าวไว้ก่อนหน้า: การพัฒนา PQC อาจถูกนำไปใช้ก่อนผ่านการเสริมความแข็งแรงหรือรับรองครบถ้วน composite คือการบรรเทาความเสี่ยงนั้น ไม่ใช่การขจัด

## การอ่านสัญกรณ์

ผู้พัฒนาจะใช้เวลากับคำอธิบายอัลกอริทึม หมายเหตุเรื่องธรรมเนียมจึงมีประโยชน์ คำอธิบายอัลกอริทึมใช้ไวยากรณ์คล้าย Python สัญลักษณ์ || แทนการต่อ byte array สองชุด และสัญกรณ์ [:] แทนการตัดช่วง byte array

สำหรับฟังก์ชันที่คืนค่าหลายค่า เอกสารใช้ (a, b) แทนคู่ของค่า โดยทั่วไปบ่งชี้ว่าฟังก์ชันคืนค่าหลายค่า และปล่อยกลไกการส่งค่าที่แท้จริง (tuple, struct, output parameter ฯลฯ) ให้ผู้พัฒนาเลือก ประโยคสุดท้ายนั้นคืออิสระที่ตั้งใจให้: ข้อกำหนดสนใจว่าคืนค่าอะไร ไม่ใช่ภาษาของคุณห่อค่าอย่างไร สัญกรณ์ (a, _) แทนคู่ที่ค่าหนึ่ง ในกรณีนี้คือค่าที่สอง ถูกละไว้

ลายเซ็นฟังก์ชันใช้รูปแบบคล้ายกัน สัญกรณ์ func(a) -> b แทนฟังก์ชันชื่อ func ที่รับ a เป็นอินพุตและให้ผลลัพธ์ b และ Func<TYPE>() แทนฟังก์ชันที่มีพารามิเตอร์ <TYPE> หมายความว่าการพัฒนาจะต่างกันเล็กน้อยตาม TYPE ที่อยู่เบื้องหลัง ธรรมเนียมสุดท้ายนี้คือสิ่งที่ทำให้คำอธิบายเดียวครอบคลุมหลายอัลกอริทึมได้โดยไม่ต้องเขียนซ้ำ ซึ่งเหมาะกับข้อกำหนดที่ครอบคลุมรูปแบบ RSA, ECDSA และ EdDSA ควบคู่กับ ML-DSA

ไม่มีอะไรในนี้ที่หวือหวา แต่นี่คือส่วนของเอกสารที่คุณจะเปิดไว้จริงตอนเขียนโค้ด และการตัดสินใจปล่อยกลไกการคืนค่าหลายค่าให้ผู้พัฒนา คือการยอมรับอย่างมีเหตุผลต่อความหลากหลายของภาษาที่ใช้กันอยู่

## ทีมที่วางแผนการย้ายระบบอยู่ตรงไหน

เมื่อรวมชิ้นส่วนเหล่านี้เป็นกรอบการตัดสินใจ RFC ให้สามสิ่งที่มีประโยชน์ และขอให้คุณจัดหาเองอีกสองสิ่ง

สิ่งที่ได้คือเหตุผล รูปทรง และขอบเขต เหตุผลคือแรงกดดันคู่ที่อธิบายไปแล้ว: อัลกอริทึมแบบดั้งเดิมจะพ่ายต่อการโจมตีด้วยควอนตัมในเวลาที่ไม่แน่นอน ขณะที่การพัฒนาใหม่อาจยังไม่ผ่านการเสริมความแข็งแรงหรือรับรองครบถ้วน รูปทรงคือ composite แบบอะตอม มีกุญแจสาธารณะเดียวและค่าลายมือชื่อเดียว ซึ่งยังคงความปลอดภัยบางส่วนไว้หากองค์ประกอบหนึ่งถูกเจาะ ขอบเขตคือรายการข้อจำกัดข้างต้น: ไม่มีอัลกอริทึมที่บังคับต้องรองรับ ไม่ครอบคลุมความเข้ากันได้ย้อนหลังโดยตรง และเป็น EUF-CMA ไม่ใช่ SUF-CMA

สิ่งที่คุณต้องจัดหาเองคือการเลือกชุดผสมและข้อตกลงด้านการทำงานร่วมกัน เพราะข้อกำหนดไม่ได้ระบุอัลกอริทึมที่บังคับต้องรองรับ การเลือกคู่จึงเป็นความรับผิดชอบของคุณ แม้ Section 10.4 จะให้รายการคำแนะนำสั้นๆ สำหรับกรณีใช้งานทั่วไป หากผลิตภัณฑ์ของคุณผ่านการรับรองกับอัลกอริทึมแบบดั้งเดิมตัวใดตัวหนึ่งแล้ว ตรรกะการรับรองซ้ำชี้ไปที่ชุดผสมที่ไม่แตะองค์ประกอบนั้น หากคุณสร้างของใหม่โดยไม่มีข้อกำหนดด้านกฎระเบียบหรือระบบเดิมให้คำนึงถึง RFC แนะนำให้มุ่งความพยายามในการพัฒนาไปที่ id-MLDSA65-ECDSA-P256-SHA512 ซึ่งเอกสารระบุว่าให้สมดุลโดยรวมระหว่างประสิทธิภาพและความปลอดภัยดีที่สุด

มีข้อโต้แย้งที่สมเหตุสมผลว่าการแบ่งงานแบบนี้ถูกต้องสำหรับมาตรฐานในขั้นนี้ การบังคับชุดผสมเดียวจะรับใช้การใช้งานบางส่วนและทิ้งส่วนอื่นไว้กลางทาง โดยเฉพาะที่ผูกกับแนวทางของหน่วยงานกำกับดูแลในภูมิภาค การไม่บังคับทำให้ข้อกำหนดใช้ได้ข้ามภูมิภาคเหล่านั้น โดยแลกกับการผลักขั้นตอนการประสานงานไปให้ผู้นำไปใช้ RFC เลือกความยืดหยุ่นและบอกคุณตรงๆ

ผมขอแย้งเบาๆ ต่อการอ่านผิดที่ชวนให้เชื่อข้อหนึ่ง ข้อความที่ว่าผู้พัฒนาจำนวนน้อยมากต้องสนใจรายการทั้งหมด อาจฟังเหมือนอนุญาตให้มองข้ามความกว้างของข้อกำหนด ไม่ใช่ นี่คือข้อความว่าใครแบกต้นทุนของความกว้างนั้น: ข้อกำหนดดูดซับไว้เพื่อให้การใช้งานส่วนใหญ่ไม่ต้องแบก หากคุณเป็นผู้เขียนไลบรารีหรือผู้ขายที่ให้บริการลูกค้าภายใต้การกำกับ ความกว้างนั้นอาจเป็นปัญหาของคุณจริง หากคุณเป็นองค์กรเดียวที่เลือก composite ตัวเดียว ส่วนใหญ่ไม่ใช่ RFC ใช้ถ้อยคำระมัดระวังกับความคาดหวังนี้ และผมจะถือว่าเป็นการคาดการณ์ ไม่ใช่การรับประกัน

## คำถามที่ข้อกำหนดยังเปิดไว้

สองประเด็นในเอกสารควรจับตา เพราะข้อกำหนดเองชี้ไว้โดยไม่ได้แก้

ประเด็นแรกคือความยาวของช่วงเปลี่ยนผ่าน RFC ระบุว่าการคุ้มครองข้อมูลด้วยสองอัลกอริทึมอาจเป็นที่ต้องการในระยะเวลายาวขึ้น และกำหนดเวลาการย้ายระบบอาจเร่งรัด สองข้อความนี้ดึงกันในทางที่น่าสนใจ: การขยับสู่ PQC อย่างรวดเร็วสนับสนุนการนำไปใช้ก่อนการเสริมความแข็งแรงเสร็จสิ้น ขณะที่ช่วงป้องกันความเสี่ยงที่ยาวกว่าสนับสนุนการคงครึ่งแบบดั้งเดิมไว้อีกนานหลังจากนั้น องค์กรจะคงทั้งสององค์ประกอบไว้นานเท่าใดจริง คือคำถามที่เอกสารยกขึ้นโดยนัยและไม่ได้ตอบ

ประเด็นที่สองคือความเข้ากันได้ย้อนหลัง RFC ระบุว่ากลไกของตนไม่ได้ให้ความเข้ากันได้ย้อนหลังระดับแอปพลิเคชันโดยชัดแจ้ง และจะต้องมีกลไกเพิ่มเติมเมื่อต้องการ เอกสารระบุขอบเขตโปรโตคอลที่ต้องคิดเรื่องการย้ายระบบและการทำงานร่วมกันให้รอบคอบ ตั้งแต่ TLS 1.3 และ IKEv2 ไปจนถึง S/MIME การลงนามเอกสารตาม eIDAS และการลงนามโค้ด แต่ปล่อยการออกแบบกลไกเพิ่มเติมเหล่านั้นไว้กับโปรโตคอลและแอปพลิเคชันเอง

สำหรับทีมที่กำลังตัดสินใจว่าจะลงแรงที่ไหนก่อน คำถามที่สองดูเป็นจุดเริ่มต้นที่ดีกว่า: ไม่ใช่ว่าจะเลือกชุดผสมใด แต่คือแอปพลิเคชันที่อัปเกรดแล้วจะทำงานอย่างไรเมื่ออีกฝ่ายยังไม่ขยับ

## คำถามที่พบบ่อย

**Composite ML-DSA คืออะไร?**
Composite ML-DSA คือรูปแบบลายมือชื่อแบบไฮบริด PQ/T ที่นิยามใน RFC 10073 รวม ML-DSA ที่นิยามใน FIPS 204 เข้ากับอัลกอริทึมแบบดั้งเดิม เช่น RSASSA-PSS, RSASSA-PKCS1-v1_5, ECDSA, Ed25519 หรือ Ed448 คู่นี้นำเสนอกุญแจสาธารณะและค่าลายมือชื่อเดียว โปรโตคอลจึงปฏิบัติต่อมันเป็นอัลกอริทึมอะตอมเดียวได้
**ทำไม RFC จึงนิยามชุดผสมอัลกอริทึมไว้มากมาย?**
RFC ระบุว่าการรองรับกรณีการรับรองซ้ำตามกฎระเบียบ มากกว่าข้อกำหนดการออกแบบอื่นใด คือแรงจูงใจของจำนวนชุดผสมที่มาก ผู้ขายอาจพบว่าการรับรองผลิตภัณฑ์ซ้ำโดยเพิ่มองค์ประกอบหลังควอนตัมไว้ข้างองค์ประกอบแบบดั้งเดิมที่สอดคล้องกฎอยู่แล้ว ง่ายกว่าการแทนที่ คาดว่าองค์กรจะใช้อัลกอริทึม composite เพียงหนึ่งหรือไม่กี่ตัว
**การใช้งานใหม่ควรเริ่มด้วยอัลกอริทึม composite ตัวใด?**
RFC ไม่ได้ระบุอัลกอริทึมที่บังคับต้องรองรับ สำหรับแอปพลิเคชันที่ไม่มีข้อกำหนดด้านกฎระเบียบหรือระบบเดิมให้คำนึงถึง Section 10.4 แนะนำให้มุ่งความพยายามในการพัฒนาไปที่ id-MLDSA65-ECDSA-P256-SHA512 และยังให้คำแนะนำสำหรับแอปพลิเคชันที่ต้องใช้ RSA ที่อ่อนไหวต่อประสิทธิภาพและแบนด์วิดท์ หรือที่อนุญาตเฉพาะ NIST PQC Level 5
**Composite ML-DSA ทำให้ระบบที่อัปเกรดแล้วทำงานร่วมกับระบบเดิมได้หรือไม่?**
ไม่ได้ RFC ระบุว่ากลไกของตนไม่ได้ให้ความเข้ากันได้ย้อนหลังระดับแอปพลิเคชันโดยชัดแจ้ง และเฉพาะระบบที่อัปเกรดแล้วเท่านั้นที่จะเข้าใจ OID ที่นิยามไว้ เมื่อต้องการคุณสมบัตินั้น จะต้องมีกลไกเพิ่มเติม
**Composite ML-DSA ไม่ได้ให้คุณสมบัติความปลอดภัยใด?**
ไม่ได้ให้ Strong Unforgeability under Chosen Message Attack (SUF-CMA) ให้เพียงคุณสมบัติ EUF-CMA ที่อ่อนกว่า RFC ระบุว่าแอปพลิเคชันที่ความปลอดภัยแบบ SUF-CMA มีความสำคัญยิ่งไม่ควรใช้ และ NOT RECOMMENDED ในกรณีที่ยังไม่ได้แสดงว่ายอมรับ EUF-CMA ได้
