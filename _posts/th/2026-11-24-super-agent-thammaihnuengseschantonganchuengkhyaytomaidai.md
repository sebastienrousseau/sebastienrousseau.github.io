# Super-agent: ทำไมหนึ่งเซสชันต่องานจึงขยายต่อไม่ได้

**งานเดี่ยวถูกจำกัดด้วยความสามารถของแบบจำลอง แต่การทำหลายงานพร้อมกันถูกจำกัดด้วยความสนใจของมนุษย์ และทางแก้คือสถาปัตยกรรม ไม่ใช่แบบจำลองที่ดีกว่า**

> **บทสรุปสำหรับผู้บริหาร**
>
> - เอเจนต์เขียนโค้ดและเอเจนต์งานเดี่ยวอื่นแสดงให้เห็นว่าแบบจำลองใช้เครื่องมือแก้ปัญหาซับซ้อนได้ โดยต้องการการเฝ้าดูต่อเนื่องและการแทรกแซงทีละขั้นจากมนุษย์น้อยลงเรื่อยๆ
> - การออกแบบกระแสหลักในวันนี้ใช้เซสชันเดียวเป็นหน่วยพื้นฐานของงาน และเซสชันแยกขาดจากกัน ผู้ใช้ที่ทำหลายงานพร้อมกันต้องสลับไปมาด้วยมือ
> - การติด CLI, MCP หรือตัวเชื่อมต่อภายนอกเข้ากับเอเจนต์เซสชันเดียวบนเครื่อง ทำให้รับข้อความจากภายนอกได้ แต่ข้อจำกัดพื้นฐานยังอยู่
> - ผู้เขียนเรียกทางเลือกนี้ว่า Super-agent และเชื่อว่ามีคุณลักษณะสี่ข้อ: ต่อเนื่อง มีผลิตภาพ เชิงรุก และคงทน
> - สถาปัตยกรรมสองระดับ คือชั้น Router บวก Worker Session ให้ทั้งปฏิสัมพันธ์ที่ต่อเนื่องและการทำงานพร้อมกันที่มีผลิตภาพ

## แบบจำลองดีขึ้น แต่เวิร์กโฟลว์ไม่

บทความนี้อ่าน "Exploring Super-agent Design: Towards a More Autonomous Agent System" โพสต์ที่เผยแพร่บน X โดย DeepSeek Harness (@DeepSeekHarness) เมื่อวันที่ 1 พฤศจิกายน 2026 เขียนโดย Yujia Qiao ในนามทีม DeepSeek Harness และนำเสนอเป็นการแปลด้วยเครื่องจากต้นฉบับภาษาจีน

เอเจนต์เขียนโค้ดและเอเจนต์งานเดี่ยวอื่นแสดงสิ่งที่ควรพูดตรงๆ แบบจำลองใช้เครื่องมือแก้ปัญหาซับซ้อนได้ และต้องการการเฝ้าดูต่อเนื่องและการแทรกแซงทีละขั้นจากมนุษย์น้อยลงเรื่อยๆ แบบจำลองยังประสานงานหลายเอเจนต์ได้ดีขึ้น ทำให้การจัดระเบียบและจัดตารางงานข้ามเซสชันใช้ได้จริง

ประเด็นที่สองสำคัญกว่าที่เห็นในตอนแรก ถ้าการประสานงานใช้ได้จริง คำถามที่น่าสนใจก็ไม่ใช่ว่าเอเจนต์ทำงานยากหนึ่งงานเสร็จได้หรือไม่อีกต่อไป แต่คือจะเกิดอะไรขึ้นเมื่อคุณส่งให้ห้างาน

เอเจนต์ส่วนตัวบอกใบ้คำตอบ เอเจนต์เหล่านี้เชื่อมต่อโดยตรงกับแพลตฟอร์มข้อความ ปฏิทิน อีเมล และงานที่ใช้ทุกวัน เฝ้าดูฟีด และช่วยทำงาน โพสต์ระบุว่าวิธีทำงานแบบออนไลน์ตลอดเวลาและขับเคลื่อนด้วยเหตุการณ์นี้ไม่ได้จำเพาะกับการใช้ส่วนตัว แต่มีคุณค่าในงานเชิงพาณิชย์อย่างการพัฒนาซอฟต์แวร์ด้วย โพสต์ยืนยันเรื่องนี้แทนการวัด และควรอ่านในแง่นั้น แต่ทิศทางชัดพอ: เอเจนต์ที่อยู่ในที่ที่งานเกิดขึ้นอยู่แล้ว แทนการรอคำสั่งใน terminal

## จุดที่การออกแบบเซสชันเดียวพัง

เอเจนต์ยังใช้เซสชันเดียวเป็นหน่วยพื้นฐานของงาน และเซสชันแยกขาดจากกัน นั่นคือนามธรรมที่เรียบร้อยสำหรับงานเดียว แต่เริ่มเก้กังทันทีที่มีหลายงาน

ผู้ใช้ที่ทำหลายงานพร้อมกันต้องสลับเซสชันด้วยมือและจำว่าแต่ละเซสชันมีอะไร จากประสบการณ์ของผู้เขียน คนหนึ่งคนมักติดตามเซสชันที่ทำงานอยู่ได้เพียง 3 ถึง 5 เซสชันพร้อมกัน ตัวเลขนี้มาจากประสบการณ์ ไม่ใช่การศึกษาแบบควบคุม จึงควรถือเป็นหลักคร่าวๆ ถึงอย่างนั้นก็ชี้ไปที่ปัญหาเชิงโครงสร้าง ในการออกแบบเหล่านี้ งานเดี่ยวถูกจำกัดด้วยความสามารถของแบบจำลอง แต่การทำหลายงานพร้อมกันถูกจำกัดด้วยความสนใจของมนุษย์

อ่านประโยคนั้นซ้ำ มันบอกว่าการปรับปรุงแบบจำลองเพียงอย่างเดียวจะไม่ยกเพดานของงานแบบขนาน เพดานคือคนที่จำเซสชันทั้งหมดไว้ในหัว ผมขอเสนอว่านี่คือกรอบที่มีประโยชน์ที่สุดในข้อโต้แย้งทั้งหมด เพราะย้ายปัญหาจากแบบจำลอง ซึ่งเป็นที่ที่ความพยายามส่วนใหญ่ลงไป ไปสู่ระบบรอบตัวมัน

## ทำไมตัวเชื่อมต่อแก้ไม่ได้

การปะแบบที่เห็นชัดคือขยายสิ่งที่มีอยู่ เพิ่ม CLI, MCP หรือตัวเชื่อมต่อภายนอกเข้ากับเอเจนต์เซสชันเดียวบนเครื่อง แล้วมันจะรับข้อความจากภายนอกได้ ประเด็นของผู้เขียนคือข้อจำกัดพื้นฐานยังอยู่

ผู้เขียนระบุข้อจำกัดเหล่านั้นอย่างเป็นรูปธรรม การตั้งค่าแบบนี้ยังทำงานในเซสชันแบบ synchronous เดียวที่ถูกบล็อกเมื่อมีการดำเนินการยาว บริบทจากงานต่างๆ ปนกัน ทุกอย่างหยุดเมื่ออุปกรณ์บนเครื่องออฟไลน์ และการทำให้ทั้งหมดทำงานต่อเนื่องต้องใช้แรงคนมาก

แต่ละข้อคือความล้มเหลวคนละแบบ การบล็อกคือปัญหาปริมาณงาน บริบทที่ปนกันคือปัญหาความถูกต้อง การออฟไลน์ไปพร้อมแล็ปท็อปคือปัญหาความพร้อมใช้งาน การดูแลด้วยมือคือปัญหาเชิงปฏิบัติการ ตัวเชื่อมต่อไม่แก้ข้อใดเลย เพราะตัวเชื่อมต่อเปลี่ยนแค่วิธีที่ข้อความมาถึง ไม่ได้เปลี่ยนว่าเซสชันคืออะไร

## แยกเอเจนต์ออกจากเซสชัน

โพสต์ระบุว่าการก้าวข้ามข้อจำกัดเหล่านี้หมายถึงการแยกเอเจนต์ออกจากเซสชันเดี่ยวที่ขับเคลื่อนด้วยมือใดๆ สิ่งที่ตามมาเขียนในรูปว่าเอเจนต์ควรเป็นอย่างไร ไม่ใช่ผลที่วัดได้ จึงควรอ่านเป็นวิทยานิพนธ์ด้านการออกแบบของผู้เขียน

วิทยานิพนธ์เป็นเช่นนี้ เอเจนต์ควรเป็นตัวตนต่อเนื่องหนึ่งเดียวที่รักษาบริบทข้ามเซสชัน และทำงานซับซ้อนหลายงานพร้อมกันโดยงานไม่รบกวนกัน ผู้เขียนเรียกเอเจนต์แบบนี้และสถาปัตยกรรมระบบของมันว่า Super-agent

ผู้เขียนรายงานตัวอย่างที่ใช้งานได้ อินสแตนซ์ Super-agent ภายในของพวกเขาซึ่งทำงานบน DeepSeek Harness ทำงานพัฒนาเดียวกันต่อข้าม IM และ GitHub ได้ มันยังเฝ้าดูฟีดแบ็กในแชตกลุ่มสาธารณะ และแม้ไม่มีใคร @-mention ก็หาต้นเหตุเองและเปิด Pull Request เพื่อแก้ โพสต์ไม่ได้ให้อัตราความสำเร็จหรือจำนวน Pull Request ของพฤติกรรมทั้งสอง จึงเป็นการสาธิตความสามารถ ไม่ใช่ benchmark ถึงอย่างนั้น พฤติกรรมที่สองก็น่าทึ่ง ไม่มีใครขอ แต่เอเจนต์ลงมือ

## คุณลักษณะสี่ข้อ

โพสต์ระบุว่า Super-agent มีคุณลักษณะพื้นฐานสี่ข้อ: ต่อเนื่อง มีผลิตภาพ เชิงรุก และคงทน ผู้เขียนวางเรื่องนี้เป็นความเชื่อของตน และแต่ละคำมีความหมายเฉพาะ

เอเจนต์ที่ต่อเนื่องให้ผู้ใช้โต้ตอบได้โดยตรงในที่ที่ทำงานอยู่แล้ว เช่น แชต IM และคอมเมนต์ใน GitHub และให้ความรู้สึกเป็นเอเจนต์เดียวเสมอ ตัวอย่างในโพสต์คือผู้ใช้ที่ขอแผน A ใน IM แล้วภายหลังเปลี่ยนเป็นแผน B ในคอมเมนต์ Pull Request บน GitHub เอเจนต์เข้าใจการเปลี่ยนแปลงและปรับสิ่งที่ทำอยู่ ช่องทางเปลี่ยน บทสนทนาไม่เปลี่ยน

เอเจนต์ที่มีผลิตภาพตอบสนองเร็ว และทำงานซับซ้อนหลายงานเสร็จแบบขนาน แต่ละงานได้มาตรฐานสูง มันยังรับคำสั่งถัดไปได้ก่อนคำสั่งหรืองานก่อนหน้าจะเสร็จ ซึ่งขจัดพฤติกรรมการบล็อกที่กล่าวไว้ก่อนหน้า

เอเจนต์เชิงรุกเฝ้าดูเหตุการณ์ในสภาพแวดล้อม ลงมือกับสิ่งที่ควรจัดการ และเงียบในกรณีอื่น ประโยคสุดท้ายควรได้รับความสนใจ เอเจนต์ที่ลงมือกับทุกอย่างคือเสียงรบกวน การอยู่เงียบเป็นส่วนหนึ่งของข้อกำหนด

เอเจนต์ที่คงทนออนไลน์ตลอดเวลา เชื่อมต่อโดยตรงกับสภาพแวดล้อมการทำงานจริงของผู้ใช้ และฟื้นตัวจากความผิดปกติโดยอัตโนมัติระหว่างการทำงานระยะยาว

จากนั้นคือข้อจำกัดที่ขับเคลื่อนการออกแบบส่วนที่เหลือ: ไม่มี ReAct loop เดี่ยวใดให้คุณลักษณะทั้งสี่ได้พร้อมกัน จึงต้องมาจากสถาปัตยกรรมระบบรอบตัวมัน โพสต์ระบุเรื่องนี้โดยไม่ลังเล และนี่คือเหตุผลที่บทความนี้เป็นเรื่องสถาปัตยกรรม ไม่ใช่เรื่องการเขียน prompt

## การบรรจบกัน และชุดปัญหาเก่า

โพสต์คาดว่าเอเจนต์ส่วนตัวและเอเจนต์สำหรับงานเชิงพาณิชย์อย่างการพัฒนาซอฟต์แวร์จะลงเอยด้วยการออกแบบที่คล้ายกัน เมื่อเป้าหมายคือระบบที่ออนไลน์ตลอดเวลาและตอบสนองต่อเหตุการณ์ในสภาพแวดล้อมพร้อมกัน นี่คือความคาดหวัง ใช้ถ้อยคำระมัดระวังตามนั้น ถ้าเป็นจริง คนที่สร้างผู้ช่วยส่วนตัวกับคนที่สร้างเอเจนต์พัฒนาซอฟต์แวร์ก็กำลังแก้ปัญหาเดียวกัน และแบ่งปันการออกแบบกันได้มาก

มีข้อสังเกตที่สองที่ผมเห็นว่าน่าอุ่นใจ การสร้างระบบแบบนี้ทำให้เกิดปัญหามากมายที่คล้ายกับปัญหาที่ศึกษากันมานานในระบบคอมพิวเตอร์ แนวคิดการออกแบบคลาสสิกจำนวนมากจากสาขานั้นจึงใช้ได้ที่นี่ด้วย ผู้เขียนไม่ได้บอกว่าแนวคิดใด และผมจะไม่เดา แต่นัยสำหรับผู้ก่อตั้งเป็นเรื่องปฏิบัติ: คุณไม่ได้เผชิญปัญหาที่ไม่มีแผนที่เลย การจัดตารางงาน การแยกส่วน และการกู้คืน ล้วนมีประวัติยาวนานแล้ว

ผู้เขียนคิดว่าห้าโมดูลเป็นกรอบพื้นฐานที่รองรับคุณลักษณะทั้งสี่ ขณะที่การพัฒนาจะแตกต่างกันไป อีกครั้ง นี่คือวิจารณญาณของพวกเขา ไม่ใช่การแยกส่วนที่พิสูจน์แล้ว สี่ในห้าโมดูลจับคู่กับคุณลักษณะดังนี้

สถาปัตยกรรมสองระดับ (Section 2) ให้ทั้งปฏิสัมพันธ์ที่ต่อเนื่องและการทำงานพร้อมกันที่มีผลิตภาพ การออกแบบที่ขับเคลื่อนด้วยเหตุการณ์ (Section 3) ทำให้เอเจนต์เป็นเชิงรุก ปฏิสัมพันธ์หลายช่องทางแบบ full-duplex (Section 4) ทำให้การแลกเปลี่ยนกับผู้ใช้แต่ละครั้งทั้งต่อเนื่องและมีผลิตภาพ การแยกการประมวลผล สถานะ และสภาพแวดล้อม (Section 5) ร่วมกับ Watchdog (Section 6) ทำให้เอเจนต์ออนไลน์อย่างคงทนข้ามอุปกรณ์และฟื้นตัวจากความผิดปกติได้เอง

ส่วนที่เหลือของบทความมุ่งที่ข้อแรก คือสถาปัตยกรรมสองระดับ

## การแลกระหว่างความต่อเนื่องกับปริมาณงาน

การรองรับทั้งปฏิสัมพันธ์ที่ต่อเนื่องข้ามช่องทางและการทำงานพร้อมกันที่มีผลิตภาพข้ามงาน บังคับให้เกิดการแลกพื้นฐานระหว่างความต่อเนื่องกับปริมาณงานในวิธีที่ระบบจัดระเบียบเซสชัน มีสองวิธีที่เห็นชัดในการจัดระเบียบ และแต่ละวิธีล้มเหลวในแบบที่คาดได้

วิธีแรกคือส่งทุกเหตุการณ์ไปที่เซสชันเดียว ได้บริบทต่อเนื่องที่สุด เพราะเซสชันนั้นเห็นทุกอย่าง ต้นทุนคือความเร็ว ReAct loop ทำงานทีละขั้น ซึ่งจำกัดความเร็วของเซสชันเดียว: งานใช้เวลานานและปริมาณงานต่ำ รายละเอียดระหว่างทางของงานต่างๆ ยังสลับปนกันในบริบทเดียว ซึ่งทำให้ผลลัพธ์แย่ลง เซสชันที่รู้มากที่สุดจึงให้เหตุผลแย่ที่สุด เพราะกำลังอ่านของที่ปนเปกัน

วิธีที่สองคือให้ทุกเหตุการณ์มีเซสชันใหม่ของตัวเอง ได้ปริมาณงานพร้อมกันสูงสุด แต่เมื่องานไม่ได้อิสระจากกันโดยสมบูรณ์ การขาดบริบทระดับรวมที่ใช้ร่วมกันทำให้ผลลัพธ์ไม่เชื่อมโยงกัน การที่หลายเซสชันตอบผู้ใช้แยกกันก็ทำให้ปฏิสัมพันธ์สับสน ผู้ใช้ได้ห้าเสียงในที่ที่ต้องการเสียงเดียว

ไม่มีขั้วใดยอมรับได้ และการแลกนี้เป็นของจริง ไม่ใช่เรื่องของการปรับจูน ระบบที่ต้องการทั้งความต่อเนื่องและปริมาณงานต้องแยกสองหน้าที่ออกจากกัน

## เซสชันเดียว สองหน้าที่

โพสต์ระบุว่าทำไมหน้าที่จึงพันกันตั้งแต่แรก ในการออกแบบที่มีอยู่ เซสชันทำสองหน้าที่: จัดการบริบทของแบบจำลอง และเป็นหน่วยการจัดการโปรเจกต์ของผู้ใช้ วัตถุเดียวแบกทั้งสองความรับผิดชอบ การปรับปรุงด้านหนึ่งจึงทำให้อีกด้านแย่ลง ให้ผู้ใช้ติดตามเซสชันเดียว บริบทก็ปนเปื้อน ให้แบบจำลองได้บริบทที่สะอาดและแยกขาด ผู้ใช้ก็ต้องจัดการหลายเซสชันเอง

นี่คือเหตุผลที่ตัวเลข 3 ถึง 5 เซสชันกัดจริง หน่วยการจัดการโปรเจกต์ของผู้ใช้คือเซสชัน จำนวนเซสชันที่ติดตามได้จึงกลายเป็นจำนวนโปรเจกต์ที่ดำเนินได้

## สถาปัตยกรรมสองระดับ

ข้อเสนอแยกความรับผิดชอบออกจากกัน ชั้น Router ที่มีอายุยาว (Section 2.1) รักษาความต่อเนื่องระดับรวมด้วยการรับมือปฏิสัมพันธ์กับมนุษย์ทั้งหมดและการประสานงานระดับรวม ชั้น Worker ที่แยกบริบท (Section 2.2) ทำงานด้วยระดับการทำงานพร้อมกันสูง รวมกันแล้ว: ชั้น Router รับมือการส่งต่อและปฏิสัมพันธ์ภายนอกทั้งหมด ขณะที่ Worker Session ที่แยกขาดกันหลายตัวทำงานพร้อมกัน

ชั้น Router คือชั้นส่งต่อระดับรวมที่มีอายุยาว ซึ่งรับปฏิสัมพันธ์จากมนุษย์จากทุกจุดเข้า นั่นคือเหตุผลที่เอเจนต์ให้ความรู้สึกเป็นเอเจนต์เดียวเสมอ ไม่ว่าข้อความจะมาทางช่องทางใด ก็ไปลงที่เดียวกัน ส่วน Worker รักษาบริบทให้แยกขาด ปัญหาการสลับปนจากการออกแบบเซสชันเดียวจึงไม่เกิดภายใน Worker

ผู้เขียนเพิ่มคำชี้แจงที่พลาดได้ง่าย สองระดับคือการแบ่งความรับผิดชอบเชิงตรรกะ และไม่มีชั้นใดต้องพัฒนาเป็นเซสชันเดียว Router ไม่จำเป็นต้องเป็นโปรเซสเดียวที่ถือบริบทเดียว และชั้น Worker ไม่จำเป็นต้องเป็น pool เดียว สถาปัตยกรรมอธิบายว่าใครรับผิดชอบอะไร ไม่ใช่มีกี่เซสชัน

ผลในทางปฏิบัติระบุไว้ตรงๆ: ระบบรับช่วงการจัดการบริบทและการดำเนินการพร้อมกัน ผู้ใช้จึงแทบไม่ต้องคิดเรื่องเซสชัน นี่คือสิ่งที่แก้เพดานความสนใจ ถ้าคนไม่ต้องจำว่าแต่ละเซสชันมีอะไรอีกต่อไป ขีดจำกัด 3 ถึง 5 ก็เลิกเป็นขีดจำกัดของจำนวนงานที่ทำได้ โพสต์ไม่ได้บอกว่าอินสแตนซ์ภายในทำงานพร้อมกันกี่งาน ผมจึงบอกไม่ได้ว่าขีดจำกัดใหม่อยู่ตรงไหน

## สิ่งที่โพสต์สนับสนุน และสิ่งที่ไม่

ควรซื่อตรงเรื่องหลักฐานตรงนี้ ข้อกล่าวอ้างที่แข็งแรงเป็นเชิงโครงสร้าง เซสชันแยกขาดกัน ReAct loop เดี่ยวทำงานทีละขั้น เซสชันเดียวที่ใช้ร่วมกันทำให้บริบทสลับปนกัน และเซสชันต่อเหตุการณ์ทำให้ผลลัพธ์ไม่เชื่อมโยง โพสต์ระบุเรื่องเหล่านี้โดยไม่ลังเล

ข้อกล่าวอ้างที่อ่อนกว่าคือส่วนที่แบกความทะเยอทะยาน นิยาม Super-agent คุณลักษณะสี่ข้อ กรอบห้าโมดูล และการบรรจบที่คาดไว้ของการออกแบบส่วนตัวกับเชิงพาณิชย์ ล้วนใช้ถ้อยคำระมัดระวังในโพสต์ ผู้เขียนเชื่อ คิด และคาด ไม่มีข้อใดนำเสนอเป็นผลที่วัดได้

อินสแตนซ์ภายในบน DeepSeek Harness ถูกอธิบายผ่านพฤติกรรม: ทำงานพัฒนาเดียวต่อข้าม IM และ GitHub และพบต้นเหตุในแชตกลุ่มสาธารณะก่อนใครขอ นี่คือการพิสูจน์ว่ามีอยู่จริง ไม่ใช่การศึกษาประสิทธิภาพ โพสต์รายงานการทดลองเบื้องต้น แต่ผู้เขียนระบุว่าใช้ภาระงานสังเคราะห์และสภาพแวดล้อมแบบง่าย และผลเป็นเพียงข้อบ่งชี้ ใน ablation นั้น Super-agent ทำงานเสร็จใน 12.4 นาทีที่ p50 และ 15.7 นาทีที่ p95 เร็วกว่าเซสชันเดียวที่มีเครื่องมือ subagent ขณะที่ใช้ cache-read token ต่อรอบมากกว่า สำหรับผู้อ่านเชิงเทคนิค นั่นคือระดับความเชื่อมั่นที่เหมาะจะนำกลับไป: การออกแบบสอดคล้องในตัวและรูปแบบความล้มเหลวของทางเลือกอื่นอธิบายไว้ดี แต่ตัวเลขมาจากงานจำลอง ไม่ใช่จากอินสแตนซ์ที่ใช้งานทุกวัน

## ผู้ก่อตั้งควรได้อะไรจากเรื่องนี้

ถ้าคุณกำลังสร้างผลิตภัณฑ์เอเจนต์ บทเรียนแรกคือเลิกถือว่าเซสชันคือผลิตภัณฑ์ เซสชันคือรายละเอียดการพัฒนาของการจัดการบริบทที่ถูกยกขึ้นเป็นส่วนติดต่อผู้ใช้ ข้อโต้แย้งของผู้เขียนคือการยกขึ้นนี้คือสิ่งที่จำกัดงานแบบขนาน และผมคิดว่าพวกเขาถูกที่วางปัญหาไว้ตรงนั้น

บทเรียนที่สองเกี่ยวกับว่าจะลงแรงที่ไหน งานเดี่ยวถูกจำกัดด้วยความสามารถของแบบจำลอง แบบจำลองที่ดีกว่าจึงช่วยงานเดี่ยว การทำหลายงานพร้อมกันถูกจำกัดด้วยความสนใจของมนุษย์ แบบจำลองที่ดีกว่าจึงไม่ได้ช่วยอย่างชัดเจน สถาปัตยกรรมช่วย Router ที่ดูดซับทุกจุดเข้าและ Worker ที่แยกบริบทออกจากกัน คือโครงสร้างประเภทที่ขยับเพดานได้

บทเรียนที่สามเกี่ยวกับขอบเขต เอเจนต์ส่วนตัวที่อยู่ในแพลตฟอร์มข้อความ ปฏิทิน อีเมล และงาน กับเอเจนต์พัฒนาเชิงพาณิชย์ที่ตอบแชตกลุ่มด้วย Pull Request ดูเหมือนคนละผลิตภัณฑ์ ผู้เขียนคาดว่าทั้งสองจะบรรจบสู่การออกแบบที่คล้ายกัน ทีมที่สร้างแบบหนึ่งจึงไม่ควรมองข้ามความก้าวหน้าของอีกแบบ

ทั้งหมดนี้ไม่ได้ทำให้การสร้างง่าย ความคงทนอย่างเดียวก็ต้องแยกการประมวลผล สถานะ และสภาพแวดล้อมออกจากกัน บวก Watchdog เพื่อให้เอเจนต์ฟื้นตัวจากความผิดปกติได้เอง ความเป็นเชิงรุกต้องการการออกแบบที่ขับเคลื่อนด้วยเหตุการณ์ ปฏิสัมพันธ์หลายช่องทางแบบ full-duplex มีหัวข้อของตัวเอง สถาปัตยกรรมสองระดับเป็นหนึ่งในห้าโมดูล ไม่ใช่คำตอบทั้งหมด

## คำถามที่ยังเปิดอยู่

โพสต์ทิ้งเรื่องหนึ่งไว้เปิด และเป็นเรื่องที่ผมอยากได้คำตอบที่สุด Router รับมือปฏิสัมพันธ์กับมนุษย์ทั้งหมดและการประสานงานระดับรวม และ Worker ถูกแยกขาดโดยการออกแบบ โพสต์ระบุว่าการแลกระหว่างความต่อเนื่องกับปริมาณงานเป็นเรื่องพื้นฐาน และการแยกสองระดับให้ทั้งสองอย่าง สำหรับงานที่แตะสภาพแวดล้อมเดียวกัน โพสต์ระบุว่า Worker ที่สมัครรับ Thread ของสภาพแวดล้อมนั้นจะได้รับการแจ้งเหตุการณ์เดียวกัน และ Router ส่งต่อกรณีส่วนน้อยที่ต้องประสานงานข้ามงาน โพสต์ยังระบุว่าเมื่องานใหญ่ขึ้นและผูกพันกันแน่นเกินกว่าที่ Router Session เดียวจะรับไหว โครงสร้างที่เหมาะสมของแต่ละชั้นยังไม่ได้ข้อยุติ ความล้มเหลวของเซสชันต่อเหตุการณ์คือผลลัพธ์ที่ไม่เชื่อมโยงจากงานที่ไม่ได้อิสระจากกัน Router จะส่งบริบทระดับรวมลงไปให้พอดีได้อย่างไร โดยไม่นำการสลับปนที่มันตั้งใจป้องกันกลับมา คือจุดที่การออกแบบจะถูกทดสอบ

## คำถามที่พบบ่อย

**Super-agent คืออะไร?**
คือชื่อที่โพสต์ใช้เรียกเอเจนต์และสถาปัตยกรรมระบบของมัน ที่แยกออกจากเซสชันเดี่ยวที่ขับเคลื่อนด้วยมือใดๆ เอเจนต์เป็นตัวตนต่อเนื่องหนึ่งเดียวที่รักษาบริบทข้ามเซสชัน และทำงานซับซ้อนหลายงานพร้อมกันโดยงานไม่รบกวนกัน

**ทำไมหนึ่งเซสชันต่องานจึงขยายต่อไม่ได้?**
เซสชันแยกขาดกัน ผู้ใช้ที่ทำหลายงานพร้อมกันจึงต้องสลับไปมาด้วยมือและจำว่าแต่ละเซสชันมีอะไร จากประสบการณ์ของผู้เขียน คนหนึ่งคนมักติดตามเซสชันที่ทำงานอยู่ได้เพียง 3 ถึง 5 เซสชันพร้อมกัน การทำหลายงานพร้อมกันจึงถูกจำกัดด้วยความสนใจของมนุษย์ ไม่ใช่ความสามารถของแบบจำลอง

**ทำไม CLI, MCP หรือตัวเชื่อมต่อจึงแก้ปัญหาไม่ได้?**
สิ่งเหล่านี้ทำให้เอเจนต์เซสชันเดียวบนเครื่องรับข้อความจากภายนอกได้ แต่ข้อจำกัดพื้นฐานยังอยู่ มันยังถูกบล็อกเมื่อมีการดำเนินการยาวในเซสชันแบบ synchronous เดียว ปนบริบทจากงานต่างๆ หยุดเมื่ออุปกรณ์บนเครื่องออฟไลน์ และต้องใช้แรงคนมากเพื่อให้ทำงานต่อเนื่อง

**สถาปัตยกรรมสองระดับทำงานอย่างไร?**
ชั้น Router ที่มีอายุยาวรับมือปฏิสัมพันธ์กับมนุษย์ทั้งหมดและการประสานงานระดับรวม ขณะที่ชั้น Worker ที่แยกบริบททำงานด้วยระดับการทำงานพร้อมกันสูง สองระดับคือการแบ่งความรับผิดชอบเชิงตรรกะ และไม่มีชั้นใดต้องพัฒนาเป็นเซสชันเดียว

**หลักฐานสนับสนุนการออกแบบแข็งแรงแค่ไหน?**
โพสต์อธิบายอินสแตนซ์ Super-agent ภายในที่ทำงานบน DeepSeek Harness และรายงานการทดลองเบื้องต้น ผู้เขียนระบุว่าการทดลองเหล่านั้นใช้ภาระงานสังเคราะห์และสภาพแวดล้อมแบบง่าย ผลจึงเป็นเพียงข้อบ่งชี้
