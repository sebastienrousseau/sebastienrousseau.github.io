ในเดือนมิถุนายน 2026 วาระเทคโนโลยีของธนาคารองค์กรและวาณิชธนกิจ (CIB) เลิกเสแสร้งเสียที Morgan Stanley, JPMorgan และ Citi นั่งอยู่ในคณะกรรมการกำกับ FINOS และตอนนี้ปฏิบัติต่อโอเพนซอร์สในฐานะโครงสร้างพื้นฐานหลัก ไม่ใช่โครงการเสริม — การเปลี่ยนแปลงที่ Banking Dive จับภาพได้ในรายงานล่าสุดเกี่ยวกับธนาคารทั้งสามแห่งที่ทุ่มน้ำหนักให้กับโค้ดร่วมผ่าน [FINOS](https://www.finos.org/) และ [Linux Foundation](https://www.linuxfoundation.org/) ([Banking Dive, 2026](https://www.bankingdive.com/news/bank-technology-open-source-finos-morgan-stanley-jpmorgan-citi/743937/ "ผู้นำเทคโนโลยีธนาคารทุ่มน้ำหนักให้กับโอเพนซอร์ส")). เหตุผลนั้นไม่สะดวกใจสำหรับเวนเดอร์: สแตก CIB ตอนนี้ต้องตรวจสอบได้ตลอดเส้นทาง และกล่องดำของซอฟต์แวร์เชิงพาณิชย์ไม่รอดการตรวจสอบ DORA Article 5

บทความนี้เชื่อมโยงการเปลี่ยนแปลงดังกล่าวเข้ากับด้านวิศวกรรม ไลบรารี Rust ที่ผมเผยแพร่ — [noyalib](https://github.com/sebastienrousseau/noyalib), [http-handle](https://github.com/sebastienrousseau/http-handle), [hsh](https://github.com/sebastienrousseau/hsh), [KyberLib](https://github.com/sebastienrousseau/kyberlib), [html-generator](https://github.com/sebastienrousseau/html-generator), [Shokunin SSG](https://github.com/sebastienrousseau/shokunin) — ไม่ใช่ประเด็นในตัวเอง แต่เป็นตัวอย่างรูปธรรมว่าสแตก CIB แบบ cloud-native มีหน้าตาอย่างไรเมื่อคุณยึดวิทยานิพนธ์ของ FINOS อย่างจริงจัง: ใบอนุญาตที่อนุญาตกว้าง, ไม่มี `unsafe`, อาร์ติแฟกต์ที่ลงนาม และที่มาของห่วงโซ่อุปทานที่ฝังอยู่ในเวลาคอมไพล์

## 01. เหตุใด CIB จึงเปิดสู่โอเพนซอร์ส

แรงกดดันสามประการผลัก CIB เข้าหาโอเพนซอร์ส และไม่มีข้อใดเป็นเรื่องของอุดมการณ์

**บุคลากร.** วิศวกรโครงสร้างพื้นฐานที่แข็งแกร่งที่สุดในปี 2026 สร้างงานในที่สาธารณะ รายงาน State of Open Source in Financial Services ปี 2025 ของ FINOS ระบุว่าฐานผู้มีส่วนร่วมยังอยู่ในขาขึ้น โดยผู้ดูแลที่สังกัดธนาคารปรากฏตัวให้เห็นทั่วโครงการรันไทม์ของ CNCF และสายงาน FINOS ([Linux Foundation, 2025](https://www.linuxfoundation.org/hubfs/Research%20Reports/05_FINOS_2025_Report.pdf?hsLang=en "สถานะของโอเพนซอร์สในบริการทางการเงิน 2025")). เมื่อ CTO ของธนาคารระดับท็อปต้องการวิศวกร Rust หรือ Kotlin อาวุโส ที่สามารถส่งมอบการเขียนใหม่ระบบเคลียริงได้ วิศวกรคนนั้นย่อมคาดหวังที่จะคอมมิตขึ้นต้นน้ำ ร้านที่มีแต่ของเชิงพาณิชย์ปิดจะแพ้บทสนทนาการจ้างงานตั้งแต่ต้น

**การปฏิบัติตามกฎ.** DORA Article 5 วางความรับผิดชอบความเสี่ยง ICT ที่มอบหมายไม่ได้ไว้บนคณะกรรมการ Basel III ผูกทุนความเสี่ยงเชิงปฏิบัติการเข้ากับการหยุดทำงาน ทั้งสองระบอบสันนิษฐานว่าสถาบันสามารถตรวจสอบทุกองค์ประกอบบนเส้นทางโปรดักชันได้ — และนั่นง่ายกว่าในเชิงโครงสร้าง เมื่อใช้โค้ดโอเพนซอร์สที่อนุญาตกว้างภายใต้ MIT, Apache 2.0 หรือ BSD-3-Clause มากกว่ารุ่นเชิงพาณิชย์แบบกล่องดำที่ SBOM ของมันคือ "เชื่อเราเถอะ" บิลล์ออฟแมททีเรียลแบบ CycloneDX และ SPDX, การยืนยันที่มาแบบ SLSA และลายเซ็น sigstore ตอนนี้คือเกณฑ์ขั้นต่ำที่ผู้กำกับดูแลคาดหวังว่าจะเห็นแนบมากับไปป์ไลน์การเผยแพร่

**ความเร็วในการส่งมอบ.** ทีมแพลตฟอร์ม CIB ที่ส่งมอบการเปลี่ยนแปลงเครื่องยนต์การชำระเงินในไม่กี่วันแทนที่จะเป็นไตรมาส ไม่ได้ชนะด้วยการทำงานหามรุ่งหามค่ำ พวกเขาชนะด้วยฐานร่วม — Kubernetes, OpenTelemetry, ไลบรารีสคีมา ISO 20022, FINOS Common Domain Model — ที่ไม่มีใครจ่ายเงินเพื่อเขียนใหม่ เศรษฐศาสตร์ไม่เข้าข้างรางแบบสั่งทำพิเศษอีกต่อไป

แรงกดดันสามประการ ข้อสรุปเดียว การเปิดสู่โอเพนซอร์สเป็นการตัดสินใจเรื่องการส่งมอบ ไม่ใช่เรื่องการจัดซื้อ

## 02. สแตก Rust แบบ zero-dependency

สแตก CIB แบบ cloud-native ในปี 2026 ไม่ใช่ภาพยุค LAMP ของ "โอเพนซอร์ส = Linux + nginx + Postgres" อีกต่อไป แต่เป็นชุดส่วนประกอบที่ปลอดภัยทางหน่วยความจำและใช้ใบอนุญาตอนุญาตกว้าง วางซ้อนเป็นชั้น — แต่ละชั้นมี SBOM ของตัวเอง ที่มาของตัวเอง และพื้นผิวภัยคุกคามที่น้อยที่สุดของตัวเอง ไลบรารี Rust ที่ผมดูแลแมปเข้ากับการจัดชั้นนั้นอย่างชัดเจน

- **Edge ingress.** [http-handle](https://github.com/sebastienrousseau/http-handle) คือเซิร์ฟเวอร์ HTTP/1.1 แบบ zero-dependency ที่สอดคล้อง RFC 7230 / 9112 เขียนใน Rust ที่ปลอดภัย — สร้างขึ้นสำหรับช่วงเวลาที่ทีมแพลตฟอร์ม CIB ตระหนักว่าชั้น ingress ไม่ควรดึง crate แบบ transitive 200 ชิ้นเข้ามา เหตุผลของมันได้รับการอธิบายไว้ใน [http-handle: Edge Ingress แบบ Zero-Dependency สำหรับธนาคารด้วย Rust](https://sebastienrousseau.com/2026-06-20-http-handle-zero-dependency-edge-ingress-banking-rust-2026)
- **ระนาบการกำหนดค่า.** [noyalib](https://github.com/sebastienrousseau/noyalib) แยกวิเคราะห์ YAML 1.2 ด้วยความสอดคล้องสเปก 406/406 พร้อมการตรวจสอบ JSON-Schema และ Concrete Syntax Tree แบบไร้สูญหาย — เพื่อให้ Kubernetes manifest, ทะเบียนเซิร์ฟเวอร์ MCP และเวิร์กโฟลว์ CI หยุดเป็นพื้นผิวการโจมตีที่เงียบเชียบ ดู [เหตุใด YAML จึงต้องการสแตก Rust ที่ปลอดภัยกว่า สำหรับ AI, MCP และโครงสร้างพื้นฐานทางการเงินในปี 2026](https://sebastienrousseau.com/2026-06-18-noyalib-safe-yaml-rust-ai-mcp-financial-infrastructure-2026)
- **องค์ประกอบเชิงเข้ารหัส.** [hsh](https://github.com/sebastienrousseau/hsh) ให้การแฮชรหัสผ่านแบบ Argon2id, bcrypt และ scrypt พร้อม API การตรวจสอบแบบ constant-time [KyberLib](https://github.com/sebastienrousseau/kyberlib) ใช้ ML-KEM-512/768/1024 ภายใต้ FIPS 203 สำหรับการย้ายระบบไปยังยุคหลังควอนตัม ที่สำรวจไว้ใน [KyberLib และการย้ายระบบธนาคารสู่ยุคหลังควอนตัมในปี 2026](https://sebastienrousseau.com/2026-06-12-kyberlib-post-quantum-banking-migration-standards-code-2026)
- **คอนเทนต์และการส่งมอบที่ขอบ.** [html-generator](https://github.com/sebastienrousseau/html-generator) คอมไพล์ Markdown ที่เข้าถึงได้ ให้เป็น HTML ที่มีโครงสร้าง; [Shokunin SSG](https://github.com/sebastienrousseau/shokunin) สร้างสิ่งพิมพ์ที่คุณกำลังอ่านอยู่; [CloudCDN](https://sebastienrousseau.com/2026-06-11-cloudcdn-open-source-blueprint-ai-native-edge-2026) ยืนอยู่ด้านหน้าในฐานะ edge แบบโอเพนซอร์สและ AI-native

ไม่มีสิ่งใดเป็น "เฟรมเวิร์ก" ในความหมายของธนาคารยุคเก่า ทั้งหมดเป็นองค์ประกอบขนาดเล็ก ที่ใช้ใบอนุญาตอนุญาตกว้าง ลงนาม พร้อมโมเดลภัยคุกคามที่ชัดเจน นั่นคือรูปร่างเชิงปฏิบัติการที่วิทยานิพนธ์ FINOS สนับสนุน — และเป็นรูปร่างที่ทีมแพลตฟอร์ม CIB สามารถปกป้องต่อหน้าผู้กำกับดูแลได้โดยไม่ต้องมีสไลด์เด็ค

ข้อแม้เล็กๆ แต่ตรงไปตรงมา: เป้าหมายไม่ใช่ "เขียนธนาคารใหม่ทั้งหมดใน Rust" แต่คือการให้ทางเลือกแก่ทีมแพลตฟอร์ม CIB ในการมีสแตกที่ปลอดภัยทางหน่วยความจำและพึ่งพา dependency น้อย ที่ชั้นรับน้ำหนัก — ingress, การแยกวิเคราะห์, crypto, build, ห่วงโซ่อุปทาน — โดยไม่บังคับให้ตัดสินใจแบบเป็นศาสนาในชั้นอื่น

## 03. โอเพนซอร์สเป็นรากฐานของวาระ ISO, AI และควอนตัม

วาระโครงสร้างหลักสามประการของ CIB ในปี 2026 — การเปลี่ยนผ่าน ISO 20022, agentic AI ในการปฏิบัติงาน และการย้ายไปสู่การเข้ารหัสหลังควอนตัม — ทั้งหมดทำงานบนโค้ดที่ตรวจสอบได้ ไม่มีข้อใดทำงานได้ในรูปสแตกเชิงพาณิชย์ปิด

**ISO 20022.** ตระกูลสคีมา pacs.008 / pacs.009 / camt ตอนนี้เป็นค่าเริ่มต้นของการชำระเงินขายส่ง FINOS โฮสต์ Common Domain Model ควบคู่กับไลบรารี Java และ Kotlin แบบโอเพนซอร์ส ที่แยกวิเคราะห์ ตรวจสอบ และกำหนดเส้นทางข้อความเหล่านั้น งานใน [การอัตโนมัติ pacs.008 และการชำระเงินระหว่างธนาคารด้วย ISO 20022](https://sebastienrousseau.com/2026-06-15-pacs008-automation-iso-20022-interbank-payments-2026) แสดงให้เห็นว่าไปป์ไลน์ระดับการเคลียริงประกอบขึ้นจากองค์ประกอบเปิดเหล่านั้นได้อย่างไร — การตรวจสอบสคีมา การส่งเงินที่มีโครงสร้าง การติดตามตลอดเส้นทาง — โดยไม่ต้องสร้างตัวแยกวิเคราะห์ใหม่ที่ทุกธนาคาร

**Agentic AI.** Model Context Protocol (MCP) คือภาษากลางในการให้เอเจนต์ AI เรียกเครื่องมือธนาคารภายใน — และเซิร์ฟเวอร์ MCP ทำงานบนทะเบียน YAML, บัญชีบริการที่จำกัดด้วย OAuth และไปป์ไลน์บันทึกการตรวจสอบ ระนาบควบคุมเป็นโอเพนซอร์สเพราะมันต้องเป็น: เอเจนต์ใดก็ตามที่แตะบัญชีแยกประเภทโปรดักชันต้องมีเวิร์กโฟลว์แบบจำกัดขอบเขตที่ตรวจสอบได้ ข้อโต้แย้งสำหรับการปฏิบัติต่อสิ่งนั้นเป็นปัญหาทางวิศวกรรมมากกว่าการเลือกเวนเดอร์ ผ่านไปใน [เหตุใด YAML จึงต้องการสแตก Rust ที่ปลอดภัยกว่า](https://sebastienrousseau.com/2026-06-18-noyalib-safe-yaml-rust-ai-mcp-financial-infrastructure-2026) และงาน dotfiles ของเวิร์กสเตชันใน [Dotfiles ที่รู้จัก AI ในปี 2026](https://sebastienrousseau.com/2026-06-16-ai-aware-dotfiles-secure-reproducible-workstation-2026)

**การเข้ารหัสหลังควอนตัม.** FIPS 203 (ML-KEM) และ FIPS 204 (ML-DSA) ตอนนี้เป็นเป้าหมายการย้ายระบบ การแลกเปลี่ยนคีย์แบบไฮบริด X25519MLKEM768 คือค่าเริ่มต้นในทางปฏิบัติใน TLS 1.3 ไม่มีสิ่งใดในนี้ทำงานได้โดยปราศจากการพัฒนาแบบเปิดที่ผู้ตรวจสอบและทีมเข้ารหัสของธนาคารสามารถอ่านได้บรรทัดต่อบรรทัด — KyberLib เป็นหนึ่งตัวอย่าง และการวางกรอบการย้ายระบบในวงกว้างเป็นหัวข้อของ [KyberLib และการย้ายระบบธนาคารสู่ยุคหลังควอนตัมในปี 2026](https://sebastienrousseau.com/2026-06-12-kyberlib-post-quantum-banking-migration-standards-code-2026)

สามวาระ การพึ่งพาร่วมหนึ่งเดียว: โค้ดเปิด ลงนามโดย sigstore รับรองโดย SLSA ลงรายการใน SBOM แบบ CycloneDX หรือ SPDX กำกับโดย OSSF scorecards นั่นคือสแตก CIB แบบ cloud-native ในปี 2026

## 04. การกลายเป็นแพลตฟอร์มภายใต้ PSD3 และ FiDA

วาระการกลายเป็นแพลตฟอร์มของยุโรป — PSD3, Payment Services Regulation และกรอบ Financial Data Access (FiDA) — คือการผูกมัดทางกฎระเบียบต่อการเงินแบบเปิด มันสันนิษฐานว่าธนาคารสามารถเปิดเผย กำกับ และตรวจสอบการไหลของข้อมูลในระดับใหญ่ได้ มาตรฐานเปิดคือเงื่อนไขเบื้องต้น ไม่ใช่ผลพลอยได้

มุมมองปี 2026 ของ Consultancy.uk เรื่องการประสาน open banking เพื่อการเติบโตของแพลตฟอร์ม ทำการสังเกตเดียวกันจากด้านธุรกิจ: สถาบันที่ชนะภายใต้ PSD3 คือสถาบันที่ปฏิบัติต่ออาณาจักร API ในฐานะผลิตภัณฑ์ ไม่ใช่ในฐานะเรื่องที่ค้างไว้คิดทีหลังเพื่อการปฏิบัติตามกฎ ([Consultancy.uk, 2026](https://www.consultancy.uk/news/42202/orchestrating-open-banking-for-platform-growth-2026-outlook "การประสาน open banking เพื่อการเติบโตของแพลตฟอร์ม — มุมมองปี 2026")). ท่าทีนั้นเป็นไปไม่ได้บนสแตกปิด การทำให้ API เป็นผลิตภัณฑ์ต้องการสเปก OpenAPI ที่จัดเวอร์ชัน, การทดสอบสัญญาแบบอัตโนมัติ, observability ข้ามผู้บริโภคทุกราย และชั้นการกำกับดูแลที่ผู้ตรวจสอบสามารถเดินผ่านได้ องค์ประกอบแต่ละชิ้นเหล่านั้นเป็นโอเพนซอร์สในปี 2026 และส่วนใหญ่อยู่ในโครงการ CNCF หรือ FINOS

ตรรกะเดียวกันขยายไปยังขอบเขตการเข้าถึงข้อมูลที่กว้างขึ้นของ FiDA — บำนาญ สินเชื่อจำนอง ผลิตภัณฑ์การลงทุน ธนาคารที่ควบคุมการแยกวิเคราะห์, ingress, การกำหนดค่า และ crypto ของตัวเองด้วยโค้ดที่ตรวจสอบได้ สามารถขยายขอบเขตได้โดยไม่ต้องออกแบบสถาปัตยกรรมใหม่ ธนาคารที่จ้างชั้นเหล่านั้นออกไปให้เวนเดอร์ปิด จะจ่ายเงินที่ปรึกษาด้านการบูรณาการต่อไปอีกสามปี วิทยานิพนธ์ของ FINOS โดยเนื้อแท้คือวิทยานิพนธ์การกลายเป็นแพลตฟอร์ม: เป็นเจ้าของมาตรฐาน แบ่งปันฐาน แข่งขันที่ผิว

## บทสรุป

สแตก CIB ในปี 2026 เปิดเป็นค่าเริ่มต้น ไม่ใช่เพราะอุดมการณ์ แต่เพราะแรงกดดันทั้งสามประการ — บุคลากร การปฏิบัติตามกฎ ความเร็วในการส่งมอบ — ดึงไปในทิศทางเดียวกัน และผู้กำกับดูแล (DORA, Basel III, PSD3, FiDA) ได้ให้สัตยาบันแล้ว รายงานของ Banking Dive เกี่ยวกับ Morgan Stanley, JPMorgan และ Citi คือเวอร์ชันสาธารณะของบทสนทนาส่วนตัวที่ทีมแพลตฟอร์มอาวุโสได้คุยกันมาเป็นเวลาสองปี

สำหรับคณะกรรมการ นัยตรงไปตรงมา คำถามไม่ใช่ "เราควรใช้โอเพนซอร์สหรือไม่" อีกต่อไป แต่คือ: เรามี SBOM, ที่มาแบบ SLSA, ลายเซ็น sigstore, OSSF scorecards และนโยบายการมีส่วนร่วมที่สอดคล้องกับ FINOS เพื่อใช้มันอย่างปลอดภัยหรือไม่ ถ้าคำตอบคือไม่ คำตอบต่อผู้กำกับดูแลก็จะเป็นไม่เช่นกัน

สำหรับผู้นำด้านวิศวกรรม นัยยิ่งคมชัดกว่า เลือกชั้นรับน้ำหนัก — ingress, การแยกวิเคราะห์, crypto, build, ห่วงโซ่อุปทาน — และกำหนดมาตรฐานบนองค์ประกอบที่ปลอดภัยทางหน่วยความจำ ใช้ใบอนุญาตอนุญาตกว้าง พร้อมโมเดลภัยคุกคามที่ชัดเจน ตัวอย่าง Rust แบบ zero-dependency ในบทความนี้คือชุดที่ใช้ได้ชุดหนึ่ง ประเด็นอยู่ที่รูปร่าง ไม่ใช่ที่แบรนด์ สร้างฐานเพื่อให้พื้นผิวเคลื่อนได้เร็ว

โอเพนซอร์สไม่ใช่คำถามของการยกระดับโครงสร้างพื้นฐานอีกต่อไป มันคือคำตอบของการยกระดับโครงสร้างพื้นฐาน
