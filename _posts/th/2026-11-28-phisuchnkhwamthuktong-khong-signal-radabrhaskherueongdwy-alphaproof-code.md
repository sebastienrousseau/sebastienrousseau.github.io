> - เมื่อนำไปใช้กับ libsignal เอเจนต์สร้างบทพิสูจน์ Lean ที่เครื่องตรวจสอบแล้วราว 6.3 ล้านบรรทัด โดยตั้งอยู่บนข้อกำหนดที่ได้รับความไว้วางใจและอรรถศาสตร์ของ AArch64 ราว 27,000 บรรทัด

> - เพราะเคอร์เนลของ Lean ตรวจทุกบทพิสูจน์ ความน่าเชื่อถือของผลลัพธ์จึงไม่ขึ้นกับความน่าเชื่อถือของเอเจนต์ผู้พิสูจน์ แต่ข้อกำหนดต้องได้รับความไว้วางใจ และข้อบกพร่องในข้อกำหนดจะทำให้การรับประกันอ่อนลง
> - ผลลัพธ์ชี้ว่า AI อาจทำให้การพิสูจน์เชิงรูปนัย ซึ่งในอดีตแพงเกินไปสำหรับซอฟต์แวร์ส่วนใหญ่ กลายเป็นสิ่งที่ทำได้จริงกับระบบในโลกจริง วิจารณญาณของมนุษย์ยังคงอยู่ในวงจร

## ทำไมผลลัพธ์นี้จึงสำคัญต่อผู้ที่ส่งมอบซอฟต์แวร์เข้ารหัสลับ

Signal ได้รับการกล่าวถึงว่าเป็นมาตรฐานโลกโดยพฤตินัยสำหรับการส่งข้อความแบบเข้ารหัสต้นทางถึงปลายทาง โดยมีรูปแบบต่างๆ ของโปรโตคอลนี้ใช้งานอยู่ใน WhatsApp แอป Messenger ของ Meta และ Google Messages เมื่อโปรโตคอลหนึ่งรองรับบทสนทนาจำนวนมากขนาดนั้น ช่องว่างระหว่างการออกแบบที่พิสูจน์แล้วว่าปลอดภัยบนกระดาษกับโค้ดที่คอมไพล์แล้วซึ่งรันจริงก็ไม่ใช่เรื่องทางวิชาการอีกต่อไป บทพิสูจน์บนกระดาษอาจไร้ที่ติ ในขณะที่การใช้งานจริงทำสิ่งที่ต่างออกไปโดยสิ้นเชิง

ช่องว่างนั้นคือเป้าหมายของงานนี้ ผู้เขียนนำเสนอบทพิสูจน์แรกของคุณสมบัติด้านความปลอดภัยระดับโปรโตคอลสำหรับการใช้งานโปรโตคอลเข้ารหัสลับที่ใช้งานแพร่หลายและไม่ได้แก้ไข อ่านประโยคนั้นสองครั้ง เพราะคำขยายทุกคำมีน้ำหนัก ระดับโปรโตคอลหมายความว่าบทพิสูจน์กล่าวถึงคุณสมบัติอย่าง forward secrecy ไม่ใช่แค่การไม่มีข้อผิดพลาดด้านหน่วยความจำ ใช้งานแพร่หลายหมายถึง libsignal ไม่ใช่ต้นแบบงานวิจัย ไม่ได้แก้ไขหมายความว่าไม่มีใครเขียนโค้ดใหม่ให้อยู่ในรูปที่เป็นมิตรกับตัวพิสูจน์มากขึ้น

สำหรับผู้ก่อตั้ง การอ่านเชิงปฏิบัติคือเรื่องต้นทุน ผู้เขียนนำเสนอการพิสูจน์เชิงรูปนัยเป็นทางเลือกแทนการไล่หาบั๊กแบบตั้งรับ: ระบุคุณสมบัติด้านความถูกต้องและความปลอดภัยที่ระบบซอฟต์แวร์ต้องบังคับใช้ แล้วพิสูจน์ทางคณิตศาสตร์ว่าระบบเป็นไปตามนั้น พวกเขาอธิบายว่าในอดีตวิธีนี้แพงเกินไปสำหรับซอฟต์แวร์ส่วนใหญ่ ผลลัพธ์ของผู้เขียนชี้ว่า AI ทำให้วิธีนี้ใช้ได้จริงกับระบบในโลกจริง นั่นเป็นข้ออ้างที่ระมัดระวัง และผมจะถือว่ามันเป็นเช่นนั้น: เป็นข้อชี้แนะที่มีกรณีศึกษาขนาดใหญ่หนึ่งกรณีรองรับ ไม่ใช่ข้อสรุปทางเศรษฐศาสตร์ที่ยุติแล้ว ถึงกระนั้น กรณีศึกษาขนาดนี้ก็เป็นหลักฐานที่จริงจังกว่าข้ออ้างส่วนใหญ่ในด้านนี้

## ปัญหาการพิสูจน์ยากกว่าที่เห็น

เอกสารต้นทางของเฟรมเวิร์กนี้อ้างถึงเกณฑ์เทียบที่คุ้นเคยว่าการพิสูจน์หนักหนาเพียงใด: คอมไพเลอร์ภาษา C ที่ผ่านการพิสูจน์อย่าง CompCert ซึ่งใช้เวลาหกคน-ปีในการพิสูจน์ ตามตัวเลขที่รายงานไว้ที่นี่ ควรใช้ตัวเลขนี้อย่างระมัดระวัง เพราะข้อความในวงเล็บเรื่องคน-ปีเป็นการเรียบเรียงของแหล่งที่มา ไม่ใช่คำพูดที่ยกมาโดยตรง ประเด็นหลักยังคงอยู่: การพิสูจน์ซอฟต์แวร์จริงจังเป็นพันธะที่กินเวลาหลายปีมาตลอด

การพิสูจน์โค้ดระดับอุตสาหกรรมที่มีอยู่แล้วถูกระบุว่ายากยิ่งกว่า เพราะผู้พิสูจน์แก้โค้ดเพื่อให้บทพิสูจน์ง่ายขึ้นไม่ได้ ไลบรารีที่ใช้งานจริงซึ่งคอมไพล์ด้วยคอมไพเลอร์แบบปรับให้เหมาะสมคือกรณีนี้พอดี หากคุณมีอิสระที่จะปรับโครงสร้างโปรแกรม คุณก็จัดรูปให้บทพิสูจน์ไหลออกมาเองได้ หากต้องรับโค้ดตามสภาพที่เป็น คุณก็ต้องรับทุกสำนวนที่เก้งก้างและทุกการตัดสินใจของคอมไพเลอร์

AlphaProof Code จงใจเลือกเส้นทางที่ยากกว่า โค้ด Rust ที่ไม่ได้แก้ไขถูกคอมไพล์ด้วยคอมไพเลอร์มาตรฐาน และไฟล์ปฏิบัติการถูกโหลดเข้า Lean พร้อมอรรถศาสตร์ของ AArch64 ในทางปฏิบัติ ผู้เขียนลิงก์ libsignal เข้ากับ harness บรรทัดคำสั่งขนาดเล็ก แล้วคอมไพล์ด้วยคอมไพเลอร์ rustc มาตรฐานเป็นรหัสเครื่อง AArch64 Linux วัตถุของการพิสูจน์คือรหัสเครื่อง นั่นเป็นเป้าหมายที่หนักแน่นกว่าการให้เหตุผลระดับซอร์สโค้ด เพราะคอมไพเลอร์ไม่ใช่สิ่งที่คุณต้องไว้วางใจให้รักษาคุณสมบัติที่พิสูจน์ไว้อีกต่อไป

## เฟรมเวิร์กแบ่งงานกันอย่างไร

AlphaProof Code คือเฟรมเวิร์กความร่วมมือระหว่างมนุษย์กับ AI สำหรับการเขียนข้อกำหนดและการพิสูจน์เชิงรูปนัยของซอฟต์แวร์ที่ใช้งานจริง เฟรมเวิร์กนี้ตั้งอยู่บนหลักการที่ผมเห็นว่าน่าเชื่อถือ: ความพยายามส่วนใหญ่ของมนุษย์ในการพิสูจน์ซอฟต์แวร์ตอนนี้อยู่ที่วิศวกรรมข้อกำหนด การเขียนบทพิสูจน์ ซึ่งเคยกินเวลาผู้เชี่ยวชาญหลายปี กลายเป็นสิ่งที่เครื่องทำได้มากขึ้นเรื่อยๆ

ผู้เขียนให้เหตุผลจากผลลัพธ์ของตนเองว่า แม้บทพิสูจน์ขนาดใหญ่เกี่ยวกับซอฟต์แวร์ก็เขียนได้โดยทีมเอเจนต์ AI เมื่อข้อกำหนดถูกกำหนดตายตัวแล้ว และเอเจนต์ผู้พิสูจน์ทำงานได้อย่างอิสระเพราะในท้ายที่สุดเคอร์เนลของ Lean ตรวจทุกบทพิสูจน์ เฟรมเวิร์กของพวกเขาแบ่งงานออกเป็นสองส่วน ผู้ใช้ที่เป็นมนุษย์และเอเจนต์ AI ร่วมกันเขียนข้อกำหนด Lean ของโค้ดที่ใช้งานจริง และเมื่อผู้ใช้ตรวจทานข้อกำหนดแล้ว ทีมเอเจนต์อิสระจะพิสูจน์ว่าโค้ดเป็นไปตามข้อกำหนดนั้น ผู้เขียนระบุชัดว่าสำหรับระบบขนาดใหญ่และซับซ้อน ความช่วยเหลือจาก AI ลดต้นทุนการเขียนข้อกำหนดและการสร้างความเชื่อมั่นได้ แต่ไม่ได้แทนที่วิจารณญาณและการตรวจทานของมนุษย์ทั้งหมด

ขั้นตอนข้อกำหนดไม่ใช่การประทับตราผ่านๆ กลุ่มเอเจนต์ผู้ตรวจทานตรวจว่าร่างข้อกำหนดซื่อตรงต่อแหล่งที่มาและต่อการใช้งานจริง ในกระบวนการของผู้เขียน ผู้ใช้ตรวจทาน แก้ไข และอนุมัติข้อกำหนดก่อนจะมีการเขียนบทพิสูจน์ใดๆ และ git commit ของข้อกำหนดจะกลายเป็นฐานอ้างอิงที่ gatekeeper ใช้ตรวจบทพิสูจน์ในภายหลัง พวกเขารายงานว่าอาจต้องวนหลายรอบระหว่างผู้ใช้กับเอเจนต์กว่าจะได้ข้อกำหนดที่ดี แม้จะมีแบบจำลองจากวรรณกรรมอยู่แล้วก็ตาม สำหรับ Signal การประกอบแบบจำลอง handshake และ ratchet เดิมเข้าด้วยกันและครอบคลุม ratchet หลังควอนตัมตัวใหม่ใช้เวลาหลายรอบของการร่างและตรวจทาน ใครที่คาดว่า prompt ครั้งเดียวจะให้ข้อกำหนดที่ไว้ใจได้ควรปรับความคาดหวังเสียใหม่

ผู้เขียนเสนอการแบ่งความรับผิดชอบ: ผู้เขียนที่เป็นมนุษย์เลือกว่าจะพิสูจน์อะไร คลี่คลายความกำกวม ประเมินการแลกเปลี่ยนด้านความปลอดภัย และตัดสินใจขั้นสุดท้ายทั้งหมด ขณะที่เอเจนต์ AI ร่างและทดสอบข้อกำหนดภายใต้การกำกับของมนุษย์ ผมเห็นว่านี่คือจุดยืนที่ถูกต้อง มันมอบวิจารณญาณให้ฝ่ายที่ถูกเรียกให้รับผิดชอบได้

เอเจนต์ทุกตัวใน AlphaProof Code รวมถึงผู้เขียนข้อกำหนด เป็นเอเจนต์เขียนโค้ดอเนกประสงค์ที่พฤติกรรมถูกกำหนดด้วย skill ซึ่งเป็นเอกสารภาษาธรรมชาติ ไม่มีสถาปัตยกรรมตัวพิสูจน์เฉพาะทางใดถูกอธิบายไว้ในที่นี้ พฤติกรรมถูกกำกับด้วยเอกสารร้อยแก้ว ทำให้ระบบตรวจสอบและปรับแต่งได้ค่อนข้างง่าย

## ความไว้วางใจอยู่ที่ใดจริงๆ

การตัดสินใจด้านการออกแบบที่สำคัญที่สุดของเฟรมเวิร์กนี้คือสิ่งที่มันปฏิเสธจะไว้วางใจ บทพิสูจน์หลายล้านบรรทัดที่เอเจนต์ AI สร้างขึ้นไม่ได้รับความไว้วางใจ เพราะข้อผิดพลาดทางตรรกะใดๆ ในบทพิสูจน์จะถูกเคอร์เนลของ Lean ปฏิเสธ พูดอีกอย่างคือ เพราะบทพิสูจน์ถูกตรวจโดยเคอร์เนลของ Lean ในท้ายที่สุด ความน่าเชื่อถือของผลลัพธ์จึงไม่ขึ้นกับความน่าเชื่อถือของเอเจนต์ผู้พิสูจน์

เรื่องนี้สำคัญเพราะ ตามที่ผู้เขียนกล่าวไว้ ความน่าเชื่อถือของผลลัพธ์ไม่ขึ้นกับความน่าเชื่อถือของเอเจนต์ผู้พิสูจน์: บทพิสูจน์ถูกตรวจโดยเคอร์เนลของ Lean ในท้ายที่สุด ตามบทความ เอเจนต์ gatekeeper ยอมรับบทพิสูจน์ก็ต่อเมื่อเคอร์เนลของ Lean ตรวจผ่าน และ Lean comparator ยืนยันว่าบทพิสูจน์นั้นพิสูจน์สำเนาข้อกำหนดที่เก็บแยกไว้ได้ตรงทุกประการ จึงมีสองเงื่อนไข บทพิสูจน์ต้องถูกต้อง และต้องเป็นบทพิสูจน์ของข้อความที่ถูกต้อง เงื่อนไขที่สองออกแบบมาเพื่อกันความล้มเหลวที่แนบเนียน: เอเจนต์ที่แก้ข้อความแล้วพิสูจน์สิ่งที่ง่ายกว่าที่ถูกขอ comparator ตรวจว่าข้อความและทุกนิยามที่ข้อความนั้นพึ่งพาเหมือนกับสำเนาที่เก็บแยกไว้ทุกประการ และบทพิสูจน์ใช้เพียงสัจพจน์มาตรฐานของ Lean เท่านั้น

ฐานที่ได้รับความไว้วางใจจึงเล็กเมื่อเทียบกับขนาดของบทพิสูจน์เอง ข้อกำหนดที่ได้รับความไว้วางใจและอรรถศาสตร์ของ AArch64 ราว 27,000 บรรทัดรองรับบทพิสูจน์ราว 6.3 ล้านบรรทัด ความใส่ใจของผู้ตรวจทานมีจำกัด และอัตราส่วนนี้บอกคุณว่าควรใช้มันที่ใด

แต่ข้อกำหนดคือจุดอ่อน และผู้เขียนพูดไว้ตรงๆ ข้อกำหนดใน AlphaProof Code ประกอบด้วยชุดข้อความทฤษฎีบท Lean พร้อมทุกนิยามที่ข้อความเหล่านั้นพึ่งพา ข้อกำหนดต้องได้รับความไว้วางใจและตรวจสอบอัตโนมัติไม่ได้ และข้อบกพร่องอาจทำให้การรับประกันที่ทฤษฎีบทให้ไว้อ่อนลง ทฤษฎีบทที่ตั้งสมมติฐานเข้มงวดเกินไปกับอินพุต ยืนยันเพียงคุณสมบัติที่อ่อนของเอาต์พุต หรือวางข้อจำกัดน้อยเกินไปกับพยานที่ถูกบ่งปริมาณเชิงมีอยู่ อาจยังเป็นจริงได้แม้กับโค้ดที่มีบั๊ก หากความผิดพลาดในข้อกำหนดทำให้ขีดความสามารถของผู้โจมตีอ่อนลง การรับประกันความปลอดภัยก็อ่อนลงตามไปด้วย

นิยามยังอาจรวมถึงสัญญา extern ที่กำหนดสมมติฐานเกี่ยวกับส่วนของระบบที่อยู่นอกขอบเขตของการรณรงค์พิสูจน์ นั่นเป็นขอบเขตที่ซื่อตรง แต่ก็ยังเป็นขอบเขต: สิ่งใดที่อยู่หลังสัญญา extern ถือเป็นสมมติฐาน ไม่ได้ถูกพิสูจน์

ดังนั้นตัวเลขพาดหัว 6.3 ล้านบรรทัด จึงเป็นตัวเลขที่สำคัญน้อยที่สุดในการประเมินว่าคุณควรไว้วางใจผลลัพธ์หรือไม่ 27,000 บรรทัดนั้นต่างหากที่ควรอ่าน

## สิ่งที่พิสูจน์ได้เกี่ยวกับ Signal

บทพิสูจน์ครอบคลุม handshake หลังควอนตัม PQXDH และ Triple Ratchet ของ Signal โดยยืนยัน forward secrecy การยืนยันตัวตน ความปลอดภัยหลังการถูกเจาะ และความลับของ handshake handshake PQXDH และ Triple Ratchet ถูกออกแบบมาเพื่อรับประกันความปลอดภัยของข้อความแม้กุญแจบางส่วนถูกเจาะ และแม้ต่อหน้าคู่ปรปักษ์ในอนาคตที่เข้าถึงคอมพิวเตอร์ควอนตัมได้

ขนบการสร้างแบบจำลองแบบคลาสสิกสองสายกำหนดกรอบความหมายของ "ความปลอดภัย" ในที่นี้ แบบจำลองเชิงสัญลักษณ์ หรือที่รู้จักกันในชื่อแบบจำลอง Dolev–Yao มองไพรมิทีฟการเข้ารหัสลับเป็น "กล่องดำ" นามธรรมที่บรรลุคุณสมบัติความปลอดภัยมาตรฐาน แบบจำลองเชิงคำนวณจำกัดความน่าจะเป็นที่ผู้โจมตีที่มีประสิทธิภาพจะสำเร็จด้วยความยากของไพรมิทีฟที่อยู่เบื้องล่าง บทพิสูจน์ความปลอดภัยเชิงคำนวณระบุว่ามีการลดรูปจากการโจมตีโปรโตคอลไปสู่การละเมิดสมมติฐานที่อยู่เบื้องล่าง

แบบจำลองทั้งสองให้การรับประกันต่างกัน และผลลัพธ์ก็แบ่งตามนั้น บทพิสูจน์ที่เอเจนต์เขียนยืนยัน forward secrecy ความปลอดภัยหลังการถูกเจาะ รวมถึงการรักษาความลับและความถูกแท้ของข้อความ โดยตรงสำหรับไบนารีที่คอมไพล์แล้วต่อผู้โจมตีแบบคลาสสิก ในแบบจำลองเชิงสัญลักษณ์ บทพิสูจน์ยืนยันความลับของ handshake ต่อผู้โจมตีควอนตัมในอนาคต ผู้อ่านที่รอบคอบควรยึดความแตกต่างนี้ไว้ ผลลัพธ์ด้านคู่ปรปักษ์ควอนตัมระบุในแบบจำลองเชิงสัญลักษณ์ ส่วนผลลัพธ์ด้านผู้โจมตีแบบคลาสสิกคือผลที่ระบุโดยตรงสำหรับไบนารีที่คอมไพล์แล้ว

ยังมีอีกประเด็นหนึ่งที่อธิบายว่าทำไมงานข้อกำหนดจึงยาก ข้อกำหนดที่มีอยู่วิเคราะห์ handshake และ ratchet แยกกัน และเกิดขึ้นก่อน ratchet หลังควอนตัมของ Signal แบบจำลองเชิงรูปนัยของ Signal ก่อนหน้านี้วิเคราะห์ handshake เริ่มต้นและ ratchet แยกกัน บทพิสูจน์เกี่ยวกับโปรโตคอลที่ใช้งานจริงต้องการทั้งสองส่วนพร้อมกัน รวมถึง ratchet หลังควอนตัม ภายใต้การชี้นำของมนุษย์ เอเจนต์ขยายข้อกำหนดที่มีอยู่ไปสู่โปรโตคอลตามที่ใช้งานจริง นี่เป็นภาพตัวอย่างที่ดีของแบบจำลองความร่วมมือในทางปฏิบัติ: วรรณกรรมให้จุดเริ่มต้น มนุษย์คุมทิศทาง และเอเจนต์ทำส่วนขยาย

ผู้เขียนยังระบุว่างานของพวกเขาแสดงให้เห็นว่า AI พิสูจน์รหัสเครื่องเทียบกับข้อกำหนดที่ซับซ้อนจากวรรณกรรมวิจัยได้ รวมถึงคุณสมบัติของปฏิสัมพันธ์ระหว่างโปรแกรมที่มีสถานะกับคู่ปรปักษ์ที่ปรับตัวได้ นั่นเป็นคุณสมบัติประเภทที่น่าจับตา โปรแกรมที่มีสถานะซึ่งเผชิญคู่ปรปักษ์ที่ปรับตัวได้คือสถานการณ์ของไคลเอนต์รับส่งข้อความพอดี

ผู้เขียนอ้างความเป็นรายแรก: ในถ้อยคำของพวกเขา นี่คือบทพิสูจน์แรกที่เชื่อมการรับประกันความปลอดภัยระดับโปรโตคอลเข้ากับโค้ดที่ไม่ได้แก้ไขของการใช้งานโปรโตคอลเข้ารหัสลับที่ใช้กันแพร่หลาย นั่นเป็นข้ออ้างของพวกเขาเอง ไม่ใช่ข้อค้นพบที่เป็นอิสระ และผมรายงานมันในฐานะข้ออ้าง พวกเขาอธิบายผลลัพธ์ว่าเป็นหมุดหมายสำคัญสู่ความท้าทายใหญ่ที่เปิดตัวในเดือนเมษายน 2026

## ข้อกำหนดจับข้อผิดพลาดจริงได้หรือไม่

ข้อกำหนดที่แยกโค้ดที่ถูกออกจากโค้ดที่เสียไม่ได้ย่อมไร้ค่า และบทพิสูจน์เทียบกับข้อกำหนดนั้นยิ่งไร้ค่ากว่า ผู้เขียนทดสอบเรื่องนี้โดยตรง พวกเขาใส่บั๊กของ libsignal สองตัวที่เคยแก้ไปแล้วกลับเข้าไป และสร้างชุดมิวแทนต์สังเคราะห์ 17 ตัว เพื่อตรวจว่าข้อกำหนดจับข้อผิดพลาดจริงได้

ผลลัพธ์ตามที่ผู้เขียนรายงาน: สำหรับบั๊กในอดีตทั้งสองตัว และจนถึงตอนนี้ 16 จาก 17 มิวแทนต์สังเคราะห์ Lean พิสูจน์ว่าร่องรอยที่บันทึกไว้ (ร่องรอยพยานหนึ่งรายการต่อกรณี) ไม่อาจอธิบายได้ด้วยข้อกำหนดเชิงสัญลักษณ์ภายใต้การตีความไพรมิทีฟแบบรูปธรรมที่ตรงกับการรันที่บันทึกไว้ การหักล้างแบบไบนารีเต็มรูปของบั๊กในอดีตทั้งสองตัวผ่านการตรวจของเคอร์เนลเทียบกับรูปแปรแบบวางตำแหน่งที่ไม่ได้รับความไว้วางใจรุ่นก่อนหน้า (36-hook) ของข้อความเท่านั้น การย้ายเป้าหมายไปยังข้อความที่ได้รับความไว้วางใจของทฤษฎีบทหลักยังเป็นงานที่ค้างอยู่

ผมอยากแม่นยำว่าผลนี้บอกอะไรและไม่ได้บอกอะไร สิบหกจากสิบเจ็ดไม่ใช่สิบเจ็ดจากสิบเจ็ด และกรณีศึกษาไม่ได้อธิบายถึงมิวแทนต์ตัวที่เหลือ ผมจึงจะไม่คาดเดา และโปรดสังเกตเงื่อนไขกำกับเรื่องบั๊กในอดีต: การหักล้างแบบไบนารีเต็มรูปถูกตรวจเทียบกับรูปแปรแบบวางตำแหน่งที่ไม่ได้รับความไว้วางใจรุ่นก่อนหน้าแบบ 36 hook ของข้อความ ไม่จำเป็นต้องเป็นรุ่นสุดท้าย รายละเอียดนี้ควรรู้ก่อนที่ใครจะอ้างผลลัพธ์ว่าเป็นชัยชนะเบ็ดเสร็จ

ถึงอย่างนั้น นี่ก็เป็นการทดสอบประเภทที่ถูกต้อง มันโจมตีข้อกำหนด ซึ่งตามเฟรมเวิร์กนี้คือที่ที่ความเสี่ยงคงเหลืออยู่ แทนที่จะอวดปริมาณบทพิสูจน์ การทดสอบแบบมิวเทชันกับข้อกำหนดมีต้นทุนต่ำเมื่อเทียบกับการรณรงค์พิสูจน์ และตอบคำถามที่บทพิสูจน์ซึ่งเคอร์เนลตรวจแล้วจำนวนเท่าใดก็ตอบไม่ได้: ข้อความนี้จะสังเกตเห็นบั๊กจริงหรือไม่

## ความหมายต่อการปฏิบัติ

ข้อจำกัดสมควรได้รับความสนใจไม่น้อยกว่าหมุดหมาย สำหรับระบบขนาดใหญ่และซับซ้อน ความช่วยเหลือจาก AI ลดต้นทุนการเขียนข้อกำหนดและการสร้างความเชื่อมั่นได้ แต่ไม่ได้แทนที่วิจารณญาณและการตรวจทานของมนุษย์ทั้งหมด ผู้เขียนไม่ได้อ้างเป็นอย่างอื่น เศรษฐศาสตร์ขยับ แต่ไม่ได้ทรุดลงเป็นศูนย์ และส่วนที่ยังเป็นของมนุษย์คือส่วนที่ตัดสินว่าการรับประกันนั้นมีความหมายหรือไม่

ผมคิดว่าการแบ่งงานนั้นถูกต้อง และมันชี้ทางที่สมเหตุสมผลให้ทีมอ่านงานนี้ อย่าถามว่าเอเจนต์เขียนบทพิสูจน์ได้หรือไม่ ผลลัพธ์ของ libsignal ราว 6.3 ล้านบรรทัดตอบเรื่องนั้นแล้ว จงถามว่าใครในทีมของคุณเขียนและตรวจทานข้อกำหนดแบบที่อธิบายไว้ที่นี่ได้: ข้อความทฤษฎีบท Lean พร้อมทุกนิยามที่ข้อความพึ่งพา โดยมีสัญญา extern กำกับว่าอะไรเป็นสมมติฐาน คนคนนั้น พร้อมกระบวนการตรวจทานรอบงานของเขา คือทรัพยากรที่หายาก

ยังมีบทเรียนด้านการออกแบบในวิธีที่ระบบจัดการกับส่วนประกอบที่ไม่น่าเชื่อถือ ระบบไม่พยายามทำให้เอเจนต์น่าเชื่อถือ แต่ทำให้ความน่าเชื่อถือของเอเจนต์ไม่เกี่ยวกับผลลัพธ์ โดยส่งทุกอย่างผ่านตัวตรวจขนาดเล็กที่คงที่ ทีมที่สร้างระบบเอเจนต์ในโดเมนอื่นถามคำถามเดียวกันกับไปป์ไลน์ของตนได้: อะไรคือสิ่งที่เทียบเท่าเคอร์เนลของ Lean และ gatekeeper กำลังตรวจข้อความที่ถูกต้องหรือไม่

สำหรับผู้อ่านนอกวงการเข้ารหัสลับ ประเด็นที่นำไปใช้ทั่วไปได้คือรูปทรงของเวิร์กโฟลว์ ไม่ใช่โปรโตคอลเฉพาะ ในการออกแบบของผู้เขียน มนุษย์และเอเจนต์ร่างข้อกำหนดด้วยกัน เอเจนต์ผู้ตรวจทานตรวจความซื่อตรง มนุษย์อนุมัติ commit หนึ่งตรึงข้อกำหนดเป็นฐานอ้างอิง เอเจนต์อิสระพิสูจน์ และ gatekeeper ตรวจทั้งว่าแต่ละบทพิสูจน์ถูกต้อง และพิสูจน์ข้อความที่อนุมัติแล้วได้ตรงทุกประการ แต่ละขั้นมุ่งเป้าไปที่รูปแบบความล้มเหลวที่ต่างกัน

ไม่ควรขายเรื่องนี้เกินจริง ข้อชี้แนะที่ว่า AI ทำให้การพิสูจน์ใช้ได้จริงกับระบบในโลกจริงถูกกล่าวอย่างระมัดระวังในแหล่งที่มา และกรณีตัวอย่างเด่นหนึ่งกรณี ไม่ว่าจะน่าประทับใจเพียงใด ก็ยังเป็นเพียงหนึ่งกรณี ข้อกำหนดยังคงเป็นสิ่งที่ต้องไว้วางใจซึ่งไม่มีเครื่องมือใดตรวจแทนคุณ และการรับประกันต่อคู่ปรปักษ์ควอนตัมเป็นผลลัพธ์ในแบบจำลองเชิงสัญลักษณ์สำหรับความลับของ handshake ไม่ใช่ผลลัพธ์เชิงคำนวณ

คำถามเปิดที่กรณีศึกษานี้ยกขึ้นคือคำถามที่ผู้เขียนชี้ไปเมื่อเรียกงานนี้ว่าหมุดหมายสู่ความท้าทายใหญ่ที่เปิดตัวในเดือนเมษายน 2026: หากการเขียนบทพิสูจน์ตอนนี้มีต้นทุนต่ำเมื่อมีข้อกำหนดแล้ว วิศวกรรมข้อกำหนดจะกลายเป็นคอขวดถัดไปที่ต้องจัดการหรือไม่ ผลการทดสอบมิวเทชันชี้ว่าข้อกำหนดทดสอบได้ และข้อค้นพบเรื่อง "การวนหลายรอบ" ชี้ว่ายังช้าอยู่ เอเจนต์จะดูดซับความช้านั้นได้มากเพียงใด ขณะที่มนุษย์ยังถือการตัดสินใจขั้นสุดท้าย นั่นคือตัวเลขที่ควรจับตาในกรณีศึกษาถัดไป

## คำถามที่พบบ่อย

**AlphaProof Code คืออะไร**
เฟรมเวิร์กจาก Google DeepMind และ Google สำหรับความร่วมมือระหว่างมนุษย์กับ AI ในการเขียนข้อกำหนดและการพิสูจน์เชิงรูปนัยของซอฟต์แวร์ที่ใช้งานจริง ผู้ใช้ที่เป็นมนุษย์และเอเจนต์ AI เขียนข้อกำหนด Lean ร่วมกัน เมื่อผู้ใช้ตรวจทานข้อกำหนดแล้ว ทีมเอเจนต์อิสระจะพิสูจน์ว่าโค้ดเป็นไปตามข้อกำหนดนั้น

**อะไรกันแน่ที่ถูกพิสูจน์ใน libsignal**
โค้ด Rust ของ libsignal ที่ไม่ได้แก้ไข คอมไพล์ด้วยคอมไพเลอร์ rustc มาตรฐานเป็นรหัสเครื่อง AArch64 Linux บทพิสูจน์ครอบคลุม forward secrecy การยืนยันตัวตน ความปลอดภัยหลังการถูกเจาะ และความลับของ handshake สำหรับ handshake หลังควอนตัม PQXDH และ Triple Ratchet ของ Signal

**ทำไมจึงไม่ต้องไว้วางใจเอเจนต์ AI**
ทุกบทพิสูจน์ถูกตรวจโดยเคอร์เนลของ Lean และ gatekeeper ยอมรับบทพิสูจน์ก็ต่อเมื่อ Lean comparator ยืนยันว่าบทพิสูจน์นั้นพิสูจน์สำเนาข้อกำหนดที่อนุมัติแล้วซึ่งเก็บแยกไว้ได้ตรงทุกประการ ข้อผิดพลาดทางตรรกะจะถูกปฏิเสธ และบทพิสูจน์ของข้อความที่ง่ายกว่าก็เช่นกัน

**อะไรที่ยังต้องไว้วางใจ**
ข้อกำหนดและอรรถศาสตร์ของ AArch64 ราว 27,000 บรรทัด บวกกับสัญญา extern ใดๆ ที่อธิบายส่วนของระบบนอกการรณรงค์ ข้อกำหนดตรวจสอบอัตโนมัติไม่ได้ และข้อบกพร่องในข้อกำหนดทำให้การรับประกันที่ทฤษฎีบทให้ไว้อ่อนลง

**งานนี้พิสูจน์ความปลอดภัยต่อผู้โจมตีควอนตัมหรือไม่**
บางส่วน ความลับของ handshake ต่อผู้โจมตีควอนตัมในอนาคตถูกยืนยันในแบบจำลองเชิงสัญลักษณ์ ส่วน forward secrecy ความปลอดภัยหลังการถูกเจาะ รวมถึงการรักษาความลับและความถูกแท้ของข้อความ ถูกยืนยันโดยตรงสำหรับไบนารีที่คอมไพล์แล้วต่อผู้โจมตีแบบคลาสสิก
