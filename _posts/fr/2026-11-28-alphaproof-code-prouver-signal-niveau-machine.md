## Pourquoi ce résultat compte pour ceux qui livrent du logiciel cryptographique

Signal est décrit comme le standard mondial de fait de la messagerie chiffrée de bout en bout, avec des variantes du protocole déployées dans WhatsApp, l'application Messenger de Meta et Google Messages. Quand un protocole sous-tend autant de conversations, l'écart entre une conception prouvée sûre sur le papier et le code compilé qui s'exécute réellement cesse d'être une question académique. Une preuve sur papier peut être irréprochable alors que l'implémentation fait tout autre chose.

C'est cet écart que vise ce travail. Les auteurs livrent les premières preuves de propriétés de sécurité au niveau du protocole pour une implémentation non modifiée et largement déployée d'un protocole cryptographique. Relisez cette phrase, car chaque qualificatif compte. Au niveau du protocole signifie que les preuves portent sur des propriétés comme la confidentialité persistante, et pas seulement sur l'absence d'erreurs mémoire. Largement déployée signifie libsignal, pas un prototype de recherche. Non modifiée signifie que personne n'a réécrit le code sous une forme plus commode pour l'assistant de preuve.

Pour les fondateurs, la lecture pratique porte sur le coût. Les auteurs présentent la vérification formelle comme une alternative à la recherche réactive de bogues : on spécifie les propriétés de correction et de sécurité qu'un système logiciel doit garantir, puis on prouve mathématiquement que le système les satisfait. Ils la décrivent comme longtemps trop coûteuse pour la plupart des logiciels. Leurs résultats suggèrent que l'IA peut la rendre praticable pour des systèmes réels. L'affirmation est nuancée, et je la traite comme telle : c'est une suggestion étayée par une seule grande étude de cas, pas un résultat économique établi. Une étude de cas à cette échelle reste néanmoins une preuve plus sérieuse que la plupart des affirmations dans ce domaine.

## Le problème de la vérification est plus difficile qu'il n'y paraît

Les sources du cadre renvoient à une référence connue pour mesurer l'exigence de la vérification : le compilateur C vérifié CompCert, dont la vérification a demandé six années-personnes, selon le chiffre rapporté ici. Prenez ce nombre avec prudence, car la parenthèse sur les années-personnes est une construction de la source plutôt qu'une citation directe. Le constat tient quand même : vérifier un logiciel sérieux a été un engagement de plusieurs années.

Vérifier du code industriel préexistant est présenté comme encore plus difficile, car l'assistant de preuve ne peut pas modifier le code pour simplifier la preuve. Une bibliothèque de production compilée par un compilateur optimisant correspond exactement à ce cas. Si vous êtes libre de restructurer le programme, vous pouvez le façonner pour que la preuve en découle naturellement. Si vous devez prendre le code tel quel, vous héritez de chaque idiome maladroit et de chaque décision du compilateur.

AlphaProof Code choisit délibérément la voie difficile. Le code Rust non modifié est compilé avec le compilateur standard, et l'exécutable est chargé dans Lean avec une sémantique d'AArch64. Concrètement, les auteurs lient libsignal à un petit programme de test en ligne de commande et le compilent avec le compilateur rustc standard en code machine AArch64 Linux. L'objet de la preuve est le code machine. C'est une cible plus exigeante que le raisonnement au niveau du code source, puisque le compilateur n'a plus à être cru sur parole pour préserver les propriétés démontrées.

## Comment le cadre répartit le travail

AlphaProof Code est un cadre de collaboration entre humains et IA pour la spécification et la vérification formelles de logiciels réels. Il repose sur un principe que je trouve convaincant : l'essentiel de l'effort humain en vérification logicielle réside désormais dans l'ingénierie de la spécification. La rédaction des preuves, qui consommait autrefois des années de spécialistes, devient de plus en plus une tâche que les machines savent accomplir.

Les auteurs soutiennent, à partir de leurs propres résultats, que même de grandes preuves sur du logiciel peuvent être écrites par des équipes d'agents d'IA une fois la spécification figée, et que les agents de preuve peuvent travailler en autonomie parce que le noyau de Lean vérifie chaque preuve au bout du compte. Leur cadre scinde le travail en deux. Un utilisateur humain et des agents d'IA rédigent ensemble des spécifications Lean de code réel, puis, une fois la spécification validée par l'utilisateur, une équipe d'agents autonomes prouve que le code la satisfait. Les auteurs sont explicites : pour des systèmes vastes et complexes, l'assistance de l'IA peut réduire le coût de la rédaction des spécifications et de l'assurance, sans remplacer entièrement le jugement et la revue humains.

La phase de spécification n'est pas une simple formalité. Un groupe d'agents relecteurs vérifie qu'un brouillon est fidèle à ses sources et à l'implémentation. Dans le processus des auteurs, l'utilisateur relit, révise et approuve la spécification avant la rédaction de toute preuve, et son commit git devient la référence au regard de laquelle le gardien vérifie ensuite les preuves. Ils indiquent qu'il peut falloir de nombreuses itérations entre l'utilisateur et les agents pour aboutir à une bonne spécification, même lorsqu'un modèle existe dans la littérature ; pour Signal, composer les modèles antérieurs de la poignée de main et du ratchet et couvrir le nouveau ratchet post-quantique a demandé plusieurs cycles de brouillons et de revues. Quiconque attend d'une requête unique une spécification digne de confiance doit revoir ses attentes.

Les auteurs proposent une répartition des responsabilités : les auteurs humains choisissent ce qu'il faut prouver, lèvent les ambiguïtés, évaluent les compromis de sécurité et prennent toutes les décisions finales, tandis que les agents d'IA rédigent et testent les spécifications sous direction humaine. C'est, selon moi, la bonne posture. Elle confie le jugement à la partie qui peut en rendre compte.

Tous les agents d'AlphaProof Code, y compris le rédacteur de spécifications, sont des agents de programmation généralistes dont le comportement est défini par des compétences (skills), c'est-à-dire des documents en langage naturel. Aucune architecture de preuve sur mesure n'est décrite ici. Le comportement est piloté par des documents en prose, ce qui rend le système relativement facile à inspecter et à ajuster.

## Où réside réellement la confiance

La décision de conception la plus importante du cadre tient à ce qu'il refuse de croire sur parole. Les preuves de plusieurs millions de lignes produites par les agents d'IA ne sont pas de confiance, car toute erreur logique dans une preuve est rejetée par le noyau de Lean. Autrement dit, comme la preuve est vérifiée en dernier ressort par le noyau de Lean, la fiabilité des résultats ne dépend pas de la fiabilité des agents qui rédigent les preuves.

Ce point est essentiel car, selon les termes des auteurs, la fiabilité des résultats ne dépend pas de la fiabilité des agents de preuve : la preuve est vérifiée en dernier ressort par le noyau de Lean. D'après l'article, l'agent gardien n'accepte une preuve que si le noyau de Lean la vérifie et si le comparateur Lean confirme qu'elle prouve exactement une copie conservée à part de la spécification. Deux conditions, donc. La preuve doit être valide, et elle doit prouver le bon énoncé. La seconde condition vise une défaillance subtile : un agent qui modifie l'énoncé et prouve quelque chose de plus facile que ce qui était demandé. Le comparateur vérifie que l'énoncé et chaque définition dont il dépend sont identiques à la copie conservée à part, et que la preuve n'utilise que les axiomes standard de Lean.

La base de confiance est donc réduite au regard de la preuve elle-même. Environ 27 000 lignes de spécifications de confiance et de sémantique AArch64 soutiennent environ 6,3 millions de lignes de preuve. L'attention d'un relecteur est limitée, et ce ratio indique où la consacrer.

Mais la spécification est le point faible, et les auteurs le disent sans détour. Dans AlphaProof Code, une spécification se compose d'un ensemble d'énoncés de théorèmes Lean et de chaque définition dont ils dépendent. Elle doit être de confiance et ne peut pas être vérifiée automatiquement, et une faille pourrait affaiblir la garantie qu'apporte le théorème. Un théorème qui pose des hypothèses trop restrictives sur les entrées, n'affirme que des propriétés faibles de la sortie ou impose trop peu de contraintes aux témoins quantifiés existentiellement peut rester vrai même pour du code bogué. Si une erreur dans la spécification affaiblit la capacité de l'attaquant, la garantie de sécurité s'affaiblit aussi.

Les définitions peuvent aussi inclure des contrats externes (extern contracts) qui posent des hypothèses sur des parties du système hors du périmètre de la campagne de vérification. Ce sont des frontières honnêtes, mais ce sont des frontières : tout ce qui se trouve derrière un contrat externe est supposé, pas prouvé.

Le chiffre phare, 6,3 millions de lignes, est donc le moins utile pour juger si l'on doit se fier au résultat. Ce sont les 27 000 lignes qu'il faut lire.

## Ce qui a été prouvé sur Signal

Les preuves couvrent la poignée de main post-quantique PQXDH et le Triple Ratchet de Signal, et établissent la confidentialité persistante, l'authentification, la sécurité post-compromission et le secret de la poignée de main. La poignée de main PQXDH et le Triple Ratchet sont conçus pour garantir la sécurité des messages même lorsque certaines clés sont compromises, et même face à de futurs adversaires disposant d'un ordinateur quantique.

Deux traditions classiques de modélisation définissent ici ce que « sécurité » veut dire. Le modèle symbolique, aussi appelé modèle de Dolev–Yao, traite les primitives cryptographiques comme des « boîtes noires » abstraites qui atteignent des propriétés de sécurité standard. Le modèle calculatoire borne la probabilité de succès d'un attaquant efficace par la difficulté des primitives sous-jacentes. La preuve de sécurité calculatoire énonce qu'il existe une réduction d'une attaque contre le protocole vers la violation d'une hypothèse sous-jacente.

Les deux modèles offrent des garanties différentes, et les résultats se répartissent en conséquence. Les preuves rédigées par les agents établissent la confidentialité persistante, la sécurité post-compromission, ainsi que la confidentialité et l'authenticité des messages directement pour le binaire compilé, face à des attaquants classiques. Dans le modèle symbolique, elles établissent le secret de la poignée de main face à un futur attaquant quantique. Un lecteur attentif doit garder cette distinction en tête. Le résultat face à l'adversaire quantique est énoncé dans le modèle symbolique, et ce sont les résultats face aux attaquants classiques qui sont énoncés directement pour le binaire compilé.

Une seconde subtilité explique pourquoi le travail de spécification a été difficile. Les spécifications existantes analysent séparément la poignée de main et le ratchet, et sont antérieures au ratchet post-quantique de Signal ; les modèles formels antérieurs de Signal analysaient séparément sa poignée de main initiale et son ratchet. Une preuve sur le protocole déployé exige les deux ensemble, ainsi que le ratchet post-quantique. Guidés par des humains, les agents étendent les spécifications existantes au protocole tel qu'il est déployé. C'est une bonne illustration du modèle de collaboration en pratique : la littérature fournit un point de départ, les humains orientent, les agents réalisent l'extension.

Les auteurs affirment aussi que leur travail montre que l'IA peut vérifier du code machine au regard de spécifications riches issues de la littérature de recherche, y compris des propriétés de l'interaction entre un programme à état et un adversaire adaptatif. C'est une classe de propriétés notable. Un programme à état face à un adversaire adaptatif, c'est précisément la situation d'un client de messagerie.

Les auteurs revendiquent l'antériorité : selon leurs termes, ce sont les premières preuves reliant des garanties de sécurité au niveau du protocole au code non modifié d'une implémentation de protocole cryptographique largement utilisée. C'est leur propre affirmation, pas un constat indépendant, et je la rapporte comme telle. Ils décrivent ces résultats comme une étape importante vers un grand défi lancé en avril 2026.

## Les spécifications détectent-elles de vraies erreurs ?

Une spécification incapable de distinguer un code correct d'un code défectueux ne vaut rien, et une preuve établie à son regard vaut encore moins. Les auteurs l'ont testé directement. Ils ont réintroduit deux bogues de libsignal déjà corrigés et construit une suite de 17 mutants synthétiques pour vérifier que les spécifications détectent de vraies erreurs.

Le résultat, tel que les auteurs le rapportent : pour les deux bogues historiques et, à ce jour, pour 16 des 17 mutants synthétiques, Lean prouve qu'une trace enregistrée (une trace témoin chacun) ne peut pas être expliquée par la spécification symbolique sous une interprétation concrète des primitives correspondant à l'exécution enregistrée. Les réfutations binaires complètes des deux bogues historiques n'ont été vérifiées par le noyau qu'au regard d'une variante antérieure (à 36 hooks), placée et non de confiance, de l'énoncé ; leur reciblage vers l'énoncé de confiance du théorème principal reste à faire.

Je tiens à être précis sur ce que cela dit et ne dit pas. Seize sur dix-sept, ce n'est pas dix-sept sur dix-sept, et l'étude de cas ne dit rien du mutant restant, donc je ne spéculerai pas à son sujet. Notez aussi la réserve sur les bogues historiques : les réfutations binaires complètes ont été vérifiées au regard d'une variante antérieure de l'énoncé, à 36 hooks, placée et non de confiance, pas nécessairement de la version finale. C'est un détail à connaître avant de citer le résultat comme un sans-faute.

C'est néanmoins le bon type de test. Il s'attaque à la spécification, là où le cadre situe le risque résiduel, au lieu de mettre en avant le volume des preuves. Le test par mutation d'une spécification coûte peu au regard de la campagne de vérification, et il répond à une question qu'aucune quantité de preuves vérifiées par le noyau ne peut trancher : cet énoncé aurait-il repéré un vrai bogue ?

## Ce que cela signifie en pratique

Les limites méritent autant d'attention que l'étape franchie. Pour des systèmes vastes et complexes, l'assistance de l'IA peut réduire le coût de la rédaction des spécifications et de l'assurance, sans remplacer entièrement le jugement et la revue humains. Les auteurs ne prétendent pas le contraire. L'économie change, mais elle ne tombe pas à zéro, et la part qui reste humaine est celle qui détermine si la garantie a un sens.

Je pense que cette répartition est juste, et elle suggère une façon raisonnable pour une équipe de lire ce travail. Ne demandez pas si des agents savent écrire des preuves ; le résultat sur libsignal, avec environ 6,3 millions de lignes, y répond. Demandez qui, dans votre équipe, sait rédiger et valider une spécification du type décrit ici : des énoncés de théorèmes Lean et chaque définition dont ils dépendent, avec des contrats externes qui marquent ce qui est supposé. Cette personne, et le processus de revue autour de son travail, constituent la ressource rare.

La façon dont le système traite les composants peu fiables offre aussi une leçon de conception. Il ne cherche pas à rendre les agents dignes de confiance. Il rend leur fiabilité sans incidence sur le résultat en faisant tout passer par un vérificateur réduit et fixe. Les équipes qui construisent des systèmes agentiques dans d'autres domaines pourraient poser la même question à leurs propres chaînes de traitement : quel est l'équivalent du noyau de Lean, et le gardien vérifie-t-il le bon énoncé ?

Pour les lecteurs extérieurs à la cryptographie, le point généralisable est la forme du flux de travail, pas le protocole précis. Dans la conception des auteurs, humains et agents rédigent ensemble la spécification, des agents relecteurs en vérifient la fidélité, un humain l'approuve, un commit la fige comme référence, des agents autonomes la prouvent, et un gardien vérifie à la fois que chaque preuve est valide et qu'elle prouve exactement l'énoncé approuvé. Chaque étape cible un mode de défaillance différent.

Rien de tout cela ne doit être survendu. L'idée que l'IA rende la vérification praticable pour des systèmes réels est formulée avec prudence dans la source, et un cas phare, aussi impressionnant soit-il, reste un seul cas. La spécification demeure un artefact de confiance qu'aucun outil ne vérifie à votre place. Et la garantie face à l'adversaire quantique est un résultat du modèle symbolique pour le secret de la poignée de main, pas un résultat calculatoire.

La question ouverte que soulève l'étude de cas est celle vers laquelle pointent les auteurs en parlant d'une étape vers un grand défi lancé en avril 2026 : si la rédaction des preuves devient bon marché dès qu'une spécification existe, l'ingénierie de la spécification devient-elle le prochain goulot d'étranglement à attaquer ? Les résultats des mutations suggèrent que la spécification peut être testée, et le constat des « nombreuses itérations » suggère qu'elle reste lente. Quelle part de cette lenteur les agents peuvent-ils absorber, pendant que les humains gardent les décisions finales ? C'est le chiffre à surveiller dans la prochaine étude de cas.

## Questions fréquentes

**Qu'est-ce qu'AlphaProof Code ?**
Un cadre de Google DeepMind et de Google pour la collaboration entre humains et IA sur la spécification et la vérification formelles de logiciels réels. Un utilisateur humain et des agents d'IA rédigent ensemble des spécifications Lean ; une fois la spécification validée par l'utilisateur, une équipe d'agents autonomes prouve que le code la satisfait.

**Qu'est-ce qui a été vérifié exactement dans libsignal ?**
Le code Rust non modifié de libsignal, compilé avec le compilateur rustc standard en code machine AArch64 Linux. Les preuves couvrent la confidentialité persistante, l'authentification, la sécurité post-compromission et le secret de la poignée de main pour la poignée de main post-quantique PQXDH et le Triple Ratchet de Signal.

**Pourquoi n'est-il pas nécessaire de faire confiance aux agents d'IA ?**
Chaque preuve est vérifiée par le noyau de Lean, et le gardien n'accepte une preuve que si le comparateur Lean confirme qu'elle prouve exactement une copie conservée à part de la spécification approuvée. Une erreur logique est rejetée, tout comme la preuve d'un énoncé plus facile.

**Qu'est-ce qui doit encore être de confiance ?**
Environ 27 000 lignes de spécifications et de sémantique AArch64, plus les éventuels contrats externes qui décrivent des parties du système hors de la campagne. La spécification ne peut pas être vérifiée automatiquement, et une faille dans celle-ci affaiblit la garantie qu'apporte le théorème.

**Ce travail prouve-t-il la sécurité face à des attaquants quantiques ?**
En partie. Le secret de la poignée de main face à un futur attaquant quantique est établi dans le modèle symbolique. La confidentialité persistante, la sécurité post-compromission, ainsi que la confidentialité et l'authenticité des messages sont établies directement pour le binaire compilé face à des attaquants classiques.
