# メッセージから地図へ：ISO 20022 と Swift の上に築くグローバル企業標準

**業界はついに決済のためのグローバル言語を手にしました。しかし企業がそれに基づいて行動するためのグローバルな地図はまだありません。** ISO 20022 と Swift の CBPR+ プログラムは、G20 ロードマップのもとでの CPMI の 2027 年末データ要件に支えられ、国際決済に豊かで構造化された調和されたデータを与えました。しかしそれらは、企業のトレジャラーやその代理として動作するシステムに対して、そのデータを現実世界でどのように公開し、保護し、バージョン管理し、挙動させるべきかを示していません。その結果、奇妙な逆転が生じています。メッセージは世界中で収束しているのに、銀行が企業にそれらを使わせる方法は銀行ごとに分断されたままなのです。本稿は、銀行と金融機関が既存のレールを用いて、調和されたメッセージからグローバル企業標準へどう移行できるかを論じます。

> **エグゼクティブサマリー**
>
> - **強制力はすでに発動しました。** ISO 20022 は現在、世界中の国際決済における標準言語です。MT/MX の共存は 2025 年 11 月に終了し、構造化アドレスは 2026 年 11 月に導入され、CPMI の調和データ要件は少なくとも 2027 年末まで続きます。
> - **調和はメッセージの境界で止まりました。** CPMI と Swift は*決済が何を語るべきか*を標準化しました。しかし*銀行が企業にそれをどう使わせるか* — チャネル、認証、サービスレベル、エラーとリトライのセマンティクス — は標準化しませんでした。
> - **その解決策は既存の標準を拡張するものであり、新しい標準を発明するものではありません。** グローバル企業標準は ISO 20022 と CBPR+ の上に位置し、3 つの問いに答えます。企業はどのインターフェースを通じて、どのセキュリティパターンのもとで、どのような挙動保証をもって、それらのメッセージを銀行横断で使えるのか。
> - **非対称性が決定的です。** 共通のインターフェースプロファイルに合意するコストは、一度、集団的に支払われます。それを 100 の二者間統合に委ねるコストは、統合工数と照合の不一致という形で、永遠に支払われます。企業標準の不在は、いまや地図を描かないという選択なのです。

## 新たな基準線：ISO 20022 はもはやデータにとって任意ではない

出発点は明白です。2025 年 11 月時点で、Swift ネットワーク上の国際決済とレポーティングにおける MT と ISO 20022 の共存期間は、金融機関にとって終了しました。CBPR+ は現在、決済指図に ISO 20022 を要求しており、次のマイルストーンはすでにカレンダーに載っています。2026 年 11 月から、非構造化の郵便アドレスは CBPR+ メッセージから削除され、完全に構造化された形式またはハイブリッド形式に置き換えられます。並行して、CPMI と PMPG は調和された ISO 20022 データ要件を公表し、より速く、より安く、より透明性の高い国際決済を目指す G20 プログラムのもとで、少なくとも 2027 年末までそれを維持することを約束しています。

言い換えれば、グローバルコミュニティは決済が**何を語るべきか**について収束しました。CPMI 自身の要件は、一意のエンドツーエンド参照、構造化された当事者情報とアドレス情報、透明な手数料から最小限の送金情報フィールドに至るまで、あらゆるものをカバーしており、そのすべては市場を越えてメッセージをより比較可能かつ機械可読にするよう設計されています。Swift はそれを具体的な CBPR+ ガイドラインと期限に翻訳し、ネットワークレベルで強制しています。それがデータ層です。豊かで、構造化され、調和されています。

## Swift と ISO 20022 がすでに企業に与えているもの

企業はこの物語における後付けではありません。Swift は 10 年をかけて「ISO 20022 for corporates」と関連する市場慣行を構築してきており、その恩恵は本物です。

メッセージレベルでは、ISO 20022 は企業に次のものを提供します。

- **照合の改善。** pain および camt メッセージにおける構造化された送金情報とエンドツーエンド ID を用いることで、債権のマッチングを加速し、手作業を削減します。
- **より良い運転資本管理。** キャッシュレポーティング（camt.052/053/054）におけるより豊かで構造化されたデータが、入金・出金キャッシュフローのより正確な予測を支えます。
- **on-behalf-of モデルと仮想口座のサポート。** 最終債務者・債権者、開始当事者、その他の役割のための専用フィールドを介して提供され、これらはレガシーな MT 構造がきれいに扱えるようには決して設計されていなかったものです。

Swift の企業向けの取り組みは理論に限られてきたわけではありません。SCORE フレームワークと CGI-MP（Common Global Implementation – Market Practice）グループは、企業の決済開始とキャッシュマネジメントのメッセージに関する詳細な ISO 20022 利用ガイドラインを生み出してきました。銀行と企業はこれらのテンプレート — MyStandards 上で公開され、実運用パイロットで洗練されたもの — を用いて、あらゆる関係ごとに新しい方言を発明することを避けています。SEB による企業向けの早期 ISO 20022 展開のようなケーススタディは、多国籍企業が複数の銀行と市場にわたって単一の pain.001 と camt のフレーバーに標準化でき、効率と統制において測定可能な成果を得られることを示しています。

したがって、構成要素は存在します。企業は恩恵を明確に理解しています。銀行はメッセージのガイドラインと例を持っています。CPMI は管轄区域を越えて最小限のデータセットを調和させました。これらのいずれもまだ提供していないのは、別の問いに対するグローバルに一貫した答えです。すなわち「メッセージはどう見えるべきか」ではなく、「銀行は企業にそれをどう使わせるべきか」という問いです。

## 欠けている層：調和されたメッセージから企業標準へ

この区別は微妙に聞こえますが、それは辞書と輸送システムの違いです。ISO 20022 と CPMI は、エンドツーエンドで伝わらなければならない語彙と文法を教えてくれます。しかしそれらは次のことを教えてくれません。

- 企業がそれらのメッセージにファイル、ポータル、host-to-host パイプ、あるいは API のいずれを通じて到達するのか — そしてそのうちどれがファーストクラスとして扱われるのか。
- それらのチャネルがどのようにクライアントを認証するのか — 独自証明書、手動のホワイトリスト、あるいは最新の OAuth2/mTLS プロファイルか。
- 企業がどのような非機能的挙動を想定できるのか — レイテンシ予算、可用性、カットオフの強制、そして STP への期待。
- エラーがどう通知され、どのリトライパターンが安全なのか — とりわけ自動化とエージェントがそれらのチャネルに対して動作するようになった今。

そのギャップは、2015 年当時よりも今のほうが重要です。当時、統合を担うのは人間であり、企業ごとの視野は数行の銀行にとどまっていました。今日、大企業とそのプラットフォームは、数十の取引相手にわたるリアルタイムの可視性、ストレートスルーの決済開始、機械駆動の照合を期待しており、しかもますますフラットファイルではなく API を通じてそれを求めています。ISO 20022 は彼らにより豊かなデータを与えました。しかしそれ自体では、予測可能なインターフェースを与えてはいません。

信頼できる**グローバル企業標準**は、ISO 20022 と CBPR+ の基準線の上に明示的に位置し — 同じ調和されたメッセージを用いて — 3 つの問いに答える必要があります。企業はどのインターフェースを通じて、どのセキュリティパターンのもとで、どのような挙動保証をもって、それらのメッセージを銀行横断で確実に使えるのか。

## グローバル企業標準が追加しなければならないもの

良い知らせは、銀行がゼロから新しい標準を発明する必要はないということです。彼らはすでに持っている標準を拡張しさえすればよいのです。

### 1. メッセージ層を固定する：調和された ISO 20022 テンプレートを採用する

第一に、銀行と企業は、CPMI の調和データ要件と既存の Swift/CGI-MP テンプレートを、国際的な企業フローにとっての**交渉の余地のない基準線**として扱うことにコミットすべきです。

それは次のことを意味します。

- 国際決済とキャッシュレポーティングに調和された ISO 20022 メッセージ（pain、pacs、camt）を用い、CBPR+ と 2026 年 11 月の要件に整合した構造化アドレスとハイブリッドアドレスを使うこと。
- 絶対に必要な場合を除いて独自の拡張を避けること — そして必要な場合には、それらを MyStandards に文書化し、闇の中で増殖させるのではなく、発見して再利用できるようにすること。
- 内部システムが、エンリッチされた ISO 20022 データをコアで MT 風の構造に平坦化して戻すのではなく、実際に保持することを確実にすること。

これが「何を語るか」の層です。CPMI が調和されたデータモデルを定義し、Swift が CBPR+ でそれを実装し、CGI-MP が企業と銀行に従うべき具体的なテンプレートを与えます。

### 2. インターフェース層を標準化する：ファイルだけでなく API プロファイル

第二に、銀行と金融機関は、ISO 20022 ベースの決済とキャッシュレポーティングのための**主要な企業インターフェース**が、ファイルとポータルの寄せ集めではなく、共通プロファイルを持つ API になると決断する必要があります。

それには次のことが含まれます。

- 企業の決済開始（pain.001）とキャッシュマネジメントメッセージ（camt.052/053/054）を、標準的なページネーション、相関付け、フィルタリングのパターンを備えた REST API を介して公開すること。
- それらの API の OpenAPI 仕様を、企業がすでに利用ガイドラインを探している場所と同じ場所で公開すること — たとえば MyStandards や同等のポータル上で、ISO 20022 テンプレートと並べて。
- 認証モデルを限られた集合にコミットすること — 企業 API には独自の SFTP キー、場当たり的な IP ホワイトリスト、銀行固有の証明書の儀式ではなく、できれば FAPI 水準の OAuth2.1 と相互 TLS を用いること。

Swift 自身の企業向けガイダンスはすでにこの方向を示唆しており、主要銀行の ISO 20022 移行ハンドブックも同様で、これらはますますメッセージの準備を企業顧客向けの API 展開と組み合わせています。グローバル企業標準はそれを明示的にするでしょう。同じ ISO 20022 メッセージ定義が、少数の予測可能な API パターンを通じて到達可能でなければならないのです。

### 3. 挙動層を定義する：SLO、エラーセマンティクス、リトライ

第三に、標準は、企業にとって — とりわけそのトレジャリーシステムとエージェントにとって — **インターフェースがどう挙動するか**が、メッセージがどう見えるかと同じくらい重要であることを認識しなければなりません。

ここでは、銀行と金融機関は、少なくとも地域単位で、次の点について調整すべきです。

- 非機能的サービスレベル：
 - 決済開始、ステータス更新、キャッシュレポーティング呼び出しに対するレイテンシの期待値。
 - 可用性目標と計画的なメンテナンス時間帯。
 - 即日および国際フローに対するストレートスルー処理の期待値とカットオフ挙動。
- 共通のエラーモデル：
 - 機関間できれいにマッピングされる共通のエラーコードとカテゴリ（バリデーションエラー、カットオフ超過、流動性問題、コンプライアンス保留、技術的失敗）。
 - 何をリトライでき、何をリトライしてはならないか、そして決済開始呼び出しにわたってべき等性キーがどう挙動すべきかについての明確なガイダンス。

この挙動層がなければ、企業は、たとえすべての銀行が pain.001 を送り camt.053 を受け取っていたとしても、各銀行を特異な統合プロジェクトとして扱い続けるでしょう。この層があれば、企業は銀行接続をよりプラグ可能なコンポーネントのように扱えます。同じメッセージ、同じ API パターン、そして「受理」「保留」「失敗」「リトライ不可」に対する同じセマンティクスです。

## 銀行と金融機関が新しい委員会なしに調整する方法

もう 1 つの標準化のギャップに直面したときの誘惑は、新しいフォーラムを発明することです。ここではそれは必要ありません。すでに ISO 20022 を統率している機関が、自らの権限を 1 層上へ拡張できます。

自然な場が 3 つあります。

- **Swift とその企業向けプログラム。** Swift はすでに CBPR+、CGI-MP、企業向け利用ガイドラインの招集点です。参照用の API プロファイルと挙動に関する推奨事項をホストできます — たとえば、既存の ISO 20022 メッセージテンプレートと並べて、正規の OpenAPI 仕様とエラー分類体系を公開することです。
- **CPMI の調和データガバナンス。** CPMI は、市場慣行グループのパネルに支えられ、少なくとも 2027 年まで調和された ISO 20022 要件を維持し発展させることにコミットしています。CPMI はデータに焦点を当てていますが、そのデータの上に一貫したインターフェース標準を築くよう市場に明示的に促し、「何が送られるか」と「それがどう使われるか」の乖離を避けることができます。
- **地域およびグローバルな市場慣行グループ。** すでに ISO 20022 の実装について調整しているグループ — CGI-MP から地域の決済協議会に至るまで — は、インターフェースの挙動を二者間交渉に委ねるのではなく、共通の API と SLO のプロファイルを自らの作業の一部として採用できます。

これは CPMI や Swift を API 規制当局に変えることではありません。**同じ調和されたメッセージが、際限なく独自のインターフェースに囲まれるべきではない**ことに合意するために、既存のコミュニティを用いることなのです。

## 今後 3 年間の段階的アプローチ

追随するのではなく主導したい銀行と金融機関にとって、その道筋は漸進的であり、すでに直面しているマイルストーンと整合しています。

### フェーズ 1 — データ作業をエンドツーエンドで完了する

- まだ未完了の箇所について、国際的な MT メッセージの CBPR+ 向け ISO 20022 への移行を完了し、内部システムが構造化された ISO データをエッジで剥ぎ取るのではなく保持することを確実にする。
- 企業の決済開始とキャッシュレポーティングのメッセージを CBPR+ と CGI-MP のテンプレートに整合させ、調和を壊す銀行固有のバリエーションを避ける。
- 2026 年 11 月の期限に先立って、銀行と企業の両チャネルにわたって構造化・ハイブリッドの郵便アドレスを実装し、企業が単一のアドレッシングモデルに依拠できるようにする。

### フェーズ 2 — API を企業のファーストクラスチャネルにする

- ISO 20022 に整合した決済開始とキャッシュレポーティングを、市場と事業部門にわたる共通プロファイルを備えた REST API を通じて公開する。
- それらの API のデフォルトのセキュリティモデルとして、独自のファイルベース認証メカニズムを置き換えるか優先度を下げつつ、FAPI 水準の OAuth2.1 と相互 TLS を採用する。
- 企業が銀行横断で容易に比較できる形で OpenAPI 仕様と開発者ガイドを公開する — 理想的には Swift や業界グループからリンクされた共通のリポジトリまたはポータル上で。

### フェーズ 3 — 挙動を標準化し、それを統治する

- Swift、CGI-MP、あるいは地域協議会のもとでワーキンググループに参加するか、その形成を支援し、企業向け ISO 20022 API の共通エラーコード、べき等性ガイドライン、リトライパターンを定義する。
- 企業の決済開始・レポーティング API のレイテンシ、可用性、STP に関する SLO を設定・公開し、CBPR+ コンプライアンスを監視するのと同じくらい厳格にそれらを監視する。
- Swift などがすでに ISO 20022 メッセージングで行ってきたように、早期採用者を参照ケースとして用いながら、企業とトレジャリープラットフォームがこれらの共通プロファイルに合わせて構築するよう促す。

企業自身にとっても、プログラムは並行しています。

- ERP と TMS プラットフォームを ISO 20022 ネイティブに近代化する。構造化された送金情報とアドレスのサポート、camt キャッシュレポーティングの完全な取り込みを含む。
- 単なる「ファイル経由の ISO 20022」ではなく、透明なサービスレベルと調和されたセマンティクスを備えた ISO 20022 整合の API を提供する銀行関係を優先する。
- より豊かなデータと予測可能な挙動を用いて、一度に 1 行ずつではなく、すべての銀行にわたって内部プロセス — 照合、予測、OBO モデル — を標準化する。

## 機会とリスク

強制力はすでに動き出しています。ISO 20022 は現在、世界中の国際決済における標準言語であり、共存は終了し、構造化データはネットワークレベルで強制されています。CPMI の調和データ要件は、フランクフルトからワシントンまで、市場慣行と規制上の期待に組み込まれつつあります。銀行は ISO 20022 移行と企業向け API 展開に多額の投資をしており、企業は新しいメッセージを扱うために ERP と TMS をアップグレードしています。

問いは、この波がメッセージの境界で止まるのか、それとも企業の体験まで貫くのかということです。もし銀行が ISO 20022 を純粋なメッセージングのアップグレードとして扱えば、企業は、同じ決済が回線上では似て見えるのに、各銀行では異なる形で到達され、統制され、理解される世界に住み続けるでしょう。逆にもし銀行が ISO 20022 と Swift のフレームワークをグローバル企業標準の**基盤**として用い — 調和を「何を」から「どう」へ拡張すれば — 企業はついに、G20 のアジェンダが何年も約束してきたものを手にできます。すなわち、単に構造的に似ているだけでなく、真に標準化された、より速く、より安く、より透明性の高い国際決済です。

ここにはおなじみの非対称性があります。共通のインターフェースプロファイルに合意するコストは、一度、集団的に支払われます。それを 100 の二者間合意に委ねるコストは、統合工数、照合の不一致、自動化の逸失機会という形で、永遠に、個別に支払われます。企業、プラットフォーム、そしてますますエージェントが ISO 20022 をネイティブに消費する準備ができている世界において、グローバル企業標準の不在は、風景の中のギャップというよりも、地図を描かないという選択なのです。

## よくある質問

**ISO 20022 は国際決済にとってまだ任意ですか。**
いいえ。2025 年 11 月時点で、Swift ネットワーク上の国際決済とレポーティングにおける MT/MX 共存期間は金融機関にとって終了し、CBPR+ は決済指図に ISO 20022 を要求しています。次のマイルストーンはすでに確定しています。2026 年 11 月から、非構造化の郵便アドレスは CBPR+ メッセージから削除され、構造化またはハイブリッド形式に置き換えられます。

**メッセージが調和されているなら、まだ何が欠けているのですか。**
インターフェースです。CPMI と Swift は決済が*何を*語るべきか — 豊かで、構造化され、比較可能なデータセット — を標準化しました。しかし銀行が企業にそれをどう到達させ使わせるか、すなわちどのチャネルがファーストクラスか、どう認証するか、企業がどのレイテンシと可用性を想定できるか、そしてエラーとリトライがどう挙動するかは標準化しませんでした。それが辞書と輸送システムの違いです。

**これを解決するために銀行は新しい標準化委員会を必要としますか。**
いいえ。すでに ISO 20022 を統率している機関が、自らの権限を 1 層上へ拡張できます。Swift はすでに CBPR+、CGI-MP、企業向け利用ガイドラインを招集しており、参照用の API プロファイルとエラー分類体系をホストできます。2027 年末まで調和データセットを統治する CPMI は、そのデータの上に一貫したインターフェース標準を築くよう促すことができます。そして地域の市場慣行グループは、共通の API と SLO のプロファイルを採用できます。

**銀行はまず何をすべきですか。**
データ作業をエンドツーエンドで完了することです — ISO 20022 をコアで平坦化するのではなく構造化されたまま保持し、2026 年 11 月に先立って構造化・ハイブリッドアドレスを実装します。次に、共通の FAPI 水準プロファイルと公開された OpenAPI 仕様を備えた、API を企業のファーストクラスチャネルにします。そして挙動を標準化します。共通のエラーコード、べき等性ガイダンス、そして CBPR+ コンプライアンスと同じくらい厳格に監視される公開された SLO です。
