# Pag-verify ng Aksyon ng Agent Bago Ito Tumakbo: Ang Gate ng JevAct

**Karamihan ng agent loop ay nagpapatakbo ng tool-call sa sandaling imungkahi ito ng model, at ipinahihiwatig ng mga resulta ng JevAct na ang isang murang checkpoint na batay sa probabilidad, na inilalagay bago mismo ang execution, ay maaaring gawing mas maaasahan ang mga agent na gumagamit ng tool, bagaman malaki ang pagkakaiba ng pakinabang depende sa benchmark.**

## Ang problema: sumusunod ang execution sa mungkahi

Ang agent na nagbu-book ng flight, nagkakansela ng order o nagbabago ng setting ng account ay gumagawa ng bagay na hindi basta-basta mababawi. Ang hindi komportableng bahagi ay kung gaano kakaunti ang nakapagitan sa mungkahi ng model at sa epekto nito. Maraming agent loop ang nagpapatakbo ng iminungkahing tool-call sa sandaling likhain ito ng model. Walang independiyenteng sumusuri kung sumusunod ang aksyon sa patakaran ng domain, o kung tapos na talaga ang gawaing itinuturing ng agent na tapos.

Ang agwat na iyan ang panimulang punto ng "Think Before You Act: Decision Gate for LLM Agents", isang arXiv preprint noong 2026 nina Iftach Shoham, Yuval David at mga kasamahan sa IBM, na nagpapakilala sa JevAct. Hindi ito bagong obserbasyon, pero sulit itong sabihin nang diretso dahil napakaraming agent tooling ang nakatuon sa pagpapahusay ng nagmumungkahi. Pinagsasalit-salit ng mga ReAct agent ang pangangatwiran at paggamit ng tool, at naging karaniwang baseline ang pattern na iyan. Nagdaragdag ang mga reflection method tulad ng Self-Refine at Reflexion ng kritika at feedback para mapabuti ang mga susunod na mungkahi o pagsubok, nang hindi ina-update ang model weights. Kapaki-pakinabang man iyan, hindi bine-verify ng mga pamamaraang iyon nang mag-isa ang isang partikular na aksyon laban sa domain policy bago mismo ang execution. Nasa ibang punto ng loop ang check na pinahahalagahan ng JevAct: pagkatapos umiral ang mungkahi at bago ito ma-commit.

## Ano ang JevAct

Ang JevAct ay isang harness na sumusuri sa mga piling mungkahi bago ang execution. Inilalarawan ito bilang runtime verification framework na humaharang sa mga piling aksyon ng agent at nagpapagana ng pagwawasto batay sa feedback. Gumagana ito nang hiwalay sa pinagbabatayang agent model at hindi nangangailangan ng anumang pagbabago sa mga parameter o tool ng model. Sa sinuring setup, nananatiling hindi nagbabago ang LLM, base prompt at mga tool ng agent.

Sa arkitektura, dinaragdagan ng JevAct ang harness ng isang ReAct agent sa pamamagitan ng pagsingit ng piling yugto ng pagsusuri sa pagitan ng pagmumungkahi ng mensahe at ng execution. Mahalaga ang salitang "piling". Hindi sinusuri ng framework ang bawat mensahe; tinutudla nito ang partikular na uri ng aksyon. Dalawa ang tinukoy sa papel. Binabago ng write call ang kapaligiran, halimbawa sa pag-book, pagkansela o pagbabago ng setting. Tinatapos ng hand-off ang pagtatangka ng agent, alinman sa paglilipat ng user sa isang tao o sa pagsasabi sa user na wala nang magagawa pa. Sa mga write nakapipinsala ang paglabag sa patakaran; sa mga hand-off maaaring sumuko nang masyadong maaga ang agent. Tumutugma sa dalawang kategoryang iyon ang ipinahayag na layunin ng framework na tukuyin ang mga posibleng hindi wastong aksyon at ang maagang pagtatapos ng gawain.

Kapag bumagsak ang isang check, hindi lang basta hinaharang ang mungkahi. Maaaring ipagpaliban ng mga check ang execution at humiling ng binagong mungkahi mula sa LLM na may pansamantalang feedback, sa loob ng nakapirming revision budget. Tumutuloy ang pumapasang mungkahi. Bumabalik sa agent ang na-flag na mungkahi na may tiyak na feedback at limitadong pagkakataong magrebisa. At nananatiling malinaw ang hatian ng trabaho: ang agent pa rin ang nagmumungkahi ng mga aksyon, at hindi pumipili ng mga ito ang Kev.

## Dalawang uri ng ebidensya, iisang gate

Nakasalalay ang disenyo sa paghahati sa pagitan ng kayang i-verify nang deterministic at ng hindi. Pinagsasama ng JevAct ang deterministic na pag-verify ng mga katotohanan sa tool state at ang probabilistic na pagtatasa ng konteksto ng usapan. Sa runtime, sinusuri ng code ang mga katotohanang makukuha sa mga tool record, at sinasagot ng Kev ang mga tanong na nakasalalay sa usapan.

Makatwiran ang paghahating iyan. Ang ilang kondisyon ng patakaran ay mga katotohanang nakaupo sa mga record ng tool, at kayang basahin ng isang programa nang walang opinyon ng anumang model. Ang ibang kondisyon ay nasa sinabi ng user at ng agent sa isa't isa, na hindi malulutas ng anumang database lookup. Ang pagbibigay ng una sa code at ng ikalawa sa isang model ay nangangahulugang tinatanong lang ang model tungkol sa mga bagay na hindi masagot ng code.

Ang offline na kalahati ang nagpapapraktikal sa paglalarawan nito. Ginagawa ng isang compiler ang domain policy na mga tanong, patakaran, executable check sa tool state, at kung kailangan, isang hand-off checklist. Sa ibang salita, kino-compile ng JevAct ang mga domain policy tungo sa mga executable state check at mga structured question na sinusuri ng isang prefill-only decision model. Sinasabi ng mga awtor na inilalatag nila ang pundasyon ng isang workflow na nagko-compile ng mga domain policy tungo sa mga tanong, decision rule, executable state check at hand-off checklist para sa isang decision-model gate. Mapagpakumbabang paraan iyan ng pagsasabi, at tatanggapin ko ito nang literal: tungkol sa pundasyon ng isang workflow ang pahayag, hindi tapos na produkto.

## Bakit decision model sa halip na LLM judge

Ang halatang alternatibo ay isang LLM judge na nagbabasa ng mungkahi at sumusulat ng hatol. Praktikal ang pagtutol ng papel. Kailangan pa ring bigyang-kahulugan ang mga malayang paliwanag ng ganitong judge bago makakilos ang isang gate, at magastos gawin ang desisyong ito gamit ang isang frontier model. Desisyon ang kailangan ng gate, hindi sanaysay.

Para diyan ginawa ang mga decision model. Ipinakilala ng Jev ang mga decision model na nagbabalik ng typed na pagpipilian, score at probabilidad sa halip na nabuong teksto. Nagbabalik sila ng mga pagpipilian at probabilidad para sa mga nakapirming tanong, na nagpapadali sa mga threshold-based na check. Prefill-only ang model na ginagamit ng JevAct at gumagawa ito ng mga paghatol na batay sa probabilidad nang hindi umaasa sa LLM generation. Ang Kev ay isang open-source na decision model na uri ng Jev, na inilalagay sa hiwalay na hakbang ng pag-verify bago ma-commit ang mga piling aksyon.

May huli, at ang mga awtor mismo ang nagsasabi nito. Hindi garantisadong calibrated o tama ang mga probabilidad ng decision model, kaya kailangang subukin ang halaga nito sa loob ng agent loop sa halip na ipagpalagay. Binabalangkas ng pangungusap na iyan ang buong empirikal na seksyon. Ang sentral na tanong ay kung maaaring magsilbi ang isang decision model bilang probability-thresholded verifier kasama ng mga executable tool-state check. Tanong itong sasagutin ng eksperimento, at nasa eksperimento ang kawili-wiling detalye.

Halo-halong larawan ang ibinibigay ng kaugnay na pananaliksik sa mga decision model kung bakit mahalaga ang pagsubok na iyon. Nag-uulat sina Li et al. ng mapagkumpitensyang resulta sa preference at evidence-grounded factuality pero mas mahinang performance kapag kailangan ang derivation. Nag-uulat sina Rao at Callison-Burch ng halo-halong resulta sa rubric at magkakapatong na pagkakamali sa mga LLM judge. Ang decision model na malakas sa ilang gawain ng paghatol at mas mahina sa iba ay eksaktong uri ng bahaging gugustuhin mong ipares sa mga deterministic na check sa halip na pagkatiwalaan nang mag-isa.

## Paano isinagawa ang paghahambing

Inihahambing ang JevAct sa isang ReAct harness na gumagamit ng parehong agent LLM sa dalawang panig. Saklaw ng mga gawain ang Airline at Telecom sa τ²-bench at mga multi-turn function-calling task sa BFCL. Ang pagpapanatiling nakapirmi ng agent LLM sa dalawang panig ang tamang kontrol para sa tanong: anumang pagkakaiba ay nagmumula sa harness, hindi sa mas malakas o mas mahinang nagmumungkahi.

Iniuulat ng papel ang mga resulta gamit ang mga numerong pass^3, mula sa Table 2, kasama ang at-least-once success. Magkasalungat ang hila ng dalawang sukat na iyon, at lumalabas na makabuluhan ang kaibahan nila. Ginagantimpalaan ng tagumpay sa lahat ng tatlong run ang agent na tama sa bawat pagkakataon. Ginagantimpalaan ng at-least-once success ang agent na tama sa alinmang pagtatangka. Dapat mas maaasahang makatulong sa una kaysa sa ikalawa ang isang verifier na nakahuhuli ng masasamang aksyon, at akma ang mga resulta sa ganoong pagbasa, bagaman ang sinasabi lang ng papel ay umaayon ang pattern sa BFCL sa mas nauulit na performance sa ilang gawain, kaya ituturing ko ang iba bilang interpretasyon at hindi natuklasan.

## Ang ipinakikita ng mga numero

Sa Telecom, pinabuti ng lahat ng walong agent ang at-least-once success at ang tagumpay sa lahat ng tatlong run. Iyan ang pinakamalinis na resulta sa papel: walang eksepsyon sa mga sinubok na agent, sa alinmang sukat.

Sa BFCL, bumuti ang lahat ng siyam na agent sa three-run success, pero halo-halo ang at-least-once na resulta. Basahin iyan nang maingat. Sa BFCL, tumaas ang mas mahigpit na sukat para sa bawat sinubok na agent, ng 0.1 hanggang 9.6 na puntos; bumuti ang maluwag na sukat para sa apat na agent at bumaba para sa lima. Kung mahalaga sa iyo na kumilos nang tama ang agent sa bawat pagkakataon, iyan ang paborableng direksyon. Kung mahalaga sa iyo kung maaaring magtagumpay rin sa wakas ang isang retry, hindi napatunayan dito ang pakinabang.

Ang Airline ang mahinang bahagi. Mas maliit ang epekto sa Airline at nag-iiba ayon sa agent. Inilalarawan ito ng buod ng mga resulta bilang partikular na pare-parehong pakinabang sa Telecom at BFCL, habang mas halo-halo ang performance sa Airline. Hindi dapat ito i-round up ng isang founder na nagbabasa nito tungo sa "pinabubuti ang lahat". Nag-uulat ang mga awtor ng pagbuti sa pagiging maaasahan ng agent sa maraming model at benchmark, pero sa Airline mas maliit at halo-halo ang pakinabang, at sinasabi nilang hindi napatutunayan ng kanilang mga natuklasan ang pantay na pakinabang. Nagbababala ang papel na sa 50 gawain ng Airline, nagagalaw ng iisang gawain ang score ng 2 percentage point, kaya dapat basahin nang maingat ang maliliit na pagkakaiba; lampas diyan, hindi ko huhulaan kung bakit naiiba ang kilos ng Airline.

Ang mga awtor mismo ang naglalagay ng pasubali sa kabuuang pagbasa: ipinahihiwatig ng mga natuklasan na maaaring mapabuti ng pagsasama ng mga structured decision model at executable verification ang pagiging maaasahan ng mga LLM agent na gumagamit ng tool. "Ipinahihiwatig" ang tamang pandiwa. Promising na resulta ito, hindi patunay.

## Ang inihihiwalay at hindi inihihiwalay ng paghahambing

May isang limitasyong nararapat ng mas mabigat na pansin kaysa karaniwan nitong natatanggap. Dahil nagdaragdag ang JevAct ng mga compiled check at pagkakataong magrebisa, sinusuri ng mga paghahambing ang buong harness, hindi ang judge nang mag-isa. Malaking pasubali iyan para sa sinumang umaasang makapagtapos na ang decision model ang gumagawa ng mabigat na trabaho. Maaaring magmula ang pakinabang sa mga probabilidad ng Kev, sa mga executable state check, sa dagdag na pagkakataong magrebisa, o sa ilang kumbinasyon. Hindi sila pinaghihiwalay ng mga pangunahing paghahambing.

Masasabi kong hindi ito kapintasan kundi tapat na paglalarawan ng kayang ipakita ng isang system paper. Ang tanong na inihaharap ng mga awtor, kung maaaring magsilbi ang isang decision model bilang probability-thresholded verifier kasama ng mga executable tool-state check, ay sinasagot sa antas ng pares, dahil nasa tanong mismo ang "kasama ng". Pero dapat itong tandaan ng mambabasang nagpapasya kung saan ilalagak ang pagsisikap. Kung gumagawa ka ng katulad, hindi mo mahihinuha mula sa ebidensyang ito na ang decision model lang ang magdadala ng pagbuti, ni ang mga code check lang.

Nangangahulugan din ito na nananatili ang pasubali sa calibration. Hindi garantisadong calibrated o tama ang mga probabilidad, at hindi inaalis ng resulta sa antas ng harness ang kawalang-katiyakang iyon. Ipinakikita nito na nakatulong ang kabuuang ayos sa mga benchmark na sinubok.

## Kung saan ito nakapuwesto sa iba pang guard design

Sumasali ang JevAct sa masikip na hanay ng mga approach sa pagbabantay sa aksyon ng agent, at makabuluhan ang mga pagkakaiba. Gumagamit ang GuardAgent ng hiwalay na agent para bumuo at magpatakbo ng verification code mula sa mga guard requirement na itinakda ng user. Kino-compile nina Zwerdling et al. ang mga patakaran ng kumpanya tungo sa mga executable guard na sumusuri sa pagsunod bago ang mga aksyon ng tool. Kinakatawan ng AgentSpec ang mga runtime constraint bilang mga trigger, predicate at enforcement action. Hinahango ng ShieldAgent ang mga mabe-verify na patakaran mula sa mga dokumento ng patakaran.

Ang iba ay umaasa sa mga model para sa pag-verify mismo. Gumagamit ang ToolSafe ng natutuhang guardrails para tasahin ang mga iminungkahing tool-call at magbalik ng feedback, habang gumagamit ang PolicyGuard at PolicyGuide ng mga model-based verifier para sa pagsunod sa patakaran at gabay sa workflow. Ibang daan ang tinatahak ng CaMeL, na nagpapatupad ng seguridad sa pamamagitan ng paghihiwalay ng pinagkakatiwalaang control flow at hindi pinagkakatiwalaang datos.

Sa kontekstong iyan, ang natatanging pagpili ng JevAct ay ang partikular nitong pagpapares. Tulad ng linya ng trabahong nagko-compile tungo sa executable guard, ginagawa nitong mga check sa tool state ang patakaran. Tulad ng mga model-based verifier, gumagamit ito ng model para sa mga paghatol na hindi kayang gawin ng code. Ang idinaragdag nito ay isang decision model na nagbabalik ng mga probabilidad para sa nakapirming pagpipilian, na ginagamit online bago tumakbo ang mga piling aksyon, na may feedback para sa rebisyon. Iniiwan nito ang mga mungkahi sa ReAct LLM at inilalagay ang Kev sa hiwalay na hakbang ng pag-verify bago ma-commit ang mga piling aksyon.

## Bakit sulit bantayan ang disenyong ito

Sa tingin ko, ang pinakakapaki-pakinabang na ideya rito ay hindi ang Kev mismo kundi ang disiplina ng paghahati. Itanong sa code ang kayang sagutin ng code. Itanong lang sa model ang nakasalalay sa usapan. Panatilihing hiwalay ang nagmumungkahi at ang nagbe-verify, para hindi ang model na nagmungkahi ng aksyon ang siya ring sumusuri rito. At gawing probabilidad laban sa threshold ang output ng verifier, para paghahambing ang gate at hindi tekstong kailangang i-parse ng kung sino.

Ginagawa ring nababasa ng disenyong iyan ang mahihinang bahagi. Kung pumalya ang isang check, maitatanong mo kung state check ba ito o tanong tungkol sa usapan. Kung mali ang mga threshold, mga numero ang mga ito na masusuri mo. Ang sariling pag-iingat ng papel na kailangang subukin ang mga probabilidad sa loob ng loop ang tamang instinct, at mas mabuting tindig ito kaysa ipagpalagay na gumagana ang isang verifier dahil mukhang makatwiran.

Kung tutuusin, nakapagpapanatag pa ang hindi pantay na mga resulta tungkol sa katapatan ng pag-uulat. Mas karapat-dapat pagdudahan ang framework na nag-aangkin ng pantay na pakinabang saanman kaysa sa isang nagpapakita ng walo sa walo sa Telecom, siyam sa siyam sa three-run success ng BFCL, halo-halong at-least-once na resulta sa BFCL, at pabagu-bagong epekto sa Airline. Nagbibigay ang pattern sa mga practitioner ng mapagpaplanuhan: pinakamalakas ang ebidensya para sa pagiging maaasahan sa paulit-ulit na run, at pinakamahina sa domain kung saan nag-iiba ang epekto ayon sa agent.

## Ano ang gagawin dito

Para sa mga teknikal na mambabasa, pang-arkitektura ang aral. Nananatiling hindi nagbabago ang LLM, base prompt at mga tool ng agent sa JevAct, kaya ang verification layer ay idinaragdag mo sa paligid ng agent at hindi itinuturo sa loob nito. Para sa mga founder, mas makitid ang praktikal na pagbasa kaysa sa headline. Nag-uulat ang papel ng mas mataas na pagiging maaasahan sa maraming model at benchmark, na mas halo-halo ang Airline, at sinusuri ng mga paghahambing nito ang buong harness at hindi ang judge nang mag-isa. Hindi napatutunayan ng mga pangunahing paghahambing kung aling bahagi ang nagdadala ng pagbuti, bagaman ipinahihiwatig ng Airline ablation ng papel na malaking bahagi nito ang galing sa programmatic verification sa setting na iyon.

Ang bukas na tanong ay ang sentral na tanong mismo ng papel: kung maaaring magsilbi ang isang decision model bilang probability-thresholded verifier kasama ng mga executable tool-state check, gayong, gaya ng sinasabi ng mga awtor, hindi garantisadong calibrated o tama ang mga probabilidad nito. Ang mga resulta sa Airline, kung saan mas maliit ang epekto at nag-iiba ayon sa agent, ang unang dapat tingnan. Kung ang pagkakaibang iyon ay nag-uugat sa mga check, sa mga threshold o sa mga patakarang kino-compile ay iniiwang bukas ng mga iniulat na resulta, at iyan ang eksperimentong pinakagusto kong makita sa susunod.

## Mga Madalas Itanong

**Ano ang JevAct?**
Ang JevAct ay isang runtime verification framework mula sa mga mananaliksik ng IBM na humaharang sa mga piling aksyon ng agent, partikular ang mga write call at hand-off, bago ang execution. Bumabalik sa agent ang na-flag na mungkahi na may tiyak na feedback at limitadong pagkakataong magrebisa. Nananatiling hindi nagbabago ang LLM, base prompt at mga tool ng agent.

**Ano ang ginagawa ng Kev sa JevAct?**
Ang Kev ay isang open-source na decision model na tulad ng Jev na sumasagot sa mga nakapirming tanong gamit ang mga probabilidad sa halip na nabuong teksto. Sa JevAct, sinasagot nito ang mga tanong na nakasalalay sa usapan, habang sinusuri ng code ang mga katotohanang makukuha sa mga tool record. Hindi pumipili ng aksyon ang Kev; ang agent pa rin ang nagmumungkahi ng mga ito.

**Paano sinuri ang JevAct?**
Inihahambing ng papel ang JevAct sa isang ReAct harness na gumagamit ng parehong agent LLM sa dalawang panig. Saklaw ng mga gawain ang Airline at Telecom sa τ²-bench at mga multi-turn function-calling task sa BFCL, at iniuulat ang tagumpay bilang at-least-once sa tatlong run at bilang tagumpay sa lahat ng tatlong run.

**Pinabuti ba ng JevAct ang bawat agent sa bawat benchmark?**
Hindi. Sa Telecom, bumuti ang lahat ng walong agent sa dalawang sukat, at sa BFCL bumuti ang lahat ng siyam sa three-run success habang halo-halo ang at-least-once na resulta. Mas maliit ang epekto sa Airline at nag-iba ayon sa agent, at sinasabi ng mga awtor na hindi napatutunayan ng mga natuklasan ang pantay na pakinabang.

**Ipinakikita ba ng papel na ang decision model lang ang nagdadala ng pakinabang?**
Hindi. Dahil nagdaragdag ang JevAct ng mga compiled check at pagkakataong magrebisa, sinusuri ng mga pangunahing paghahambing ang buong harness, hindi ang judge nang mag-isa. Binabanggit din ng mga awtor na hindi garantisadong calibrated o tama ang mga probabilidad ng decision model.
