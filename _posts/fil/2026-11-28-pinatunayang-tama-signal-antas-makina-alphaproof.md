## Bakit mahalaga ang resultang ito sa mga naglalabas ng cryptographic software

Inilalarawan ang Signal bilang de facto na pandaigdigang pamantayan para sa end-to-end encrypted messaging, at may mga bersyon ng protocol na naka-deploy sa WhatsApp, sa Messenger app ng Meta at sa Google Messages. Kapag nasa ilalim ng ganoon karaming usapan ang isang protocol, hindi na akademikong isyu ang agwat sa pagitan ng disenyong napatunayang ligtas sa papel at ng compiled code na talagang tumatakbo. Maaaring walang mali ang proof sa papel habang ibang-iba ang ginagawa ng implementation.

Ang agwat na iyan ang tinutugunan ng gawaing ito. Ibinibigay ng mga may-akda ang mga unang proof ng security property sa antas ng protocol para sa isang malawakang naka-deploy at hindi binagong implementation ng cryptographic protocol. Basahin ulit ang pangungusap na iyan, dahil may silbi ang bawat qualifier. Ang "antas ng protocol" ay nangangahulugang tinutugunan ng mga proof ang mga katangian gaya ng forward secrecy, hindi lang ang kawalan ng memory errors. Ang "malawakang naka-deploy" ay nangangahulugang libsignal, hindi research prototype. Ang "hindi binago" ay nangangahulugang walang sumulat muli ng code sa hugis na mas madali para sa prover.

Para sa mga founder, gastos ang praktikal na pagbasa. Inilalahad ng mga may-akda ang formal verification bilang alternatibo sa reaktibong paghahanap ng bug: tinutukoy mo ang correctness at security properties na dapat ipatupad ng isang software system, saka mo patutunayan sa matematika na natutugunan ito ng system. Inilalarawan nila ito bilang dati ay masyadong magastos para sa karamihan ng software. Ipinahihiwatig ng resulta ng mga may-akda na kayang gawin itong praktikal ng AI para sa totoong mga system. May pasubali ang claim na iyan, at ganoon ko ito ituturing: isang mungkahing sinusuportahan ng isang malaking case study, hindi isang tiyak na resulta sa ekonomiya. Gayunman, mas mabigat na ebidensya ang isang case study na ganito kalaki kaysa sa nakukuha ng karamihan ng claim sa larangang ito.

## Mas mahirap ang verification kaysa sa inaakala

Itinuturo ng source material ng framework ang isang kilalang benchmark kung gaano kahirap ang verification: ang verified C compiler na CompCert, na inabot ng anim na person-year bago na-verify, ayon sa bilang na iniulat dito. Mag-ingat sa bilang na iyan, dahil ang parenthetical tungkol sa person-years ay pagkakabuo ng source at hindi direktang sipi. Nananatili pa rin ang punto: ilang taon ng pangako ang pag-verify ng seryosong software.

Sinasabing mas mahirap pa ang pag-verify ng umiiral na industrial-strength code, dahil hindi mababago ng prover ang code para mapadali ang proof. Ganito mismo ang kaso ng isang production library na kinompile ng optimising compiler. Kung malaya kang baguhin ang istruktura ng programa, mahuhubog mo ito para natural na lumabas ang proof. Kung kailangan mong tanggapin ang code kung ano ito, mamanahin mo ang bawat hindi komportableng idiom at bawat desisyon ng compiler.

Sadyang pinipili ng AlphaProof Code ang mas mahirap na daan. Kinokompile ang hindi binagong Rust code gamit ang karaniwang compiler, at ikinakarga sa Lean ang executable kasama ang semantics ng AArch64. Sa konkreto, iniuugnay ng mga may-akda ang libsignal sa isang maliit na command-line harness at kinokompile ito gamit ang karaniwang rustc compiler tungo sa AArch64 Linux machine code. Ang machine code ang pinatutunayan. Mas matibay na target iyan kaysa sa pangangatwiran sa antas ng source, dahil hindi na kailangang pagkatiwalaan ang compiler na mapapanatili nito ang mga katangiang naipakita mo.

## Paano hinahati ng framework ang trabaho

Ang AlphaProof Code ay isang framework para sa pagtutulungan ng tao at AI sa formal specification at verification ng totoong software. Nakasandig ito sa isang prinsipyong kapani-paniwala sa akin: nasa pagbuo ng specification na ngayon ang karamihan ng pagsisikap ng tao sa software verification. Ang pagsulat ng proof, ang bahaging dati ay umuubos ng ilang taon ng mga espesyalista, ay lalong nagagawa na ng mga makina.

Ikinakatwiran ng mga may-akda, batay sa sarili nilang resulta, na kahit malalaking proof tungkol sa software ay kayang isulat ng mga team ng AI agents kapag naitakda na ang specification, at na kayang magtrabaho nang awtonomo ang proof agents dahil sinusuri ng kernel ng Lean ang bawat proof sa huli. Hinahati ng framework nila ang trabaho sa dalawa. Magkasamang sumusulat ang isang taong user at ang AI agents ng Lean specifications ng totoong code, at kapag nasuri na ng user ang isang specification, isang team ng autonomous agents ang nagpapatunay na natutugunan ito ng code. Malinaw ang mga may-akda na para sa malalaki at masalimuot na system, kayang bawasan ng tulong ng AI ang gastos ng pagsulat ng specification at assurance, pero hindi nito lubusang mapapalitan ang paghuhusga at pagsusuri ng tao.

Hindi basta pagtatatak ang yugto ng specification. Isang grupo ng reviewer agents ang sumusuri kung tapat ang isang draft sa mga source nito at sa implementation. Sa proseso ng mga may-akda, sinusuri, binabago at inaaprubahan ng user ang specification bago isulat ang anumang proof, at ang git commit nito ang nagiging baseline na pagbabatayan ng gatekeeper sa pagsuri ng mga proof. Iniuulat nila na maaaring umabot ng maraming ikot ng iteration sa pagitan ng user at ng agents bago makabuo ng mahusay na specification, kahit may umiiral nang modelo sa literatura; para sa Signal, ilang ikot ng draft at review ang kinailangan para pagsamahin ang mga naunang modelo ng handshake at ratchet at masaklaw ang bagong post-quantum ratchet. Dapat ayusin ang inaasahan ng sinumang umaasang makakabuo ng mapagkakatiwalaang specification ang iisang prompt.

Nagmumungkahi ang mga may-akda ng paghahati ng responsibilidad: pinipili ng mga taong may-akda kung ano ang patutunayan, nilulutas ang mga kalabuan, tinitimbang ang security trade-offs at gumagawa ng lahat ng huling desisyon, habang nagda-draft at sumusubok ng specifications ang AI agents sa ilalim ng direksyon ng tao. Tama ang paninindigang ito para sa akin. Ibinibigay nito ang paghuhusga sa panig na maaaring managot dito.

Lahat ng agents sa AlphaProof Code, kasama ang specification writer, ay general-purpose coding agents na ang pag-uugali ay itinatakda ng skills, mga dokumentong nakasulat sa natural na wika. Walang inilalarawang espesyal na prover architecture dito. Ginagabayan ng mga dokumentong prosa ang pag-uugali, kaya medyo madaling suriin at ayusin ang system.

## Saan talaga nakalagay ang tiwala

Ang pinakamahalagang desisyon sa disenyo ng framework ay kung ano ang ayaw nitong pagkatiwalaan. Hindi pinagkakatiwalaan ang multi-milyong linyang proof na gawa ng AI agents, dahil tinatanggihan ng kernel ng Lean ang anumang lohikal na mali sa isang proof. Sa ibang salita, dahil sa huli ay sinusuri ng kernel ng Lean ang proof, hindi nakasalalay ang pagiging maaasahan ng mga resulta sa pagiging maaasahan ng proving agents.

Mahalaga ito dahil, gaya ng sinabi ng mga may-akda, hindi nakasalalay ang pagiging maaasahan ng mga resulta sa pagiging maaasahan ng proving agents: sa huli ay sinusuri ng kernel ng Lean ang proof. Ayon sa papel, tinatanggap lang ng gatekeeper agent ang isang proof kung nasuri ito ng kernel ng Lean at kinumpirma ng Lean comparator na eksaktong pinatutunayan nito ang isang nakatabing kopya ng specification. Dalawang kondisyon, kung gayon. Dapat balido ang proof, at dapat ito ay proof ng tamang pahayag. Ang ikalawang kondisyon ay idinisenyo laban sa isang tusong pagkabigo: isang agent na binabago ang pahayag at nagpapatunay ng mas madali kaysa sa hiniling. Sinusuri ng comparator na kapareho ng nakatabing kopya ang pahayag at bawat definition na inaasahan nito, at na tanging standard axioms ng Lean ang ginagamit ng proof.

Kaya maliit ang trusted base kung ihahambing sa mismong proof. Humigit-kumulang 27,000 linya ng pinagkakatiwalaang specifications at AArch64 semantics ang sumusuporta sa humigit-kumulang 6.3 milyong linya ng proof. May hangganan ang atensyon ng isang reviewer, at sinasabi ng ratio na ito kung saan ito dapat gamitin.

Pero ang specification ang mahinang bahagi, at tahasan itong sinasabi ng mga may-akda. Ang isang specification sa AlphaProof Code ay binubuo ng isang hanay ng Lean theorem statements kasama ang bawat definition na inaasahan ng mga ito. Kailangan itong pagkatiwalaan at hindi ito masusuri nang awtomatiko, at maaaring pahinain ng isang depekto ang garantiyang ibinibigay ng theorem. Ang isang theorem na gumagawa ng labis na mahigpit na assumptions sa inputs, nagsasaad lang ng mahihinang katangian ng output, o naglalagay ng masyadong kaunting constraints sa mga existentially quantified witness ay maaaring tumayo kahit para sa may-bug na code. Kung pinahihina ng mali sa specification ang kakayahan ng attacker, humihina rin ang security guarantee.

Maaari ring magsama ang mga definition ng extern contracts na nagtatakda ng mga assumption tungkol sa mga bahagi ng system na labas sa saklaw ng verification campaign. Tapat na hangganan ang mga iyon, pero hangganan pa rin: anumang nasa likod ng isang extern contract ay ipinagpapalagay, hindi pinatutunayan.

Kaya ang headline na bilang, 6.3 milyong linya, ang pinakamaliit ang halaga sa pagtimbang kung dapat mong pagkatiwalaan ang resulta. Ang 27,000 linya ang dapat basahin.

## Ano ang napatunayan tungkol sa Signal

Saklaw ng mga proof ang post-quantum na PQXDH handshake at Triple Ratchet ng Signal, at itinatatag ng mga ito ang forward secrecy, authentication, post-compromise security at handshake secrecy. Idinisenyo ang PQXDH handshake at ang Triple Ratchet para matiyak ang seguridad ng mga mensahe kahit nakompromiso ang ilan sa mga key, at kahit laban sa mga adversary sa hinaharap na may access sa quantum computer.

Dalawang klasikong tradisyon ng modelling ang humuhubog sa kahulugan ng "seguridad" dito. Ang symbolic model, kilala rin bilang Dolev–Yao model, ay itinuturing ang cryptographic primitives bilang abstraktong "black boxes" na may standard security properties. Nililimitahan naman ng computational model ang tsansa ng tagumpay ng isang efficient attacker batay sa hirap ng mga pinagbabatayang primitive. Sinasabi ng computational security proof na may umiiral na reduction mula sa isang atake sa protocol tungo sa paglabag sa isang pinagbabatayang assumption.

Magkaiba ang garantiyang ibinibigay ng dalawang modelo, at hinati ang mga resulta nang naaayon. Itinatatag ng mga proof na isinulat ng agents ang forward secrecy, post-compromise security, at confidentiality at authenticity ng mensahe nang direkta para sa compiled binary laban sa mga classical attacker. Sa symbolic model, itinatatag nila ang handshake secrecy laban sa isang quantum attacker sa hinaharap. Dapat panghawakan ng maingat na mambabasa ang pagkakaibang iyan. Nakasaad sa symbolic model ang resulta laban sa quantum adversary, at ang mga resulta laban sa classical attacker ang nakasaad nang direkta para sa compiled binary.

May ikalawang komplikasyon na nagpapaliwanag kung bakit mahirap ang trabaho sa specification. Hiwalay na sinusuri ng mga umiiral na specification ang handshake at ang ratchet, at mas nauna ang mga ito sa post-quantum ratchet ng Signal; magkahiwalay na sinuri ng mga naunang formal model ng Signal ang paunang handshake at ang ratchet nito. Kailangan ng isang proof tungkol sa protocol na talagang naka-deploy ang dalawa nang magkasama, kasama ang post-quantum ratchet. Sa gabay ng tao, pinalalawak ng agents ang mga umiiral na specification tungo sa protocol gaya ng pagkaka-deploy nito. Magandang halimbawa ito ng collaboration model sa praktika: nagbibigay ang literatura ng panimulang punto, gumagabay ang tao, at ang agents ang gumagawa ng pagpapalawak.

Sinasabi rin ng mga may-akda na ipinapakita ng kanilang gawa na kayang i-verify ng AI ang machine code laban sa mayayamang specification mula sa research literature, kasama ang mga katangian ng interaksyon sa pagitan ng isang stateful program at isang adaptive adversary. Kapansin-pansing uri iyan ng katangian. Ang isang stateful program na humaharap sa isang adaptive adversary ay eksaktong sitwasyon ng isang messaging client.

Inaangkin ng mga may-akda na sila ang nauna: sa kanilang salita, ito ang mga unang proof na nag-uugnay ng mga security guarantee sa antas ng protocol sa hindi binagong code ng isang malawakang ginagamit na implementation ng cryptographic protocol. Sarili nilang claim ito, hindi isang malayang natuklasan, at ganoon ko ito iniuulat. Inilalarawan nila ang mga resulta bilang mahalagang milestone tungo sa isang grand challenge na inilunsad noong Abril 2026.

## Nahuhuli ba ng specifications ang totoong mga mali?

Walang silbi ang isang specification na hindi kayang paghiwalayin ang tamang code at sirang code, at lalong walang halaga ang isang proof laban dito. Direktang sinubok ito ng mga may-akda. Ibinalik nila ang dalawang dating naayos na bug ng libsignal at bumuo ng suite ng 17 synthetic mutant para suriin kung nahuhuli ng specifications ang totoong mga mali.

Ang kinalabasan, ayon sa ulat ng mga may-akda: para sa dalawang makasaysayang bug at, sa ngayon, sa 16 sa 17 synthetic mutant, pinatutunayan ng Lean na ang isang naitalang trace (tig-isang witness trace) ay hindi maipaliliwanag ng symbolic specification sa ilalim ng isang konkretong interpretasyon ng primitives na tumutugma sa naitalang run. Ang buong binary refutations ng dalawang makasaysayang bug ay sinuri ng kernel laban lang sa isang naunang (36-hook) untrusted placed variant ng pahayag; bukas pa ang paglilipat ng mga ito sa trusted statement ng pangunahing theorem.

Gusto kong maging tiyak kung ano ang sinasabi at hindi sinasabi nito. Ang labing-anim sa labimpito ay hindi labimpito sa labimpito, at walang paliwanag ang case study tungkol sa natitirang mutant, kaya hindi ako manghuhula tungkol dito. Pansinin din ang pasubali sa mga makasaysayang bug: sinuri ang buong binary refutations laban sa isang naunang untrusted placed variant ng pahayag na may 36 hook, hindi kinakailangang ang huling bersyon. Detalyeng dapat malaman iyan bago banggitin ng sinuman ang resulta bilang ganap na tagumpay.

Gayunman, ito ang tamang uri ng pagsubok. Inaatake nito ang specification, kung saan sinasabi ng framework na naroon ang natitirang panganib, sa halip na ipagmalaki ang dami ng proof. Mura ang mutation testing ng isang specification kumpara sa verification campaign, at sinasagot nito ang tanong na hindi kayang sagutin ng anumang dami ng proof na sinuri ng kernel: mapapansin kaya ng pahayag na ito ang isang totoong bug?

## Ang kahulugan nito sa praktika

Kasinghalaga ng milestone ang mga limitasyon. Para sa malalaki at masalimuot na system, kayang bawasan ng tulong ng AI ang gastos ng pagsulat ng specification at assurance, pero hindi nito lubusang mapapalitan ang paghuhusga at pagsusuri ng tao. Walang ibang sinasabi ang mga may-akda. Nagbabago ang ekonomiya, pero hindi ito bumabagsak sa zero, at ang bahaging nananatiling gawa ng tao ang nagpapasya kung may kahulugan ang garantiya.

Sa tingin ko tama ang paghahating iyan, at nagmumungkahi ito ng makatwirang paraan para basahin ng isang team ang gawaing ito. Huwag itanong kung kayang sumulat ng proof ng agents; sinasagot na iyan ng resulta sa libsignal, na humigit-kumulang 6.3 milyong linya. Itanong kung sino sa team mo ang kayang sumulat at sumuri ng specification na tulad ng inilalarawan dito: Lean theorem statements kasama ang bawat definition na inaasahan ng mga ito, na may extern contracts na nagmamarka kung ano ang ipinagpapalagay. Ang taong iyon, at ang proseso ng review sa paligid ng trabaho niya, ang kakaunting resource.

May aral din sa disenyo kung paano tinatrato ng system ang mga hindi maaasahang bahagi. Hindi nito sinusubukang gawing mapagkakatiwalaan ang agents. Ginagawa nitong walang epekto sa resulta ang pagiging mapagkakatiwalaan nila sa pamamagitan ng pagdaan ng lahat sa isang maliit at nakapirming checker. Maaaring itanong ng mga team na bumubuo ng agentic systems sa ibang larangan ang parehong tanong sa sarili nilang pipelines: ano ang katumbas ng kernel ng Lean, at tamang pahayag ba ang sinusuri ng gatekeeper?

Para sa mga mambabasang labas sa cryptography, ang hugis ng workflow ang maaaring gamitin sa ibang konteksto, hindi ang partikular na protocol. Sa disenyo ng mga may-akda, magkasamang nagda-draft ng specification ang tao at agents, sinusuri ng reviewer agents kung tapat ito, inaaprubahan ito ng tao, pinipirmi ito ng isang commit bilang baseline, pinatutunayan ito ng autonomous agents, at sinusuri ng isang gatekeeper kung balido ang bawat proof at kung eksaktong pinatutunayan nito ang inaprubahang pahayag. Iba-ibang failure mode ang tinutugunan ng bawat yugto.

Hindi dapat palakihin ang alinman dito. May pasubali sa source ang mungkahing ginagawang praktikal ng AI ang verification para sa totoong mga system, at ang iisang flagship case, gaano man kahanga-hanga, ay iisang kaso lang. Nananatiling pinagkakatiwalaang artefact ang specification na walang tool na sumusuri para sa iyo. At ang garantiya laban sa quantum adversary ay resulta sa symbolic model para sa handshake secrecy, hindi computational.

Ang bukas na tanong na itinataas ng case study ay ang itinuturo mismo ng mga may-akda nang tawagin nila itong milestone tungo sa isang grand challenge na inilunsad noong Abril 2026: kung mura na ang pagsulat ng proof kapag may specification na, ang specification engineering na ba ang susunod na bottleneck na dapat tugunan? Ipinahihiwatig ng mga resulta ng mutation na masusubok ang specification, at ipinahihiwatig ng natuklasang "maraming ikot ng iteration" na mabagal pa rin ito. Gaano kalaki sa kabagalang iyan ang kayang akuin ng agents, habang nananatili sa tao ang mga huling desisyon? Iyan ang bilang na dapat bantayan sa susunod na case study.

## Mga Madalas Itanong

**Ano ang AlphaProof Code?**
Isang framework mula sa Google DeepMind at Google para sa pagtutulungan ng tao at AI sa formal specification at verification ng totoong software. Magkasamang sumusulat ng Lean specifications ang isang taong user at ang AI agents; kapag nasuri na ng user ang isang specification, isang team ng autonomous agents ang nagpapatunay na natutugunan ito ng code.

**Ano mismo ang na-verify sa libsignal?**
Ang hindi binagong Rust code ng libsignal, kinompile gamit ang karaniwang rustc compiler tungo sa AArch64 Linux machine code. Saklaw ng mga proof ang forward secrecy, authentication, post-compromise security at handshake secrecy para sa post-quantum na PQXDH handshake at Triple Ratchet ng Signal.

**Bakit hindi kailangang pagkatiwalaan ang AI agents?**
Sinusuri ng kernel ng Lean ang bawat proof, at tinatanggap lang ng gatekeeper ang isang proof kung kinumpirma ng Lean comparator na eksaktong pinatutunayan nito ang isang nakatabing kopya ng inaprubahang specification. Tinatanggihan ang lohikal na mali, at gayundin ang proof ng mas madaling pahayag.

**Ano pa ang kailangang pagkatiwalaan?**
Humigit-kumulang 27,000 linya ng specifications at AArch64 semantics, kasama ang anumang extern contracts na naglalarawan ng mga bahagi ng system na labas sa campaign. Hindi masusuri nang awtomatiko ang specification, at pinahihina ng isang depekto rito ang garantiyang ibinibigay ng theorem.

**Pinatutunayan ba ng gawa ang seguridad laban sa quantum attackers?**
Bahagya. Itinatatag sa symbolic model ang handshake secrecy laban sa isang quantum attacker sa hinaharap. Ang forward secrecy, post-compromise security, at confidentiality at authenticity ng mensahe ay itinatatag nang direkta para sa compiled binary laban sa mga classical attacker.
