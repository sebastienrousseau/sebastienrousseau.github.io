# Composite ML-DSA: Post-Quantum Hybrid Bilang Iisang Algorithm

**Ang pinakamatibay na ideya sa Standards Track RFC na ito: hindi kailangang baguhin ng post-quantum hybrid ang iyong protocol. Sa pagpapakita ng iisang public key at iisang signature value, hinahayaan ng Composite ML-DSA na ang umiiral na cryptographic agility mechanisms ang gumawa ng trabaho, habang ang sadyang malaking menu ng mga kombinasyon ay para sa mga regulator, hindi sa mga implementer.**

## Bakit pa kailangan ng hybrid signature

Ang dokumento ay RFC 10073, *Composite Module-Lattice-Based Digital Signature Algorithm (ML-DSA) for Use in X.509 Public Key Infrastructure*, na inilathala ng IETF noong Nobyembre 2026 at isinulat nina M. Ounsworth, J. Gray, M. Pala, J. Klaußner at S. Fluhrer.

Nagsisimula ang RFC sa premisang sinasabi nito nang walang pasubali: magiging bulnerable sa quantum attacks ang mga tradisyonal na signature algorithm gaya ng RSA, DSA at ang kanilang elliptic curve variants. Inilalarawan nito ang sitwasyon bilang usapin lang ng oras. Ayon dito, masisira ang mga tradisyonal na algorithm sa hinaharap pero mananatiling matibay sa pansamantala, at ang tanging hindi tiyak ay kung kailan.

Mahalaga ang balangkas na iyon dahil isinasara nito ang tamad na pagbasa sa problema. Kung tiyak ang pagkasira at petsa lang ang hindi alam, hindi neutral na pagpili ang maghintay. Pero kasing-prangka rin ang dokumento sa gastos ng maagang paglipat. Maaaring mangailangan ang agresibong migration timelines ng pag-deploy ng post-quantum cryptography (PQC) algorithms bago lubusang napatibay o na-certify ang kanilang mga implementasyon. May pasubali rito ang RFC, at dapat ganoon din tayo: "may" ang sinasabi nito, hindi "will".

Pagtabihin ang dalawang presyong iyon at lilitaw ang katwiran para sa hybrid. Gusto mo ng proteksiyon laban sa quantum na hinaharap, pero bata pa ang mga bagong algorithm at ang kanilang mga implementasyon. Sinasabi ng RFC na maaaring kanais-nais ang dual-algorithm data protection sa mas mahabang panahon, bilang panangga laban sa mga security vulnerability at iba pang depekto sa mga bagong implementasyon. Muli, may kondisyon ang pananalita. Nagmumungkahi ang dokumento ng katwiran; hindi nito sinasabing napatunayan nitong laging tama ang hybrid.

Dapat malinaw kung ano ang naibibigay ng composite. May natitirang seguridad ang mga composite algorithm kahit masira ang isa sa kanilang component algorithm. "Some security" ang parirala, hindi buong seguridad, at hindi ito pinalalabis ng RFC. Ang praktikal na pagbasa: hindi awtomatikong mauuwi sa wala ang pagbigay ng isang component.

## Ang dokumento at ang mga may-akda nito

Bago pumunta sa mekanika, sulit ang isang talata sa pinagmulan, dahil dapat alam ng mga founder at engineer na tumitimbang ng isang standard kung anong klase ng standard ito. Nasa stream ng Internet Engineering Task Force (IETF) ang RFC at Standards Track ang kategorya nito. Inilathala ito noong Nobyembre 2026 at may ISSN 2070-1721. Inilalarawan ito ng boilerplate bilang Internet Standards Track document: produkto ng IETF na kumakatawan sa consensus ng IETF community at inaprubahan para ilathala ng IESG.

Sumasaklaw ang listahan ng may-akda sa apat na organisasyon. Nakalista sina M. Ounsworth at J. Gray mula sa Entrust, si M. Pala mula sa OpenCA Labs, si J. Klaußner mula sa Bundesdruckerei GmbH at si S. Fluhrer mula sa Cisco Systems. Hindi ako magbabasa ng higit pa sa komposisyong iyon kaysa sa sinusuportahan ng dokumento. Ang ipinapakita ng listahan ay hindi ito artefact ng iisang vendor.

Sinasabi rin ng dokumento sa mga mambabasa kung paano basahin ang normative language nito. Ang mga key word gaya ng "MUST" at "SHOULD" ay dapat ipakahulugan ayon sa BCP 14 (RFC 2119 at RFC 8174) kapag, at kapag lamang, nakasulat ang mga ito sa malalaking titik. Karaniwang praktika ito, pero ito ang dahilan kung bakit walang espesyal na bigat ang maliit na titik na "should" sa espesipikasyong ito. Tugma rin ang espesipikasyon sa terminolohiyang tinukoy sa RFC 9794.

## Isang public key, isang signature value

Madaling sabihin ang sentral na desisyon sa disenyo. Iisang public key at signature value ang ipinapakita ng composite algorithm, kaya maaari itong ituring na iisang atomic algorithm sa antas ng protocol.

Mas matapang na pagpili ito kaysa sa unang tingin, at sa tingin ko ito ang tama. Direktang ipinapaliwanag ng RFC ang kaibahan: maraming PQ/T hybrid ang nangangailangan ng pagbabago sa protocol para gawin itong "hybrid aware", samantalang ipinapakita ng espesipikasyong ito ang hybrid bilang standalone algorithm at kaya nitong samantalahin ang umiiral na cryptographic agility mechanisms.

Isipin kung ano ang ibig sabihin nito sa sinumang kailangang mag-ship. Ang hybrid na kailangang maunawaan ng protocol ay hybrid na sumasagi sa bawat protocol na gustong gumamit nito. Ang hybrid na mukhang ordinaryong algorithm ay sumisingit sa anumang negotiation o algorithm-identification machinery na umiiral na. Sa kontekstong ito, tinutukoy ng RFC ang "algorithm" bilang karaniwang tumutukoy sa anumang function na may rehistradong Object Identifier (OID) para gamitin sa loob ng ASN.1 AlgorithmIdentifier. May sariling pagkakakilanlan ang composite sa scheme na iyon, at tinatrato ito ng nakapaligid na sistema gaya ng alinmang iba.

May kaugnay na punto sa bokabularyo na naglilinaw kung ano ang inaangkin at hindi inaangkin ng RFC. Tinutukoy nito ang Protocol Backwards Compatibility bilang property kung saan maaaring idagdag ang bagong feature sa isang protocol nang hindi kailangang baguhin ang espesipikasyon ng protocol at kaunting pagbabago lang sa mga implementasyon nito. Direktang tinututukan ng atomic-algorithm approach ang ganitong uri ng mababang-alitan na pagdaragdag. Inilalarawan ito ng RFC bilang layunin ng disenyo: dapat kayang tratuhin ng mga protocol gaya ng PKCS #10, CMP, X.509, CMS at Trust Anchor Format ang mga composite algorithm gaya ng alinmang ibang algorithm, nang hindi kailangan ng protocol layer ng anumang "hybrid awareness".

## Ano ang laman ng composite

Ang post-quantum na kalahati ay ML-DSA, ang Module-Lattice-Based Digital Signature Algorithm na tinukoy sa FIPS 204. Ginagamit ito ng espesipikasyon bilang Post-Quantum component ng mga PQ/T hybrid nito. Kinukuha ang tradisyonal na kalahati mula sa isang tinukoy na set. Ibinibigay ang mga instantiation ng Composite ML-DSA scheme batay sa ML-DSA, RSASSA-PSS, RSASSA-PKCS1-v1_5, ECDSA, Ed25519 at Ed448.

Tinitiyak ng seksiyon ng terminolohiya ang bawat tradisyonal na component. Lumalabas ang RSA bilang Probabilistic Signature Scheme, RSASSA-PSS, na tinukoy sa RFC 8017. Ang ECDSA ay ang Elliptic Curve Digital Signature Algorithm na tinukoy sa FIPS 186-5. Ang EdDSA ay ang Edwards-curve Digital Signature Algorithm na tinukoy sa RFC 8410, na may dalawang parameter set: Ed25519 at Ed448. Ginagamit ang Public Key Infrastructure (PKI) ayon sa RFC 5280, at ang DER ay Distinguished Encoding Rules ayon sa X.690.

Nagbibigay ang dokumento ng maliit na halimbawa ng itinuturing na composite cryptographic element. Ang mga halimbawa nito ay mga asymmetric algorithm gaya ng "ML-DSA-65" o "RSASSA-PSS". At malawak ang gamit ng "signature": isang digital cryptographic signature, nang walang palagay kung aling algorithm.

Hindi tinatalakay ng artikulong ito ang panloob na konstruksiyon ng composite signature, na tinutukoy ng RFC sa sarili nitong mga seksiyon sa key generation, signing, verification at serialisation. Ang mahalaga rito: ang hugis na nakikita mula sa labas, isang key at isang signature, ang property na pinagbabatayan ng natitirang disenyo.

## Bakit napakaraming kombinasyon

Kung susuriin mo ang listahan ng component algorithm at magtataka kung bakit napakaraming pares ang tinutukoy ng isang espesipikasyon, diretsong sumasagot ang RFC. Ang paglilingkod sa regulatory re-certification use case, higit sa alinmang ibang design requirement, ang nagtutulak sa malaking bilang ng algorithm combinations sa espesipikasyong ito. Idinadagdag nito na iniangkop ang mga kombinasyon para matugunan ang regulatory guidelines sa ilang rehiyon.

May pasubali pero kongkreto ang katwiran sa likod ng use case. Sa ilang sitwasyon, maaaring mas madaling i-re-certify ang isang umiiral na produkto sa pamamagitan ng pagdaragdag ng Post-Quantum gamit ang PQ/T hybrid sa isang compliant na solusyon nang hindi binabago ang tradisyonal na component, kaysa palitan ang tradisyonal na component. Sa madaling salita, maaaring mas gusto ng vendor na may certified na tradisyonal na algorithm na huwag itong galawin at ikabit na lang ang post-quantum na kalahati sa tabi nito. Gumagana lang ang ganitong kagustuhan kung may pares ang espesipikasyon para sa anumang tradisyonal na algorithm na gamit na ng produkto. Kaya malawak.

Kumbinsido ako sa paninindigang ito sa disenyo, at kapaki-pakinabang itong pagtutuwid sa likas na hilig na dapat minimal ang isang standard. Mas malinis ang maikling listahan, pero pipilitin nito ang ilang produkto na palitan ang isang certified na component, na siyang mismong gastos na iniiwasan ng mga kombinasyon. Ang mahabang listahan ang presyo ng pagsalubong sa mga regulated na produkto kung nasaan na sila.

Maingat din ang RFC na pigilang maging pasanin sa mambabasa ang lawak na iyon. Inaasahang pipili ang mga organisasyon na mag-deploy ng iisang composite algorithm, o iilan lang, at napakakaunting implementer ang kailangang mag-alala sa buong listahan. Pansinin ang pasubali: "expected". Hula ito tungkol sa gawi ng deployment, hindi requirement. Pero sinasabi nito kung paano basahin ang dokumento. Hindi mo kailangang i-implement ang lahat; ang kailangan mo ay hanapin ang iyong pares.

## Ang iniiwan ng espesipikasyon

Malinaw ang isang mahusay na standard sa mga gilid nito, at ganoon ang isang ito. Apat na limitasyon ang namumukod.

Una, hindi tinutukoy ng espesipikasyon ang anumang mandatory-to-implement algorithm. Kasama ng inaasahang pagpili ng mga organisasyon ng isa o iilang composite, ibig sabihin nito ay nakadepende ang interoperability ng dalawang partido sa pagpili nila ng magkatugmang kombinasyon. Hindi nagtatalaga ang RFC ng default na dapat suportahan ng lahat, at nagbababala ito na maaaring hatiin ng dami ng kombinasyon ang ecosystem sa mga subgroup na hindi interoperable kapag pumili ang iba't ibang komunidad ng mga subset na hindi nagsasanib. Hinihikayat nito ang mga organisasyon sa partikular na application domain na tumukoy ng mga profile na pumipili ng kaunting composite. Ito ang ituturo ko bilang pinakapraktikal na kahihinatnan para sa isang team na nagpaplano ng rollout: kailangan mong pagkasunduan ang iyong pares sa iyong mga counterparty sa halip na ipagpalagay ito.

Ikalawa, hindi ibinibigay ang backwards compatibility sa kahulugan ng patuloy na interoperability ng mga upgraded system sa mga legacy system. Sulit itong ihiwalay sa punto sa antas ng protocol sa itaas. Tinutukoy ng RFC ang Application Backwards Compatibility bilang property na nagsasaad kung matagumpay na makakapagtatag ng komunikasyon ang isang upgraded at isang hindi upgraded na application. Tahasan ang Section 10.3: hindi nagbibigay ng application backwards compatibility ang mga mekanismo sa dokumento, mga upgraded system lang ang makakaunawa sa mga OID na tinutukoy nito, at kakailanganin ng karagdagang mekanismo kung saan kailangan ang property na iyon. Nakakatulong ang atomic-algorithm na disenyo sa mga pagbabago sa protocol, pero hindi nito inaangking nalulutas kung makakausap ng isang upgraded na application ang hindi pa na-upgrade.

Ikatlo, may limitasyon sa security property. Angkop ang Composite ML-DSA kung katanggap-tanggap ang signature primitive na may mas mahinang EUF-CMA property sa halip na ang mas matibay na Strong Unforgeability under Chosen Message Attack (SUF-CMA) property, na hindi iniaalok ng Composite ML-DSA. Kung nakadepende ang iyong application sa SUF-CMA, hindi akma ang scheme na ito ayon sa espesipikasyon. Malinis at nasusuring hangganan ito, at dapat itong ihambing ng isang founder na sumusuri sa scheme sa sarili niyang mga requirement bago magpatuloy.

Ikaapat, at mas katamtaman, inaamin ng dokumento na may panganib din ang presyon ng timeline, gaya ng tinalakay kanina: maaaring ma-deploy ang mga PQC implementation bago sila lubusang napatibay o na-certify. Mitigasyon ng panganib na iyon ang composite, hindi pag-aalis nito.

## Pagbasa sa notasyon

Gugugol ng oras ang mga implementer sa mga paglalarawan ng algorithm, kaya kapaki-pakinabang ang isang tala sa kanilang mga kumbensiyon. Gumagamit ang mga paglalarawan ng algorithm ng Python-like na syntax. Ang simbolong || ay kumakatawan sa concatenation ng dalawang byte array, at ang notasyong [:] ay kumakatawan sa byte array slicing.

Para sa mga function na nagbabalik ng ilang value, gumagamit ang dokumento ng (a, b) para kumatawan sa isang pares ng value, karaniwang nagpapahiwatig na nagbabalik ang function ng maraming value, at iniiwan sa implementer ang eksaktong mekanismo ng paghahatid (tuple, struct, output parameters, atbp.). Sinadyang kalayaan ang huling sugnay na iyon: ang mahalaga sa espesipikasyon ay kung ano ang ibinabalik, hindi kung paano ito binabalot ng iyong wika. Ang notasyong (a, _) ay kumakatawan sa pares kung saan binabalewala ang isang value, ang ikalawa sa kasong ito.

Ganoon din ang pattern ng mga function signature. Ang notasyong func(a) -> b ay kumakatawan sa function na nagngangalang func na tumatanggap ng a bilang input at naglalabas ng b. At ang Func<TYPE>() ay kumakatawan sa function na naka-parameterise sa <TYPE>, ibig sabihin ay may maliliit na pagkakaiba ang implementasyon nito depende sa pinagbabatayang TYPE. Ang huling kumbensiyong ito ang nagpapahintulot sa iisang paglalarawan na sumaklaw sa ilang pinagbabatayang algorithm nang hindi inuulit para sa bawat isa, na akma sa espesipikasyong sumasaklaw sa mga variant ng RSA, ECDSA at EdDSA kasama ng ML-DSA.

Walang kinang ang alinman dito, pero ito ang bahagi ng dokumentong talagang bukas sa harap mo habang nagsusulat ng code, at makatwirang konsesyon sa iba't ibang wikang ginagamit ang desisyong iwan sa implementer ang mekanismo ng maramihang pagbabalik.

## Saan nito iniiwan ang team na nagpaplano ng migration

Kung pagsasamahin ang mga piyesang ito sa isang balangkas ng desisyon, tatlong kapaki-pakinabang na bagay ang ibinibigay ng RFC at dalawa ang hinihingi nitong ikaw ang magbigay.

Ang ibinibigay nito ay katwiran, hugis at hangganan. Ang katwiran ay ang pares ng presyong nailarawan na: babagsak sa quantum attacks ang mga tradisyonal na algorithm sa hindi tiyak na panahon, habang maaaring hindi pa lubusang napatibay o na-certify ang mga bagong implementasyon. Ang hugis ay ang atomic composite, na may isang public key at isang signature value, na may natitirang seguridad kung masira ang isang component. Ang hangganan ay ang listahan ng mga limitasyon sa itaas: walang mandatory-to-implement algorithm, walang direktang saklaw sa backwards compatibility, at EUF-CMA sa halip na SUF-CMA.

Ang hinihingi nitong ikaw ang magbigay ay pagpili ng kombinasyon at kasunduan sa interoperability. Dahil walang pinangangalanang mandatory-to-implement algorithm ang espesipikasyon, responsibilidad mo ang pagpili ng pares, bagaman nag-aalok ang Section 10.4 ng maikling listahan ng rekomendasyon para sa mga karaniwang use case. Kung certified na ang iyong produkto sa isang partikular na tradisyonal na algorithm, itinuturo ng lohika ng re-certification ang kombinasyong hindi gumagalaw sa component na iyon. Kung bumubuo ka ng bago na walang regulatory requirement o legacy implementation na isasaalang-alang, inirerekomenda ng RFC na ituon ang implementasyon sa id-MLDSA65-ECDSA-P256-SHA512, na ayon dito ay nagbibigay ng pinakamahusay na kabuuang balanse ng performance at seguridad.

May makatwirang argumento na ito ang tamang hatian ng trabaho para sa isang standard sa yugtong ito. Kung nag-utos ng iisang kombinasyon, napaglingkuran sana ang ilang deployment at naiwan ang iba, lalo na ang mga nakatali sa rehiyonal na regulatory guidelines. Sa hindi pag-uutos, nananatiling magagamit ang espesipikasyon sa mga rehiyong iyon, kapalit ng pagpasa ng isang hakbang ng koordinasyon sa mga adopter. Flexibility ang pinipili ng RFC at sinasabi nito iyon sa iyo.

Marahan din akong tututol sa isang nakatutuksong maling pagbasa. Ang pahayag na napakakaunting implementer ang kailangang mag-alala sa buong listahan ay maaaring tunog pahintulot na balewalain ang lawak ng espesipikasyon. Hindi. Pahayag ito tungkol sa kung sino ang nagpapasan ng gastos ng lawak na iyon: sinasalo ito ng espesipikasyon para hindi na kailangan ng karamihan ng deployment. Kung library author ka o vendor na naglilingkod sa mga regulated na customer, maaaring problema mo nga ang lawak; kung isa kang organisasyong pumipili ng iisang composite, kadalasan hindi. May pasubali ang RFC sa inaasahan, at ituturing ko itong hula, hindi garantiya.

## Ang mga tanong na iniiwang bukas ng espesipikasyon

Dalawang hibla sa dokumento ang sulit bantayan dahil ang espesipikasyon mismo ang nagtuturo sa kanila nang hindi nilulutas.

Ang una ay ang haba ng transisyon. Sinasabi ng RFC na maaaring kanais-nais ang dual-algorithm data protection sa mas mahabang panahon, at na maaaring agresibo ang migration timelines. Nagbabanggaan ang dalawang pahayag na iyon sa kawili-wiling paraan: ang mabilis na paglipat sa PQC ay nangangatwiran para sa pag-deploy bago makumpleto ang pagpapatibay, habang ang mas mahabang panahon ng pananggalang ay nangangatwiran para panatilihin ang tradisyonal na kalahati nang matagal pagkatapos noon. Kung gaano katagal talaga pananatilihin ng mga organisasyon ang parehong component ay tanong na ipinahihiwatig ng dokumento at hindi sinasagot.

Ang ikalawa ay ang backwards compatibility. Sinasabi ng RFC na tahasang hindi nagbibigay ng application backwards compatibility ang mga mekanismo nito at kakailanganin ng karagdagang mekanismo kung saan ito kailangan. Inililista nito ang hanay ng mga protocol kung saan kailangang pag-isipan ang migration at interoperability, mula TLS 1.3 at IKEv2 hanggang S/MIME, eIDAS document signing at code signing, pero iniiwan nito sa mga protocol at application mismo ang disenyo ng mga karagdagang mekanismong iyon.

Para sa mga team na nagpapasya kung saan unang gugugulin ang pagsisikap, ang ikalawang tanong ang mukhang mas mainam na simulan: hindi kung aling kombinasyon ang aampunin, kundi kung paano kikilos ang isang upgraded na application kapag hindi pa gumagalaw ang partido sa kabilang dulo.

## Mga Madalas Itanong

**Ano ang Composite ML-DSA?**
Ang Composite ML-DSA ay isang PQ/T hybrid signature scheme na tinukoy sa RFC 10073. Pinagsasama nito ang ML-DSA, na tinukoy sa FIPS 204, at isang tradisyonal na algorithm gaya ng RSASSA-PSS, RSASSA-PKCS1-v1_5, ECDSA, Ed25519 o Ed448. Iisang public key at signature value ang ipinapakita ng pares, kaya maaari itong ituring ng mga protocol bilang iisang atomic algorithm.
**Bakit napakaraming algorithm combination ang tinutukoy ng RFC?**
Sinasabi ng RFC na ang paglilingkod sa regulatory re-certification use case, higit sa alinmang ibang design requirement, ang nagtutulak sa malaking bilang ng kombinasyon. Maaaring mas madali para sa isang vendor na i-re-certify ang produkto sa pamamagitan ng pagdaragdag ng post-quantum component sa tabi ng isang compliant na tradisyonal na component kaysa palitan ito. Inaasahang mag-de-deploy ang mga organisasyon ng iisang composite algorithm o iilan lang.
**Aling composite algorithm ang dapat simulan ng bagong deployment?**
Walang pinangangalanang mandatory-to-implement algorithm ang RFC. Para sa mga application na walang regulatory requirement o legacy implementation na isasaalang-alang, inirerekomenda ng Section 10.4 na ituon ang implementasyon sa id-MLDSA65-ECDSA-P256-SHA512. Nagbibigay rin ito ng rekomendasyon para sa mga application na nangangailangan ng RSA, sensitibo sa performance at bandwidth, o NIST PQC Level 5 lang ang pinapayagan.
**Napapanatili ba ng Composite ML-DSA ang paggana ng mga upgraded system kasama ng mga legacy?**
Hindi. Sinasabi ng RFC na tahasang hindi nagbibigay ng application backwards compatibility ang mga mekanismo nito at mga upgraded system lang ang makakaunawa sa mga OID na tinutukoy nito. Kung saan kailangan ang property na iyon, kakailanganin ng karagdagang mekanismo.
**Anong security property ang hindi iniaalok ng Composite ML-DSA?**
Hindi nito iniaalok ang Strong Unforgeability under Chosen Message Attack (SUF-CMA), kundi ang mas mahinang EUF-CMA property lang. Sinasabi ng RFC na hindi ito dapat gamitin ng mga application kung saan kritikal ang SUF-CMA security, at NOT RECOMMENDED ito kung saan hindi pa napapatunayang katanggap-tanggap ang EUF-CMA.
