## Gumaling ang mga modelo; hindi ang workflow

Binabasa ng artikulong ito ang "Exploring Super-agent Design: Towards a More Autonomous Agent System", isang post na inilathala sa X ng DeepSeek Harness (@DeepSeekHarness) noong 1 Nobyembre 2026, isinulat ni Yujia Qiao sa ngalan ng team ng DeepSeek Harness at ipinakilala bilang machine translation ng orihinal na nasa wikang Tsino.

May ipinakita ang coding agents at iba pang single-task agent na sulit sabihin nang diretso. Kaya ng mga modelo na gumamit ng tools para lutasin ang masalimuot na problema, at paunti nang paunti ang kailangan nilang tuloy-tuloy na pagbabantay at hakbang-hakbang na pakikialam ng tao. Mas mahusay na rin ang mga modelo sa pag-coordinate ng maraming agent, kaya praktikal nang ayusin at i-schedule ang trabaho sa iba't ibang session.

Mas mahalaga ang ikalawang punto kaysa sa unang tingin. Kung praktikal ang koordinasyon, hindi na kawili-wiling tanong kung kayang tapusin ng agent ang isang mahirap na task. Ang tanong ay kung ano ang mangyayari kapag lima ang iniabot mo.

Nagpapahiwatig ng sagot ang personal agents. Direkta silang kumokonekta sa pang-araw-araw na messaging, calendar, email at work platforms, binabantayan ang mga feed, at tumutulong sa mga task. Sinasabi ng post na hindi lang pang-personal ang ganitong laging-online at event-driven na paraan ng pagtatrabaho at mahalaga rin ito sa komersiyal na trabaho gaya ng software development. Iginigiit nito ito sa halip na sukatin, at dapat itong basahin nang ganoon. Pero malinaw ang direksiyon: isang agent na nakaupo sa mismong mga lugar kung saan nangyayari na ang trabaho, sa halip na naghihintay ng prompt sa isang terminal.

## Saan bumibigay ang single-session na disenyo

Iisang session pa rin ang basic na yunit ng trabaho ng mga agent, at hiwalay ang mga session sa isa't isa. Malinis na abstraction iyon para sa iisang task. Nagiging asiwa ito sa sandaling marami na.

Kailangang manu-manong lumipat-lipat ng session ang user na nagpapatakbo ng ilang task nang sabay at tandaan kung ano ang laman ng bawat isa. Sa karanasan ng mga may-akda, karaniwang 3 hanggang 5 aktibong session lang ang kayang sundan ng isang tao nang sabay. Galing sa karanasan ang numerong iyon, hindi sa kontroladong pag-aaral, kaya ituring itong rule of thumb. Gayunman, itinuturo nito ang istruktural na problema. Sa mga disenyong ito, kakayahan ng modelo ang hangganan ng iisang task, pero atensiyon ng tao ang hangganan ng multi-tasking.

Basahin nang dalawang ulit ang pangungusap na iyon. Sinasabi nito na hindi kusang itataas ng pagpapahusay sa modelo ang kisame ng parallel na trabaho. Ang kisame ay ang taong may hawak ng mga session sa kanyang isip. Ipaglalaban kong ito ang pinakakapaki-pakinabang na balangkas sa buong argumento, dahil inililipat nito ang problema mula sa modelo, kung saan napupunta ang karamihan ng pagsisikap, patungo sa sistemang nakapaligid dito.

## Bakit hindi ito naaayos ng connectors

Ang halatang tagpi ay palawakin ang umiiral na. Magdagdag ng CLIs, MCP o external connectors sa isang lokal na single-session agent, at makakatanggap ito ng external messages. Ang punto ng mga may-akda ay nananatili ang mga basic na limitasyon nito.

Kongkreto nilang inililista ang mga limitasyong iyon. Tumatakbo pa rin ang ganitong setup sa iisang synchronous session na humihinto sa mahahabang operasyon. Naghahalo ang mga context mula sa iba't ibang task. Humihinto ang lahat tuwing nag-o-offline ang lokal na device. At kailangan ng maraming manu-manong pagsisikap para mapanatiling tumatakbo ang buong kaayusan.

Iba-ibang uri ng kabiguan ang bawat isa. Problema sa throughput ang pag-block. Problema sa katumpakan ang halo-halong context. Problema sa availability ang pag-offline kasama ng laptop. Problema sa operasyon ang manu-manong pagpapanatili. Wala sa mga ito ang tinutugunan ng connector, dahil binabago lang ng connector kung paano dumarating ang mga mensahe. Hindi nito binabago kung ano ang session.

## Paghihiwalay ng agent sa session

Sinasabi ng post na para malampasan ang mga hangganang ito, kailangang ihiwalay ang agent sa anumang iisang session na manu-manong pinapatakbo. Ang kasunod ay binigkas bilang kung ano dapat ang agent sa halip na isang nasukat na resulta, kaya pinakamainam itong basahin bilang design thesis ng mga may-akda.

Ganito ang thesis. Dapat iisang tuloy-tuloy na entity ang agent na nagpapanatili ng context nito sa iba't ibang session at sabay na nagtatrabaho sa ilang masalimuot na task, nang hindi nagbabanggaan ang mga task. Super-agent ang tawag ng mga may-akda sa ganitong uri ng agent at sa arkitektura ng sistema nito.

Nag-uulat sila ng gumaganang halimbawa. Ang kanilang internal na Super-agent instance, na tumatakbo sa DeepSeek Harness, ay kayang ituloy ang iisang development task sa IM at GitHub. Binabantayan din nito ang feedback sa mga pampublikong group chat at, kahit walang nag-@-mention dito, kusang hinahanap ang mga root cause at nagbubukas ng Pull Requests para ayusin ang mga ito. Hindi nagbibigay ang post ng success rate o bilang ng Pull Requests para sa dalawang gawing ito, kaya mga demonstrasyon ng kakayahan ang mga ito, hindi benchmark. Gayunman, kapansin-pansin ang ikalawang gawi. Walang humiling, at kumilos ang agent.

## Apat na katangian

Sinasabi ng post na may apat na basic na katangian ang Super-agent: tuloy-tuloy, produktibo, proaktibo at persistent. Inilalahad ito ng mga may-akda bilang kanilang paniniwala, at may tiyak na kahulugan ang bawat termino.

Ang tuloy-tuloy na agent ay hinahayaan ang mga user na direktang makipag-ugnayan dito kung saan sila nagtatrabaho na, gaya ng IM chats at GitHub comments, at palagi itong pakiramdam na iisang agent. Ang halimbawa ng post ay isang user na humihingi ng Plan A sa IM at kalaunan ay lumilipat sa Plan B sa isang comment sa GitHub Pull Request. Naiintindihan ng agent ang pagbabago at inaayos ang ginagawa nito. Nagbago ang channel; hindi ang usapan.

Ang produktibong agent ay mabilis tumugon at sabay na kumukumpleto ng ilang masalimuot na task, bawat isa sa mataas na pamantayan. Kaya rin nitong tanggapin ang susunod na instruksiyon bago matapos ang naunang utos o task. Inaalis nito ang pag-block na inilarawan kanina.

Ang proaktibong agent ay nagbabantay ng mga event sa kapaligiran nito, kumikilos sa anumang sulit asikasuhin, at tahimik kung hindi. Karapat-dapat pansinin ang huling sugnay. Ingay ang agent na kumikilos sa lahat. Bahagi ng espesipikasyon ang pananahimik.

Ang persistent na agent ay laging online, direktang kumokonekta sa totoong working environment ng user, at awtomatikong bumabangon mula sa mga anomalya sa pangmatagalang operasyon.

Pagkatapos ay dumarating ang limitasyong nagtutulak sa natitirang disenyo: walang iisang ReAct loop na makapagbibigay ng apat na katangian nang sabay, kaya kailangan silang manggaling sa arkitektura ng sistemang nakapaligid dito. Sinasabi ito ng post nang walang pasubali, at ito ang dahilan kung bakit artikulo ito tungkol sa arkitektura at hindi tungkol sa prompting.

## Pagtatagpo, at isang lumang hanay ng problema

Inaasahan ng post na magkakaroon ng magkakahawig na disenyo ang personal agents at ang mga agent para sa komersiyal na trabaho gaya ng software development kapag ang layunin ay isang laging-online na sistemang sabay na tumutugon sa mga event sa kapaligiran. Inaasahan ito, at may kaukulang pasubali. Kung magkatotoo, iisang problema ang nilulutas ng mga gumagawa ng personal assistant at ng mga gumagawa ng development agent, at maaari silang magbahagi ng malaking bahagi ng disenyo.

May ikalawang obserbasyong nakapagpapanatag sa akin. Nagbubunga ang pagbuo ng ganitong sistema ng maraming problemang kahawig ng matagal nang pinag-aaralan sa computer systems, kaya maraming klasikong ideya sa disenyo mula sa larangang iyon ang naaangkop din dito. Hindi sinasabi ng mga may-akda kung aling mga ideya, at hindi ako manghuhula. Pero praktikal ang implikasyon para sa mga founder: hindi ka humaharap sa lubusang hindi pa namamapang problema. Mahaba na ang kasaysayan ng scheduling, isolation at recovery.

Sa tingin ng mga may-akda, limang module ang bumubuo sa basic na framework na sumusuporta sa apat na katangian, bagaman mag-iiba-iba ang mga implementasyon. Muli, paghuhusga nila ito at hindi napatunayang dekomposisyon. Ganito naka-map ang apat sa mga module sa mga katangian.

Ang two-level architecture (Section 2) ang nagbibigay ng parehong tuloy-tuloy na interaksiyon at produktibong concurrency. Ang event-driven na disenyo (Section 3) ang nagpapaproaktibo sa agent. Ang full-duplex multi-channel interaction (Section 4) ang nagpapanatiling tuloy-tuloy at produktibo ang bawat palitan sa mga user. Ang paghihiwalay ng compute, state at environments (Section 5), kasama ng isang Watchdog (Section 6), ang nagpapanatiling persistent na online ang agent sa iba't ibang device at nagpapahintulot ditong kusang bumangon mula sa mga anomalya.

Nakatuon ang natitirang bahagi ng artikulong ito sa una sa mga iyon, ang two-level architecture.

## Ang trade-off sa pagitan ng continuity at throughput

Ang pagsuporta sa parehong tuloy-tuloy na interaksiyon sa iba't ibang channel at produktibong concurrency sa iba't ibang task ay nagpipilit ng pundamental na trade-off sa pagitan ng continuity at throughput sa paraan ng pag-aayos ng sistema sa mga session nito. May dalawang halatang paraan ng pag-aayos, at bawat isa ay bumibigay sa mahuhulaang paraan.

Ang una ay ipadala ang bawat event sa iisang session. Nagbibigay ito ng pinakatuloy-tuloy na context, dahil nakikita ng session na iyon ang lahat. Bilis ang kapalit. Isang hakbang sa bawat pagkakataon ang takbo ng ReAct loop, na naglilimita sa bilis ng iisang session: matagal ang mga task at nananatiling mababa ang throughput. Nauuwi ring magkakasalit sa iisang context ang mga intermediate na detalye ng iba't ibang task, na nagpapababa sa kalidad ng resulta. Kaya ang session na pinakamaraming alam ay siya ring pinakamahinang mangatwiran, dahil gulo ang binabasa nito.

Ang ikalawa ay bigyan ang bawat event ng sariling bagong session. Pinapalaki nito ang concurrent throughput, pero kapag hindi lubusang independiyente ang mga task, nagiging hiwa-hiwalay ang kanilang mga resulta dahil walang pinagsasaluhang global context. Nakalilito rin ang interaksiyon kapag ilang session ang hiwa-hiwalay na sumasagot sa user. Limang boses ang natatanggap ng user samantalang isa lang ang gusto niya.

Hindi katanggap-tanggap ang alinmang dulo, at totoo ang trade-off, hindi usapin ng pag-tune. Ang sistemang gusto ng parehong continuity at throughput ay kailangang paghiwalayin ang dalawang trabaho.

## Isang session, dalawang trabaho

Tinutukoy ng post kung bakit nagkabuhol ang mga trabaho sa simula pa lang. Sa mga umiiral na disenyo, dalawang trabaho ang ginagawa ng isang session: pinamamahalaan nito ang context ng modelo, at ito ang yunit ng project management ng user. Iisang object ang nagdadala ng dalawang responsibilidad, kaya ang pagpapahusay sa isa ay nagpapasama sa isa pa. Bigyan ang user ng iisang session na susundan, at madudumihan ang context. Bigyan ang modelo ng malinis at hiwalay na mga context, at kailangang salu-saluhin ng user ang mga ito.

Ito ang dahilan kung bakit tumatama ang numerong 3 hanggang 5 session. Session ang yunit ng project management ng user, kaya ang bilang ng session na kaya nilang subaybayan ang nagiging bilang ng proyektong kaya nilang patakbuhin.

## Ang two-level architecture

Hinahati ng mungkahi ang mga responsibilidad. Pinananatili ng pangmatagalang Router layer (Section 2.1) ang global continuity sa pamamagitan ng paghawak sa lahat ng interaksiyon ng tao at global coordination. Nagpapatakbo ng mga task nang may mataas na concurrency ang context-isolated na Worker layer (Section 2.2). Kung pagsasamahin: hawak ng Router layer ang lahat ng routing at external interaction, habang sabay-sabay na nagsasagawa ng mga task ang maraming hiwalay na Worker Session.

Ang Router layer ay pangmatagalang global routing layer na tumatanggap ng interaksiyon ng tao mula sa bawat entry point. Kaya palaging pakiramdam na iisang agent ang agent. Anumang channel ang dinaanan ng mensahe, iisang lugar ang binabagsakan nito. Samantala, pinananatiling hiwalay ng mga Worker ang kanilang mga context, kaya hindi lumilitaw sa loob nila ang problema ng pagsasalit mula sa single-session na disenyo.

May idinadagdag na paglilinaw ang mga may-akda na madaling makaligtaan. Lohikal na paghahati ng responsibilidad ang dalawang antas, at hindi kailangang i-implement ang alinmang layer bilang iisang session. Hindi kinakailangang iisang process na may iisang context ang Router, at hindi kinakailangang iisang pool ang Worker layer. Inilalarawan ng arkitektura kung sino ang responsable sa ano, hindi kung ilang session ang umiiral.

Diretsong sinasabi ang praktikal na kahihinatnan: inaako ng sistema ang context management at concurrent execution, kaya bihirang kailanganin ng mga user na mag-isip tungkol sa mga session. Ito ang tumutugon sa kisame ng atensiyon. Kung hindi na kailangang tandaan ng tao kung ano ang laman ng bawat session, hindi na ang limitasyong 3 hanggang 5 ang hangganan ng bilang ng task na maaaring tumakbo. Hindi sinasabi ng post kung ilang task ang sabay na pinapatakbo ng internal instance nito, kaya hindi ko masasabi kung nasaan ang bagong hangganan.

## Ano ang sinusuportahan ng post, at ano ang hindi

Sulit maging tapat tungkol sa ebidensiya rito. Istruktural ang matitibay na pahayag. Hiwalay ang mga session, isang hakbang sa bawat pagkakataon ang takbo ng iisang ReAct loop, nagsasalit ng mga context ang iisang pinagsasaluhang session, at nagiging hiwa-hiwalay ang mga resulta kapag may session bawat event. Sinasabi ito ng post nang walang pasubali.

Ang mas malalambot na pahayag ang nagdadala ng ambisyon. Ang depinisyon ng Super-agent, ang apat na katangian, ang limang-module na framework at ang inaasahang pagtatagpo ng personal at komersiyal na disenyo ay pawang may pasubali sa post. Pinaniniwalaan, iniisip at inaasahan ito ng mga may-akda. Walang iniharap bilang nasukat na resulta.

Inilalarawan ang internal instance sa DeepSeek Harness sa pamamagitan ng mga gawi: pagpapatuloy ng iisang development task sa IM at GitHub, at pagtukoy ng mga root cause sa mga pampublikong group chat bago pa may magtanong. Existence proof ito, hindi pag-aaral ng performance. Nag-uulat ang post ng mga paunang eksperimento, pero sinasabi ng mga may-akda na synthetic workloads at pinasimpleng environment ang gamit nila at indikatibo lang ang mga resulta. Sa ablation na iyon, natapos ng Super-agent ang mga task sa 12.4 minuto sa p50 at 15.7 minuto sa p95, mas mabilis kaysa sa iisang session na may subagent tool, habang mas maraming cache-read tokens ang ginamit bawat run. Para sa teknikal na mambabasa, iyan ang tamang antas ng kumpiyansang dapat dalhin: magkakaugnay ang disenyo at mahusay na nailarawan ang mga failure mode ng mga alternatibo, pero galing sa simulated na trabaho ang mga numero, hindi sa instance na ginagamit araw-araw.

## Ano ang dapat makuha rito ng isang founder

Kung bumubuo ka ng agent product, ang unang aral ay itigil ang pagtrato sa session bilang produkto. Ang session ay implementation detail ng context management na itinaas bilang user interface. Ang argumento ng mga may-akda ay ang pagtataas na ito ang naglilimita sa parallel na trabaho, at sa tingin ko tama silang doon ilagay ang problema.

Ang ikalawang aral ay tungkol sa kung saan mo ilalagay ang pagsisikap. Kakayahan ng modelo ang hangganan ng iisang task, kaya nakakatulong ang mas mahusay na modelo sa iisang task. Atensiyon ng tao ang hangganan ng multi-tasking, kaya hindi halatang nakakatulong dito ang mas mahusay na modelo. Ang arkitektura ang nakakatulong. Ang Router na sumasalo sa bawat entry point at mga Worker na nagpapanatiling hiwalay ang mga context ang uri ng istrukturang nagpapagalaw sa kisame.

Ang ikatlo ay tungkol sa saklaw. Mukhang magkaibang produkto ang personal agents na nakaupo sa messaging, calendar, email at work platforms at ang komersiyal na development agents na sumasagot sa isang group chat sa pamamagitan ng Pull Request. Inaasahan ng mga may-akda na magtatagpo sila sa magkakahawig na disenyo, kaya hindi dapat balewalain ng team na bumubuo ng isa ang pag-unlad ng isa pa.

Wala sa mga iyon ang nagpapadali sa pagbuo. Ang persistence pa lang ay humihingi ng paghihiwalay ng compute, state at environments, kasama ng isang Watchdog para kusang bumangon ang agent mula sa mga anomalya. Humihingi ang proactivity ng event-driven na disenyo. May sariling seksiyon ang full-duplex multi-channel interaction. Isa lang sa limang module ang two-level architecture, hindi ang buong sagot.

## Isang bukas na tanong

May isang bagay na iniiwang bukas ng post, at ito ang pinakagusto kong masagot. Hawak ng Router ang lahat ng interaksiyon ng tao at global coordination, at hiwalay ang mga Worker ayon sa disenyo. Sinasabi ng post na pundamental ang trade-off sa pagitan ng continuity at throughput, at ibinibigay ng two-level na paghahati ang dalawa. Para sa mga task na sumasagi sa iisang environment, sinasabi nitong natatanggap ng mga Worker na naka-subscribe sa Thread ng environment na iyon ang parehong event notifications, at ipinapasa ng Router ang iilang kasong nangangailangan ng koordinasyon sa iba't ibang task. Sinasabi rin nito na kapag lumaki at naging mas mahigpit ang pagkakaugnay ng mga task kaysa sa kayang hawakan ng iisang Router Session, hindi pa tiyak ang tamang istruktura para sa bawat layer. Ang kabiguan ng session bawat event ay hiwa-hiwalay na resulta mula sa mga task na hindi independiyente. Kung paano ipapasa ng Router pababa ang sapat lang na global context, nang hindi ibinabalik ang pagsasalit na dapat sana nitong pigilan, doon masusubok ang disenyo.

## Mga Madalas Itanong

**Ano ang Super-agent?**
Ito ang tawag ng post sa isang agent, at sa arkitektura ng sistema nito, na hiwalay sa anumang iisang session na manu-manong pinapatakbo. Iisang tuloy-tuloy na entity ang agent na nagpapanatili ng context nito sa iba't ibang session at sabay na nagtatrabaho sa ilang masalimuot na task nang hindi nagbabanggaan ang mga task.

**Bakit hindi nagsi-scale ang isang session bawat task?**
Hiwalay ang mga session, kaya kailangang manu-manong lumipat-lipat ang user na nagpapatakbo ng ilang task nang sabay at tandaan kung ano ang laman ng bawat isa. Sa karanasan ng mga may-akda, karaniwang 3 hanggang 5 aktibong session lang ang kayang sundan ng isang tao nang sabay, kaya atensiyon ng tao ang hangganan ng multi-tasking, hindi kakayahan ng modelo.

**Bakit hindi nalulutas ng CLIs, MCP o connectors ang problema?**
Pinapahintulutan nila ang isang lokal na single-session agent na tumanggap ng external messages, pero nananatili ang mga basic na limitasyon nito. Humihinto pa rin ito sa mahahabang operasyon sa iisang synchronous session, naghahalo ng mga context mula sa iba't ibang task, humihinto kapag nag-offline ang lokal na device, at nangangailangan ng maraming manu-manong pagsisikap para mapanatiling tumatakbo.

**Paano gumagana ang two-level architecture?**
Hawak ng pangmatagalang Router layer ang lahat ng interaksiyon ng tao at global coordination, habang nagpapatakbo ng mga task nang may mataas na concurrency ang context-isolated na Worker layer. Lohikal na paghahati ng responsibilidad ang dalawang antas, at hindi kailangang i-implement ang alinmang layer bilang iisang session.

**Gaano katibay ang ebidensiya para sa disenyo?**
Inilalarawan ng post ang isang internal na Super-agent instance na tumatakbo sa DeepSeek Harness at nag-uulat ng mga paunang eksperimento. Sinasabi ng mga may-akda na synthetic workloads at pinasimpleng environment ang gamit ng mga eksperimentong iyon, kaya indikatibo lang ang mga resulta.
