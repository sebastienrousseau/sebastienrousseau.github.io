# 靜態網站產生器（SSG）：企業級策略深度剖析與架構藍圖

*研究日期：2026-06-22。基於對 `static-site-generator` v0.0.41 的程式碼檢視，以及對 2026 年 SSG 生態的網路研究。*

**對受監管的出版方而言，靜態網站產生器已不再只是設計工具；它是營運風險邊界的一部分。** 開源的 Rust [static-site-generator](https://github.com/sebastienrousseau/static-site-generator) 正是建立在這個前提上，將安全、無障礙、國際化與 AI 內容管線移至編譯期，讓一次未通過的檢查在建置階段即中止，而非流入正式環境。本分析將 0.0.41 版真正交付的功能，與其文件至今仍僅止於承諾的部分區分開來，列出它尚未具備的五項企業能力，並提出一條對齊 DORA、歐洲無障礙法案（European Accessibility Act）與現代供應鏈標準、分階段邁向 1.0 版的路徑。

> **執行摘要**
>
> - **發布如今是一道營運風險邊界。** 在 DORA、歐洲無障礙法案與 GDPR 之下，每一項對外資產都可能成為供應鏈遭滲透、遭竄改與招致監管風險的進入點。編譯期模型透過在交付前拒絕不合規的輸出，收窄這道邊界。
> - **這套引擎的差異化能力由編譯器強制執行，而非文件中的願景。** 工作區全域的 `forbid(unsafe_code)`、真正的 SHA-256/384 SRI、自動 CSP 萃取，以及建置期 WCAG 2.2 AA 門禁，將安全與無障礙從事後稽核轉為硬性的建置失敗。
> - **0.0.41 版存在文件與程式碼的落差。** 原生壓縮、透過相依圖進行的增量重建，以及 AVIF 支援雖有描述卻不具功能；本文針對每一處落差指出確切的原始碼位置。
> - **邁向 1.0 的路徑是一段序列，而非願望清單。** 先是穩健性（0.0.42），接著是增量正確性（0.1.0），最後才是受監管買家所要求的企業能力：WASM 沙箱、本地語意搜尋，以及可驗證的 SLSA 來源證明（1.0.0）。

## 現有優勢

`static-site-generator` 的程式碼呈現數項獨到的工程決策，將它與老牌的 JavaScript 及 Go 引擎區隔開來：

- **編譯期安全姿態：** 工作區全域的 `#![forbid(unsafe_code)]` 提供編譯期的記憶體安全保證。建置管線會產生真正的 SHA-256/SHA-384 子資源完整性（SRI）雜湊（`src/plugins/assets.rs`），並執行自動的內容安全政策（CSP）萃取，移除 unsafe-inline 的指令碼與樣式。版本經過簽署、附帶 Sigstore 證明，並在每次建置時產出 CycloneDX 1.5 SBOM。  
- **由編譯器強制執行的無障礙門禁：** 網頁內容無障礙指南（WCAG）2.2 AA 級的檢查，透過由 Playwright 驅動的建置期 axe-core 剖析器，在編譯管線內執行。無障礙成為一道硬性的建置門禁，而非發布後的稽核：若某頁未通過，編譯即中止並回報確切的行號錯誤。  
- **資料自主的 AI 管線：** 一條本地 LLM 的翻譯與中繼資料萃取管線（透過本地 Ollama 或 llama.cpp 端點），讓機構得以自動化內容摘要、JSON-LD 結構描述產生與多語翻譯，而無須將財報發布前的揭露資訊或敏感智慧財產送往公有雲的 AI API。  
- **平行化編譯：** Rust 的記憶體安全保證，支撐起一條平行化、由 Rayon 驅動的 HTML 與資產管線（`src/core/pipeline.rs`）。外掛管線執行融合式轉換，其中 `SearchPlugin`、`SeoPlugin`、`CanonicalPlugin` 與 `JsonLdPlugin` 皆在 `par_iter()` 上運作，因此每一頁只讀取與寫入磁碟一次。  
- **供應鏈與相依項衛生：** 將樣板引擎從 Tera 遷移至 MiniJinja（`v0.0.37`），縮減了二進位檔大小、在編譯期移除了如 `rand` 這類遞移相依項，並產生精簡的相依項足跡，降低軟體供應鏈的暴露面。

## 落差與現實狀況

儘管具備這些出色的優勢，對 v0.0.41 的嚴謹程式碼檢視，仍揭示出文件宣稱與實際 Rust 程式碼之間，數處架構、功能與開發者體驗上的落差：

### 架構落差

- **空白折疊對比原生壓縮：** README 承諾提供「原生 JS/CSS 壓縮」，但 `MinifyPlugin`（`src/plugins/plugins.rs:96-116`）實際上僅是個粗略的空白折疊器。它會在遇到 `<pre>` 元素時短路，並折疊 HTML 中的連續空白，卻不執行具語法感知的原生 CSS 或 JS 壓縮。此外，它只處理頂層頁面，不會遞迴走訪子目錄（如 `/blog/` 或 `/tags/`），使深層頁面未經壓縮。  
- **失效的增量基礎設施：** 相依追蹤圖（位於 `src/core/depgraph.rs` 的 `DepGraph`）雖被編譯並載入 `PluginContext.dep_graph`，卻從未在正式程式碼中被實際填入。`add_dep()` 方法僅在單元測試中被呼叫，使 README 中「透過相依圖進行增量重建」的宣稱目前仍屬願景。  
- **批次編譯對比串流編譯：** `streaming::compile_batch` 模組（`src/core/streaming.rs`）並非真正串流。它改以批次方式將頁面編譯至暫存目錄，為每一批次從頭執行 `staticdatagen::compile`，再合併輸出。這導致可觀的磁碟 I/O 開銷與重複剖析，偏離了真正的串流架構。  
- **外掛生命週期階段違規：** 在建置過程中產生新 HTML 頁面的外掛，如 `TaxonomyPlugin`、`PaginationPlugin` 與 `I18nPlugin`，是在 `after_compile` 中直接寫入磁碟，而非使用 `transform_html` 生命週期。因此，若 `CanonicalPlugin`、`JsonLdPlugin`、`RobotsPlugin` 與 `AccessibilityPlugin` 等關鍵後處理外掛註冊在先，這些外掛所產生的頁面便會繞過它們。這使得標籤、分類與分頁頁面缺少正確的正規連結（canonical link）、JSON-LD 結構描述或無障礙驗證。  
- **`LlmPlugin` 中對 `curl` 的外殼呼叫：** 本地 LLM 內容管線（`src/plugins/llm.rs`）直接對主機的 `curl` 執行檔進行外殼呼叫，以查詢本地端點。這帶來嚴重的跨平台缺陷（例如在 PATH 中沒有 curl 的 Windows 主機上）、構成安全風險（外殼注入向量），並在封閉或網路隔離的 CI 環境中失效。  
- **HTML 改寫中的粗糙字串操作：** `image_plugin.rs` 與 `search.rs` 的萃取器，以脆弱的 `str::find` 與 `str::rfind` 操作改寫 HTML 字串。此做法對於破損的 HTML 標籤、註解內的 `<img>` 標籤、alt 文字中的字元實體，或既有的 `srcset` 屬性極度脆弱，可能導致輸出損毀。  
- **未實作的 AVIF 支援：** 儘管 AVIF 影像編碼在文件中著墨甚多，`image_plugin.rs` 中的實作卻是個樁，其中的 `avif_variants` 僅回傳 `Vec::new()`，使該功能無法運作。  
- **輪詢式的檔案監看器：** 本地開發伺服器的監看器（`src/server/watch.rs`）採用輪詢而非檔案系統事件 API，導致閒置時 CPU 用量過高，且修改延遲達次秒級。

### 功能與開發者體驗落差

- **未追蹤遞移相依項：** 相依圖無法追蹤巢狀相依（例如：某子樣板的變更影響到一個版面配置，進而影響到某頁面），此點已由單元測試 `transitive_not_tracked` 驗證。  
- **缺少增量編譯的 CLI 旗標：** 沒有任何 `--incremental` CLI 旗標接上執行編譯器，使開發者無法運用快取建置。  
- **HMR 僅限 CSS：** 熱模組替換（Hot Module Replacement，HMR）僅支援 CSS；對 HTML、版面配置或 Markdown 檔案的任何修改都會觸發整頁重新載入，拖累開發者的作業速度。  
- **子指令不足：** 由於缺少如 `ssg dev`、`ssg build`、`ssg check` 與 `ssg lint` 這類標準子指令，開發者必須手動傳入冗長的旗標（`ssg -s public -w`）。

## 我們尚缺的架構能力（新發現）

除了 v0.0.41 的既有落差之外，以金融級的風險輪廓評估本專案，還浮現出數項它尚未提供、但企業買家會要求的能力：

### 1. WebAssembly 外掛沙箱（零信任擴充）

雖然編譯器二進位檔本身以安全的 Rust 撰寫，但允許任意第三方外掛在主機系統上原生執行，卻引入了嚴重的供應鏈弱點。一個遭滲透的第三方外掛可輕易存取主機的檔案系統、讀取專有的 Markdown 檔案，或外洩私密憑證。

* **尚缺的能力：** 一個沙箱化的執行環境。為達成零信任編譯，編譯器應在嵌入式的 WebAssembly 執行環境（如 `wasmtime`）內執行第三方外掛。外掛應僅透過受限的 WebAssembly 系統介面（WASI）與主機互動，將其存取權嚴格限縮於正在轉換的該頁面。

### 2. 透過串流式 AST 進行零複製 HTML 剖析（`lol_html`）

將 HTML 剖析層遷移至完整的記憶體內 DOM 函式庫（如 Kuchiki 或 html5ever），在處理超過 100,000 頁的網站時，會引入可觀的記憶體開銷與處理停頓。

* **尚缺的能力：** 一個串流式、零複製的 HTML 改寫器。運用 Cloudflare 的 `lol_html`（Low-Output-Latency HTML 改寫器），可讓編譯器在單一串流通道中剖析、檢視並修改 HTML 元素，且記憶體配置近乎為零，與平行串流編譯器所設定的次秒級建置目標相符。

### 3. 本地語意向量搜尋（本地 RAG）

目前的搜尋索引（`SearchPlugin`）會產生一份龐大、扁平的 JSON 索引，僅能執行簡單的用戶端字串比對，缺乏對模糊搜尋、詞幹還原或語意查詢的支援。Pagefind 是一項改善，但它仍仰賴下載一份龐大的索引。

* **尚缺的能力：** 嵌入式的語意搜尋。編譯器應在建置期運用一個本地、輕量、Rust 原生的向量嵌入模型（如透過 `candle` 或 `ort` / ONNX Runtime 執行的 MiniLM-L6 模型）。它應為每一頁的每個段落產生密集向量嵌入，並輸出一份精簡的向量索引。編譯為 WASM 的用戶端搜尋元件，便能直接在瀏覽器中執行真正的離線語意搜尋。

### 4. 確定性的翻譯與推論快取

由於本地 LLM 推論（例如透過 Ollama 或 Llama.cpp）對 CPU/GPU 的耗用極高，在每次建置時為數千頁進行翻譯或產生中繼資料，在運算上是不可行的。

* **尚缺的能力：** 以內容雜湊為基礎的推論快取。編譯器必須維護一份涵蓋所有 LLM 操作的確定性快取。若某 Markdown 檔案內容與其翻譯參數的 SHA-256 雜湊與某快取項相符，編譯器便應重用已快取的翻譯與中繼資料，略過多餘的本地推論。

### 5. 支援平行擴展的非同步檔案 I/O

雖然外掛管線已透過 Rayon 平行化，但標準的同步磁碟寫入會阻塞 Rayon 的作業系統執行緒，在寫入數萬頁時形成 I/O 瓶頸。

* **尚缺的能力：** 非同步、非阻塞的磁碟 I/O。編譯器應將耗費 CPU 的任務（Markdown 剖析、壓縮）與受磁碟約束的寫入解耦，運用非同步 I/O 執行緒池或 Linux 的 `io_uring` 繫結（透過 `rio` 或 `tokio`），在不阻塞平行 CPU 執行單元的前提下平行寫入已編譯的頁面。

## 策略性的 1.0 藍圖

以下藍圖將已解決的落差與新發現的企業級能力，整合為一套結構化、按時序排列的版本發布框架。

### 階段一：0.0.42（穩健性與正確性修補，1 至 2 週）

1. **重建 `MinifyPlugin`：** 整合 `minify-html`、`oxc_minifier` 與 `lightningcss`，以提供原生、具語法感知的 HTML、JS 與 CSS 壓縮。並確保外掛會遞迴走訪 `site_dir` 之下所有巢狀目錄。  
2. **強化 AI 管線的安全：** 將 `LlmPlugin` 從原生的 `curl` 外殼呼叫移植至 `ureq`（一個輕量、同步、安全的 Rust HTTP 用戶端），以確保跨平台相容性並消除外殼注入弱點。

### 階段二：0.1.0（可信度與增量次版本，2 至 3 個月）

1. **填入 `DepGraph` 並啟用 `--incremental`：** 完整接上 `DepGraph`，以追蹤樣板對頁面與 Markdown 對頁面的相依關係。實作一層快取失效機制並接上 `--incremental` CLI 旗標，於暖快取環境中以次 200ms 的重建為目標。  
2. **透過 `lol_html` 進行串流式 AST 改寫：** 以由 `lol_html` 驅動的串流式、零複製 HTML 改寫器，取代 `image_plugin.rs`、`search.rs` 與 CSP 注入中脆弱的字串改寫。  
3. **事件驅動的監看器與元件級 HMR：** 將監看模組從輪詢移植至事件驅動的 `notify` crate，並實作僅限 CSS 與部分 HTML 的熱重載，達成次 100ms 的瀏覽器更新。  
4. **統一指令 CLI：** 重新設計編譯器介面，以支援標準子指令：`ssg dev`、`ssg build`、`ssg check`（無障礙／SEO 稽核）與 `ssg deploy`。  
5. **確定性推論快取：** 為所有本地 LLM 的翻譯、摘要與中繼資料萃取任務，實作一層以內容雜湊為基礎的快取。

### 階段三：1.0.0（企業與正式環境大版本，6 至 12 個月）

1. **零信任 WASM 外掛沙箱：** 嵌入一個 WebAssembly 執行環境（`wasmtime` 或 `wasmer`），在具備能力式（capability-based）檔案系統與網路存取的完全沙箱環境中執行第三方外掛。  
2. **本地語意向量搜尋（本地 RAG）：** 嵌入一個本地、Rust 原生的嵌入模型（透過 `candle` 或 `ort`），將密集的段落嵌入編譯為一份精簡索引，實現私密的用戶端語意搜尋。  
3. **伺服器島（Server Islands）與 WASM 邊緣目標：** 在編譯後的 `ssg-wasm` 核心之上，於邊緣執行環境（如 Cloudflare Workers、Vercel Edge 或 Netlify Edge）實作 `<ssg-island>` 元件執行。  
4. **非同步平行 I/O 引擎：** 重新設計檔案系統寫入模組，改用非同步 I/O 執行緒池與 `io_uring` 繫結，消除平行寫入期間 CPU 工作執行緒的阻塞。  
5. **SLSA v1.1 建置來源證明與 SPDX 3.0 合規：** 提供可透過數學方式驗證的 SLSA 第 3 級建置來源證明，並產生符合 SPDX 3.0 的 SBOM，完整滿足現代軟體供應鏈安全標準。

## 法規與合規整合

在高風險的企業與金融領域，軟體是透過合規與風險資本的視角來評估。`static-site-generator` 的架構藍圖與各項主要法規要求直接對齊：

- **DORA 第 6 條（資通訊技術風險管理）：** 在編譯期計算並注入 SHA-384 SRI 雜湊與嚴格的內容安全政策，滿足了保護數位發布通道免於供應鏈注入、網頁竄改與跨網站指令碼（XSS）向量的要求。  
- **DORA 第 7 條（資通訊系統韌性）：** 藉由改用不可變、編譯期已驗證的靜態資產，金融機構得以消除資料庫與執行期伺服器的弱點，降低營運風險乘數，並縮減在 Basel III 之下所需提列的風險資本準備。  
- **歐洲無障礙法案（EAA）指令 (EU) 2019/882：** 將無障礙稽核左移至編譯管線，作為一道硬性的編譯器門禁，可保證在部署前達成 100% 合規，消除在 EAA 與 ADA Title III 之下品牌受損與民事訴訟的風險。  
- **GDPR 第 25 條（設計即隱私）：** 將翻譯與中繼資料管線執行於本地、網路隔離的硬體上，讓專有草稿、財務指標與個人資料不流向公有第三方雲端 LLM 供應商，支持資料自主原則的合規。

## 常見問答

**相較於 README 的宣稱，0.0.41 版今日實際交付了什麼?**
安全與無障礙模型是真實的，並已在程式碼中強制執行：工作區全域的 `forbid(unsafe_code)`、SHA-256/384 SRI 產生、CSP 萃取、附帶 Sigstore 證明與 CycloneDX SBOM 的簽署版本，以及一道會中止建置的 WCAG 2.2 AA 門禁。有三項已載於文件的功能在 v0.0.41 中並不具功能。`MinifyPlugin` 只是個空白折疊器，而非具語法感知的壓縮器；本應驅動增量重建的 `DepGraph` 雖被編譯，卻從未在正式程式碼中被填入；而 AVIF 編碼是個樁，其 `avif_variants` 回傳空向量。

**無障礙門禁究竟是真正的編譯器門禁，還是建置後的 Linter?**
它是一道建置門禁。WCAG 2.2 AA 檢查透過由 Playwright 驅動的建置期 axe-core 剖析器，在編譯管線內執行；未通過的頁面會使編譯中止並回報確切的行號錯誤，而非事後發出警告。這正是歐洲無障礙法案的義務所需的特性：不合規的輸出無法抵達部署。

**在 LLM 外掛中對 `curl` 進行外殼呼叫為何重要?**
本地 LLM 管線（`src/plugins/llm.rs`）呼叫主機的 `curl` 執行檔以觸及本地端點。這將建置耦合於一個主機執行檔，在 PATH 中沒有 `curl` 的系統上會失效，引入外殼注入的攻擊面，並在網路隔離的 CI 中損壞。將此呼叫移植至如 `ureq` 這類 Rust HTTP 用戶端，可消除外部相依與注入向量，這也是它列為 0.0.42 修補第二項的原因。

**邁向 1.0 之路上最重要的單一項目是什麼?**
填入 `DepGraph` 並接上 `--incremental` 旗標。增量重建是文件與實際引擎之間的可信度落差，而每一項關於在 100,000 頁以上仍達次秒級建置的下游宣稱，都仰賴相依圖去追蹤樣板對頁面與 Markdown 對頁面的邊，而非停留在僅供測試的基礎設施。
