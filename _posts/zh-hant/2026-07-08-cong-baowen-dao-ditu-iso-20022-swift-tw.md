# 從訊息到地圖：在 ISO 20022 與 SWIFT 之上建立全球企業標準

**業界終於有了一套支付的全球語言，卻仍沒有一張讓企業據以行動的全球地圖。** ISO 20022 與 SWIFT 的 CBPR+ 計畫為跨境支付帶來了豐富、結構化、協調一致的資料，並在 G20 路線圖之下由 CPMI 的 2027 年底資料要求進一步強化。它們尚未做到的，是告訴企業財資主管、或代其行動的系統，這些資料在真實世界中應如何被揭露、保護、版本控管與行為運作。其結果是一種奇特的倒置：訊息正在全球範圍內趨於一致，但銀行讓企業使用這些訊息的方式，卻仍是逐家銀行各自為政、支離破碎。本文闡述銀行與金融機構如何從協調一致的訊息，邁向一套全球企業標準——並且使用它們既有的軌道。

> **執行摘要**
>
> - **驅動因素已然啟動。** ISO 20022 如今是全球跨境支付的標準語言；MT/MX 並存已於 2025 年 11 月結束，結構化地址於 2026 年 11 月上路，CPMI 的協調資料要求則至少延續至 2027 年底。
> - **協調止步於訊息邊界。** CPMI 與 SWIFT 標準化了*一筆支付必須說什麼*。它們並未標準化*一家銀行如何讓企業使用它*——通道、驗證、服務水準，以及錯誤與重試語意。
> - **解方是延伸既有標準，而非發明一套新標準。** 一套全球企業標準座落於 ISO 20022 與 CBPR+ 之上，並回答三個問題：企業要透過哪些介面、在哪種安全模式之下、以何種行為保證，才能跨銀行使用這些訊息。
> - **這種不對稱是決定性的。** 商定一套共用介面設定檔的成本，是集體地一次付清；把它交給上百個雙邊整合去解決的成本，則是永遠付不完，體現在整合工時與對帳斷點之中。缺少一套企業標準，如今已不是地貌上的空缺，而是一個選擇不去繪製地圖的決定。

## 新的基準線：ISO 20022 在資料層面已不再是選項

起點毫不含糊。自 2025 年 11 月起，SWIFT 網路上跨境支付與報表的 MT 與 ISO 20022 並存期，對金融機構而言已經結束。CBPR+ 現已要求支付指令採用 ISO 20022，而下一個里程碑早已列入行程：自 2026 年 11 月起，非結構化的郵政地址將自 CBPR+ 訊息中移除，改採完全結構化或混合格式。與此同時，CPMI 與 PMPG 已發布協調一致的 ISO 20022 資料要求，並承諾在 G20 追求更快、更省、更透明跨境支付的計畫之下，至少維持至 2027 年底。

換言之，全球社群已就一筆支付**必須說什麼**達成一致。CPMI 本身的要求涵蓋一切——從唯一的端到端參考編號、結構化的當事人與地址資訊、透明的費用，到最低限度的匯款附言欄位——全都是為了讓訊息在各市場之間更具可比性、更利於機器讀取。SWIFT 已將其轉化為具體的 CBPR+ 準則與大限，並在網路層級強制執行。這就是資料層：豐富、結構化、協調一致。

## SWIFT 與 ISO 20022 已經給了企業什麼

企業在這段故事裡並非事後才想到的配角。SWIFT 已投入十年打造「ISO 20022 for corporates」及相關的市場實務，其效益是實實在在的。

在訊息層面，ISO 20022 為企業提供了：

- **更佳的對帳能力**，藉由在 pain 與 camt 訊息中運用結構化的匯款附言與端到端 ID，加速應收帳款比對並減少人工作業。
- **更好的營運資金管理**，因為現金報表（camt.052/053/054）中更豐富、更結構化的資料，可支撐對現金流入與流出更精準的預測。
- **對代理模式與虛擬帳戶的支援**，透過為最終付款人／收款人、發起方及其他角色設計的專屬欄位——這些是傳統 MT 結構從未被設計來乾淨承載的。

SWIFT 的企業工作並不限於理論。SCORE 框架與 CGI-MP（Common Global Implementation – Market Practice）工作組已為企業支付發起與現金管理訊息，產出詳盡的 ISO 20022 使用準則。銀行與企業運用這些範本——發布於 MyStandards 並藉由實際試點加以精進——以避免為每一段關係都發明新的方言。諸如 SEB 早期為企業推行 ISO 20022 的案例研究顯示，跨國企業能夠在多家銀行與多個市場之間，統一採用單一的 pain.001 與 camt 格式，並在效率與控管上取得可衡量的成效。

因此，構件已然存在。企業對效益有清楚的認識；銀行有訊息準則與範例；CPMI 已在各司法管轄區之間協調出最低限度的資料集。而這一切尚未提供的，是對另一個問題的全球一致答案：不是「訊息應該長什麼樣子？」，而是「一家銀行應如何讓企業使用它？」

## 缺失的那一層：從協調一致的訊息到企業標準

這項區別聽來細微，卻是一部字典與一套運輸系統之間的差別。ISO 20022 與 CPMI 告訴你必須端到端傳遞的詞彙與文法。它們並未告訴你：

- 企業是透過檔案、入口網站、host-to-host 管道，還是 API 去取得這些訊息——又或者其中哪一種被視為首要通道。
- 這些通道如何驗證客戶端——是專屬憑證、人工白名單，還是現代的 OAuth2/mTLS 設定檔。
- 企業可以假定何種非功能性行為——延遲預算、可用性、截止時間的執行，以及 STP 期望。
- 錯誤如何被通報、哪些重試模式是安全的——尤其是當自動化與智能體開始對這些通道採取行動之後。

這道落差如今比 2015 年更為要緊。當年，整合者是一個人，視野是每家企業對接寥寥數家銀行。如今，大型企業及其平台期望在數十個交易對手之間取得即時可視性、直通式發起與機器驅動的對帳——而且愈來愈是透過 API，而非平面檔案。ISO 20022 給了它們更豐富的資料，卻未憑其自身給它們一個可預期的介面。

一套可信的**全球企業標準**，必須明確地座落於 ISO 20022 與 CBPR+ 這條基準線之上——使用相同的協調一致訊息——並回答三個問題：企業要透過哪些介面、在哪種安全模式之下、以何種行為保證，才能可靠地跨銀行使用這些訊息？

## 一套全球企業標準必須增補什麼

好消息是，銀行不必從零發明一套新標準。它們只須延伸自己已經擁有的那些。

### 1. 鎖定訊息層：採用協調一致的 ISO 20022 範本

首先，銀行與企業應承諾，將 CPMI 協調資料要求及既有的 SWIFT/CGI-MP 範本，視為跨境企業金流**不可妥協的基準線**。

這意味著：

- 對跨境支付與現金報表使用協調一致的 ISO 20022 訊息（pain、pacs、camt），並使結構化與混合地址對齊 CBPR+ 及 2026 年 11 月的要求。
- 除非絕對必要，否則避免客製化的擴充——而當確有必要時，將其記載於 MyStandards，使其能被發現與重用，而非在暗處恣意增生。
- 確保內部系統確實保留經豐富化的 ISO 20022 資料，而不是在核心系統將其重新壓扁回類 MT 的結構。

這就是「要說什麼」的那一層：CPMI 定義協調資料模型；SWIFT 在 CBPR+ 中將其付諸運作；CGI-MP 給企業與銀行具體可循的範本。

### 2. 標準化介面層：API 設定檔，而不只是檔案

其次，銀行與金融機構需要下定決心：ISO 20022 支付與現金報表的**首要企業介面**，將是附帶共用設定檔的 API，而非檔案與入口網站拼湊而成的補丁。

這牽涉到：

- 透過 REST API 揭露企業支付發起（pain.001）與現金管理訊息（camt.052/053/054），並採用標準化的分頁、關聯與篩選模式。
- 在企業本就會查閱使用準則的同一個地方——例如與 MyStandards 或同類入口網站上的 ISO 20022 範本並列——發布這些 API 的 OpenAPI 規格。
- 承諾採用一組有限的驗證模型——最好是搭配雙向 TLS 的 FAPI 等級 OAuth2.1 於企業 API——而非客製化的 SFTP 金鑰、臨時的 IP 白名單，以及各家銀行特有的憑證儀式。

SWIFT 本身的企業指引已朝此方向暗示，各大銀行的 ISO 20022 移轉手冊亦然——後者愈來愈把訊息就緒與面向企業客戶的 API 上線相互搭配。一套全球企業標準會把這一點明確化：相同的 ISO 20022 訊息定義，必須能透過少數幾種可預期的 API 模式來觸及。

### 3. 定義行為層：SLO、錯誤語意與重試

第三，該標準必須承認：對企業而言——尤其是對其財資系統與智能體而言——**介面如何行為運作**，與訊息長什麼樣子同等重要。

在此，銀行與金融機構至少應在區域層級上，就以下事項進行協調：

- 非功能性服務水準：
 - 支付發起、狀態更新與現金報表呼叫的延遲期望。
 - 可用性目標與計畫性維護時段。
 - 對當日與跨境金流的直通式處理（STP）期望與截止時間行為。
- 一套共用的錯誤模型：
 - 能在各機構之間乾淨對應的共通錯誤代碼與分類（驗證錯誤、逾截止時間、流動性問題、合規凍結、技術失敗）。
 - 明確指引哪些可以重試、哪些絕不可重試，以及冪等性金鑰在各支付發起呼叫之間應如何運作。

若沒有這一層行為層，即便各家銀行都在傳送 pain.001、接收 camt.053，企業仍會繼續把每一家銀行當成一個獨具個性的整合專案。有了它，企業便能把銀行連線更當作一個可插拔的元件來對待：相同的訊息、相同的 API 模式、對「已接受」「處理中」「已失敗」與「請勿重試」的相同語意。

## 銀行與金融機構如何在無需新委員會的情況下協調

面對又一道標準化落差時，人的誘惑是去發明一個新的論壇。在此並無此必要。那些本就在照管 ISO 20022 的機構，能把職權範圍向上延伸一層。

三個場域是自然而然的選擇：

- **SWIFT 及其企業計畫。** SWIFT 本就是 CBPR+、CGI-MP 與企業使用準則的召集點。它可以主持參考用的 API 設定檔與行為建議——例如，在既有的 ISO 20022 訊息範本旁，發布標準化的 OpenAPI 規格與錯誤分類體系。
- **CPMI 的協調資料治理。** CPMI 已承諾至少維護並演進其協調一致的 ISO 20022 要求至 2027 年，並由一組市場實務工作組支持。CPMI 雖聚焦於資料，卻能明確鼓勵各市場在該資料之上建立一致的介面標準，以避免「送出去的是什麼」與「怎麼被使用」之間出現分歧。
- **區域與全球的市場實務工作組。** 那些本就在協調 ISO 20022 實作的工作組——從 CGI-MP 到各區域支付理事會——能把共通的 API 與 SLO 設定檔納入其工作的一環，而不是把介面行為留給雙邊協商。

這並不是要把 CPMI 或 SWIFT 變成 API 的監理機關。而是要運用既有的社群去達成一項共識：**相同的協調一致訊息，不應被無止盡的客製化介面所環繞**。

## 未來三年的分階段路徑

對於想要領先而非跟隨的銀行與金融機構而言，這條路徑是漸進的，並與它們本就要面對的里程碑對齊。

### 第一階段——把資料工作做到端到端徹底完成

- 對於仍未完成之處，完成跨境 MT 訊息移轉至 CBPR+ 的 ISO 20022，並確保內部系統保留結構化的 ISO 資料，而非在邊緣將其剝除。
- 使企業支付發起與現金報表訊息對齊 CBPR+ 與 CGI-MP 範本，避免破壞協調一致性的各家銀行特有變體。
- 趕在 2026 年 11 月大限之前，於銀行與企業兩端的通道實作結構化與混合郵政地址，使企業能倚賴單一的地址模型。

### 第二階段——讓 API 成為首要的企業通道

- 透過附帶共用設定檔的 REST API，跨市場、跨業務線揭露對齊 ISO 20022 的支付發起與現金報表。
- 採用搭配雙向 TLS 的 FAPI 等級 OAuth2.1 作為這些 API 的預設安全模型，取代或降低對客製化、以檔案為基礎之驗證機制的優先度。
- 以企業能輕易在各家銀行之間相互比較的方式，發布 OpenAPI 規格與開發者指南——最理想的是放在一個由 SWIFT 或業界工作組連結的共用儲存庫或入口網站。

### 第三階段——標準化行為並加以治理

- 加入或協助組建工作組——隸屬於 SWIFT、CGI-MP 或各區域理事會——以為企業 ISO 20022 API 定義共通的錯誤代碼、冪等性指引與重試模式。
- 為企業支付發起與報表 API 設定並發布延遲、可用性與 STP 的 SLO，並如同監控 CBPR+ 合規那般嚴謹地加以監控。
- 鼓勵企業與財資平台依循這些共通設定檔進行建置，並以早期採用者作為參考案例——正如 SWIFT 等機構在 ISO 20022 訊息傳遞上早已做過的那樣。

對企業本身而言，這套計畫是並行的：

- 使 ERP 與 TMS 平台現代化，成為 ISO 20022 原生，包括支援結構化匯款附言與地址，以及對 camt 現金報表的完整取用。
- 優先選擇提供對齊 ISO 20022 之 API、並附帶透明服務水準與協調一致語意的銀行關係，而不只是「以檔案承載 ISO 20022」。
- 運用更豐富的資料與可預期的行為，跨所有銀行標準化內部流程——對帳、預測、代理模式——而不是一家一家地做。

## 機會與風險

驅動因素已然運轉。ISO 20022 如今是全球跨境支付的標準語言，並存已然結束，結構化資料正在網路層級被強制執行。CPMI 的協調資料要求，正從法蘭克福到華盛頓，被嵌入市場實務與監理期望之中。銀行正大舉投入 ISO 20022 移轉與企業 API 上線；企業則正在升級 ERP 與 TMS 以處理這些新訊息。

問題在於，這波浪潮是止步於訊息邊界，還是貫穿至企業體驗。若銀行把 ISO 20022 當成單純的訊息傳遞升級，企業將繼續活在一個世界裡：同一筆支付在線路上看起來相似，但在每一家銀行卻以不同方式被觸及、被控管、被理解。反之，若銀行把 ISO 20022 與 SWIFT 的框架當成一套全球企業標準的**基石**——把協調從「什麼」延伸到「如何」——那麼企業終能擁有 G20 議程多年來承諾的東西：更快、更省、更透明，且真正被標準化、而不只是結構相似的跨境支付。

這裡有一種熟悉的不對稱。商定一套共用介面設定檔的成本，是集體地一次付清。把它交給上百個雙邊協議去解決的成本，則是永遠付不完、逐一分擔，體現在整合工時、對帳斷點與錯失的自動化機會之中。在一個企業、平台，以及愈來愈多的智能體，都已準備好原生取用 ISO 20022 的世界裡，缺少一套全球企業標準，與其說是地貌上的一道空缺，不如說是一個選擇不去繪製地圖的決定。

## 常見問題

**跨境支付採用 ISO 20022 仍是選項嗎？**
不是。自 2025 年 11 月起，SWIFT 網路上跨境支付與報表的 MT/MX 並存期，對金融機構而言已經結束，而 CBPR+ 要求支付指令採用 ISO 20022。下一個里程碑亦已確定：自 2026 年 11 月起，非結構化的郵政地址將自 CBPR+ 訊息中移除，改採結構化或混合格式。

**若訊息已經協調一致，那還缺什麼？**
介面。CPMI 與 SWIFT 標準化了一筆支付*必須*說什麼——一套豐富、結構化、可比的資料集。它們並未標準化一家銀行*如何*讓企業去觸及並使用它：哪個通道是首要的、它如何驗證、企業可以假定何種延遲與可用性，以及錯誤與重試如何行為運作。這就是一部字典與一套運輸系統之間的差別。

**銀行需要一個新的標準委員會來解決這件事嗎？**
不需要。那些本就在照管 ISO 20022 的機構，能把職權範圍向上延伸一層。SWIFT 已召集 CBPR+、CGI-MP 與企業使用準則，可以主持參考用的 API 設定檔與錯誤分類體系；治理協調資料集至 2027 年底的 CPMI，可以鼓勵在該資料之上建立一致的介面標準；各區域的市場實務工作組，則可以採用共通的 API 與 SLO 設定檔。

**一家銀行首先該做什麼？**
把資料工作做到端到端徹底完成——保留結構化的 ISO 20022，而非在核心系統將其壓扁，並趕在 2026 年 11 月之前實作結構化與混合地址。接著，讓 API 成為首要的企業通道，附帶共用的 FAPI 等級設定檔與已發布的 OpenAPI 規格。然後，標準化行為：共通的錯誤代碼、冪等性指引，以及如同監控 CBPR+ 合規那般嚴謹加以監控的、已發布的 SLO。
