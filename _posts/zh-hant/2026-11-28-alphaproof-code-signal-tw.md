# 以 AlphaProof Code 在機器碼層級證明 Signal 的正確性

**AlphaProof Code 運用 AI 智能體團隊，為 libsignal 撰寫約 630 萬行經機器檢查的 Lean 證明，而這些證明所針對的，正是未經修改、編譯後的二進位檔。**

## 為什麼這項成果對交付密碼軟體的人至關重要

Signal 被稱為端對端加密通訊事實上的全球標準，其協定變體已部署於 WhatsApp、Meta 的 Messenger 應用程式與 Google Messages。當一個協定承載如此多的對話時，紙面上證明安全的設計與實際執行的編譯程式碼之間的落差，就不再只是學術問題。紙面證明可以完美無瑕，實作卻可能完全是另一回事。

這項工作鎖定的正是這道落差。作者首次針對一個廣泛部署、未經修改的密碼協定實作，提出協定層級安全性質的證明。這句話值得讀兩遍，因為每個限定詞都有分量。協定層級，代表證明處理的是前向保密這類性質，而不只是沒有記憶體錯誤。廣泛部署，代表對象是 libsignal，而不是研究原型。未經修改，代表沒有人為了遷就證明器而把程式碼改寫成更友善的形態。

對創辦人而言，務實的解讀關乎成本。作者把形式化驗證定位為被動式找錯誤的替代方案：先規定軟體系統必須落實的正確性與安全性質，再以數學證明系統滿足這些性質。他們指出，這種方法過去對多數軟體而言成本過高。作者的結果顯示，AI 能讓它在真實世界的系統中變得可行。這是一個有所保留的論點，我也會如此看待：它是由一項大型案例研究支撐的推論，而非已有定論的經濟學結果。即便如此，這種規模的案例研究，比這個領域多數的論點都更有分量。

## 驗證問題比表面上更難

該框架的資料提到一個衡量驗證難度的熟悉基準：經過驗證的 C 編譯器 CompCert，依此處報告的數字，其驗證耗費六個人年。這個數字要謹慎看待，因為關於人年的括注是資料方的建構，而非直接引述。但論點依然成立：驗證嚴肅的軟體，一直是需要投入多年的工作。

據稱，驗證既有的工業級程式碼更加困難，因為證明者不能為了簡化證明而修改程式碼。經最佳化編譯器編譯的正式環境函式庫，正是這種情況。如果可以自由重構程式，就能把它塑造成證明水到渠成的樣子。如果必須原樣接受程式碼，就得承接每一個彆扭的慣用寫法與每一個編譯器決策。

AlphaProof Code 刻意選擇較難的路。未經修改的 Rust 程式碼以標準編譯器編譯，產生的執行檔連同 AArch64 語意一起載入 Lean。具體而言，作者把 libsignal 連結進一個小型命令列測試框架，再以標準 rustc 編譯器編譯為 AArch64 Linux 機器碼。證明的對象是機器碼。這比原始碼層級的推理更強，因為你不再需要信任編譯器會保留你已證明的性質。

## 框架如何分工

AlphaProof Code 是一套讓人類與 AI 協作完成真實世界軟體形式化規格與驗證的框架。它建立在一個我認為很有說服力的原則上：軟體驗證中的大部分人力，如今都落在設計規格。撰寫證明，這個過去要耗費專家數年時間的部分，正愈來愈多地交由機器完成。

作者根據自己的結果主張，一旦規格確定，即使是關於軟體的大型證明，也能由 AI 智能體團隊撰寫；而且由於 Lean 核心最終會檢查每一個證明，證明智能體可以自主運作。他們的框架把工作一分為二。人類使用者與 AI 智能體協作撰寫真實世界程式碼的 Lean 規格；一旦使用者審查通過某份規格，就由一組自主智能體證明程式碼滿足該規格。作者明確表示，對大型複雜系統而言，AI 輔助能降低撰寫規格與保證工作的成本，但無法完全取代人的判斷與審查。

規格階段不是橡皮圖章。一組審查智能體會檢查草案是否忠於其來源與實作。在作者的流程中，使用者在撰寫任何證明之前審查、修訂並核准規格，其 git 提交成為守門者之後核對證明的基準線。他們指出，即使文獻中已有現成模型，使用者與智能體之間也可能要經過多輪迭代才能得到一份好的規格；以 Signal 為例，整合先前的交握與棘輪模型並涵蓋新的後量子棘輪，經歷了好幾輪草擬與審查。期待單次提示就能產出可信規格的人，應該調整預期。

作者提出一種責任劃分：人類作者選擇要證明什麼、釐清歧義、評估安全取捨並做出所有最終決定，AI 智能體則在人類指導下草擬並測試規格。我認為這是正確的立場。它把判斷交給能為之負起當責的一方。

AlphaProof Code 中的所有智能體，包括規格撰寫者，都是通用的程式設計智能體，其行為由技能（skills）定義，也就是以自然語言寫成的文件。這裡沒有描述任何量身打造的證明器架構。行為由文字文件引導，使系統相對容易檢視與調整。

## 信任究竟落在哪裡

該框架最重要的設計決策，是它拒絕信任什麼。AI 智能體產生的數百萬行證明不受信任，因為證明中的任何邏輯錯誤都會被 Lean 核心拒絕。換句話說，由於證明最終由 Lean 核心檢查，結果的可靠性並不取決於證明智能體的可靠性。

這一點之所以重要，用作者的話來說，是因為結果的可靠性並不取決於證明智能體的可靠性：證明最終由 Lean 核心檢查。根據論文，守門者智能體只有在 Lean 核心檢查通過、且 Lean comparator 確認該證明恰好證明了一份預留的規格副本時，才會接受這個證明。也就是兩個條件。證明必須有效，而且必須是對正確命題的證明。第二個條件旨在防範一種隱蔽的失敗：智能體修改了命題，證明了比要求更容易的東西。comparator 會檢查命題及其依賴的每一個定義是否與預留副本完全相同，並檢查證明是否只使用 Lean 的標準公理。

以證明本身的規模衡量，受信任的基礎相對很小。約 2.7 萬行受信任的規格與 AArch64 語意，支撐約 630 萬行證明。審查者的注意力有限，這個比例告訴你該把注意力花在哪裡。

但規格是弱點，作者對此直言不諱。在 AlphaProof Code 中，規格由一組 Lean 定理陳述及其依賴的每一個定義組成。它必須受到信任，無法自動檢查，而其中的瑕疵可能削弱定理所提供的保證。一個對輸入做出過度嚴格的假設、只斷言輸出的弱性質，或對存在量化的見證約束過少的定理，即使對有錯誤的程式碼也可能成立。如果規格中的錯誤削弱了攻擊者的能力，安全保證也會隨之削弱。

定義中還可以包含外部契約（extern contracts），用來界定驗證範圍以外的系統部分的假設。這些是誠實的邊界，但終究是邊界：外部契約背後的東西是假設的，而不是證明的。

因此，那個標題數字，630 萬行，恰恰是評估是否應信任此結果時最不重要的數字。真正需要閱讀的是那 2.7 萬行。

## 關於 Signal 證明了什麼

這些證明涵蓋 Signal 的後量子 PQXDH 交握與 Triple Ratchet，確立了前向保密、身分驗證、洩漏後安全性與交握保密。PQXDH 交握與 Triple Ratchet 的設計目標，是即使部分金鑰遭到洩漏，甚至面對未來能使用量子電腦的對手，也能確保訊息安全。

兩種經典的建模傳統界定了這裡「安全」的意涵。符號模型，又稱 Dolev–Yao 模型，把密碼原語視為達成標準安全性質的抽象「黑盒子」。計算模型則以底層原語的困難度，界定高效攻擊者的成功機率。計算安全證明指出，存在一個從對協定的攻擊到違反某項底層假設的歸約。

兩種模型提供的保證不同，結果也據此區分。智能體撰寫的證明針對古典攻擊者，直接為編譯後的二進位檔確立前向保密、洩漏後安全性，以及訊息的機密性與真實性。在符號模型中，它們確立了對抗未來量子攻擊者的交握保密。細心的讀者應牢記這項區別。針對量子對手的結果是在符號模型中陳述的，而直接針對編譯後二進位檔陳述的，是關於古典攻擊者的結果。

還有第二個複雜之處，說明了規格工作為何困難。現有規格分別分析交握與棘輪，而且早於 Signal 的後量子棘輪；先前 Signal 的形式化模型分別分析其初始交握與棘輪。要證明已部署的協定，需要把兩者結合起來，再加上後量子棘輪。在人的指導下，智能體把現有規格延伸到實際部署的協定。這很能說明協作模式在實務上的樣貌：文獻提供起點，人類掌舵，智能體完成延伸。

作者也表示，他們的工作顯示 AI 能依據研究文獻中的豐富規格驗證機器碼，包括有狀態程式與自適應對手之間互動的性質。這是一類值得關注的性質。面對自適應對手的有狀態程式，正是通訊用戶端所處的情境。

作者主張自己是首創：用他們的話說，這是首批將協定層級安全保證連結到一個廣泛使用的密碼協定實作未修改程式碼的證明。這是他們自己的說法，而非獨立的發現，我也照此轉述。他們把這些結果形容為邁向 2026 年 4 月發起的一項重大挑戰（grand challenge）的重要里程碑。

## 規格能抓出真正的錯誤嗎？

一份無法區分正確程式碼與錯誤程式碼的規格毫無價值，針對它的證明就更沒有價值。作者直接對此進行測試。他們重新引入 libsignal 中兩個先前已修正的錯誤，並建立一套包含 17 個合成變異體的測試組，以檢查規格能否抓出真正的錯誤。

作者報告的結果是：對於兩個歷史錯誤，以及目前 17 個合成變異體中的 16 個，Lean 證明了一條記錄下來的軌跡（每個各一條見證軌跡），在與記錄執行相符的具體原語詮釋下，無法由符號規格解釋。兩個歷史錯誤的完整二進位反駁，只針對命題較早一個（36 個掛鉤的）不受信任的置放變體通過核心檢查；將其重新對準主定理的受信任命題，仍是未解的問題。

我想精確說明這項結果說了什麼、沒說什麼。17 個中的 16 個不等於 17 個中的 17 個，而案例研究沒有交代剩下那個變異體的情況，所以我不做揣測。也要注意歷史錯誤上的限定：完整的二進位反駁是針對命題較早一個 36 個掛鉤、不受信任的置放變體檢查的，未必是最終版本。在有人把這項結果當成全面勝利引用之前，這個細節值得知道。

儘管如此，這是正確類型的測試。它攻擊的是規格，也就是框架所指的殘餘風險所在，而不是炫耀證明的數量。對規格進行變異測試，相較於整個驗證工作成本很低，而且它回答了一個再多經核心檢查的證明也回答不了的問題：這個命題能否察覺一個真正的錯誤？

## 這對實務意味著什麼

限制與里程碑同樣值得關注。對大型複雜系統而言，AI 輔助能降低撰寫規格與保證工作的成本，但無法完全取代人的判斷與審查。作者並未提出相反的主張。經濟性在改變，但不會降到零，而仍由人承擔的那部分，正是決定保證是否有意義的部分。

我認為這種分工是正確的，它也為團隊解讀這項工作提供了一個合理的角度。不要問智能體能否撰寫證明；libsignal 的結果，約 630 萬行，已經回答了這個問題。要問的是，你的團隊裡誰能撰寫並審查這裡描述的那種規格：Lean 定理陳述加上它們所依賴的每一個定義，再以外部契約標明哪些是假設。這個人，以及圍繞其工作的審查流程，才是稀缺資源。

系統對待不可靠元件的方式，也蘊含一項設計教訓。它並不試圖讓智能體變得可信。它把一切交給一個小而固定的檢查器，讓智能體是否可信與結果無關。在其他領域建構智能體系統的團隊，可以對自己的管線提出同樣的問題：Lean 核心的對應物是什麼，守門者檢查的是不是正確的命題？

對密碼學以外的讀者而言，可推廣的重點是工作流程的形態，而不是特定協定。在作者的設計中，人類與智能體共同草擬規格，審查智能體檢查其忠實度，由人類核准，一次提交把它凍結為基準線，自主智能體完成證明，守門者則同時檢查每個證明是否有效，以及它是否恰好證明了核准的命題。每個階段針對一種不同的失效模式。

這一切都不應被誇大。AI 讓驗證在真實世界系統中變得可行的推論，在資料中本身就有所保留；而一個旗艦案例，無論多麼令人印象深刻，也只是一個案例。規格仍是一個受信任的產物，沒有任何工具會替你檢查。而且針對量子對手的保證，是關於交握保密的符號模型結果，而不是計算模型結果。

這項案例研究提出的開放問題，正是作者把它稱為邁向 2026 年 4 月發起的一項重大挑戰的里程碑時所指向的問題：如果一旦有了規格，撰寫證明就已變得便宜，那麼規格工程是否會成為下一個需要攻克的瓶頸？變異測試的結果顯示規格可以測試，而「多輪迭代」的發現則顯示這個過程仍然緩慢。在人類保有最終決定權的前提下，這種緩慢有多少能被智能體吸收？這是下一項案例研究中值得關注的數字。

## 常見問題

**什麼是 AlphaProof Code？**
這是 Google DeepMind 與 Google 推出的一套框架，用於人類與 AI 協作完成真實世界軟體的形式化規格與驗證。人類使用者與 AI 智能體共同撰寫 Lean 規格；一旦使用者審查通過某份規格，就由一組自主智能體證明程式碼滿足該規格。

**在 libsignal 中究竟驗證了什麼？**
libsignal 未經修改的 Rust 程式碼，以標準 rustc 編譯器編譯為 AArch64 Linux 機器碼。這些證明涵蓋 Signal 後量子 PQXDH 交握與 Triple Ratchet 的前向保密、身分驗證、洩漏後安全性與交握保密。

**為什麼不需要信任 AI 智能體？**
每一個證明都由 Lean 核心檢查，而守門者只有在 Lean comparator 確認該證明恰好證明了核准規格的預留副本時才會接受。邏輯錯誤會被拒絕，證明一個較容易的命題同樣會被拒絕。

**還有什麼必須受到信任？**
約 2.7 萬行規格與 AArch64 語意，以及描述驗證範圍以外系統部分的外部契約。規格無法自動檢查，其中的瑕疵會削弱定理所提供的保證。

**這項工作是否證明了對抗量子攻擊者的安全性？**
部分是。對抗未來量子攻擊者的交握保密是在符號模型中確立的。前向保密、洩漏後安全性，以及訊息的機密性與真實性，則是針對古典攻擊者、直接為編譯後的二進位檔確立的。
