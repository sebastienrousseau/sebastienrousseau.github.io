# 超級智能體：為什麼「一個任務一個工作階段」無法擴展

**單一任務受限於模型能力，多工卻受限於人的注意力；解方是架構，而不是更好的模型。**

> - 當今主流設計以單一工作階段作為基本工作單位，且工作階段彼此隔離。同時平行處理多項任務的使用者，必須手動在它們之間切換。
> - 為本機單一工作階段智能體加上 CLI、MCP 或外部連接器，雖能讓它接收外部訊息，但其根本限制依然存在。
> - 作者把替代方案稱為超級智能體，並認為它具備四項特性：連續、高產、主動與持久。
> - 雙層架構（Router 層加上 Worker 工作階段）同時提供連續的互動與高產的並行。

## 模型進步了，工作流程沒有

本文解讀〈Exploring Super-agent Design: Towards a More Autonomous Agent System〉，這是 DeepSeek Harness（@DeepSeekHarness）於 2026 年 11 月 1 日在 X 上發表的貼文，由 Yujia Qiao 代表 DeepSeek Harness 團隊撰寫，並註明為中文原文的機器翻譯。

程式開發智能體與其他單一任務智能體，已經證明了一件值得直說的事。模型能用工具解決複雜問題，而且需要人類持續監看與逐步介入的程度愈來愈低。模型協調多個智能體的能力也提升了，使跨工作階段組織與排程工作變得可行。

第二點比乍看之下更重要。如果協調可行，值得問的就不再是智能體能否完成一項困難任務，而是當你一次交給它五項時會發生什麼。

個人智能體透露了答案。它們直接連上日常的通訊、行事曆、電子郵件與工作平台，監看資訊流，並協助處理任務。貼文表示，這種永遠在線、事件驅動的工作方式並非個人用途所獨有，在軟體開發等商業工作中同樣有價值。這是主張而非量測，也應該這樣讀。但方向夠清楚了：一個身處工作原本就在發生之處的智能體，而不是在終端機裡等待提示詞的智能體。

## 單一工作階段設計在哪裡失靈

智能體仍以單一工作階段作為基本工作單位，而且工作階段彼此隔離。對單一任務而言，這是個整齊的抽象。任務一多，就開始彆扭。

同時平行處理多項任務的使用者，必須手動在工作階段之間切換，並記住每一個裡面有什麼。依作者的經驗，一個人通常只能同時追蹤 3 到 5 個活躍的工作階段。這個數字來自經驗而非對照研究，請當作經驗法則看待。即便如此，它指出了結構性的問題。在這類設計下，單一任務受限於模型能力，多工卻受限於人的注意力。

這句話值得讀兩遍。它是說，光改善模型，並不會提高平行工作的上限。上限是那個把所有工作階段記在腦子裡的人。我認為這是整個論證中最有用的框架，因為它把問題從模型（大多數心力投注之處）移到了模型周邊的系統。

## 為什麼連接器解決不了

顯而易見的補丁，是擴充既有的東西。為本機單一工作階段智能體加上 CLI、MCP 或外部連接器，它就能接收外部訊息。作者的論點是：其根本限制依然存在。

他們具體列出這些限制。這種配置仍在單一同步工作階段中執行，遇到長時間操作就會阻塞。不同任務的上下文會混在一起。本機裝置一離線，一切就停擺。而要讓整套配置持續運作，需要大量人工維護。

每一項都是不同類型的失效。阻塞是吞吐量問題。上下文混雜是正確性問題。筆電一離線就停擺是可用性問題。人工維護是營運問題。連接器一項也解決不了，因為連接器只改變訊息如何抵達，不改變工作階段是什麼。

## 讓智能體與工作階段脫鉤

貼文表示，要突破這些限制，就必須讓智能體與任何單一、由人工驅動的工作階段脫鉤。接下來的內容是以「智能體應該是什麼」來表述，而非量測結果，因此最好當作作者的設計論點來讀。

論點是這樣的。智能體應該是一個連續的實體，跨工作階段保有上下文，同時處理多項複雜任務，而任務之間互不干擾。作者把這類智能體及其系統架構稱為超級智能體。

他們回報了一個實際運作的例子。他們在 DeepSeek Harness 上執行的內部超級智能體實例，能跨 IM 與 GitHub 延續同一項開發任務。它也會監看公開群組聊天中的回饋，即使沒有人 @ 它，也會自行找出根本原因並開出 Pull Request 加以修正。貼文沒有提供這兩項行為的成功率或 Pull Request 數量，因此它們是能力展示，而非基準測試。儘管如此，第二項行為仍令人印象深刻。沒有人要求，智能體就行動了。

## 四項特性

貼文表示，超級智能體具備四項基本特性：連續、高產、主動與持久。作者將此表述為他們的信念，而每個詞都有特定意涵。

連續的智能體，讓使用者在原本工作的地方（例如 IM 聊天與 GitHub 留言）直接與它互動，而且感覺始終是同一個智能體。貼文的例子是：使用者在 IM 中要求方案 A，之後在 GitHub Pull Request 留言中改為方案 B。智能體理解這項變更，並調整正在做的事。管道變了，對話沒有斷。

高產的智能體回應迅速，並能平行完成多項複雜任務，每一項都達到高水準。它也能在前一個指令或任務完成前，就接受下一個指令。這消除了前面描述的阻塞行為。

主動的智能體監看環境中的事件，對值得處理的事採取行動，其餘時候保持安靜。最後這一句值得注意。對什麼都採取行動的智能體只是噪音。保持安靜，本身就是規格的一部分。

持久的智能體永遠在線，直接連上使用者真實的工作環境，並在長時間運作中自動從異常中恢復。

接著是驅動其餘設計的限制條件：任何單一 ReAct 迴圈都無法同時提供這四項特性，因此它們必須來自周邊的系統架構。貼文對此毫無保留，這也是本文談的是架構、而非提示詞的原因。

## 殊途同歸，以及一組老問題

貼文預期，當目標是一個永遠在線、能並行回應環境事件的系統時，個人智能體與軟體開發等商業工作用的智能體，最終會走向相似的設計。這是一項預期，措辭也相應保留。如果成立，打造個人助理的人和打造開發智能體的人，其實在解決同一個問題，可以共用大量設計。

還有第二個觀察讓我感到踏實。建構這樣的系統，會遇到許多與電腦系統領域長期研究的問題非常相似的難題，因此該領域許多經典的設計理念在此同樣適用。作者沒有說是哪些理念，我也不做猜測。但對創辦人而言，意涵很實際：你面對的並非完全未知的問題。排程、隔離與恢復早已有悠久的歷史。

作者認為，有五個模組構成支撐這四項特性的基本框架，而具體實作會各有不同。同樣地，這是他們的判斷，而非經過證明的分解。其中四個模組與特性的對應如下。

雙層架構（第 2 節）同時提供連續的互動與高產的並行。事件驅動設計（第 3 節）讓智能體變得主動。全雙工多管道互動（第 4 節）讓與使用者的每一次交流都既連續又高產。將運算、狀態與環境分離（第 5 節），再加上 Watchdog（第 6 節），讓智能體能跨裝置持久在線，並自行從異常中恢復。

本文其餘部分集中在第一個模組：雙層架構。

## 連續性與吞吐量之間的取捨

要同時支援跨管道的連續互動與跨任務的高產並行，系統在組織工作階段的方式上，就必須面對連續性與吞吐量之間的根本取捨。組織工作階段有兩種顯而易見的方式，而兩者都會以可預期的方式失靈。

第一種是把每個事件都導向同一個工作階段。這能得到最連續的上下文，因為該工作階段看得到一切。代價是速度。ReAct 迴圈一次只執行一步，這限制了單一工作階段的工作速度：任務耗時長，吞吐量低。不同任務的中間細節也會在同一個上下文中交錯，使結果品質下降。於是，知道得最多的工作階段，推理反而最差，因為它讀的是一團混雜的內容。

第二種是讓每個事件都有自己的新工作階段。這能將並行吞吐量最大化，但當任務並非完全獨立時，缺乏共享的全域上下文，會讓它們的結果彼此脫節。多個工作階段各自回覆使用者，也讓互動變得混亂。使用者想要一個聲音，得到的卻是五個。

兩個極端都無法接受，而這項取捨是真實的，不是調參數就能解決的問題。一個想同時兼顧連續性與吞吐量的系統，必須把這兩份工作拆開。

## 一個工作階段，兩份工作

貼文指出了這兩份工作一開始為何糾纏在一起。在既有設計中，一個工作階段做兩份工作：它管理模型的上下文，同時也是使用者的專案管理單位。同一個物件承擔兩種責任，改善其中一項就會損害另一項。讓使用者只追蹤一個工作階段，上下文就會被污染。給模型乾淨、隔離的上下文，使用者就得在它們之間疲於奔命。

這正是 3 到 5 個工作階段這個數字之所以要命的原因。使用者的專案管理單位就是工作階段，因此他們能追蹤多少個工作階段，就決定了他們能推動多少個專案。

## 雙層架構

這項提案把責任拆開。長期存活的 Router 層（第 2.1 節）處理所有人機互動與全域協調，藉此維持全域連續性。上下文隔離的 Worker 層（第 2.2 節）以高並行度執行任務。合起來看：Router 層處理所有路由與對外互動，多個隔離的 Worker 工作階段則並行執行任務。

Router 層是一個長期存活的全域路由層，接收來自每一個入口的人機互動。這就是智能體感覺始終是同一個智能體的原因。無論訊息從哪個管道抵達，都落在同一個地方。與此同時，Worker 各自保持上下文隔離，因此單一工作階段設計中的交錯問題不會在它們內部發生。

作者補充了一個容易忽略的說明。兩個層級是責任的邏輯劃分，任何一層都不必實作為單一工作階段。Router 不一定是持有單一上下文的單一行程，Worker 層也不一定是單一資源池。這個架構描述的是誰負責什麼，而不是存在多少個工作階段。

實務上的後果說得很直接：系統接手上下文管理與並行執行，使用者很少需要去想工作階段的事。這正是解決注意力上限的關鍵。如果人不再需要記住每個工作階段裡有什麼，3 到 5 的限制就不再是可同時執行任務數的上限。貼文沒有說明其內部實例同時執行多少項任務，因此我無法說出新的上限落在哪裡。

## 貼文支持什麼，不支持什麼

在證據這件事上，值得坦誠以對。強的主張是結構性的。工作階段彼此隔離，單一 ReAct 迴圈一次只執行一步，單一共享工作階段會讓上下文交錯，每個事件一個工作階段會讓結果脫節。貼文對這些毫無保留。

承載雄心的，反而是較軟的主張。超級智能體的定義、四項特性、五模組框架，以及個人與商業設計將殊途同歸的預期，在貼文中都有所保留。作者是「認為」、「判斷」、「預期」。沒有一項是以量測結果呈現。

在 DeepSeek Harness 上的內部實例，是透過行為來描述的：跨 IM 與 GitHub 延續同一項開發任務，以及在任何人開口前就在公開群組聊天中找出根本原因。這是存在性證明，而非效能研究。貼文確實回報了初步實驗，但作者表示實驗使用合成工作負載與簡化環境，結果僅供參考。在該消融實驗中，超級智能體完成任務的時間在 p50 為 12.4 分鐘、p95 為 15.7 分鐘，快於搭配子智能體工具的單一工作階段，但每次執行使用了更多快取讀取 token。對技術讀者而言，這就是該帶走的信心程度：設計是一致的，替代方案的失效模式描述得很好，但數字來自模擬工作，而非日常使用中的實例。

## 創辦人該從中帶走什麼

如果你在打造智能體產品，第一課是：別再把工作階段當成產品。工作階段是上下文管理的實作細節，被拉抬成了使用者介面。作者的論點是，正是這種拉抬限制了平行工作，而我認為他們把問題定位在這裡是對的。

第二課關於心力該放在哪裡。單一任務受限於模型能力，所以更好的模型有助於單一任務。多工受限於人的注意力，所以更好的模型未必有幫助。架構才有幫助。一個吸納所有入口的 Router，加上彼此隔離上下文的 Worker，正是能移動上限的那種結構。

第三課關於範圍。身處通訊、行事曆、電子郵件與工作平台的個人智能體，和用一個 Pull Request 回應群組聊天的商業開發智能體，看起來是不同的產品。作者預期它們會走向相似的設計，因此打造其中一種的團隊，不該忽視另一種的進展。

這些都不會讓建構變得容易。光是持久性，就需要分離運算、狀態與環境，再加上 Watchdog 讓智能體自行從異常中恢復。主動性需要事件驅動設計。全雙工多管道互動自有一節。雙層架構只是五個模組之一，不是完整的答案。

## 一個開放問題

貼文留下一件未解的事，也是我最想得到答案的一件。Router 處理所有人機互動與全域協調，而 Worker 在設計上彼此隔離。貼文說連續性與吞吐量之間的取捨是根本性的，而雙層拆分兩者兼得。對於觸及同一環境的任務，它說訂閱該環境 Thread 的 Worker 會收到相同的事件通知，而少數需要跨任務協調的情況由 Router 轉達。它也說，一旦任務變得比單一 Router 工作階段所能處理的更大、耦合更緊，每一層的合適結構仍未定案。每個事件一個工作階段的失效，在於非獨立任務的結果彼此脫節。Router 如何只往下傳遞剛好足夠的全域上下文，又不重新引入它原本要防止的交錯，正是這個設計將接受考驗之處。

## 常見問題

**什麼是超級智能體？**
這是貼文為一種與任何單一、由人工驅動的工作階段脫鉤的智能體及其系統架構所取的名稱。這個智能體是一個連續的實體，跨工作階段保有上下文，同時處理多項複雜任務，而任務之間互不干擾。

**為什麼「一個任務一個工作階段」無法擴展？**
工作階段彼此隔離，因此同時平行處理多項任務的使用者，必須手動在它們之間切換，並記住每一個裡面有什麼。依作者的經驗，一個人通常只能同時追蹤 3 到 5 個活躍的工作階段，因此多工受限於人的注意力，而非模型能力。

**為什麼 CLI、MCP 或連接器解決不了這個問題？**
它們讓本機單一工作階段智能體能接收外部訊息，但其根本限制依然存在。它仍在單一同步工作階段中遇到長時間操作就阻塞、混雜不同任務的上下文、本機裝置離線就停擺，而且需要大量人工維護才能持續運作。

**雙層架構如何運作？**
長期存活的 Router 層處理所有人機互動與全域協調，上下文隔離的 Worker 層則以高並行度執行任務。兩個層級是責任的邏輯劃分，任何一層都不必實作為單一工作階段。

**這項設計的證據有多強？**
貼文描述了在 DeepSeek Harness 上執行的內部超級智能體實例，並回報了初步實驗。作者表示這些實驗使用合成工作負載與簡化環境，因此結果僅供參考。
