# Composite ML-DSA：把後量子混合簽章變成單一原子演算法

**這份標準軌 RFC 最有力的主張是：後量子混合方案不必改動你的協定。Composite ML-DSA 以單一公鑰與單一簽章值對外呈現，讓既有的密碼敏捷性機制承擔工作；而刻意擴大的組合清單，服務的是監理機關，而非實作者。**

> - 複合方案以單一原子演算法對外呈現，因此協定可以仰賴既有的密碼敏捷性，而不必修改。

## 為什麼需要混合簽章

這份文件是 RFC 10073，*Composite Module-Lattice-Based Digital Signature Algorithm (ML-DSA) for Use in X.509 Public Key Infrastructure*，由 IETF 於 2026 年 11 月發布，作者為 M. Ounsworth、J. Gray、M. Pala、J. Klaußner 與 S. Fluhrer。

RFC 開篇就提出一個不加保留的前提：RSA、DSA 及其橢圓曲線變體等傳統簽章演算法，終將在量子攻擊下失守。它把情勢界定為純粹的時間問題。它說，傳統演算法未來會被攻破，但在此之前仍然強健，唯一的不確定是何時。

這個界定很重要，因為它排除了對問題的偷懶解讀。如果攻破是確定的，只是日期未知，那麼等待就不是中性的選擇。但文件對提早遷移的代價同樣坦白。激進的遷移時程，可能需要在後量子密碼學（PQC）演算法的實作尚未完全強化或取得認證前就部署。RFC 對此有所保留，我們也該如此：它說的是「可能」，不是「必然」。

把這兩股壓力並列，混合方案的理由就浮現了。你需要防範量子時代的到來，但新演算法及其實作都還年輕。RFC 表示，雙演算法的資料保護在較長期間內可能是值得的，用以對沖新實作中的安全漏洞與其他實作缺陷。措辭同樣是有條件的。文件提出一個理由，並未宣稱已證明混合方案永遠是正確選擇。

值得說清楚複合方案到底帶來什麼。即使其中一個元件演算法被攻破，複合演算法仍保有一定的安全性。用語是「一定的安全性」，不是完整的安全性，RFC 也沒有誇大。實務上的解讀是：一個元件失效，不會自動讓你一無所有。

## 文件與作者

在進入機制之前，出處值得用一段說明，因為評估標準的創辦人與工程師應該知道它是哪一類標準。這份 RFC 屬於網際網路工程任務組（IETF）系列，類別為標準軌（Standards Track）。它於 2026 年 11 月發布，ISSN 為 2070-1721。制式說明將其描述為網際網路標準軌文件：IETF 的產出，代表 IETF 社群的共識，並經 IESG 核准發布。

作者橫跨四個組織。M. Ounsworth 與 J. Gray 列名 Entrust，M. Pala 來自 OpenCA Labs，J. Klaußner 來自 Bundesdruckerei GmbH，S. Fluhrer 來自 Cisco Systems。我不會對這個組成做超出文件所能支持的解讀。這份名單確實顯示的是：這不是單一廠商的產物。

文件也告訴讀者如何解讀其規範性用語。「MUST」、「SHOULD」等關鍵詞，僅在全大寫出現時，才依 BCP 14（RFC 2119 與 RFC 8174）的定義解讀。這是標準做法，但也正因如此，本規範中小寫的「should」不具特殊效力。本規範也與 RFC 9794 所定義的術語一致。

## 一把公鑰，一個簽章值

核心設計決策很容易說明。複合演算法呈現單一公鑰與簽章值，因此在協定層可視為單一原子演算法。

這個選擇比乍看之下更大膽，而我認為它是對的。RFC 直接說明對比：許多 PQ/T 混合方案需要修改協定，使其「混合感知」；本規範則把混合方案呈現為獨立的演算法，因而能善用既有的密碼敏捷性機制。

想想這對必須交付產品的人意味著什麼。協定必須理解的混合方案，會牽動每一個想使用它的協定。看起來和其他演算法沒兩樣的混合方案，則能直接嵌入既有的協商或演算法識別機制。RFC 在此脈絡下將「演算法」定義為：泛指任何具有已註冊物件識別碼（OID）、可用於 ASN.1 AlgorithmIdentifier 中的函式。複合方案在這套體系中取得自己的身分，周邊系統就像對待其他演算法一樣對待它。

一個相關的詞彙問題，可以釐清 RFC 主張了什麼、沒主張什麼。它將協定向後相容（Protocol Backwards Compatibility）定義為：新功能可加入協定，而無需修改協定規格，且只需對實作做最小幅度變更的性質。原子演算法的做法，正是瞄準這種低摩擦的新增。RFC 將此界定為設計意圖：PKCS #10、CMP、X.509、CMS 與 Trust Anchor Format 等協定，應能像對待其他演算法一樣對待複合演算法，協定層不需要任何「混合感知」。

## 複合方案由什麼組成

後量子的一半是 ML-DSA，即 FIPS 204 所定義的模組晶格數位簽章演算法（Module-Lattice-Based Digital Signature Algorithm）。本規範以它作為 PQ/T 混合方案的後量子元件。傳統的一半則取自一組既定的演算法。Composite ML-DSA 方案的具體實例，基於 ML-DSA、RSASSA-PSS、RSASSA-PKCS1-v1_5、ECDSA、Ed25519 與 Ed448。

術語章節逐一界定每個傳統元件。RSA 以 RFC 8017 所定義的機率簽章方案 RSASSA-PSS 出現。ECDSA 是 FIPS 186-5 所定義的橢圓曲線數位簽章演算法。EdDSA 是 RFC 8410 所定義的 Edwards 曲線數位簽章演算法，有兩組參數集：Ed25519 與 Ed448。公開金鑰基礎建設（PKI）依 RFC 5280 的定義使用，DER 則指 X.690 所定義的唯一編碼規則（Distinguished Encoding Rules）。

文件以一個小例子說明何謂複合密碼元素。它舉的例子是非對稱演算法，例如「ML-DSA-65」或「RSASSA-PSS」。「簽章」一詞則採廣義用法：指數位密碼簽章，不預設是哪一種演算法。

本文不深入複合簽章的內部構造，RFC 在金鑰產生、簽署、驗證與序列化等章節中自有規範。這裡的重點是：對外可見的形狀（一把金鑰、一個簽章），正是設計其餘部分所仰賴的性質。

## 為什麼組合這麼多

如果你瀏覽元件演算法清單，納悶一份規範為何要定義這麼多配對，RFC 的回答很直白。服務監理重新認證的使用情境，比任何其他設計需求更能說明本規範為何有如此多的演算法組合。它補充說，這些組合是為了符合特定地區的監理指引而量身打造。

這個使用情境背後的推理有所保留，但很具體。在某些情況下，對已合規的解決方案透過 PQ/T 混合加入後量子元件、而不更動傳統元件，可能比替換傳統元件更容易重新認證既有產品。換句話說，已取得認證傳統演算法的廠商，可能寧可原封不動，把後量子的一半並排掛上。這種偏好只有在規範為產品既有的傳統演算法提供配對時才行得通。廣度由此而來。

我認為這個設計立場有說服力，也有效矯正「標準應該最小化」的直覺。短清單會比較整齊，但會迫使部分產品更換已認證的元件，而這正是這些組合要避免的成本。長清單，是在受監理產品現有位置與之會合所付出的代價。

RFC 也謹慎地避免這種廣度成為讀者的負擔。預期機構會選擇部署單一複合演算法或少數幾種，極少有實作者需要關心整份清單。注意其中的保留：「預期」。這是對部署行為的預測，不是要求。但它告訴你該如何閱讀這份文件。你不需要全部實作；你要做的是找到你的配對。

## 規範沒有涵蓋什麼

好的標準清楚交代自己的邊界，這份也是。有四項限制特別突出。

第一，規範沒有指定任何強制實作演算法。再加上預期機構只會挑選一種或少數幾種複合方案，這意味著雙方能否互通，取決於彼此是否選了相容的組合。RFC 沒有指定一個人人都須支援的預設值，並警告組合數量可能在不同社群選擇互不重疊的子集時，使生態系分裂成無法互通的小群體。它鼓勵特定應用領域的機構定義設定檔（profile），從中挑選少數幾種複合方案。我會把這點標示為對規劃推行的團隊而言最實際的後果：你必須與交易對手約定配對，而不能想當然耳。

第二，不提供「升級後的系統持續與舊系統互通」意義上的向後相容。這一點值得與前述協定層的論點分開看。RFC 將應用程式向後相容（Application Backwards Compatibility）定義為：表示已升級與未升級的應用程式能否成功建立通訊的性質。第 10.3 節講得很明白：文件中的機制不提供應用程式向後相容，只有升級後的系統能理解它所定義的 OID，在需要該性質之處，必須另有機制。原子演算法的設計有助於處理協定變更，但並未宣稱能解決已升級的應用程式能否與未升級者對話的問題。

第三，有一項安全性質上的限制。Composite ML-DSA 適用於可以接受較弱 EUF-CMA 性質的簽章原語的場合，而非較強的選擇訊息攻擊下強不可偽造性（SUF-CMA），Composite ML-DSA 不提供後者。如果你的應用仰賴 SUF-CMA，依規範所述，這個方案並不適合。這是一條清楚、可檢驗的界線，評估這個方案的創辦人應先拿自己的需求對照，再往下走。

第四，也較為低調的一點：文件承認時程壓力本身就帶有風險，如前所述，PQC 實作可能在尚未完全強化或取得認證前就被部署。複合方案是緩解這項風險的手段，而非消除它。

## 解讀記號

實作者會花不少時間在演算法描述上，因此說明其慣例是有用的。演算法描述採用類 Python 語法。符號 || 表示兩個位元組陣列的串接，記號 [:] 表示位元組陣列切片。

對於回傳多個值的函式，文件以 (a, b) 表示一對值，通常表示函式回傳多個值，確切的傳遞機制（tuple、struct、輸出參數等）留給實作者決定。最後這一句是刻意給予的自由：規範在意的是回傳什麼，而非你的語言如何包裝它。記號 (a, _) 表示一對值中有一個值（此例為第二個）被忽略。

函式簽名也依循類似模式。記號 func(a) -> b 表示名為 func 的函式，以 a 為輸入並產生 b。Func<TYPE>() 則表示以 <TYPE> 參數化的函式，意即其實作會依底層 TYPE 而略有不同。這最後一項慣例，讓一份描述能涵蓋多種底層演算法而不必逐一重複，正適合一份同時橫跨 RSA、ECDSA、EdDSA 變體與 ML-DSA 的規範。

這些都不光鮮，但卻是你寫程式時真正會開在手邊的部分；而把多值回傳機制留給實作者，是對現行眾多程式語言的合理讓步。

## 這對規劃遷移的團隊意味著什麼

把這些拼成一個決策框架，RFC 給了你三樣有用的東西，並要求你自行補上兩樣。

它給你的是一個理由、一個形狀與一條邊界。理由是前述的兩股壓力：傳統演算法將在不確定的時間點於量子攻擊下失守，而新實作可能尚未完全強化或取得認證。形狀是原子複合方案，一把公鑰、一個簽章值，元件被攻破時仍保有一定安全性。邊界是上述的限制清單：沒有強制實作演算法、不直接涵蓋向後相容，以及提供 EUF-CMA 而非 SUF-CMA。

它要求你自行補上的，是組合的選擇與互通協議。由於規範沒有指定強制實作演算法，挑選配對是你的責任，不過第 10.4 節針對常見使用情境提供了簡短的建議清單。如果你的產品已以特定傳統演算法取得認證，重新認證的邏輯會指向保留該元件不動的組合。如果你在打造全新的東西，沒有監理要求或舊有實作需要考量，RFC 建議將實作心力集中在 id-MLDSA65-ECDSA-P256-SHA512，它表示這個組合在效能與安全性之間提供最佳的整體平衡。

有合理的論據認為，這種分工對現階段的標準是正確的。強制單一組合，會照顧到部分部署，卻讓其他部署陷入困境，特別是受地區監理指引約束的那些。不做強制，讓規範能跨地區使用，代價是把協調步驟推給採用者。RFC 選擇了彈性，也明白告訴你。

我也要溫和地反駁一種誘人的誤讀。「極少有實作者需要關心整份清單」這句話，聽起來像是允許你忽略規範的廣度。並非如此。它說的是誰承擔這份廣度的成本：規範把成本吸收下來，讓多數部署不必承擔。如果你是函式庫作者，或是服務受監理客戶的廠商，這份廣度很可能就是你的問題；如果你是只挑一種複合方案的單一機構，大致就不是。RFC 對這項預期有所保留，我也會把它當作預測，而非保證。

## 規範留下的開放問題

文件中有兩條線索值得關注，因為規範本身點出了它們，卻沒有解決。

第一是過渡期的長度。RFC 表示雙演算法資料保護在較長期間內可能是值得的，又說遷移時程可能很激進。這兩句話以一種耐人尋味的方式互相拉扯：快速轉向 PQC，支持在強化完成前就部署；較長的對沖期，則支持在那之後仍長期保留傳統的一半。機構實際上會同時保留兩個元件多久，是文件隱含提出卻沒有回答的問題。

第二是向後相容。RFC 表明其機制明確不提供應用程式向後相容，在需要之處必須另有機制。它列出需要審慎思考遷移與互通的各種協定，從 TLS 1.3、IKEv2 到 S/MIME、eIDAS 文件簽署與程式碼簽署，但把這些額外機制的設計留給協定與應用程式本身。

對於正在決定先把力氣花在哪裡的團隊，第二個問題看來是較好的起點：不是要採用哪一種組合，而是當對方還沒升級時，你升級後的應用程式會如何表現。

## 常見問題

**什麼是 Composite ML-DSA？**
Composite ML-DSA 是 RFC 10073 所定義的 PQ/T 混合簽章方案。它將 FIPS 204 所定義的 ML-DSA，與 RSASSA-PSS、RSASSA-PKCS1-v1_5、ECDSA、Ed25519 或 Ed448 等傳統演算法結合。這一對以單一公鑰與簽章值呈現，因此協定可將其視為一個原子演算法。
**RFC 為什麼定義這麼多演算法組合？**
RFC 表示，服務監理重新認證的使用情境，比任何其他設計需求更能說明組合為何如此之多。對廠商而言，在已合規的傳統元件旁加入後量子元件，可能比替換它更容易讓產品重新取得認證。預期機構只會部署一種或少數幾種複合演算法。
**新的部署應該從哪一種複合演算法開始？**
RFC 沒有指定任何強制實作演算法。對於沒有監理要求或舊有實作需要考量的應用，第 10.4 節建議將實作心力集中在 id-MLDSA65-ECDSA-P256-SHA512。它也針對需要 RSA、對效能與頻寬敏感，或僅允許 NIST PQC Level 5 的應用提供建議。
**Composite ML-DSA 能讓升級後的系統持續與舊系統互通嗎？**
不能。RFC 表明其機制明確不提供應用程式向後相容，只有升級後的系統能理解它所定義的 OID。在需要該性質之處，必須另有機制。
**Composite ML-DSA 不提供哪一項安全性質？**
它不提供選擇訊息攻擊下強不可偽造性（SUF-CMA），只提供較弱的 EUF-CMA 性質。RFC 表示，SUF-CMA 安全性至關重要的應用不應使用它；在尚未證明 EUF-CMA 可接受的情況下，NOT RECOMMENDED（不建議）使用。
