# स्टॅटिक साइट जनरेटर (SSG): एंटरप्राइझ-दर्जाचा धोरणात्मक सखोल अभ्यास व आर्किटेक्चरल रोडमॅप

*संशोधन दिनांक: 2026-06-22. `static-site-generator` च्या v0.0.41 आवृत्तीच्या कोडबेस तपासणीवर आणि 2026 च्या SSG परिदृश्याच्या वेब संशोधनावर आधारित.*

**नियमन-अधीन प्रकाशकासाठी स्टॅटिक साइट जनरेटर आता केवळ एक डिझाइन साधन राहिलेले नाही; ते परिचालन-जोखीम परिघाचा भाग आहे.** ओपन-सोर्स Rust [static-site-generator](https://github.com/sebastienrousseau/static-site-generator) याच आधारावर बांधला गेला आहे, जो सुरक्षा, अ‍ॅक्सेसिबिलिटी, आंतरराष्ट्रीयीकरण आणि AI कंटेंट पाइपलाइन कंपाइल-टाइमकडे हलवतो, जेणेकरून अयशस्वी तपासणी प्रॉडक्शनपर्यंत पोहोचण्याऐवजी बिल्डच थांबवते. हे विश्लेषण, आवृत्ती 0.0.41 प्रत्यक्षात काय पुरवते ते तिच्या दस्तऐवजीकरणात अजूनही केवळ आश्वासित असलेल्या गोष्टींपासून वेगळे करते, ती अद्याप नसलेल्या पाच एंटरप्राइझ क्षमता मांडते, आणि DORA, युरोपियन अ‍ॅक्सेसिबिलिटी कायदा व आधुनिक पुरवठा-साखळी मानकांशी सुसंगत अशा 1.0 प्रकाशनाकडे टप्प्याटप्प्याने जाणारा मार्ग सुचवते.

> **कार्यकारी सारांश**
>
> - **प्रकाशन आता एक परिचालन-जोखीम परिघ आहे.** DORA, युरोपियन अ‍ॅक्सेसिबिलिटी कायदा आणि GDPR अंतर्गत, प्रत्येक सार्वजनिक मालमत्ता ही पुरवठा-साखळी तडजोड, विकृतीकरण आणि नियामक जोखमीसाठी संभाव्य प्रवेशद्वार आहे. कंपाइल-टाइम प्रारूप अनुरूप नसलेले आउटपुट पुरवण्यापूर्वीच नाकारून तो परिघ संकुचित करते.
> - **इंजिनचे वेगळेपण कंपाइलरद्वारे लागू केलेले आहे, दस्तऐवजीकृत अपेक्षा नाहीत.** वर्कस्पेस-व्यापी `forbid(unsafe_code)`, खरे SHA-256/384 SRI, स्वयंचलित CSP निष्कर्षण, आणि बिल्ड-टाइम WCAG 2.2 AA गेट हे सुरक्षा व अ‍ॅक्सेसिबिलिटीला पश्चातकालीन लेखापरीक्षणांऐवजी कठोर बिल्ड अपयशांमध्ये रूपांतरित करतात.
> - **आवृत्ती 0.0.41 मध्ये दस्तऐवजीकरण-ते-कोड अशी दरी आहे.** नेटिव्ह मिनिफिकेशन, डिपेंडन्सी ग्राफद्वारे इन्क्रिमेंटल रीबिल्ड्स, आणि AVIF समर्थन यांचे वर्णन केलेले आहे पण ती कार्यरत नाहीत; लेख प्रत्येक त्रुटी नेमक्या स्रोत-स्थानासह नमूद करतो.
> - **1.0 कडे जाणारा मार्ग हा एक क्रम आहे, इच्छांची यादी नाही.** आधी सुदृढता (0.0.42), नंतर इन्क्रिमेंटल शुद्धता (0.1.0), त्यानंतर नियमन-अधीन खरेदीदाराला आवश्यक असलेल्या एंटरप्राइझ क्षमता, WASM सँडबॉक्सिंग, लोकल सिमेंटिक शोध आणि पडताळणीयोग्य SLSA provenance (1.0.0).

## सद्य सामर्थ्ये

`static-site-generator` कोडबेसमध्ये अनेक विशिष्ट अभियांत्रिकी निर्णय दिसतात जे तिला जुन्या JavaScript आणि Go इंजिनांपासून वेगळे ठरवतात:

- **कंपाइल-टाइम सुरक्षा पवित्रा:** वर्कस्पेस-व्यापी `#![forbid(unsafe_code)]` कंपाइल-टाइम मेमरी-सुरक्षा हमी देते. बिल्ड पाइपलाइन खरे SHA-256/SHA-384 Subresource Integrity (SRI) हॅश तयार करते (`src/plugins/assets.rs`) आणि स्वयंचलित Content Security Policy (CSP) निष्कर्षण करते, जे unsafe-inline स्क्रिप्ट्स व स्टाइल्स काढून टाकते. प्रकाशने स्वाक्षरीकृत असतात, Sigstore attestation वाहून नेतात, आणि प्रत्येक बिल्डवर CycloneDX 1.5 SBOM तयार करतात.  
- **कंपाइलरद्वारे लागू केलेले अ‍ॅक्सेसिबिलिटी गेट:** Web Content Accessibility Guidelines (WCAG) 2.2 Level AA तपासण्या Playwright-चालित बिल्ड-टाइम axe-core पार्सरद्वारे कंपायलेशन पाइपलाइनमध्येच चालतात. अ‍ॅक्सेसिबिलिटी हे प्रकाशनोत्तर लेखापरीक्षणाऐवजी एक कठोर बिल्ड गेट बनते: पृष्ठ अयशस्वी झाल्यास, कंपायलेशन नेमक्या ओळ-क्रमांक त्रुटींसह थांबते.  
- **डेटा-सार्वभौम AI पाइपलाइन:** एक लोकल-LLM भाषांतर आणि मेटाडेटा-निष्कर्षण पाइपलाइन (लोकल Ollama किंवा llama.cpp एंडपॉइंट्सद्वारे) संस्थेला कमाई-पूर्व प्रकटीकरणे किंवा संवेदनशील बौद्धिक संपदा सार्वजनिक क्लाउड AI API कडे न पाठवता कंटेंट सारांशीकरण, JSON-LD schema निर्मिती आणि बहुभाषिक भाषांतर स्वयंचलित करू देते.  
- **समांतरीकृत कंपायलेशन:** Rust च्या मेमरी-सुरक्षा हमी एका समांतरीकृत, Rayon-चालित HTML आणि अ‍ॅसेट पाइपलाइनला आधार देतात (`src/core/pipeline.rs`). प्लगइन पाइपलाइन एकत्रित रूपांतरे कार्यान्वित करते, जिथे `SearchPlugin`, `SeoPlugin`, `CanonicalPlugin` आणि `JsonLdPlugin` हे `par_iter()` वर कार्य करतात, त्यामुळे प्रत्येक पृष्ठ एकदाच डिस्कवरून वाचले व लिहिले जाते.  
- **पुरवठा-साखळी आणि डिपेंडन्सी स्वच्छता:** टेम्पलेट इंजिन Tera वरून MiniJinja कडे स्थलांतरित केल्याने (`v0.0.37`) बायनरी आकार कमी झाला, `rand` सारख्या ट्रान्झिटिव्ह डिपेंडन्सी कंपाइल-टाइमला काढल्या गेल्या, आणि एक सुसंगत डिपेंडन्सी फूटप्रिंट तयार झाला जो सॉफ्टवेअर पुरवठा-साखळी जोखीम कमी करतो.

## त्रुटी आणि प्रत्यक्ष वास्तव

या अपवादात्मक सामर्थ्यांनंतरही, v0.0.41 च्या काटेकोर कोडबेस तपासणीत तिच्या दस्तऐवजीकरण दाव्यांमध्ये आणि प्रत्यक्ष Rust कोडमध्ये अनेक आर्किटेक्चरल, कार्यात्मक आणि डेव्हलपर-अनुभव त्रुटी उघड होतात:

### आर्किटेक्चरल त्रुटी

- **व्हाइटस्पेस कोलॅप्स विरुद्ध नेटिव्ह मिनिफिकेशन:** README "नेटिव्ह JS/CSS मिनिफिकेशन" चे आश्वासन देत असले तरी, `MinifyPlugin` (`src/plugins/plugins.rs:96-116`) हा केवळ एक भोळसट व्हाइटस्पेस-कोलॅप्सर म्हणून कार्य करतो. तो `<pre>` घटकांवर शॉर्ट-सर्किट करतो आणि HTML मधील व्हाइटस्पेस-अनुक्रम कोलॅप्स करतो, परंतु वाक्यरचनात्मकदृष्ट्या जागरूक नेटिव्ह CSS किंवा JS मिनिफिकेशन करत नाही. शिवाय, तो केवळ शीर्ष-स्तरीय पृष्ठे प्रक्रिया करतो आणि उप-निर्देशिका (जसे की `/blog/` किंवा `/tags/`) मध्ये पुनरावृत्तीने फिरत नाही, त्यामुळे खोल पृष्ठे अ-मिनिफाइड राहतात.  
- **मृत इन्क्रिमेंटल पायाभूत सुविधा:** डिपेंडन्सी ट्रॅकिंग ग्राफ (`src/core/depgraph.rs` मधील `DepGraph`) कंपाइल होतो आणि `PluginContext.dep_graph` मध्ये लोड होतो, परंतु प्रॉडक्शन कोडमध्ये तो प्रत्यक्षात कधीच भरला जात नाही. `add_dep()` ही पद्धत केवळ युनिट चाचण्यांमध्ये बोलावली जाते, ज्यामुळे README चा "डिपेंडन्सी ग्राफद्वारे इन्क्रिमेंटल रीबिल्ड्स" हा दावा सध्या केवळ अपेक्षित आहे.  
- **बॅच कंपायलेशन विरुद्ध स्ट्रीमिंग कंपायलेशन:** `streaming::compile_batch` मॉड्यूल (`src/core/streaming.rs`) खऱ्या अर्थाने स्ट्रीम करत नाही. त्याऐवजी, तो पृष्ठे बॅचमध्ये एका तात्पुरत्या निर्देशिकेत कंपाइल करतो, प्रत्येक बॅचसाठी `staticdatagen::compile` सुरुवातीपासून कार्यान्वित करतो, आणि आउटपुट विलीन करतो. यामुळे लक्षणीय डिस्क I/O अतिरिक्त भार आणि पुनरावृत्त पार्सिंग होते, जे खऱ्या स्ट्रीमिंग आर्किटेक्चरपासून विचलन आहे.  
- **प्लगइन जीवनचक्र टप्पा उल्लंघने:** बिल्ड प्रक्रियेदरम्यान नवीन HTML पृष्ठे तयार करणारे प्लगइन, जसे की `TaxonomyPlugin`, `PaginationPlugin` आणि `I18nPlugin`, हे `transform_html` जीवनचक्र वापरण्याऐवजी `after_compile` मध्ये थेट डिस्कवर लिहितात. परिणामी, या प्लगइन्सद्वारे तयार केलेली पृष्ठे, आधी नोंदणीकृत असलेल्या महत्त्वाच्या पश्च-प्रक्रिया प्लगइन्सना (जसे की `CanonicalPlugin`, `JsonLdPlugin`, `RobotsPlugin` आणि `AccessibilityPlugin`) टाळून पुढे जातात. यामुळे टॅग, श्रेणी आणि पृष्ठांकित पृष्ठे योग्य canonical लिंक्स, JSON-LD schema किंवा अ‍ॅक्सेसिबिलिटी पडताळणीशिवाय राहतात.  
- **`LlmPlugin` मध्ये `curl` कडे शेल-आउट करणे:** लोकल LLM कंटेंट पाइपलाइन (`src/plugins/llm.rs`) लोकल एंडपॉइंट्सची चौकशी करण्यासाठी थेट होस्टच्या `curl` बायनरीकडे शेल-आउट करते. यामुळे गंभीर क्रॉस-प्लॅटफॉर्म बग्स येतात (उदा., PATH मध्ये curl नसलेल्या Windows होस्टवर), सुरक्षा जोखीम निर्माण होते (शेल इंजेक्शन वेक्टर्स), आणि बंदिस्त किंवा नेटवर्क-विलग CI वातावरणांमध्ये ती अयशस्वी होते.  
- **HTML रीरायटिंगमध्ये भोळसट स्ट्रिंग हाताळणी:** `image_plugin.rs` आणि `search.rs` निष्कर्षक HTML स्ट्रिंग्स नाजूक `str::find` आणि `str::rfind` ऑपरेशन्स वापरून पुनर्लिखित करतात. हा दृष्टिकोन तुटलेल्या HTML टॅग्स, कमेंट्समधील `<img>` टॅग्स, alt टेक्स्टमधील character entities, किंवा पूर्व-अस्तित्वात असलेल्या `srcset` गुणधर्मांसमोर अत्यंत असुरक्षित असतो, ज्यामुळे खराब आउटपुट होऊ शकते.  
- **अंमलात न आणलेले AVIF समर्थन:** AVIF इमेज एन्कोडिंगचे विपुल दस्तऐवजीकरण केलेले असले तरी, `image_plugin.rs` मधील अंमलबजावणी हे एक स्टब आहे जिथे `avif_variants` केवळ `Vec::new()` परत करते, त्यामुळे हे वैशिष्ट्य अकार्यक्षम राहते.  
- **पोलिंग-आधारित वॉचर:** लोकल डेव्हलपमेंट सर्व्हरचा वॉचर (`src/server/watch.rs`) फाइलसिस्टम इव्हेंट API ऐवजी पोलिंग वापरतो, ज्यामुळे जास्त निष्क्रिय CPU वापर आणि सेकंदाहून कमी बदल-विलंब होतो.

### कार्यात्मक व DX त्रुटी

- **ट्रान्झिटिव्ह डिपेंडन्सी ट्रॅकिंग नाही:** डिपेंडन्सी ग्राफ नेस्टेड डिपेंडन्सी ट्रॅक करू शकत नाही (उदा., एका सब-टेम्पलेटमधील बदल जो एका लेआउटवर परिणाम करतो जो एका पृष्ठावर परिणाम करतो), हे `transitive_not_tracked` या युनिट चाचणीने पडताळले आहे.  
- **इन्क्रिमेंटल कंपायलेशन CLI फ्लॅग नाही:** एक्झिक्युशन कंपायलरशी जोडलेला `--incremental` CLI फ्लॅग नाही, ज्यामुळे डेव्हलपर्सना कॅश केलेले बिल्ड्स वापरता येत नाहीत.  
- **HMR केवळ CSS पुरते मर्यादित आहे:** Hot Module Replacement (HMR) केवळ CSS ला समर्थन देते; HTML, लेआउट किंवा markdown फाइल्समधील कोणताही बदल संपूर्ण पृष्ठ पुनर्भारण करवतो, ज्यामुळे डेव्हलपर वेग घसरतो.  
- **सबकमांड तूट:** डेव्हलपर्सना शब्दबहुल फ्लॅग्स (`ssg -s public -w`) हाताने द्यावे लागतात, कारण `ssg dev`, `ssg build`, `ssg check` आणि `ssg lint` सारख्या मानक सबकमांड्स अस्तित्वात नाहीत.

## आपल्याकडे अनुपस्थित असलेल्या आर्किटेक्चरल त्रुटी (नवीन शोध)

v0.0.41 मधील त्रुटींपलीकडे, प्रकल्पाचे वित्तीय-दर्जाच्या जोखीम-प्रोफाइलविरुद्ध मूल्यांकन केल्यास अशा अनेक क्षमता समोर येतात, ज्या ती अद्याप पुरवत नाही परंतु एंटरप्राइझ खरेदीदाराला आवश्यक असतील:

### 1. WebAssembly प्लगइन सँडबॉक्सिंग (झिरो-ट्रस्ट विस्तार)

कंपाइलर बायनरी स्वतः सुरक्षित Rust मध्ये लिहिलेली असली तरी, अनियंत्रित तृतीय-पक्ष प्लगइन्सना होस्ट प्रणालींवर मूळपणे कार्यान्वित होऊ देणे हे एक गंभीर पुरवठा-साखळी असुरक्षा निर्माण करते. तडजोड झालेला तृतीय-पक्ष प्लगइन सहजपणे होस्टच्या फाइलसिस्टममध्ये प्रवेश करू शकतो, मालकीच्या Markdown फाइल्स वाचू शकतो, किंवा खाजगी क्रेडेन्शियल्स बाहेर पाठवू शकतो.

* **अनुपस्थित क्षमता:** एक सँडबॉक्स केलेले कार्यान्वयन वातावरण. झिरो-ट्रस्ट कंपायलेशन साध्य करण्यासाठी, कंपाइलरने तृतीय-पक्ष प्लगइन्स एका एम्बेडेड WebAssembly रनटाइममध्ये (जसे की `wasmtime`) कार्यान्वित करावेत. प्लगइन्सनी होस्टशी केवळ एका मर्यादित WebAssembly System Interface (WASI) द्वारे संवाद साधावा, ज्यामुळे त्यांचा प्रवेश काटेकोरपणे रूपांतरित होणाऱ्या पृष्ठापुरता मर्यादित राहील.

### 2. स्ट्रीमिंग AST द्वारे झिरो-कॉपी HTML पार्सिंग (`lol_html`)

HTML पार्सिंग स्तर एका पूर्ण इन-मेमरी DOM लायब्ररीकडे (जसे की Kuchiki किंवा html5ever) स्थलांतरित केल्याने 100,000 हून अधिक पृष्ठे असलेल्या साइट्स हाताळताना लक्षणीय मेमरी अतिरिक्त भार आणि प्रक्रिया-थांबे येतात.

* **अनुपस्थित क्षमता:** एक स्ट्रीमिंग, झिरो-कॉपी HTML रीरायटर. Cloudflare चे `lol_html` (Low-Output-Latency HTML rewriter) वापरल्याने कंपाइलरला HTML घटक एकाच स्ट्रीमिंग पासमध्ये, जवळपास-शून्य मेमरी वाटपासह, पार्स, तपासणी व सुधारणा करता येतात, जे समांतर स्ट्रीमिंग कंपाइलरच्या सेकंदाहून कमी बिल्ड्सच्या लक्ष्याशी जुळते.

### 3. लोकल सिमेंटिक व्हेक्टर शोध (लोकल RAG)

सध्याचा शोध निर्देशांक (`SearchPlugin`) एक जड, सपाट JSON निर्देशांक तयार करतो जो साधे क्लायंट-साइड स्ट्रिंग जुळवणी करतो, आणि त्यात फझी शोध, स्टेमिंग किंवा सिमेंटिक क्वेरींना समर्थन नसते. Pagefind ही एक सुधारणा आहे, परंतु ती अजूनही एका मोठ्या निर्देशांकाच्या डाउनलोडवर अवलंबून असते.

* **अनुपस्थित क्षमता:** एम्बेडेड सिमेंटिक शोध. कंपाइलरने बिल्ड-टाइमला एक लोकल, हलके Rust-नेटिव्ह व्हेक्टर एम्बेडिंग मॉडेल (जसे की `candle` किंवा `ort` / ONNX Runtime द्वारे कार्यान्वित MiniLM-L6 मॉडेल) वापरावे. त्याने प्रत्येक पृष्ठ-परिच्छेदासाठी घन व्हेक्टर एम्बेडिंग तयार करावेत आणि एक सुसंगत व्हेक्टर निर्देशांक द्यावा. WASM कडे कंपाइल केलेले क्लायंट-साइड शोध विजेट नंतर थेट ब्राउझरमध्ये खरा ऑफलाइन सिमेंटिक शोध करू शकते.

### 4. डिटरमिनिस्टिक भाषांतर आणि इन्फरन्स कॅशिंग

लोकल LLM इन्फरन्स (उदा., Ollama किंवा Llama.cpp द्वारे) अत्यंत CPU/GPU-केंद्रित असल्यामुळे, प्रत्येक बिल्डवर हजारो पृष्ठांचे भाषांतर करणे किंवा मेटाडेटा तयार करणे संगणकीयदृष्ट्या प्रतिबंधात्मक आहे.

* **अनुपस्थित क्षमता:** कंटेंट-हॅश-आधारित इन्फरन्स कॅशिंग. कंपाइलरने सर्व LLM ऑपरेशन्सचा एक डिटरमिनिस्टिक कॅश राखला पाहिजे. जर एखाद्या markdown फाइलच्या मजकुराचा आणि तिच्या भाषांतर पॅरामीटर्सचा SHA-256 हॅश एखाद्या कॅश नोंदीशी जुळला, तर कंपाइलरने पुनरावृत्त लोकल इन्फरन्स टाळून कॅश केलेले भाषांतर व मेटाडेटा पुनर्वापरावे.

### 5. समांतर स्केलिंगसाठी असिंक्रोनस फाइल I/O

प्लगइन पाइपलाइन Rayon द्वारे समांतरीकृत असली तरी, मानक सिंक्रोनस डिस्क राइट्स Rayon च्या OS थ्रेड्सना अवरोधित करतात, ज्यामुळे हजारो पृष्ठे लिहिताना एक I/O अडथळा निर्माण होतो.

* **अनुपस्थित क्षमता:** असिंक्रोनस, अ-अवरोधक डिस्क I/O. कंपाइलरने CPU-केंद्रित कार्ये (Markdown पार्सिंग, मिनिफिकेशन) डिस्क-बद्ध राइट्सपासून विलग करावीत, आणि समांतर CPU एक्झिक्युटर्सना अवरोधित न करता कंपाइल केलेली पृष्ठे समांतरपणे लिहिण्यासाठी असिंक्रोनस I/O थ्रेड पूल्स किंवा Linux `io_uring` बाइंडिंग्ज (`rio` किंवा `tokio` द्वारे) वापराव्यात.

WCAG 2.2 AA तपासण्या Playwright-चालित बिल्ड-टाइम axe-core पार्सरद्वारे कंपायलेशन पाइपलाइनमध्ये चालतात, आणि अयशस्वी पृष्ठ नंतर इशारा देण्याऐवजी नेमक्या ओळ-क्रमांक त्रुटींसह कंपायलेशन थांबवते. युरोपियन अ‍ॅक्सेसिबिलिटी कायद्याच्या बंधनाला हाच गुणधर्म आवश्यक आहे: अनुरूप नसलेले आउटपुट तैनातीपर्यंत पोहोचू शकत नाही.

**LLM प्लगइनमध्ये `curl` कडे शेल-आउट करणे का महत्त्वाचे आहे?**
लोकल LLM पाइपलाइन (`src/plugins/llm.rs`) लोकल एंडपॉइंट्सपर्यंत पोहोचण्यासाठी होस्टच्या `curl` बायनरीला बोलावते. ते बिल्डला एका होस्ट एक्झिक्युटेबलशी जोडते, PATH वर `curl` नसलेल्या प्रणालींवर अयशस्वी होते, शेल-इंजेक्शन पृष्ठभाग निर्माण करते, आणि नेटवर्क-विलग CI मध्ये तुटते. कॉल `ureq` सारख्या Rust HTTP क्लायंटकडे पोर्ट केल्याने बाह्य डिपेंडन्सी आणि इंजेक्शन वेक्टर दूर होतो, म्हणूनच ती 0.0.42 पॅचमधील दुसरी बाब आहे.

**1.0 कडे जाणाऱ्या मार्गावरील सर्वात महत्त्वाची एकच बाब कोणती?**
`DepGraph` भरणे आणि `--incremental` फ्लॅग जोडणे. इन्क्रिमेंटल रीबिल्ड्स ही दस्तऐवजीकृत आणि प्रत्यक्ष इंजिनमधील विश्वासार्हता-दरी आहे, आणि 100,000 हून अधिक पृष्ठांवर सेकंदाहून कमी बिल्ड्सबद्दलचा प्रत्येक पुढील दावा हा डिपेंडन्सी ग्राफ केवळ-चाचणी पायाभूत सुविधा राहण्याऐवजी टेम्पलेट-ते-पृष्ठ आणि markdown-ते-पृष्ठ कडा ट्रॅक करण्यावर अवलंबून आहे.
